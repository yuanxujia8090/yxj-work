# Mixed Playbook

<stage name="mixed">
  <inputs>先遵守主入口的交付分流与记录强度。普通任务使用当前目标、范围、待办和实际结果；严格任务读取 contract、state 和当前阶段材料。明确只读时不落盘。</inputs>
  <procedure>## 阶段入口

普通任务按本阶段的业务步骤执行；下面的 contract/state、初始化、evidence/audit 和候选要求只适用于严格记录。用户授权的目标文档写指定位置。

适用场景：一个任务同时包含研究、设计、实施或运维动作，且阶段之间有明确依赖。
输入：总目标、各阶段边界、研究问题、决策门和不可逆操作清单。
输出：按顺序连接的阶段产物、每阶段的完成条件、验证层级和下一阶段依赖。
不做什么：不跳过研究决策门，不把多个阶段混成一个无法验证的动作，不扩大任何子阶段范围。
停止条件：依赖链完整且每阶段独立可交接，或某个前置阶段阻塞并记录原因。

1. 先按主入口选择未知最少的最短阶段；只有确有外部事实未知时才进入 `research`，不以 mixed 路由无条件前置研究。
2. 需要设计、计划、实施或修复时，按目标进入对应阶段；用户明确设计并修复时，同一任务按需 design/plan → exec 或 bugfix，不改类型绕验收、不新增任务、不要求重复批准已授权实施。
3. 进入实施前必须读取 `playbooks/exec.md`，核对当前委派、单写者、依赖接力、短小直接执行例外和完成门；不能只创建工作项后由父会话包办。
4. decision gate 只在确有研究阶段时使用；`proceed` 后进入解决剩余未知所需的最短阶段，`design_only`、`gather_more` 或 `do_not_build` 时写清原因、证据和下一步，不创建没有依据的执行任务。
5. 每个阶段独立写 done_when、产物、验证层级和下一阶段依赖；阶段结束追加 checkpoint。研究结论、设计决策和执行结果都落在同一任务目录，禁止只依赖聊天上下文交接。</procedure>
  <quality_check>当前阶段独立验收，不因阶段多升级为长模式。</quality_check>
  <exit>普通任务交付实际结果、验证与限制，不创建状态文件。严格任务核对真实证据，用 task.py finish 或 complete 提交候选；阻塞保留状态，不放宽必需验收。</exit>
</stage>

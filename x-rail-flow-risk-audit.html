01

主链路：严格任务从取号到落地

所有任务先共用一段"分叉前"的骨架：入口 → 路由（按交付结果）→ 记录强度两问。 普通任务到此结束（零留存直做）；严格任务继续走完整生命周期，每一步都有脚本可查的产物： contract.md → state.md → evidence → 完成门。

1

入口：用户给出目标

/x-rail 普通入口；/x-rail-long 用于跨会话、外部等待或独立依赖汇总。 用户只要分析时只在回复里交付，不创建任务或目标文件；要写文档时只写授权目录。

/x-rail <goal>　·　用户禁止、更高规则和宿主限制优先
2

路由：按交付结果分流 决策点 D1

先看要交付什么（解释 / 调查 / 研究 / 方案 / 审查 / 修改 / 操作 / 组合），再决定记录强度。 "按当前未知选最短路径"，不要求默认走完整阶段链路。

SKILL.md → routing 模块（阶段、说明文件和按需参考映射）
3

记录强度判定：两问 决策点 D2

failure_cost_high? 与 recovery_or_handoff_needed? 都否 → 普通路径（零留存）； 任一真、敏感动作、外部等待或用户要求 → 严格路径。不能确定时选严格。

普通任务不创建 contract / state / 封存快照 / 输入摘要 / 候选状态
4

取号与写契约

读 .work-docs/index.md 分配 task-id（{YYYYMMDD}-{NN}-{slug}，当日自增不回收）， 写 contract.md：目标、范围、禁止动作、风险、审查策略、Acceptance（编号验收）、Decision Gates、变更。

已有严格任务必须续接原契约，不得用普通流程降级
5

封存与 start

check-contract.sh 校验契约 → task.py start 校验字段、封存快照（绑定契约指纹与修订号）、 生成 state.md。start 拒绝覆盖已有状态。

python3 <skill-dir>/scripts/task.py start <task-dir>
6

实施与取证 决策点 D6

按 task_type 选 playbook 实施；取证三通道：run 自动验收（执行命令 + expect 匹配 → evidence + 输入摘要）、 capture + record 人工验收、record --review 审查报告。

每次 run 使用新证据名；失败保留失败输出，旧证据不覆盖
7

更新与 finish

task.py update 记录进度、阻塞、恢复第一步与工作项状态；task.py finish 生成 done 候选（不执行验证命令，只调用原有完成检查）。

整体 next_action 只写第一动作，其余在各项；部分受阻不等于全部停工
8

完成门与交付 决策点 D9

task.py complete 全量校验（验收、依赖、工作项、快照链、预算、deadline）→ 候选 status: done → 更新 index.md。失败保留正式状态、索引和候选。

候选必须 status: done；完成前再次核对契约、状态、候选字节和证据输入
普通路径对照：两问都否 → 目标 → 读 → 最小改动 → 实际验证 → 交付，不建 contract / state / 快照，零留存。 命令时间线（严格）：start → (run | capture+record | record --review) × N → update × N → finish → complete。 任何一步失败停在原地，由模型读报错修正后重试；失败候选留在 tmp/。
D1

决策点：按交付结果路由

路由来自 SKILL.md → routing 模块。核心规则：先看要交付什么，再决定记录强度； 只读分析在回复列项、不落盘；仅要方案文档只写授权位置。R-01 路由是纯语义裁量，无脚本校验。

判定树

交付结果 → 路径匹配树

  • 简单解释或单一事实？ fast-answer 直接回答，不建任务目录
  • 调查？（怎么工作 / 为什么 / 是否确定） investigate 只读，回复列项不落盘
  • 研究 / 方案 / 审查？
    • 研究 research
    • 方案设计 design 仅要方案文档只写授权位置
    • 审查 review 按风险、覆盖不足、需求分歧或关键逻辑重改触发
  • 低风险、可逆的小修改或文档？
    • 缺陷修复 bugfix
    • 实施 exec 复杂或大范围实施先拆工作项（见 D3）
    • 计划 plan
  • 操作指引？ ops 敏感动作先确认（见 D5）
  • 组合任务？ mixed 多阶段混合，按主导交付结果记类型
  • 复杂或大范围实施 / 跨会话 / 外部等待 / 必需依赖汇总 / 敏感动作？ 对应阶段 + 严格记录 /x-rail-long；多个阶段本身不触发长模式
升级/降级

偏离最直观匹配的规则

升级 · 严格记录
复杂或大范围实施、跨会话、外部等待、必需依赖汇总或敏感动作 → 对应阶段 + 严格记录。复杂但当前会话可完成的任务不自动进入长模式。
降级 · 最短路径
解决当前未知的最短路径优先，不要求默认完整阶段链路；简单解释直接 fast-answer。
续接规则
已有严格任务必须续接原契约，不得用普通流程降级；同范围进行中任务续用编号。
只读边界
investigate / research / review 是只读的：在回复列项、不落盘，不顺手改代码；用户要写文档时只写授权目录。
参考技能读取
chain-unknown / impact-unknown 等触发条件由模型自查（R-02）；TypeScript 规则仅在项目规范不足且当前代码使用该语言时读取。
R-01（P1）· 路由与阶段选择是纯语义裁量。"交付结果 → 阶段"的映射与"选最短路径"全部由模型判断；跳阶段（该 plan 直接 exec）、错分类（实施任务标成 investigate）不触发任何校验。 test-flow.sh 只做关键词静态断言，其自身注释也承认"仅检查规则表达与引用，不代表模型已遵守"。证据：skills/x-rail/SKILL.md（routing 表）· scripts/test-flow.sh（末尾自注）。
D2

决策点：记录强度两问（核心分叉）

全体系最重要的分叉：两个问题决定任务是否留下任何记录。都否 → 普通路径零留存；任一真 → 严格路径完整生命周期。 不能确定选严格——兜底防过度自信，但防不住"悄悄低估"（R-03）。

判定树

两问 → 普通 / 严格

  • 失败代价高？（failure_cost_high?）
  • 需要恢复或交接？（recovery_or_handoff_needed?）
  • 都否，且未触发条件 普通路径 目标 → 读 → 最小改动 → 实际验证 → 交付；不建任何文件
  • 任一真 / 敏感动作 / 外部等待 / 用户要求 严格路径 contract + state + 证据 + 完成门（见图 01 主链路）
  • 不确定 选严格
对照

普通 vs 严格：行为差异

普通任务
不创建 contract.md / state.md / 封存快照 / 输入摘要 / 候选状态；按实际完成条件验证，不创建预算状态。
严格任务
完整证据链：契约记录目标、范围、禁止动作、风险、审查策略；每条验收有 outcome / verification / verification_type / layer / required；可选项必须预先写 skip_reason。
规模 ≠ 强度
任务规模 L1/L2/L3 是预算，不等于记录强度；复杂但当前会话可完成的任务不自动进入长模式。
字段纪律
契约字段从第一列写 key: value，不是 Markdown 列表；确认只针对不可逆、支出、对外发布、需求范围变化。
R-03（P1）· 两问判定无客观标准；低估即零留存，事后不可审计。 "失败代价高""需要恢复/交接"没有可测边界；模型低估一次，整个任务就没有 contract、没有证据、没有审计轨迹。 兜底规则"不能确定选严格"能防过度自信，但无法发现"悄悄低估"；普通路径下没有任何机制能在事后回答"当初是否应该走严格"。 证据：skills/x-rail/SKILL.md L24-27（记录强度两问）· playbooks/verification.md（普通/严格对照）。
D3

决策点：拆分与工作项状态机

新严格实施契约在首个二级标题前采用 work_items_schema: 1，把需求（R）拆成工作项（W）并关联验收（A）。 拆分判定全定性（R-10）；start 仅对 task_type ∈ {exec, bugfix} 强制此字段——换类型即可绕过（R-08）。

拆分条件

什么时候必须拆

必须拆
复杂或大范围实施按逻辑独立性、复杂度、范围和依赖拆成可验证工作项并持久记录；多个独立复杂逻辑、一个跨模块大范围需求、单需求内权限/并发/多步写入，都不能因需求少免拆。
可以合
多个局部简单同源改动可合项并说明依据；不按五个、六个数量分流。
复用
已有合格计划核对覆盖后复用；只读分析在回复列项、不落盘；仅要方案文档只写授权位置。
覆盖校验
每个需求至少被一项覆盖，每项至少关联一条验收；依赖无环，未知引用、重复标识或缺失状态拒绝（work_items.py definitions）。
记录位置
契约记 W 的名称与范围；状态记执行者与进度。工作项名称和范围走契约变更，执行者和进度走状态更新。

R-08（P0）· 类型绕过：mixed / ops 不强制 work_items_schema，换类型即跳过拆分记录。 task.py start 仅当 task_type ∈ {exec, bugfix} 时强制 work_items_schema: 1； 一个本应拆分的实施任务标注为 mixed 或 ops，整个工作项状态机（七状态、verified 过门、active_work_items 检查）全部失效。 文档声明"不能换类型绕过"，脚本不拦——声明与机制脱节。 证据：scripts/task.py start 中 task_type in {'exec','bugfix'} and work_items is None → raise。
R-10（P1）· 拆分判定全定性；工作项清单质量决定整个状态机的有效性。 是否拆分全靠判断；一个工作项糊住三个需求也能过校验（覆盖只需引用，不限制粒度）；反向地，粒度太细会让 review 指针与证据管理成本爆炸。 粒度标准"一个工作项对应一个可独立验证的交付"没有可执行边界。证据：skills/x-rail/SKILL.md（work_items 拆分条件）· scripts/work_items.py definitions。
D4

决策点：委派与执行纪律

调用 /x-rail 即授权当前目标范围内默认主动委派完整执行单元；目标、读写范围与验收明确时， 默认把完整执行单元交给子代理，不等逐次点名。共享写入由同一子代理承接；短小且主会话已掌握材料时直接完成。

委派规则

授权、边界与接力

授权范围
调用入口即授权默认主动委派；不代表无限成本、新购买、生产、不可逆、发布或范围变更。用户禁止、更高规则和宿主限制优先。
并行 / 接力
独立且资源隔离的项可并行，有依赖项在前置满足后接力；不可并行或文件共享不是父会话包办理由，共享写入由同一子代理承接。父状态仅主会话一个写入者。
直接完成
短小且主会话已掌握材料、交接成本明显更高时直接完成；紧密耦合的实现由同一位执行者承接（R-12：成本感知主观）。
子代理时限
子代理总时限沿用宿主与代理配置，默认省略 timeoutMs/maxRuntimeMs，不另设运行倒计时；任务记录的总期限与无进展阈值不转换成子代理总时限。
接口固定
templates/child-task.md 固定工作项、输入、允许路径、依赖、验收、权限、成本和正式输出绑定；实现者独立副本，共享接口与配置唯一归属。
核对产出
父会话核对产物、差异和实际验证再更新父状态，通知不自动通过验收；基础设施失败立即报告并暂停原依赖，不换协议、不自动重发、不冒充独立审查。
执行纪律

TDD 与报告分层

TDD 默认
新增或改变条件、解析、权限、金额和数据写入等非平凡逻辑默认先写失败测试；纯文档、文案、简单样式按内容或渲染核对（R-11：边界模糊，失败前证据缺失不拦完成）。
用户路径
影响用户流程时按验收沿登录、页面入口、操作、请求和结果检查必要路径；没有先失败与后通过证据，不声称使用了 TDD。
报告分层
代码写入、检查通过、使用路径已验证、全部必需验收满足分别报告；完成任务不自动包含上线。
大输出
预计超过 8KB 的工具输出先保留原始结果到任务允许的证据路径，上下文只带命令、退出码、通过数量与证据路径；不能判断全局结果时停止，不用尾部截断掩盖失败。
缺失 按角色模型分配。pstack 为每个子代理角色分配显式模型（role → model 表，verifier 用不同模型族做独立验证）； x-rail 未定义模型分配机制——委派仅授权完整执行单元，子代理模型与总时限沿用宿主与代理配置（SKILL.md L102）。 已检索 skills/ 全目录与 templates/child-task.md，未发现 role→model 配置。
部分缺失 PR / babysit / 发布编排。pstack 有 Opening a PR → Babysit → Shipping 完整交付链路； x-rail 交付止于 done 状态 + 索引更新，无 PR 创建、babysit、发布编排流程。 （x-worktree、x-resolving-merge-conflicts 为辅助技能，不构成编排链路。）
R-11（P1）· TDD 边界模糊；"失败前证据"缺失不影响完成。 完成门校验的是"证据存在且自洽"，不是"证据强度"；一个跑在实现之后的测试同样能让 run 通过——TDD 纪律完全依赖自律。 证据：skills/x-rail/SKILL.md（execution/TDD 条款）· playbooks/exec.md。
D5

决策点：确认红线与成本授权

确认只针对四类敏感动作：不可逆、支出、对外发布、需求范围变化。action_categories: none 可以豁免确认，不豁免所需审查； 有敏感动作时必须绑定当前动作的用户确认来源。

敏感动作必须绑定用户确认

  • 不可逆操作（删除、覆盖类）
  • 支出（新购买或订阅单独确认）
  • 对外发布（面向外部系统的动作）
  • 需求范围变化（scope-change）

确认来源写入契约：confirmation_by / confirmation_at / confirmation_source，绑定当前动作。

成本授权unlimited 语义

  • 用户明确"解除成本限制 / 不限制成本 / 不计成本" → 本任务持续不限成本，阶段切换、恢复和已授权委派都沿用。
  • 取消默认费用、调用/资料次数、总时长上限和文档 6/20 次收口；同范围执行费用不重复确认。
  • 无进展、重复错误、必需验收和敏感操作边界仍生效；宿主或账户硬限制只能报告。
  • 否定句、引用、假设和"解除阻塞"不构成授权。
记录字段

授权与确认的落盘方式

cost_control
严格任务在 contract 顶部记录 cost_control: unlimited 和 cost_authorization: 当前用户原话及来源；start 生成 budget: unlimited，不加默认总期限。
Decision Gates
契约的 Decision Gates 记录授权；风险决定审查强度。有敏感动作时必须绑定当前动作的用户确认来源。
旧任务
按契约版本规则登记授权；检查器不再以旧数值预算或总期限超限阻断。来源是否真实由执行者核对，脚本只检查记录。
普通任务
沿用当前授权，不为此创建状态；不创建预算状态。
R-05（P0）· 契约变更的批准缺口：扩大 scope / 放宽审查 / 降低 risk 都不需要批准。 契约修订链只对"旧 required 验收被弱化"强制 approved_by ≠ none。其他任何修订——扩大 scope、把 review_policy 从 user-confirm 改成 auto、 把 risk 从 medium 降到 low、移除 forbidden 项——只要求 Contract Changes 记录字段非空。 scope-change 是四类敏感动作之一，但修订路径可以绕过确认门：写一份变更记录、approved_by: none 即可。 组合后果：一个 medium 任务可在执行中合法变成 low + auto 审查，完全绕开独立审查要求——全体系最值钱的绕过口子。 证据：scripts/task_checks.py 契约修订校验（weakened 判定仅覆盖旧 required 验收）· SKILL.md（敏感动作 action_categories）。

R-06P2 · 顶层字段错位被静默忽略

契约头部字段只从第一个 ## 之前解析。把 cost_control 等可选字段误写到某个 section 之后 → 不报错，按默认值处理。 想声明 unlimited 却写错位置，任务照常以 8h deadline 运行，到超期才发现（撞上 R-18 死锁）。

证据：scripts/task_checks.py 头部字段解析（只取首个 ## 前）

R-07P1 · 确认与授权的"证据"由执行者自填

confirmation_by / confirmation_at / confirmation_source、cost_authorization 全部由模型写入契约，脚本只校验字段存在且非空； 无法证明"用户确实确认过"。设计文档自认"防误操作，不抵御同等写权限的执行者"——这是确认机制的天花板。

证据：scripts/task_checks.py 契约字段校验 · SKILL.md（authority 边界说明）
D6

决策点：验证裁决与取证三通道

严格任务的验证由三条取证通道构成：run 自动验收 / capture + record 人工验收 / record --review 审查报告。 新状态必须 evidence_schema: 2，绑定 contract_revision 和 contract_fingerprint；每条 passed 必需验收绑定唯一非空证据。

三通道

取证：命令 → 证据 → 状态

task.py run自动验收：执行命令 + expect 匹配 → evidence/*.txt + *.inputs.json
→
capture + record非自动：先采集输入快照 → 实际观察 → 登记
→
record --review审查报告：policy ≠ auto 时必过
run 通过条件
退出码 0 且所有 --expect 子串出现在输出里；至少一个 expect（不能只靠退出码）。run 只接受 verification_type: automatic 验收。
输入摘要
记录版本、契约版本、绝对 workspace_root、相关文件相对路径、存在状态和原字节 SHA-256；只绑定该项相关材料，允许无关文件变化；已删除文件记录 absent；状态、证据和快照不自我绑定；路径不能越界。
时间线
staleness 判定 = run_at ≥ 输入文件最大 mtime（last_edit）；时间带时区，转换 UTC 后比较。审查报告同样绑定输入、契约版本和时间。
登记纪律
每次 run 使用新的证据名，失败保留失败输出，旧证据不覆盖；--used 仅为兼容旧调用的可选观察值，写入 tool_count_note，不参与预算、完成门或效率结论。
边界
run 不替代人工、消费端、外部服务或独立审查；命令文本是数据，校验器不执行；脚本不证明人工结论真实、审查独立或验收范围完整。
观察面

五类观察面（verification.md）

五类观察面不是新的任务等级；契约仍只使用现有 layer（验证所处环境）和 verification_type（谁 / 怎样验证）。像验收一条网页功能：先看零件装对，再看插口能用，再沿用户路径走完，最后确认交给别人后能照做。

零件层语法与静态：零件装对了吗（编译 / 类型 / lint）syntax / static
接口层配置与契约：插口能用吗（字段 / 配置 / 接口对齐）config
路径层沿用户路径走完（登录 / 入口 / 操作 / 请求 / 结果）local
运行层真实行为发生：外部服务 / 真实运行环境runtime / external
交付层交给别人能照做（消费端 / 可复现 / 交接）consumer
required 语义
run / record 除原 required=yes 外，仅对 work_items_schema=1 清单中被 work_item.acceptances 引用的 required=no 可选验收开放登记，未引用的可选验收仍拒绝。
not_run
not_run 可以没有证据文件，不能制造空白通过记录；提交或子代理通知不是通过证据。
R-13（P1）· expect 是子串包含匹配，弱断言轻松通过。 通过条件 = 退出码 0 且所有 expect 子串出现（all(value in observed for value in expect)）；--expect ok 这种弱断言几乎必然通过。 文档规定"文本包含不能证明行为正确、expect 必须指向行为特征"——纯自律。证据强度是整条链上最容易被"合规地"稀释的一环，且稀释后看不出破绽。 证据：scripts/task.py run · playbooks/verification.md（expect 强度规则）。
部分缺失 swarm 多路独立裁决。pstack 在每个 code-ready SHA 上 fan out 10+ lanes（gates / live / perf / audit）聚合成一个 verdict； x-rail 只有单审查者记录（record --review）+ 可选独立审查（需委派授权），无多 lane 并行裁决机制。

R-14P2 · 输入文件 mtime 在未来 → 永久 stale

时钟漂移、拷贝保留未来时间戳、归档恢复等场景下，证据永远"过期"，且没有命令能修正（只能等真实时间追上 mtime，或重跑）。

证据：scripts/task.py run（last_edit 取输入 max mtime）· task_checks.py（evidence stale 检查）

R-15P2 · 证据无 TTL：external 层证据不随时间失效

证据只在"输入文件变化"时失效；外部系统状态变化（环境漂移、数据过期、权限变更）不触发失效。文档要求"外部证据写明时效要求"并人工判断，无机制；长周期任务收尾时可能用三个月前的外部验证过门。

证据：playbooks/verification.md（外部证据时效条款）
D7

决策点：审查策略与独立审查

风险决定审查强度。契约里的 review_policy 三档：auto（低风险，无审查要求）、 user-confirm（用户确认后继续）、full-review（独立审查必须）。 policy ≠ auto 时，done 门要求一条 passed 的 review 证据。

审查策略

三档策略与独立审查规则

auto
低风险默认；无独立审查要求。
user-confirm
审查结论需用户确认后继续；done 门要求 passed 的 review 证据。
full-review
独立审查必须；高风险或用户明确要求时采用。
review 触发
按风险、覆盖不足、需求分歧、用户要求或关键逻辑重改触发。
独立审查
独立审查需要委派授权；未获授权单列阻塞，不能把主会话核对冒充独立审查。
审查绑定
审查报告绑定输入、契约版本和时间；不能以旧报告为改后的代码放行。实现自检后固定输入，审查集中交回必修问题，集中修复并重跑受影响检查。
修复后复核
优先恢复原审查运行定向复核，不可恢复记录原因并按宿主规则替代；不能替代必要的独立最终审查，不能把必修改可选。

R-16P1 · 无降级路径：卡死或违约二选一

review_policy ≠ auto 时 done 门要求 passed 的 review 证据；独立审查需要委派授权，没有授权时文档要求"单列阻塞，不能把主会话核对冒充独立审查"。 官方没有降级通道：改 policy 需要契约变更——回到 R-05 的批准缺口，降级反而比阻塞"容易"。 结果是合规姿势卡死、违规姿势畅通，激励方向反了。

证据：SKILL.md（decision_policy）· task_checks.py check_review · playbooks/review.md（无授权则 blocked）

R-17P2 · 单 review 指针 × 多工作项时序耦合

任务级只有一条最新 review_evidence；每个工作项转 verified 时都要求"当前 review 有效 + 该工作项引用的验收全 passed + 证据输入未变"。 审查后修复任一必修项 → 所有已 verified 工作项引用的证据输入集合需要重新核对；时序做错会集体失效（fail-closed 能发现，但流程复杂、容易返工）。

证据：task_checks.py check_work_item_evidence · task.py record --review
D8

决策点：预算、熔断与恢复

任务规模 L1/L2/L3 是预算不是记录强度；60/150/400 是离线记录提示（未接入宿主真实计数时不填写）。 无进展提醒 20/60 次；长任务另有 30 分钟无进展和 8 小时总上限（非 unlimited）。

预算与熔断

阈值一览与暂停纪律

调用预算 L1/L2/L3
60 / 150 / 400 次——离线记录提示；真实计数不可用时按连续无进展、重复错误、时间和验证失败判断是否暂停。不把提示当作效率证明或完成门。
无进展阈值
20/60 次提醒；长任务 updated_at − last_progress_at ≥ 1800s 时 in_progress 直接 fail（30 分钟）。update --progress --reason --next-action 重置计时。
deadline
long / L3 且非 unlimited：默认 started_at + 8h。超期后无法 resume、无法 done——见 R-18。
unlimited
解除成本限制后取消默认费用、调用/资料次数、总时长上限；无进展、重复错误、必需验收和敏感操作边界仍生效；宿主或账户硬限制只能报告。
暂停纪律
暂停和等待用户分开记录；停止保留准确错误、原运行、产物、已知/未知和恢复第一步。恢复续用原任务编号，读索引、contract、state、最近 checkpoint、handoff、audit/runs.json 与相关 evidence，核对工作区与输入。
恢复外部运行
原外部运行先查再恢复，不可查时 unknown 或 blocked，不重复启动。阶段、提交、会话或工作项变化不新建任务。
R-18（P0）· deadline 死锁：超 8 小时后无法恢复、无法完成。 long / L3 且非 unlimited 的任务默认 deadline = started_at + 8h。超期后： 转回 in_progress → 候选 updated_at > deadline → fail（deadline exceeded; state must be paused）； 转 done → 直接 fail（done state exceeded deadline）；连普通字段更新（stage 等）也会因为候选 updated_at 刷新而 fail。 唯一合法出路是转 blocked/stopped/cancelled，或用户解除成本限制 + 手工契约变更（改 state 的 cost_control 需要手改——又是手工操作）。 一个健康的 8 小时任务在第 9 小时想收尾，会被自己的状态机锁死。这是最硬的机制缺陷。 证据：scripts/task.py start（deadline 计算）· task_checks.py check_state（observed > deadline 对 in_progress 与 done 双分支 fail）。

R-19P1 · calls_since_progress 没有递增方 → 无进展预算不可触发

无进展熔断阈值 20/60 次基于 calls_since_progress；该计数器只在 start 初始化、在 --progress / run passed / record passed 时重置为 0。 全代码库没有任何递增路径（除非手工编辑 state.md）→ 阈值永远不会达到 → 无进展熔断是死代码。

同理 60/150/400 的调用预算与真实调用计数完全脱节——写进 state、展示在 summary，但没有任何真实来源。预算体系目前是半成品。

证据：scripts/task.py（start 写 0 / update、run、record 重置 0，无递增）· task_checks.py check_state（calls 阈值校验）

R-20P2 · 预算超限同样无法恢复

used > limit 且尝试转 in_progress → fail；used == limit 且仍在 in_progress 也 fail（预算耗尽）。 因无递增接口（R-19），现实中多为手工填数触发；一旦触发与 deadline 一样无合法恢复路径。与 R-18 是同一个"恢复语义缺失"问题的两个实例。

证据：task_checks.py check_state（budget 超限分支）

R-21P2 · --progress 以任意文本声明"真实新结论"

update --progress --reason ... --next-action ... 即可重置无进展计时，内容不验证。30 分钟硬校验的时间压力可能诱导模型在无实质结论时写下形式化的 progress 文本——记录在、实质无。

证据：scripts/task.py update --progress · task_checks.py check_state（30 分钟无进展检查）

R-22P2 · runs.json 与契约 Dependencies 强绑定

runs.json 每条记录必须匹配契约当前 Dependencies 的 key + task_id。契约变更（合法）删除某个依赖后，历史 run 行变成"非法记录"直接 fail，且没有提示"去清理 runs.json"。变更与历史数据的联动清理未文档化。

证据：task_checks.py（runs 行与 dependencies 匹配校验）
D9

决策点：完成门（done 全量校验）

两级过门：工作项 verified（关联验收及证据当前有效）→ 任务 done（八项全量校验）。 候选必须 status: done；finish 不执行验证命令，只调用原有完成检查。

done 门

P1–P8 八项校验

  • state.status = done 的全量校验
    • P1 required 验收全部 passed：证据行完整 + 输入 sha256 有效 + run_at ≥ last_edit
    • P2 review_evidence passed（policy ≠ auto 时必须有）
    • P3 Dependencies 全部 done：递归校验子任务（strict 模式）R-23
    • P4 工作项全部 verified / skipped，无 active_work_items
    • P5 契约指纹与修订号匹配，封存快照链完整
    • P6 预算 / 无进展阈值未超 R-19 / R-20
    • P7 deadline 未超（done 超期直接拒绝）R-18
    • P8 工作项任务：next_action 已更新为交付 / 结束说明
子任务边界
子任务 done 不自动通过父验收；完成要求全部必需验收、必需依赖、授权、快照、输入与预算通过。
候选与索引
失败保留正式状态、索引和候选；complete 成功后 state = done + index.md 正则修复（见 08 节 R-04）。

R-23P2 · legacy 子任务卡父任务

父任务 done 时递归 check_state 子任务，以 strict 模式运行——legacy（旧格式）子任务会被 "strict state requires evidence_schema: 2" 拒绝。 旧记录能查、能读，但一旦被新任务依赖就卡住父任务。迁移期问题，修法未文档化。

证据：task_checks.py check_state（依赖递归调用 strict）

R-24P2 · needed_acceptances 行为差异

无工作项时，required=no 的 passed 验收也参与 inputs 校验；有工作项时，仅"未被 skip 的工作项所引用"的验收参与。 两种模式下"哪些验收被校验"集合不同，文档未说明；后补工作项可能改变既有验收的校验行为。

证据：task_checks.py check_state（needed_acceptances 计算分支）

R-09P2 · ready 模式不查封存一致性

"封存快照 vs 当前契约字节比对"只在 seal / locked 模式做；实施前跑的 check-contract.sh 默认 ready 模式不做此检查。 契约被改但未提升 revision，ready 检查看不出来，要等下一次 run/update（locked）才爆。不会漏过最终门，但"检查点"语义比预期弱。

证据：scripts/check-contract.sh L5（MODE 默认 ready）· task_checks.py L228（seal/locked 分支才做快照比对）

chain-unknown / impact-unknown 等触发条件由模型自查，"该读不读 / 读多读少"无验证。影响输出质量而非流程正确性，无法观测；属于设计边界，记录在案。

R-12P2 · 委派判定（授权 / 成本 / 短小直接做）成本感知主观

"交接成本明显更高时直接完成""未获授权直接执行并记录权限原因"靠模型判断。无观测手段；记录里的"权限原因"是自述文本，属设计边界。

证据：playbooks/exec.md（委派章节）

R-25P2 · install --update 无交互确认，直接删除已标记目录

--update 对已标记目录先 rm -rf 再复制；脚本无确认提示，"删除型安装需事先授权"只是文档约定。误敲一条命令即可删掉运行时目录——标记只防"来源不符"，不防目标目录内的本地修改（整体替换会一并丢弃；copy 模式的"先验证后写入"做得较严）。

证据：scripts/install.sh（--update 分支）

R-26P1 · 体系本质：记录自洽校验 ≠ 行为强制

脚本能 fail-closed 地校验"记录之间是否自洽"（sha256、时间线、状态机、快照链），但不能验证"行为是否真实发生"（真确认、真独立审查、真进展、强断言）。这不是 bug，是设计前提——也是绝大多数"裁量类风险"的共同根源：能靠"写得合规"通过的门，等于没有门。

建议方向：凡是影响完成门结果的判定，要么有机器可查的锚点（文件、sha、计数），要么在报告里显式标记为"自述"。

证据：SKILL.md（authority 边界）· playbooks/verification.md（自述与机器校验的划分）
三个风险热点（优先处理顺序建议）：

1. 机制缺口三连（R-05 / R-08 / R-18）——前两个让合规路径被静默绕过，第三个让合规路径直接走不通。都是小改动可修：变更批准面扩展（scope / risk / policy 弱化纳入批准）、start 对"声明为实施类"的补充判定或至少 warning、deadline 增加"超期后允许 pause → 带解释恢复"的出口。

2. 判定不可验证层（R-03 / R-10 / R-16）——记录强度、拆分、审查触发是三大裁量点。短期无法机器化，但可以在记录里强制"判定理由"（为什么普通 / 为什么这样拆 / 为什么不需要独立审查），把不可验证变成"可事后审计的自述"。

3. 预算体系半成品（R-19 / R-20 / R-21）——数字写进 state、显示在 summary、定义了阈值，但没有真实来源。要么接入真实计数，要么明确降级为"展示性字段，不做门"。现状介于两者之间，是最容易误导后续开发者的一块。

1. 这是什么

x-rail 不是一个替人写代码的「大提示词」，而是一套会话管理制度。它管三件事：

  • 边界：这次任务允许改什么、不允许改什么，工作流文件写在哪，代码改到哪为止。
  • 证据：每个结论必须有可复现的命令输出或真实运行结果支撑，「编译过了」「agent 说完成了」都不算。
  • 续接：任务可以中断、过夜、换会话。第二天的新会话只读文件就能接着干，不依赖上一次对话的记忆。

它由四个入口技能（你自己敲命令触发）和三十一个辅助技能（入口按阶段主动读取，或你点名调用）组成。 入口负责流程骨架，辅助技能是每个阶段的具体方法，十三条 x-principle-* 则是短小的单条工程原则，被其他技能引用。

谁在什么时候读哪份文件，是写死的：入口 x-rail 里有一张「阶段 → 参考技能」映射表（见 第 7 节）， 进入某阶段就先读该阶段的 playbook，再按表里的分支条件读取参考文件。plan 的实施计划读参考技能，轻量文档读模板；没有第二份清单。

2. 安装与调用

安装哪些技能由 scripts/runtime-skills.txt 决定：4 个入口 + 31 个辅助技能，一起复制到同一个技能目录。因为同级安装，入口里的相对读取路径 ../<技能名>/SKILL.md 在源仓库和安装目标下都成立。

cd /Users/yuanxj/Documents/github/x-rail

# 1) 先自检仓库
bash scripts/check-repo.sh

# 2) 安装（默认拒绝覆盖已有目录）
bash scripts/install.sh --dest "$HOME/.pi/agent/skills"

# 3) 安装后校验：源仓库与安装目标逐项对照
bash scripts/check-workflow.sh --source "$PWD" --installed "$HOME/.pi/agent/skills"

若要更新已安装副本，只覆盖带本仓库写入标记 .x-rail-installed 的目录：

bash scripts/check-repo.sh
bash scripts/install.sh --dest "$HOME/.pi/agent/skills" --update

软链安装（开发模式）：技能目录直连源仓库，改动即时生效，与复制模式互斥；--link 拒绝接管目录、他处软链和断链，--unlink 只删除指向本仓库的链接：

bash scripts/install.sh --dest "$HOME/.pi/agent/skills" --link
bash scripts/install.sh --dest "$HOME/.pi/agent/skills" --unlink

日常执行用前三个入口；只读会话分析用 /x-self-check。所有入口仅由用户明确调用。

命令用途对应场景
/x-rail <任务说明>普通任务入口：调研、设计、计划、执行、修复、审查本文 5.1 – 5.5
/x-rail-long <长任务说明>跨会话、外部等待或独立依赖汇总。多个阶段本身不触发。本文 5.6 – 5.7
/x-handoff <补充说明>把当前任务写成交接文件，供新会话继续（只能你主动调用）本文 5.7
辅助技能全部设置了 disable-model-invocation: true，也就是模型不会因为任务内容自动唤起它们。 两种加载方式：入口按映射表主动读取，或你主动点名 /x-why、/x-arena。看不到它们被自动调用是设计如此，不是没生效。

3. 核心流程：一次任务从头到尾

流程环节变多了，但主线只有一条：先立规矩，再干活，最后拿证据交差。下面是一次正式任务从敲命令到交付的完整路径；每个环节的细节在 第 4 节 展开，产物落盘位置在 第 8 节。

/x-rail <任务说明>
  │
  ├─ L0 快问快答 ──────────────► 直接回答，不建任何目录（到此结束）
  │
  └─ L1 / L2 / L3 正式任务
       1 路由       按目标选阶段（单阶段，或开发 / 排查 / 调研三条链路）
       2 建骨架     取 task-id → 建 .work-docs/tasks/<task-id>/ → 写最小 contract.md
       3 契约校验   check-contract.sh 通过才开工（没过就改契约，不许先干后补）
       4 启动摘要   9 行中文摘要：阶段 / 任务 / 风险 / 允许改动 / 禁止动作 /
                    必过验收 / 已有证据 / 阻塞 / 下一步第一动作
       5 阶段执行   读 playbook → 按映射表读参考技能 → 断言驱动读取 → 结果写进 evidence/
       6 决策门     风险决定审查；不可逆、花钱、对外发布、改范围需要确认
       7 固定收尾   写契约 → task.py seal（快照 audit/contract-r<N>.md）→ 实施与取证
                    → 报告 → 候选 state → task.py complete --candidate
                    → check-state.sh → index.md
       8 完成门     必需验收 + 必需依赖 + 授权 + 契约快照 + 输入摘要 + 预算
                    全部通过才允许 status: done
  │
  └─ 任一环节熔断 ──► status: blocked + audit/ 失败记录 + checkpoint / handoff
                      下个会话只读文件恢复，且必须换一条实质不同的策略
  • 2–4 是「先立规矩再干活」：契约没过校验就不广泛读取，更不动目标代码。细节见 4.2；轻量文档分支（4.7）骨架最薄，但同样要过契约与状态校验；L0 完全不建目录。
  • 4 的启动摘要不是第二套状态源：九行内容全部读自 contract、state 和最近 checkpoint，只告诉你当前边界和第一步动作；缺字段显示「未记录」，不另建文件。示例见 skills/x-rail/playbooks/verification.md。
  • 5–6 是干活的主体：读哪些文件由入口的「阶段 → 参考技能」表写死（第 7 节）；每轮读取都要回答一个断言、缩小一个未知项或留下一条证据。验证怎么做见 4.3。
  • 7–8 是出口：收尾顺序固定——先封存契约再开工，先落证据再写候选状态，最后用 task.py complete --candidate 提交，直接改 state.md 不算完成。完成条件见 4.4，熔断与恢复规则见 4.5。

三条常用链路（design → plan → exec → review、investigate → bugfix → review、research → 决策门）就是把第 5 步的阶段串起来：每个阶段各自重复 2–7，决策门放行才进下一阶段，mixed 同样不新增清单。长任务入口 x-rail-long 走同一条主线，只多两件事：每个阶段结束追加 audit/checkpoint-<序号>.md 并同步 state，暂停或跨天前先写 handoff.md；恢复时按 index.md → contract.md → state.md → 最近 checkpoint → handoff.md → audit/runs.json → evidence/ 只读续接（见 5.7）。

判断流程走到哪，只看两个文件：state.md 的 stage 和 status 回答「现在在哪一步、还能不能继续」；contract.md 的 Acceptance 回答「做到什么才算完」。对话记忆不算数，文件里没有就是没发生。

4. 五个必须先懂的机制

4.1 路由：L0 与 L1/L2/L3

每次调用先分流。fast-answer（L0）是快问快答——术语解释、简单命令说明、单一事实确认——直接回答，不创建任何工作目录。

除此之外进正式任务，按层级记账：

层级典型规模工具调用预算无进展阈值
L1一次读取 + 一个小改动6020 次工具调用
L2多步骤、需要设计和计划15020 次工具调用
L3 / long规模较大；long 另按跨会话、外部等待或依赖汇总判断400，另有 8 小时上限每个子任务 60 次工具调用或 30 分钟

同时按目标路由到阶段：investigate（现状、定位、恢复）、research（外部事实、产品、市场、技术选型）、design（方案设计，不改代码）、plan（逐任务实施规格）、exec（按计划改并验证）、bugfix（复现、根因、最小修复、回归）、review（只读审查）、ops（平台操作手册，不代点网页）、mixed（研究 → 决策门 → 设计/计划 → 执行 → 验证）。

三条常用链路：

  • 开发：design → plan → exec → review。需求明确且改动很小可跳过 design，但要在契约里写明原因。
  • 排查修复：investigate → bugfix → review。无法稳定复现就停在 investigate，不要假装进入修复。
  • 调研：research → decision gate。只有决策门判 proceed 才继续进开发和评审。

4.2 契约与状态

正式任务先创建任务骨架和最小契约，再动真东西：contract.md（这次任务做什么、范围到哪、怎么算做完）和 state.md（现在在哪一步、有哪些证据、被什么挡住）。先写契约并用 task.py seal 封存，再运行 task.py check。每种规模均有编号验收、风险、授权和版本。明确只读分析时在回复交付，不为骨架落盘。

新任务的契约在 done_when 摘要之外，还有带编号的 Acceptance 验收条件（A1、A2…），每条写 outcome（可观察结果）、verification（怎么验）、verification_type（automatic / manual / consumer / external）、layer（验证层级）和 required（是否必过）；顶层还要写 risk（low / medium / high）、risk_reason、review_policy（auto / user-confirm / full-review）、contract_revision、Decision Gates 和 Contract Changes。任务规模 L1/L2/L3/long 与影响风险是两回事：低风险自动核对，中高风险按策略审查。确认只针对不可逆、费用、对外发布和需求范围变化。独立委派必须有当前授权。

严格模式要求的顶层字段是 task_id、level、task_type、objective、scope、forbidden、risk、risk_reason、review_policy、contract_revision、done_when，另有三个必备小节：Unknowns、Decision Gates、Contract Changes。task_type 取阶段名之一；Acceptance 至少要有一条 required: yes，写成 required: no 的可选项必须同时写 skip_reason。契约实质变化要提升 contract_revision，并在 audit/contract-change-r<N>.md 记录新旧值、原因、批准来源和受影响证据；只改文字不升版本会被 --seal/--locked 拦下。

长任务另写 ## Dependencies 段，一行一条 dependency: <键>|task_id=<子任务目录名>|required=yes|acceptance=<父契约里的验收编号>；required=no 的依赖同样要写 skip_reason。完成时递归检查子契约、快照、状态和证据，拒绝循环、重复、自引用和目录逃逸。状态文件本身不能是软链，也不能指向任务目录之外。

动代码前先跑结构校验（只查字段、枚举和策略关系，不给文字打分；默认严格模式，历史明确 --legacy-readonly，不能据此提交新完成）：

bash skills/x-rail/scripts/check-contract.sh .work-docs/tasks/<task-id>        # 默认 --ready
bash skills/x-rail/scripts/check-contract.sh .work-docs/tasks/<task-id> --draft  # 确认门未完成时只能起草
bash skills/x-rail/scripts/check-contract.sh .work-docs/tasks/<task-id> --seal    # 固化契约快照到 audit/contract-r<N>.md
bash skills/x-rail/scripts/check-contract.sh .work-docs/tasks/<task-id> --locked  # 交付前复核历史快照与变更记录

有敏感动作但确认仍为 pending 时，只有 --draft 能通过；契约字段必须从第 1 列写成 key: value，不能写成 Markdown 列表项 - key: value，检查器会直接提示格式错误。契约实质变化必须提升 contract_revision 并在 Contract Changes 记录原因、批准人和受影响证据，改了内容但没升版本号会被 --seal/--locked 拦下。

状态只会按下面这条路走：

in_progress ──► done        （只能通过完成判定）
                │
                ├──► blocked       （工具、证据、依赖、边界问题，可恢复）
                └──► stopped       （不可逆动作、等你拍板、生产变更、花钱、对外发布、改需求范围）

blocked ──► in_progress           （阻塞解除 / 共同前提重新验证通过 / 有新证据的新策略）

4.3 证据与证据新鲜度

每条证据记录 acceptance（绑定哪条验收条件，如 A1）、command、run_at、result、相关文件的 last_edit_at、inputs（输入摘要文件）和 contract_revision，证据文件本身必须真实存在。运行时间早于文件最后修改时间的证据作废——改了代码还引用旧跑出来的结果，等于没验证。

inputs 指向一个 JSON 摘要文件，记录 version、contract_revision、绝对 workspace_root 和 files 列表；每项写相对 path、state: present（已删除写 absent）和原字节 sha256。它只绑定与该条验收相关的材料，无关文件变化不受影响；状态文件、证据自身和契约快照不自我绑定，路径不能越出任务目录。

验证分五层，按契约要求从窄到宽跑：syntax/config → static → runtime/local → external → consumer。关键词搜索和 grep 属于 static，只能证明「字符串在那儿」，不能单独证明「行为生效」。

4.4 完成判定

下面六项同时成立才能写 status: done：

  1. 所有 required（必需）验收为 passed，每条绑定唯一非空证据，且证据比相关文件新；
  2. 所有 required 依赖已结束（## Dependencies 里 required=yes 的子任务，递归检查）；
  3. 授权齐备：决策门允许交付，敏感动作已确认或已豁免；
  4. 契约快照链完整：audit/contract-r<N>.md 与每次变更的 audit/contract-change-r<N>.md 都在；
  5. 输入摘要一致：inputs 列出的相关文件原字节未变；
  6. 预算未超限，且没有未处理的越界文件。

出现 failed、blocked、not_run、未解决的决策门、仍在跑的 required 依赖，或输入摘要对不上，一律禁止标 done。可选（optional）项必须在契约里声明，并写明跳过原因。

新任务必须写 evidence_schema: 2。passed 必需验收绑定唯一非空证据、时间、相关输入摘要和契约版本。审查绑定当前材料，必需依赖递归检查。完成只用任务内候选调用 task.py complete --candidate。失败保留正式状态与索引，历史不自动降级。

4.5 预算与熔断

熔断的触发条件（每个子任务独立计数）：

  • 同一命令 + 同一错误首行出现 2 次；
  • 错误各不相同时，required 验证连续失败 3 次；
  • L1/L2 连续 20 次工具调用无进展；L3/long 每子任务 60 次工具调用或 30 分钟无进展；
  • 第三方技能越界写入 .work-docs 之外的路径；
  • 共同前提被证据否定。

熔断后必须：停止同策略重试 → 在 audit/ 记录失败动作、错误摘要、策略指纹（修改文件 + 执行命令 + 错误首行）和证据 → 状态改为 blocked 并填 blocked_by、attempted_paths、shared_assumption、unblock_condition、next_action → 写 checkpoint 或交接 → 父任务不得 done。

预算上限按层级取值：L1/L2/L3 分别为 60/150/400 次工具调用，L3 另有 8 小时上限。开工后发现真实范围将超出当前 level 预算（例如复现或实测成本显著高于预估）时，在 contract.md 与 state.md 显式升级 level 并记录原因，预算上限同步调整，不允许静默超支。used 小于 limit 可继续；相等时合法候选可完成，否则暂停；超限只能有原因地暂停。离线检查不代表宿主自动计数或终止。

恢复时，新策略指纹不能与已有指纹相同。模型请求首次超时后，不原样重试：先在 audit/ 写恢复摘要，只保留「已确认事实、未决断言、下一步」三段内容；宿主允许时降低思考级别或切换更快模型，但不修改 Pi 全局配置。说不出新旧策略差在哪，就停下来交给人。

为控制长会话耗时，采用断言驱动读取：先列断言，再按断言定位实现符号和局部代码，并立即写 evidence；低风险、只读、review_policy: auto 的审查使用轻量 review，跳过与验收无关的构建、测试和全量参考材料。固定顺序：写 contract → seal → 实施和取证 → 写报告 → 写候选 state → task.py complete --candidate → 更新索引。

4.6 技能加载边界

辅助技能加载后仍受当前任务的契约、.work-docs 文件边界、预算、熔断和验证要求约束。如果技能自带规则与当前契约冲突，以契约为准，并把差异记到 audit/。

调用第三方技能前先按 playbooks/third-party-skill.md 分类：只读的可以直接跑；能指定输出根的必须传入本次任务目录；固定写入或写入不可知的，只能在隔离的临时目录里试跑，否则任务标 blocked。调用前后都要存目录清单，发现 .work-docs 之外的意外文件立即熔断，且未经授权不得移动、删除或覆盖那个文件。

4.7 轻量文档整理

材料和目标已确定的测试用例、检查清单、变更说明默认 L1 / plan，不新增阶段。用 skills/x-rail/templates/document-task.md 填最小契约和状态，运行校验器后读固定主材料，立即写初稿，再只为具体缺口补读。默认不研究校验器源码，不加载实施计划的「做可重复工具」参考技能。

「我要测试下」表示用户拿用例去测，不等于要求 Agent 代跑。默认不搭环境、不执行测试、不全量审查、不检查发布；未确定功能仍走 design，实施规格仍走原计划分支，实际执行另进 exec。

  • 6 次资料工具调用检查点：材料足够就写初稿，不足先写已有条目与具体缺口。批量读取按实际动作计数，不能靠包裹命令绕过。
  • 20 次总工具调用检查点：验收齐全则交付；仅可选细节缺失则说明；关键必过事实缺失则保持非 done。不能降低必过项，不能把部分初稿标完成。
  • 补读前指出初稿中的哪条预期结果或事实缺口；单纯读取或查询环境不算进展。固定方案和提交；若纳入未提交差异先明确范围，合并状态通常只作执行前提。

验收的是覆盖、事实和可理解性，不是运行环境；证据按原格式绑定，网站运行层保留 not_run。交付注明「用例已整理，测试未执行」。检查点是技能约束，不是宿主自动拦截或速度保证；是否减少空转需要实际模型会话验证。模板与流程回归可运行 bash scripts/test-document-template.sh 和 bash scripts/test-flow.sh。

5. 七类日常场景

下面每节按同一模板写：什么情况下用它、怎么敲、内部走什么、你会拿到什么产物、验收看什么、常见坑。标 原生阶段 的是工作流本来就有这个阶段；标 组合用法 的是用现有阶段拼出来的用法。

5.1 产品调研 原生阶段 research

什么时候用
要摸外部事实：某个产品/竞品/市场情况、技术选型对比、用户反馈、某个方向值不值得做。和「代码里怎么跑的」无关——那属于 investigate。
怎么敲
/x-rail 调研 <产品/技术>：现在有哪些替代方案，各自的能力边界和真实使用成本，给出是否值得投入的判断
想强制收敛到结论，就把停止条件一起写进去： 
/x-rail 调研 X。要求：隐含假设显式列出，结论必须能落到 proceed / do_not_build，每条附证据出处
内部走什么
读 playbooks/research.md，价值未知时读 x-why，实现未知时读 x-how。要点：先把对象、术语、版本、环境确认清楚（身份不明就阻塞，禁止直接下结论）→ 把请求改写成可证伪的问题，拆成 1–5 条断言 → 证据按优先级取：官方文档/API、官方仓库/发布说明、一手数据或用户原话、可复现测量，最后才是二手来源 → 维护证据台账（claim / source / date / fact_or_inference / confidence / reproducible / contradiction / scope）→ 事实、推断、未知分开写 → 只有当一个测量可能改变决策时，才真去跑它。
产物落在哪
最终报告写 .work-docs/tasks/<task-id>/outputs/；证据台账和运行记录写 evidence/ 或 audit/。报告结尾必须给 decision_gate: proceed | design_only | gather_more | do_not_build，并附开发交接：范围、证据指针、验收方向、仍需人拍板的不可逆决策。
验收看什么
每条结论有没有来源和日期；事实与推断有没有混在一起；失败路径有没有记（「搜不到」不等于「不存在」）；决策门有没有给，而不是留一句「供参考」。
常见坑
把「查到了几篇文章」当结论；把不可复现的一次性体验当数据；没确认版本就开始横向对比。以上三种都会被 research playbook 挡回 gather_more。

5.2 需求评估 组合用法

什么时候用
需求来了，要先判断：这事该不该做、做到哪一层、边界在哪、有没有隐含的不可逆代价。工作流没有单独的「需求评估」阶段，它由三块拼成：research 的决策门 + design 的范围与不可逆决策清单 + x-interrogate 的对抗评审。
怎么敲
/x-rail 评估需求：<需求描述>。产出：（1）该需求解决的真实问题，不做会怎样；
（2）最小可用范围 vs 完整范围；（3）涉及的不可逆决策；（4）有证据支撑的结论：
proceed / design_only / do_not_build。不要改代码。
需要更强的对抗时点名它： 
/x-interrogate 刚才的需求评估结论，找出我漏掉的前提和盲点
内部走什么
先按 research 建立事实（现状、已有能力、外部约束）并给决策门；design playbook 要求写出当前链路、可复用能力、边界、假设与备选方案，并显式定义 done_when、带编号的 Acceptance 验收条件、risk/review_policy、验证层级、文件边界和不可逆决策，定稿前跑 check-contract.sh 过结构校验；证据不足就停在 design_only 或 gather_more，不建执行任务。对抗评审阶段读 x-interrogate，用多个独立视角挑战同一批改动或结论。
产物落在哪
outputs/ 下的一份评估报告（含范围切分与决策门）；研究证据与台账在 evidence/；决策记录在 audit/。
验收看什么
「最小范围」是否写清了不做什么；不可逆决策是否单列（例如数据结构定型、对外发布、花钱）；决策门是不是四选一而不是「都可以」；每条判断有没有证据指针。
常见坑
把需求评估做成方案设计（越界改代码或提前定实现）；结论是「可以做」但没说清做到哪停；漏掉不可逆项，等执行到一半才发现退不回来。

5.3 方案设计 原生阶段 design

什么时候用
需求已经明确，要定结构和接缝：模块怎么切、接口长什么样、数据怎么流、放在哪一层。这个阶段明确不改项目代码。
怎么敲
/x-rail 设计 <要做的东西> 的实现方案：模块边界、接口、数据流、验证方式和不可逆决策
想先探形状，再定稿： 
/x-prototype 用一次性脚本验证「状态这样设计是否够用」，结论写回设计
方案有分叉、想同时看多个答案： 
/x-arena 同一个接口设计给我 3 个独立候选，选出底稿，并把其余的优点嫁接进来
内部走什么
读 playbooks/design.md，并主动读取：x-codebase-design（深层模块的共同词汇：接口、接缝、可测试性）、x-architect（先画类型、签名、模块骨架）、x-arena（并行候选 + 嫁接）、x-prototype（一次性原型回答设计问题），以及三条原则 x-principle-redesign-from-first-principles、x-principle-foundational-thinking、x-principle-outcome-oriented-execution。
产物落在哪
设计写 .work-docs/tasks/<task-id>/outputs/。设计阶段不碰项目代码；如果研究证据不够，就停在 design_only 或 gather_more，不创建执行任务。
验收看什么
有没有写清当前链路和可复用能力；有没有备选方案与取舍；done_when、验证层级、文件边界、不可逆决策是否齐全；接口是否让下游代码变简单，而不是把复杂度搬了个位置。
常见坑
把设计写成实现清单（跳过「为什么」直接排任务）；新需求硬塞进旧结构而不重新审视整体形状（redesign-from-first-principles 就是针对这个）；类型和数据结构没定就先写逻辑（foundational-thinking 的适用点）。

5.4 开发执行 原生阶段 plan → exec → review

什么时候用
方案定了，要真正动代码（也可以是文档、配置、脚本）。
怎么敲
/x-rail 按上面的设计实现 <功能名>。范围：<文件/模块>，其他文件不动
需求明确、改动很小，可以一句走完全程： 
/x-rail 给 <模块> 加上 <行为>，跑通现有测试，给出改动前后的对比输出
想在同一任务里连着走完： 
/x-rail 实现 <功能>：先计划、再执行、最后只读审查一遍
内部走什么
读 playbooks/plan.md：抄下已批准的 done_when 和边界（不得扩大范围），把工作拆成可独立验证的任务，每个任务写清目标文件、允许改动、必需验证、期望证据、被阻塞时的退路；每个验证和子任务都标 required 或 optional，optional 必须写跳过原因。计划写 outputs/，并给出第一个可执行动作。
然后读 playbooks/exec.md：先读契约、计划、状态、目标文件、调用方、测试和当前差异 → 新格式契约先跑 check-contract.sh 过结构校验 → 动手前先写下「本次逻辑改动 + 它需要什么验证」→ 只改任务边界内的文件（用户项目文件是目标，工作流记录留在 .work-docs）→ 由窄到宽跑验证 → 验证失败就记录策略指纹，换一条实质不同的路 → 真实输出存 evidence/，决策和检查点进 audit/。对应的参考技能是 x-typescript-best-practices（读写 TS 时）、x-principle-type-system-discipline（让非法状态不可表示）、x-principle-boundary-discipline（校验集中在系统边界）、x-principle-laziness-protocol（偏删除、最小改动）。
最后读 playbooks/review.md（只读）：对照契约、改动集、证据和未验证项，检查正确性、安全边界、可维护性、完成条件覆盖、工作流文件边界，把发现分成 must-fix / consider / note / rejected，并说明哪些没审；审查结果按契约的 review_policy 写到 review_evidence 指向的路径（如 outputs/review.md），中/高风险任务缺这条审查证据不能标 done。参考技能：x-requesting-code-review、x-receiving-code-review、x-interrogate、x-principle-prove-it-works。
产物落在哪
计划与审查报告进 outputs/；命令真实输出进 evidence/；决策、checkpoint、失败记录进 audit/；可复用的临时夹具进 tmp/。项目代码按契约修改，但不被当成工作流产物。
验收看什么
required 验证是否全 passed 且证据比代码新；改动是否越出契约范围；计划里的 optional 项是否写了跳过原因；审查是否说清了未覆盖部分，中/高风险任务是否留下匹配 review_policy 的审查证据；退出码、文件存在、编译通过、agent 自报完成，都不能单独满足完成条件。
常见坑
把「可以顺手改」当授权，范围外顺手改了别的文件；验证只跑关键词 grep 就宣称行为生效（只能算 static）；改了代码还引用改动前的旧结果。

5.5 问题定位排查 原生阶段 investigate → bugfix → review

什么时候用
出现异常行为、报错、结果不对、线上症状；或者只是想知道「现在到底是什么状态」。分两步：先定位（investigate），能稳定复现才进修复（bugfix）。
怎么敲
/x-rail 定位：<症状描述>。给出最小复现、受影响范围和证据，先不改代码
复现稳定后再修： 
/x-rail 修复 <症状>：先复现，追根因，最小改动，跑回归，给出修复前后的对比输出
想知道「这块代码改动会波及哪里」时点名： 
/x-blast-radius 我要改 <函数/模块>，列出可能被影响的其他地方，并用真实运行证明安全前提
内部走什么
playbooks/investigate.md：先读任务状态、契约和近期证据，再大范围探索 → 说清可观察的问题和 done_when，找出能回答它的最小读取或运行检查 → 先缩小文件、配置、服务、版本范围再跑命令 → 结论分「事实 / 推断 / 未知」并带证据指针 → 说明命中的验证层级 → 契约没要求就不产出正式报告，命令结果进 evidence/、决策进 audit/ → 证据不足以回答就设 blocked，填清尝试路径、共同前提、解除条件和下一步。
playbooks/bugfix.md：用「期望 vs 实际」复现，优先一条失败命令或行为测试 → 复现失败就记录尝试路径并停止猜测 → 定位根因和那个错误假设（带文件/日志证据）→ 做最小的根因修复，只治症状的缓解措施必须显式标注 → 重跑原复现面和相关既有检查 → 连续三次 required 验证失败就停止修改、记录策略指纹、重新验证共同前提 → 保留「修复前失败、修复后通过」两段证据，可复现的任务缺任一段都不能算完成。
参考技能：x-principle-fix-root-causes、x-principle-attack-the-premise（多个共享同一前提的修复都失败时，先普查失衡方，再质疑前提）；investigate 阶段还会读 x-how（这块怎么跑的）和 x-blast-radius（改动波及面）。
产物落在哪
复现命令与前后输出进 evidence/；根因结论、绕过方案、失败策略指纹进 audit/；需要交付的分析写 outputs/。
验收看什么
「修复前失败 / 修复后通过」是否都有真实输出；根因是否指到具体文件和日志；缓解措施有没有被标成「只治症状」；回归是否跑了原来那条复现命令，而不是换了条更容易过的命令。
常见坑
复现不了就开始猜着改；用空值判断把崩溃盖住（fix-root-causes 明确反对「让崩溃闭嘴的空值保护」）；同一命令同一错误重复试（第二次就熔断，必须换方法）；把「搜不到相关代码」当成「问题不存在」。

5.6 长任务执行 入口 x-rail-long

什么时候用
满足以下任一条就进长任务（否则用普通 /x-rail）：跨两个以上阶段、跨会话或过夜、多个子任务、长时间外部运行（等训练、等构建、等第三方批处理）、研究→决策→开发的交接、证据量明显超出普通阈值。
怎么敲
/x-rail-long <长任务说明>。预算：400 次工具调用或 8 小时；每个阶段结束写 checkpoint
建议把「分几个阶段、每阶段验证什么」写清楚，后面的 checkpoint 就按这个切。
内部走什么
在当前命令执行目录初始化唯一的 .work-docs，建 L3 契约和状态；父任务和每个子任务都用唯一 task id，格式 {YYYYMMDD}-{NN}-{slug}（当天日期 + 当日两位自增序号，从 01 起、不回收空号）。取号前先读 .work-docs/index.md：同范围且进行中的任务续用原 id，否则取当天最大序号 +1 并追加索引行。
每个阶段结束追加一个 audit/checkpoint-<序号>.md，写明状态、本阶段 done_when、真实验证输出、证据路径、下一阶段依赖、阻塞和下一步第一动作；同时更新 state.md 的 stage、status、next_action、calls_since_progress、last_progress_at、updated_at。阶段结束不等于任务完成。
准备暂停、过夜、等外部运行或结束会话前，必须更新 state.md 和 handoff.md。handoff.md 是第二天的入口，标准是「新会话只读它就能执行第一步」。
长任务熔断阈值：每子任务 60 次工具调用或 30 分钟无进展；同一命令同一错误首行 2 次；required 验证连续失败 3 次；越界写入；共同前提被否定。总预算默认 400 次工具调用或 8 小时，耗尽写最终 checkpoint，不标 done。
产物落在哪
除常规的 outputs/ evidence/ audit/ tmp/ 外，长任务多了两个关键文件：阶段记录 audit/checkpoint-<序号>.md（只追加，不覆盖旧记录）和恢复入口 handoff.md（只保留当前恢复所需内容）。
验收看什么
每个阶段是否有对应 checkpoint 且带真实验证输出；state.md 的阶段与状态是否和最新 checkpoint 一致；父任务是否在 required 子任务还 in_progress/blocked/stopped 时被标了 done（应当禁止）。
常见坑
把「阶段做完了」写成任务完成；过夜前忘了写 handoff，第二天只能靠聊天记录回忆；checkpoint 覆盖旧文件导致历史丢失；预算耗尽后强行标 done。

5.7 长任务次日状态检查（恢复） 恢复流程 + x-handoff

什么时候用
过夜、换会话、外部运行等完了，或者你只是想确认昨天那件事现在到哪了、下一步第一动作是什么。
怎么敲
/x-rail-long 继续 <task-id>：先给恢复摘要（当前状态、已完成、下一步第一动作、阻塞、证据位置），再执行下一步
不确定 task-id 时直接问： 
/x-rail-long 检查 <项目目录>/.work-docs 下有哪些未完成任务，每个给一行状态摘要
内部走什么
新会话不依赖上一次对话记忆。启动已有任务时先依次读取：.work-docs/index.md → 任务 state.md → audit/ 下最近的 checkpoint-*.md → handoff.md → evidence/；然后在回复开头给出恢复摘要，至少包含：当前状态、已完成、下一步第一动作、阻塞、证据位置；之后才动任务。
恢复时重新读一次 checkpoint 和证据。如果状态与证据不一致，以证据为准，并先把状态退回 in_progress 或 blocked，不得直接宣称完成。恢复只能来自三种理由：阻塞解除、共同前提重新验证通过、有新证据的新策略；且新策略指纹不能与已有指纹相同。
想主动补一份交接时
你点名 /x-handoff（入口不会自动触发它）。它只写当前任务的 .work-docs/tasks/<task-id>/handoff.md，不得写到工作区外。步骤：读 state.md、contract.md、最近 checkpoint 和 evidence → 检查每条证据的 run_at 是否不早于相关文件的 last_edit_at，新鲜的就直接引用，过期的重跑并记真实结果 → 更新 handoff.md，内容含背景、done_when、当前阶段与状态、验证输出、已完成、下一步第一动作、卡点与已尝试策略、约束、待拍板、关键文件和证据路径 → 熔断过的任务还要写 blocked_by、attempted_paths、shared_assumption、unblock_condition 和禁止重复的策略指纹 → 自检「新会话只读这份文件能否直接执行下一步」。
产物落在哪
handoff.md（恢复入口）、state.md（当前状态）、audit/checkpoint-*.md（阶段记录，只追加）。
验收看什么
恢复摘要里有没有「下一步第一动作」和「证据位置」两项；引用的证据是否仍然新鲜；有没有出现「状态说 done、证据却不支持」的情况（出现就该退回 in_progress/blocked）。
常见坑
拿上一会话的记忆当事实；把 handoff 当完成证明（它只是状态入口）；状态与证据冲突时顺着状态走。

6. skills 目录逐个说明

35 个技能全部设置 disable-model-invocation: true：不会被任务内容自动唤起。加载方式只有两种——入口按第 7 节映射表主动读取，或你主动点名 /x-<名字>。

6.1 四个入口技能

x-rail
普通任务入口。支持 fast-answer、investigate、research、design、plan、exec、bugfix、review、ops、mixed 十种路由。契约格式、状态字段、熔断规则、完成判定和文件边界都由它定义。
用：/x-rail <任务说明>。绝大多数日常任务从这里进。
x-rail-long
跨会话、外部等待或独立依赖汇总入口。引用普通规则，只补阶段记录、依赖与原运行恢复。多个阶段或高风险不自动触发。
用：/x-rail-long <长任务说明>。进入判据见 5.6。
x-handoff
把当前任务写成 handoff.md，作为下一个会话的恢复入口，并保证里面的「下一会话第一步」与 next_action 第一条一致。
用：/x-handoff <补充说明>。要收工、过夜、或把任务交给下一个会话接着干时。入口不得自动触发它，只能你点名。
x-self-check
只读分析 Pi 会话记录，默认看最近七日，--days 21 看三周，也可用成对带时区的 --start/--end 指定窗口（结束不包含）。统计入口调用、执行片段、工具动作、等待、错误和覆盖缺口，不联网、不执行日志里的指令。显式给 --task-root 与 --task-mode strict|legacy-readonly 时，复用检查器核对关联任务记录，只输出检查器版本摘要与原字节一致性；不给就不读任务记录。
用：/x-self-check <时间窗口或任务>。保存报告时写当前任务的 outputs/ 和 evidence/。

6.2 理解代码（investigate / research 阶段读取）

x-how
回答「这段是怎么跑起来的」。覆盖子系统架构、运行时流程、上手心智模型，以及「这块该放哪、哪个包拥有它、是不是这层」的归属与分层问题。
用：动一个不熟的模块之前；/x-how <模块> 的调用链。问「为什么这么设计」要用 x-why。
x-why
回答「当初为什么这么定」。覆盖设计缘由、回归原因、事后复盘、有数据支撑的阈值。它会自己发现可用的 MCP 数据源，并行查询各类证据：源码版本库、issue 跟踪、长文档、实时聊天、基础设施可观测、错误跟踪、产品分析数仓，最后给出带引用的决策与取舍读解。
用：/x-why 为什么当初选了 X；复盘「这次回归是谁引入的」。问运行时行为用 x-how。
x-blast-radius
找出一次改动在 diff 之外可能波及的地方，并用真实运行证明「它之所以安全的那个关键事实」，而不是写一篇分析交差。
用：/x-blast-radius 改 <函数> 会影响谁；或审查一个你不太放心的小 diff。

6.3 设计与对抗评审（design / review 阶段读取）

x-codebase-design
设计「深层模块」的共同词汇：接口怎么定、接缝放哪、怎么让代码更好测试、更好被检索和阅读，以及在哪找「加深」的机会。
用：改模块接口、决定分层切分时；也是其他技能需要这套词汇时的共同参照。
x-architect
先勾出类型、函数签名和模块结构，再让实现把内容填进去；设计定稿后仍保持在场，避免实现走形。
用：/x-architect 设计 <模块>，或任何「直接写代码会锁死错误形状」的非平凡工作。
x-arena
同一任务并行生成 N 个候选方案，选一个当底稿，再把落选者里更强的部分嫁接到它上面。
用：/x-arena <任务>。一次尝试就会锁死形状、而你不确定该选哪种形状时。
x-prototype
造一个用完就扔的原型来回答设计问题——状态模型或逻辑合不合手、界面大概该什么样。产物是结论，不是要留下的代码。
用：/x-prototype 验证 <设计假设>。
x-interrogate
让多个 LLM 评审者从互相独立的角度挑战同一批改动，找盲点。对应「对抗评审」「多模型评审」「压力测试这段代码」「把它撕开看看」。
用：/x-interrogate <改动或结论>。需求评估、方案定稿、重要改动合入前的第二双眼睛。

6.4 代码审查与冲突处理（review 阶段读取）

x-requesting-code-review
主动请求代码审查的规范流程，用来确认「做出来的东西是否符合要求」。委派形态的操作规则与实测数据见 docs/review-delegation.md：默认由主会话直接执行，只有当前用户或项目规则明确授权才启动独立审查；取证（跑命令、比对）交脚本，判断（归类、定级）交独立审查者。
用：完成任务、实现主要功能后，或合并前。
x-receiving-code-review
收到评审意见后该怎么处理：先核实、再实现，禁止表演式附和，也禁止不看技术依据就照做。对不清楚或技术上可疑的意见，要求技术上的严谨与验证。
用：别人（或另一个模型）给了你 review 意见，正准备动手改之前。
x-resolving-merge-conflicts
解决正在进行的 git 合并 / 变基冲突的标准做法。
用：/x-resolving-merge-conflicts，仓库正处于 merge 或 rebase 冲突中时。

6.5 写作与语言规范

x-unslop
去掉任何文本里的 AI 味。设计要求是「始终适用」——只要在产出给人看的文字就该带上。
用：写报告、文档、需求说明、对外文字时。入口把它列在「按需读取」里。
x-technical-writing
分层技术写作标准：Diátaxis 结构（教程 / 操作 / 参考 / 解释四类文档各司其职）、Google 开发者写作风格的句子、STE 指令写法、Global English 语法。
用：/x-technical-writing；写或审文档、RFC、README、PR 描述、提交信息时。
x-html
把一个主题或一份文档做成一个自包含的中文 HTML 讲解：面向初中生阅读水平，以图为主（内联 SVG 与 CSS，不联网、不外链），文字遵循受控短句写法（一句一个意思、不超过 20 字、一段最多 3 句）。自带检查器 scripts/check_html.py，机器核对离线、标签闭合、图有名称、每节有图、句子不过长。
用：/x-html <主题或文档路径>；要“讲给不懂的人听”、给文章配图、做网页图册时。不写 API 参考（用 x-technical-writing），不联网查资料（先让 research 出结论）。
x-teach
把一摊工作讲清楚到人真的懂。它会调用 x-how 和 x-why，再把两边查到的东西编成一段解释。
用：/x-teach <模块或改动>；「帮我真正搞懂 X」「给我讲讲这次改动」。
x-typescript-best-practices
TypeScript 最佳实践，声明了文件匹配范围 **/*.ts、**/*.tsx。
用：读或改任何 .ts / .tsx 时（exec 阶段的参考技能）。

6.6 人工步骤与验证（ops 阶段读取）

x-wizard
生成一个交互式 bash 向导，一步步带人做那些只有人能做的事：开基础设施、配密钥或 CI secrets、走一个陌生的第三方后台、跑一次性迁移或切换。
用：/x-wizard <目标>。agent 自己能做的步骤不要用它。
x-create-verification-skill
生成一个项目本地验证技能，让它像用户那样驱动你的应用——不挑语言、框架或平台。适合「这个项目没有脚本化手段证明 UI / CLI / 服务行为」。它属于 ops 阶段的参考技能。
用：/x-create-verification-skill，或「给这个仓库做一个控制技能」。

6.7 十三条工程原则（x-principle-*）

这些是短小的单条原则，多数由其他技能引用，也可以在你自己卡住时点名。格式统一为：一句话是什么 → 什么时候用。

x-principle-fix-root-causes
调试时把每个症状追到根因并在根因处修：先复现，一路问「为什么」直到追上，拒绝用空值判断让崩溃闭嘴。
用在：bugfix 阶段。
x-principle-attack-the-premise
当两个以上共享同一前提的修复都在同一个关口失败时，先普查「哪些角色持有这个失衡」，然后质疑前提，而不是再写一个假设前提成立的修复。
用在：连续修复失败、bugfix 阶段触发熔断前后。
x-principle-prove-it-works
完成之后、宣布完成之前，对着真实产物验证：跑功能、读实际值、看 diff。不接受代理指标、自述或「编译通过」。
用在：review 阶段，以及你自己的完成判定时刻。
x-principle-foundational-thinking
写逻辑之前先定核心类型和数据结构，安排「搭骨架」与「做功能」的先后，先问清并发各方共享什么。数据结构对了，下游代码就变得显然。
用在：design 阶段。
x-principle-type-system-discipline
让非法状态无法被表示、给语义化的基础类型打标记、在边界解析外部数据、不向编译器撒谎、穷尽所有变体、从权威 schema 派生类型。
用在：exec 阶段，任何静态类型语言的类型设计或签名评审。
x-principle-boundary-discipline
把校验、错误处理、框架适配集中在系统边界（命令行、配置、网络、外部 API）；内部信任类型，业务逻辑留在纯函数里。
用在：exec 阶段接线校验、错误处理或框架适配时。
x-principle-laziness-protocol
重构或评估 diff 大小时，偏向删除和「能解决问题的最小改动」；对新增抽象、分层、信号透传保持警惕。
用在：exec 阶段。
x-principle-redesign-from-first-principles
把新需求融进既有设计时，按「这个需求从第一天就是基础假设」重新设计，而不是把它当外挂焊上去。
用在：design 阶段。
x-principle-outcome-oriented-execution
有计划的重写或迁移（阶段边界明确）中，朝目标架构收敛；不要用一次性的兼容代码去维持顺滑的中间态。
用在：design 阶段，以及多阶段迁移任务。
x-principle-build-the-lever
任何非平凡工作（不只是批量工作：编辑、迁移、分析、检查），优先造出「做它或证明它」的工具——codemod、脚本、生成器，或子代理照着走的技能。工具才是审阅者能重跑的产物。
用在：plan 阶段。
x-principle-guard-the-context-window
大输出先工具内统计、筛选或索引，主会话保留有界摘要。上下文大本身不授权委派。
用在：按需读取——长任务、大范围扫描时。
x-principle-encode-lessons-in-structure
当你第二次写同一条指令，或发现同一个纠正反复出现时，把规则编码成 lint、元数据标记、运行时检查或脚本，而不是再写一段文字。
用在：按需读取——发现重复纠正、想固化流程时。
x-principle-separate-before-serializing-shared-state
并发各方可能写同一份文件、分支、键或状态对象时，先消除共享；只有「一个共享写入方」是真实不变量时，才从结构上串行化。
用在：按需读取——并行任务、共享文件或共享状态设计时。

8. 文件边界与目录结构

以命令实际执行的目录为工作根，创建或复用一个 .work-docs/：

<执行目录>/.work-docs/
├── index.md                     任务索引（task-id / scope / status / updated_at）
└── tasks/<task-id>/
    ├── contract.md              这次做什么、范围、done_when、Acceptance 验收条件与 risk/review_policy
    ├── state.md                 当前阶段、状态、证据、阻塞、预算
    ├── handoff.md               恢复入口（新会话只读它就能开工）
    ├── evidence/                命令真实输出、来源指针、可复现测量、失败证据
    ├── outputs/                 最终报告、设计、计划、操作手册
    ├── audit/                   决策、checkpoint-<序号>.md、失败记录、策略指纹、contract-r<N>.md、contract-change-r<N>.md、runs.json
    └── tmp/                     可复用夹具、一次性验证材料

<task-id> 就是任务目录名，格式 {YYYYMMDD}-{NN}-{slug}，例如 20260928-01-yxj-work-independent-workflow。日期是任务首次创建当天的本地日期；{NN} 是当日两位自增序号，从 01 起、不回收空号；{slug} 是小写短名。

取号规则（按顺序执行）：

  1. 读 .work-docs/index.md。若有覆盖同一范围且仍在进行中的任务，续用原 id，不新建。
  2. 否则列出 .work-docs/tasks/，取当天日期目录中最大的 {NN}，加 1。
  3. 已完成或已删除的任务号不得重用或重编。
  4. 把新任务追加到 .work-docs/index.md。

契约与状态里的 task_id 字段等于完整目录名，这样从任务自己的记录就能定位回目录。完成时任务目录里会出现临时的 candidate.md，它只是提交给 task.py complete 的候选状态，提交成功后不再需要。docs/file-boundary.md 只存在于源仓库、不随安装复制，所以运行时技能把需要的规则内联在自己文件里——不要指向那个路径。

工作流生成的持久文件只能落在上面这个目录树里。禁止写到 .audit/、docs/handoff/、00-Inbox/、项目的 docs 目录、外部 local:// 或外部 .audit/。用户指定的项目代码是任务目标，不是工作流产物：在契约和证据里记录它的路径，但不要把它复制进 .work-docs（除非你要求）。

9. state.md 字段速查

state.md 用「每行一个 key: value」的简单格式，方便脚本校验。固定字段：

字段含义
task_id等于任务目录名
levelL1 / L2 / L3（long 模式按 L3/long 计阈值）
stage当前阶段（investigate / research / design / plan / exec / bugfix / review / ops / mixed）
statusin_progress / done / blocked / stopped / cancelled
done_when什么算做完（可逐条，摘要自 Acceptance）
contract_revision / contract_fingerprint新格式任务必填：必须与契约的版本号和内容指纹一致
evidence_schema新任务必填 2；历史明确只读模式
evidence一行一条：evidence:名称|acceptance=A1|command=...|run_at=...|result=...|last_edit_at=...|inputs=...|contract_revision=1，证据文件必须存在
unknowns还没搞清的事
blocked_by被什么挡住（status 为 blocked 时必需）
unblock_condition满足什么才能解除阻塞（blocked 时必需）
next_action下一步第一动作（blocked 时必需）
calls_since_progress距上次有效进展的工具调用次数，有进展就归零
last_progress_at上次有效进展的时间
budgetused/limit
started_at / deadline_at可选；写了就会被校验。超过 deadline_at 仍写 in_progress（或 done）会被 check-state.sh 拦下
strategy_fingerprints已用过的策略指纹（修改文件 + 执行命令 + 错误首行）
review_evidence中/高风险完成必填：review_evidence 绑定 policy、status、path、inputs、contract_revision、run_at、last_edit_at
updated_at最后更新时间

必需验证项单独一行，名称是契约 Acceptance 里的验收编号：required_verification: A1 status=passed evidence=evidence/check.txt，状态只能是 passed | failed | not_run | blocked；启用 evidence_schema: 2 时 evidence= 指向的文件必须存在，且对应 evidence 行的 acceptance= 必须等于 A1。

有效进展包括有证据的新结论、目标产物新版本或必需验收转为 passed。只读结论不要求落盘；目录创建、更新时间和重复读取不算。每次有效进展都更新 calls_since_progress（归零）、last_progress_at、budget 和 strategy_fingerprints。

11. 常见疑问

为什么辅助技能没有被自动唤起？

因为全部设了 disable-model-invocation: true。这是刻意设计：避免模型因为「看到 .ts 文件」或「看到报错」就自行塞进一段技能指令，让任务范围失控。要用就两条路——入口按阶段读，或你点名。

装完看不到它们，是不是没装成功？

用 check-workflow.sh 对照源仓库和安装目标，它会逐项检查目录、安装标记和文件。这比「在列表里看到」可靠。

任务卡住了怎么办？

看 state.md 的 status。是 blocked 就看 blocked_by 和 unblock_condition，那两条就是你需要提供的输入；是 stopped 通常意味着等你拍板（不可逆动作、花钱、对外发布、改需求范围）。恢复必须换一条实质不同的策略，同一策略重试会被熔断规则挡住。

证据过期是什么意思？

证据的 run_at 早于相关文件的 last_edit_at。等于「跑完之后又改了代码」，那条证据不再代表当前状态，必须重跑。

为什么 check-contract 报 fields must use key: value？

契约字段写成了 Markdown 列表项 - key: value。字段必须顶格从第 1 列写成 key: value；去掉行首的 - 即可。

为什么 check-contract 说 confirmation is pending？

契约含敏感动作，但确认仍为 pending，需明确本动作授权才能执行。起草阶段可以用 --draft 模式校验其余结构；拍板后把 confirmation_status 改成 confirmed 并补齐 confirmation_by、confirmation_at、confirmation_source，默认的 --ready 才能通过。

为什么 task.py complete 说 required acceptance not passed？

报错里会跟具体原因：验收还没 passed、证据文件不存在或比相关文件旧、inputs 摘要与当前文件对不上、必需依赖没结束，或契约快照链缺了一环。逐项补齐后重新提交；不要为了让它通过而降低 required 验收。提交失败会保留正式 state.md 和索引，不会把半成品写成 done。

契约改了却被拦（contract changed without a new revision）？

--seal 会把当时契约的原字节存成 audit/contract-r<N>.md。之后改了任何内容而不提升 contract_revision，新字节就对不上旧快照。正确做法：升版本号，在 audit/contract-change-r<N>.md 写新旧值、原因、批准来源和受影响证据，并在 Contract Changes 段引用它。改了必过验收且被放宽时，还需要批准来源。

seal 到底做了什么？

把当前 contract.md 原字节存成 audit/contract-r<N>.md，形成一份不能静默改动的历史链。开工前 --seal 一次，之后的修复删改都会现形；交付前用 --locked 复核整条链与变更记录。追加新任务时不用重新封存旧版本。

为什么 check-state 拒绝我的 done？

逐条对照报错：最常见的是 required 验收没绑定 evidence（缺 acceptance= 指针或证据文件不存在）、evidence 比代码旧、中/高风险任务缺 review_evidence。这些是 evidence_schema: 2 的完成门，目的就是把「agent 自称完成」挡在门外。

为什么 grep 通过不算验证过？

grep 属于 static 层，只能证明文本里出现了某个字符串。如果契约要求 runtime/local 或 consumer 层，就必须真的运行并观察行为。

一个任务里能顺手改点别的吗？

不能。plan 阶段明确「不得扩大范围」。确实需要改范围，就得回到需求评估、重新定义契约，而不是在执行中悄悄扩大。

第三方技能把文件写到 .work-docs 外面了？

立即熔断（blocked_by: external_skill_write_outside_work_docs），保留现场，不要移动、删除或覆盖那个文件，等确认后再处置。

长任务预算用完了但活还没干完？

写 checkpoint 和暂停原因。刚好耗尽且全部验收通过时可提交完成候选；否则暂停。追加预算须记录授权和新策略，不因换一天重置。

用于 AI(Artificial Intelligence，人工智能) 辅助编程的任务流程。普通任务先读、修改、验证并交付。严格任务保存范围、证据和恢复记录。本文说明两种流程、七类日常场景，以及 skills/ 目录中 36 个技能的用法。

1. 这是什么

三种读法。第一次接触：先看第 3 节两张流程图，再扫第 4 节各节的配图，建立整体印象，不必逐字读。要干活：直接跳到第 5 节找对应场景，按命令抄。查规则：第 4 节看机制，第 9、10 节展开字段与命令，第 12 节是一页速查。

x-rail 管理编程任务的范围、验证和恢复。普通任务直接读材料、修改、验证并交付。严格任务还保存完整记录，供中断后继续使用。

  • 先固定目标和允许改动的范围。用户已有修改必须保留。
  • 先运行检查，再核对实际结果。每条结论只覆盖证据能证明的内容。
  • 需要跨会话恢复时保存任务记录。新会话先核对记录和实际产物，再继续。

仓库有 4 个入口技能和 32 个辅助技能。技能是供模型读取的操作说明。入口决定流程，辅助技能提供具体方法。其中 13 个 x-principle-* 文件各说明一条工程原则。

像前端按路由加载页面，x-rail 按当前问题选择阶段。skills/x-rail/SKILL.md 的 routing 模块是执行映射的唯一来源。它指定阶段说明和辅助技能的读取条件。

阶段说明称为 playbook。先读当前阶段说明，再按具体问题读取辅助技能。第 7 节提供查阅表。

2. 安装与调用

scripts/runtime-skills.txt 是安装清单的唯一来源。安装脚本将 36 个技能放到同一个目录。入口的相对路径 ../<技能名>/SKILL.md 因此可以同时用于源码和安装副本。

需要 Bash（命令脚本解释器）和 Python 3.10 或更新版本。项目脚本只使用标准库。先在新的隔离目录验证安装：

cd /Users/yuanxj/Documents/github/x-rail
bash scripts/check-repo.sh
install_dir="$(mktemp -d "${TMPDIR:-/tmp}/x-rail-skills.XXXXXX")"
bash scripts/install.sh --dest "$install_dir"
bash scripts/check-workflow.sh --source "$PWD" --installed "$install_dir"

check-repo.sh 检查仓库结构和规则一致性。check-workflow.sh 对照源仓库与安装目标。两者通过只能证明结构和文件符合检查要求，不能证明模型会遵守全部规则。

全局安装会改变其他会话可用的技能。执行前确认目标路径和目录归属。复制安装默认拒绝覆盖已有目录。

--update 会删除并替换已标记的技能目录，目录内的本地修改会丢失。仅处理带 .x-rail-installed 标记且来源匹配的副本。执行更新前必须取得明确同意。

--unlink 会删除指向本仓库的技能链接。执行前必须取得明确清理授权。链接指向的源文件仍由源仓库保存。

确认全局安装后，可使用以下命令。按当前安装形态选一条，不要混用：

# 新的复制安装
bash scripts/install.sh --dest "$HOME/.pi/agent/skills"
# 更新已标记的复制副本，需要覆盖授权
bash scripts/install.sh --dest "$HOME/.pi/agent/skills" --update
# 开发用链接安装：改源文件后，链接读取新内容
bash scripts/install.sh --dest "$HOME/.pi/agent/skills" --link
# 删除指向本仓库的链接，需要清理授权
bash scripts/install.sh --dest "$HOME/.pi/agent/skills" --unlink

--link 保留已经正确指向本仓库的链接。它拒绝接管已有目录、外来链接和失效链接。链接指向主仓库时，隔离分支的修改不会影响安装内容。

命令用途对应场景
/x-rail <任务说明>处理普通任务，按需要启用严格记录5.1 至 5.5
/x-rail-long <任务说明>跨会话、外部等待或必需依赖汇总5.6 至 5.7
/x-handoff <补充说明>为当前任务保存交接5.7
/x-self-check <时间窗口>只读分析会话记录，默认最近七日6.1
所有技能都设置了 disable-model-invocation: true，意思是禁止模型按任务内容自动唤起。入口只能由用户明确调用。辅助技能由入口按条件读取，或由用户点名调用。

3. 核心流程：一次任务从头到尾

先确定交付结果，再选择阶段和记录强度。只要分析，就在回复交付。要修改，就完成允许范围内的修改和必要验证。已有严格任务始终续接原记录。

严格任务的文件只有两个：contract.md 是任务约定，state.md 是进度记录。start、run、finish 是 task.py 的三个子命令。

严格任务的启动摘要来自契约、状态和最近的阶段记录。摘要说明当前阶段、目标、风险、允许改动、禁止动作、必过验收、证据、阻塞和下一步。缺字段写“未记录”。摘要不创建第二份状态文件。

阶段按当前问题选择。已确认方案不重复设计，小修改可直接执行。审查只在风险、验证不足、需求分歧、用户要求或关键逻辑重改时触发。多个阶段本身不要求长模式。

普通任务用实际工具结果和最终回复交付。严格任务用契约确定边界，用状态定位进度，用证据证明结果。状态写了完成，仍需核对证据是否支持。

4. 七个必须先懂的机制

4.1 路由：交付目标与记录强度

像处理前端页面需求，先区分解释页面、画方案和改组件。x-rail 的阶段表示当前要做哪类工作，不表示任务必须经过几步。

阶段名当前工作
fast-answer简单事实、术语或命令解释，直接回答
investigate确认现状、定位问题或恢复任务
research核对外部事实、产品或技术选型
design确定方案、范围和取舍，不改代码
plan拆实施步骤，或整理已确定材料
exec按明确目标或计划修改并验证
bugfix复现错误、查根因、修复并回归
review只读检查变更和验收依据
ops编写平台操作指引，不代点网页
mixed组合当前目标所需的阶段

记录强度先回答两个问题：failure_cost_high，失败代价是否高；recovery_or_handoff_needed，是否需要跨会话恢复或交接。

  • 两者都为否，且当前会话能完成时，走普通流程。
  • 任一为是，走严格流程。敏感动作、外部等待、必需依赖汇总、独立审查要求或明确要求留档也使用严格记录。
  • 明确只读分析时不为流程写文件。已有严格任务不能降级，也不能放宽原验收。
  • 需要长模式时用 x-rail-long。进入条件是跨会话、外部等待或依赖汇总。规模大或高风险本身不触发长模式。

规模等级只用于严格任务的预算提示。L0 表示直接回答；L1、L2、L3 分别表示小、中、大规模，long 表示长模式。

规模离线调用数提示无进展提醒
L16020 次
L215020 次
L3 或 long400；新状态另有 8 小时截止时间每子任务 60 次，或长任务 30 分钟

未接入宿主真实计数时，调用数是提醒。宿主指运行模型和工具的程序。检查脚本不能据此证明效率，也不会自动终止会话。时间和已有数值预算的校验见 4.5。

4.2 契约与状态（严格任务）

像给组件写验收清单，契约先写可观察结果，再写检查方法。普通任务在回复里说明这些内容。严格任务才写成 contract.md 和 state.md。

Acceptance 是验收清单。A1 表示第一条验收条件，A2 表示第二条。done_when 是完成条件的文字摘要，不能替代逐条验收。

每条验收字段含义
outcome检查什么，以及通过时能看到什么
verification在什么环境中，用哪个命令或操作核对
verification_type验证方式，见 4.3
layer验证环境或层级，见 4.3
requiredyes 表示必过，no 表示可选
skip_reason可选项必须预先写明跳过原因

契约至少有一条必过验收。顶层字段还包括 task_id（任务编号）、level（规模）、task_type（任务阶段）、objective（目标）、scope（允许范围）、forbidden（禁止动作）。

risk 表示低、中、高风险，值为 low、medium、high。risk_reason 解释风险原因。review_policy 指定审查策略，值为 auto、user-confirm、full-review。策略名不授予操作权限。

contract_revision 是契约版本号。三个必备小节为 Unknowns（未知）、Decision Gates（授权记录）、Contract Changes（契约变更记录）。风险决定审查强度，确认只针对不可逆、费用、对外发布和需求范围变化。独立审查另需当前委派授权。

写契约时，每个字段都从第一列写成 key: value，意思是“字段名：值”。不要加列表符号。以下命令供严格任务使用：

# 在源仓库运行；消费项目请换成实际安装技能目录
bash skills/x-rail/scripts/check-contract.sh .work-docs/tasks/<任务编号> --draft
bash skills/x-rail/scripts/check-contract.sh .work-docs/tasks/<任务编号> --ready
bash skills/x-rail/scripts/check-contract.sh .work-docs/tasks/<任务编号> --seal
bash skills/x-rail/scripts/check-contract.sh .work-docs/tasks/<任务编号> --locked

--draft 检查草稿，允许授权仍待确认。--ready 检查能否执行，也是默认模式。--seal 保存原字节快照。--locked 核对快照和变更链。新任务用 start 自动执行初始化、封存和校验。

契约变化时先提高版本号。在 audit/contract-change-r<版本号>.md 记录新旧值、原因、批准来源和受影响证据，再引用到变更小节。旧快照不能改写。历史任务只能显式用 --legacy-readonly 只读核对，不能据此提交新完成。

父任务用 Dependencies 小节声明必需依赖。依赖像页面需要先拿到接口数据，子任务通过后，父任务仍需核对自己的结果：

dependency: build|task_id=<子任务目录名>|required=yes|acceptance=A1

build 是依赖名称示例。可选依赖用 required=no，并写 skip_reason。完成检查递归核对子任务，拒绝循环、重复、自引用和越出目录的路径。

4.3 证据与证据新鲜度

像修改组件后重新跑测试，证据必须代表当前文件。运行时间早于相关文件最后修改时间时，证据过期。严格任务还比较文件内容摘要，避免仅凭时间放行。

每条证据绑定 acceptance（验收编号）、command（实际命令或核对动作）、run_at（运行时间）、result（实际结果）、last_edit_at（相关文件最后修改时间）、inputs（输入摘要路径）和契约版本。

时间必须带时区和秒。检查器换算成 UTC(Coordinated Universal Time，协调世界时) 后比较。命令文本是记录数据，状态校验器不会执行它。

inputs 指向 JSON(JavaScript Object Notation，结构化文本格式) 文件。它记录摘要格式版本、契约版本、绝对工作根路径和相关文件清单。每个文件有相对路径、存在状态和 SHA-256(Secure Hash Algorithm 256-bit，256 位安全散列算法) 内容摘要。摘要像文件指纹，文件字节变化后，摘要也会变化。

存在文件写 present，删除文件写 absent。输入摘要不包含任务状态、契约、证据、审计或临时目录。路径不能越出工作根。输入集合由执行者声明，检查器不能证明材料选得完整。

layer证据能证明什么
syntax/config语法、类型或配置结构符合要求
static文件内容或静态规则符合要求
runtime/local本机实际运行符合预期
external外部服务、账号或权限的实际结果
consumer用户或下游使用产物时能达到目标

验证方式独立于环境。automatic 是自动命令或断言，manual 是人工核对，consumer 是最终使用者验收，external 是依赖外部服务或权限的验证方式。自动调用外部服务可写 automatic + external。本地用户流程可写 consumer + runtime/local。

按完成条件选择必要层级。文本搜索只能证明字符串出现。--expect 只核对输出包含指定文字，验证命令本身仍需检查真实结果。优先用断言、明确测试计数或机器可读结果。

4.4 完成判定

普通任务核对实际结果与完成条件后交付。严格任务还通过完成门。完成门是提交状态前的检查，以下要求必须同时满足：

  1. 全部必过验收通过，每条绑定唯一非空证据。证据覆盖规定的方式和层级，时间与当前输入匹配。
  2. 全部必需依赖通过递归检查。父任务自己的验收也通过。
  3. 授权记录允许交付，敏感动作有匹配的确认来源。审查满足当前风险策略。
  4. 契约版本、内容摘要、快照链和变更记录一致。
  5. 适用的数值预算和时间限制通过。调用数未跟踪时，不制造人工计数。
  6. 已处理文件边界问题，当前正式状态和候选在提交前保持一致。

验收结果为 passed（通过）、failed（结果不符）、not_run（尚未执行）或 blocked（被权限或依赖挡住）。必过项只有 passed 可以完成。可选项需提前声明和说明原因。

新状态必须写 evidence_schema: 2，表示使用第二版证据格式。run 只处理必过且自动的验收。finish 生成候选，再复用 complete --candidate 检查和提交。失败保留正式状态、索引和候选。

任务状态有 in_progress（进行中）、done（完成）、blocked（可恢复阻塞）、stopped（等待授权或主动停止）、cancelled

（取消）。阻塞解除后先核对证据再恢复。取消和停止都不等于完成。

4.5 预算与暂停

失败后先读准确报错，再换方法。第一次失败就不原样重复。以下累计情况要求暂停当前策略：

  • 同一命令和同一错误首行出现两次。
  • 必过验证连续失败三次，即使错误不同。
  • 小规模任务连续 20 次无进展；大规模或长任务每子任务 60 次，或长任务 30 分钟无进展。
  • 第三方技能意外写到允许记录目录之外。
  • 实际证据否定多个步骤共同依赖的假设。

有证据的新结论、目标产物新版本或必过验收通过属于有效进展。创建目录、改时间和重复读取不算。只读结论可以直接在回复交付。

普通任务说明失败、影响和下一步。严格任务还保存失败动作、准确错误和证据。strategy_fingerprints 记录策略指纹，内容是“修改文件、执行命令、错误首行”。新策略必须有实质变化。

严格任务设为阻塞时，填写 blocked_by（阻塞原因）、attempted_paths（已试路径）、shared_assumption（共同假设）、unblock_condition（解除条件）和 next_action（下一步）。长任务再保存阶段记录和交接。

规模预算为 60/150/400。新状态写 budget: untracked/60 等格式，表示调用数未跟踪。旧的 used/limit 数值格式仍受校验。兼容参数 --used 只写 tool_count_note，即执行者观察值，不参与预算或完成门。

新大规模和长模式状态记录 8 小时截止时间。无真实计数时，依据时间、连续无进展和验证失败决定暂停。暂停和等待用户分开说明。换会话或换一天不自动重置已有预算。

模型请求超时后保留“已确认事实、未决问题、下一步”摘要。宿主允许时调整本次模型设置，不能修改全局配置。原外部运行先查询再恢复。工具或运行基础设施失败时，保留准确错误和运行引用，不切换执行协议重发。

4.6 技能加载边界

当前用户授权决定允许动作。辅助技能加载后仍受任务范围、验证和文件边界约束。技能说明不能扩大范围，也不能授权委派。

独立委派像请另一位开发者接手明确的一项检查。启动前需要当前用户或项目规则明确授权。先确认可用能力，再固定任务、输入、输出位置和验收。默认由主会话直接执行。

调用第三方技能前读 playbooks/third-party-skill.md，即第三方技能的文件边界说明。只读技能可使用；可指定输出目录的技能必须传入本任务目录；固定或未知写入的技能只能在隔离目录验证，否则保持阻塞。

调用前后保存文件清单。发现越界文件后立即暂停并保留现场。未经明确同意，不移动、删除或覆盖文件。独立审查所需工具不可用时单列阻塞，不能把作者自查写成独立审查。

4.7 普通与严格文档整理

材料和目标已确定时，测试用例、检查清单和变更说明走轻量文档分支。普通文档直接固定目标、依据、范围和验收，读取材料后写初稿并核对。用户指定文件是任务目标，可以在原位置修改。

需要严格记录时才使用 skills/x-rail/templates/document-task.md 模板，并用 start 生成状态。模板不负责判断意图。普通文档不为流程创建任务目录。

/x-rail 根据 plans/<版本>/ 和提交 <固定提交> 整理手工测试用例。我要测试下。

“我要测试下”表示用户拿用例去测试。它不授权模型代跑。整理用例默认不搭环境、不执行测试、不做全量审查、不检查发布。

  • 到 6 次资料动作时检查材料是否足够。足够就写初稿；不足就写已确认内容和具体缺口。
  • 补读前指出要确认初稿中的哪条事实或预期结果。批量调用仍按实际动作计数。
  • 到 20 次总动作时判断能否交付。必过事实缺失就说明阻塞，不能把部分初稿标为完成。

这些是执行提醒，不是宿主自动拦截。文档验证覆盖、事实和可理解性。严格文档才将核对结果绑定到证据。未执行的测试必须写“测试未执行”。

5. 七类日常场景

每个场景说明使用时机、命令、执行方法、交付位置和验收。只读结论默认在回复交付。用户要文档时写指定位置。严格任务的内部报告和证据才写入任务目录。

5.1 产品调研 原生阶段 research

什么时候用
需要外部事实、替代方案、成本或技术选型依据时。代码运行链路属于调查阶段。
怎么敲
/x-rail 调研 <产品或技术>：替代方案、能力边界、真实成本和投入建议。每条结论附来源和日期。
内部走什么
先确认对象、版本和环境，再拆成能由证据回答的问题。优先官方资料、一手数据和可复现测量。事实、推断、未知分别说明。价值原因不明时读 x-why；实现不明时读 x-how。只有测量能改变决策时才运行。
交付与位置
默认回复交付结论。要求报告时写授权位置；严格记录的报告写 outputs/，来源和运行记录写 evidence/ 或 audit/。结尾写 decision_gate，即下一步决策：proceed（可继续）、design_only（只设计）、gather_more（继续取证）或 do_not_build（不做）。可继续不等于自动授权开发。
验收与常见问题
每条判断有来源、日期和适用范围。结论能解释下一步。搜索摘要不当作一手事实，单次体验不当作稳定数据。搜索失败只说明当前取证结果。

5.2 需求评估 组合用法

什么时候用
需要判断该不该做、最小范围和代价时。按未知组合研究与设计阶段，不默认走完整开发流程。
怎么敲
/x-rail 评估需求：<描述>。说明真实问题、最小范围、代价、风险和有证据的建议。只分析，不改文件。
需要多个独立视角且已授权委派时，可点名 /x-interrogate 挑战结论。
内部走什么
先核对现有能力和约束，再比较做与不做的结果。列出假设、最小范围、替代方案和敏感动作。证据不足时继续取证，不提前进入实施。
交付与位置
只分析就在回复交付。要求评估文档时写指定位置；严格任务的内部报告写 outputs/。不会为了结构校验而创建只读任务文件。
验收与常见问题
建议明确且有依据。范围说明具体。不把需求评估当作修改代码的授权，不把“可以做”当作开发已通过验收。

5.3 方案设计 原生阶段 design

什么时候用
目标已明确，但模块职责、接口、数据流或取舍未确定时。只设计不改项目代码。
怎么敲
/x-rail 设计 <目标> 的方案：当前链路、可复用能力、模块边界、数据流、验证方式和风险。只在回复交付。
需要写方案文件时，补充明确输出路径。
内部走什么
先读当前结构，再选择组件和假设更少的方案。架构取舍时读 x-codebase-design，跨模块分析时读 x-architect。已授权竞争方案时才读 x-arena。原型能回答关键未知时才读 x-prototype。
交付与位置
只设计在回复交付。指定文档写授权位置。严格任务的内部设计写 outputs/。写原型或并行生成候选需符合当前授权和输出边界。
验收与常见问题
方案说明当前链路、替代方案、取舍和验收方向。关键假设有证据或明确标为未知。多个候选不是默认要求，设计说明不能冒充实现结果。

5.4 开发执行 按需选择 plan / exec / review

什么时候用
需要修改代码、配置、脚本或文档时。明确小修改可以直接执行。
怎么敲
/x-rail 按已确认方案实现 <功能>。范围：<文件或模块>。保留已有修改，运行必要检查，给出实际结果。
内部走什么
先固定目标、范围、完成条件和验证动作。读目标文件、调用方、相关测试和当前差异。需要拆解才进入计划阶段。按范围做最小修改，再核对实际结果。风险或验证不足时追加审查。项目规范优先，当前语言是 TypeScript（带类型检查的 JavaScript）且规范不足时才读语言专用技能。
交付与位置
普通任务直接交付改动、验证和限制，目标文件写原位置。严格任务的内部计划和审查写 outputs/，真实输出写 evidence/，决策和阶段记录写 audit/。
验收与常见问题
完成条件有对应结果，相关证据代表当前文件，改动符合允许范围。审查按策略执行。只看退出码、编译通过或模型自报完成，不能证明行为符合要求。

5.5 问题定位排查 investigate / bugfix

什么时候用
出现报错、结果错误或需要确认现状时。原因和复现不清楚就先调查。
怎么敲
/x-rail 定位：<症状>。说明现状、问题、影响和证据。只分析，不改文件。
/x-rail 修复 <症状>：先复现，查根因，最小修改，重跑原复现和相关检查。
内部走什么
先核对目录、分支、版本和当前差异，再比较期望与实际。能稳定复现后沿共同入口和全部相关调用方查根因。修复后重跑原复现。运行链路不明时读 x-how；影响不明时读 x-blast-radius；需要深入核对根因时读对应原则。
交付与位置
普通任务在回复给出根因、改动和修复前后结果。严格任务把真实输出写 evidence/，根因和失败策略写 audit/。
验收与常见问题
可复现问题要有修复前失败与修复后通过的证据。复现不了就说明限制，不猜着改。失败后换方法。只缓解症状的措施必须明确标注。

5.6 长任务执行 入口 x-rail-long

什么时候用
需要跨会话或过夜、等待外部运行，或汇总必需子任务时。多个阶段、大规模或高风险本身不触发长模式。
怎么敲
/x-rail-long <目标>。需要跨会话继续；每阶段结束保存记录，暂停前保存恢复第一步。
内部走什么
续用同范围进行中任务，或创建新的严格记录。每个阶段结束追加 audit/checkpoint-<序号>.md，即阶段检查记录，并同步状态。暂停、过夜或等待前保存 handoff.md 交接摘要。外部运行引用保存在 audit/runs.json，包含原运行标识、提供方、工作区、观察时间和输出位置，不保存密钥。
交付与位置
记录写当前执行目录的 .work-docs/tasks/<任务编号>/。父契约声明必需依赖。阶段结束不等于任务完成，子任务完成不自动通过父验收。
验收与常见问题
阶段记录与当前状态一致。必需子任务、父验收和证据都通过才完成。预算无真实计数时保留未跟踪格式；到时间或无进展限制就保存事实并暂停。

5.7 长任务次日状态检查（恢复） 恢复与交接

什么时候用
换会话、过夜或外部运行结束后继续。只看状态时保持只读。
怎么敲
/x-rail-long 继续 <任务编号>：先核对状态、证据和原运行，再给恢复摘要并执行下一步。
/x-rail-long 检查 <项目目录>/.work-docs 下的未完成任务。只在回复给状态摘要。
/x-handoff 保存当前任务的真实状态、约束、证据和下一会话第一步。
内部走什么
按顺序读索引、契约、状态、最近阶段记录、交接、原运行记录和相关证据。核对工作区、代码版本、未提交差异和输入摘要。原运行先查询，再恢复；无法查询就说明未知或阻塞，不重复启动。
交接与恢复
x-handoff 只能由用户点名，写当前任务的交接文件。它运行严格状态检查，核对证据和原运行。过期证据需要实际重验。末尾“下一会话第一步”与状态的 next_action 第一条一致。长模式在暂停前保存交接是自身规则，不自动唤起该技能。
验收与常见问题
摘要包含当前状态、已完成、阻塞、证据位置和可执行第一步。状态与证据冲突时先核对证据，不能直接宣布完成。交接摘要不能扩大授权，也不能代替完成证明。

6. skills 目录逐个说明

36 个技能都禁止模型自动唤起。入口按第 7 节映射表中的条件读取辅助技能，用户也可主动点名。单条工程原则的适用阶段说明，不表示主入口会自动加载它。

6.1 四个入口技能

x-rail
普通任务入口。支持 fast-answer、investigate、research、design、plan、exec、bugfix、review、ops、mixed 十种路由。契约格式、状态字段、熔断规则、完成判定和文件边界都由它定义。
用：/x-rail <任务说明>。绝大多数日常任务从这里进。
x-rail-long
跨会话、外部等待或独立依赖汇总入口。引用普通规则，只补阶段记录、依赖与原运行恢复。多个阶段或高风险不自动触发。
用：/x-rail-long <长任务说明>。进入判据见 5.6。
x-handoff
把当前任务写成 handoff.md，作为下一个会话的恢复入口，并保证里面的「下一会话第一步」与 next_action 第一条一致。
用：/x-handoff <补充说明>。要收工、过夜、或把任务交给下一个会话接着干时。入口不得自动触发它，只能你点名。
x-self-check
只读分析 Pi（运行本地模型和工具的程序）的会话记录。默认看最近七日，--days 21 看三周。指定窗口时成对使用 --start 和 --end，不包含结束时刻。统计入口、执行片段、工具动作、等待、错误和覆盖缺口，不联网、不执行日志指令。显式给任务根与检查模式时才核对关联任务记录，输出检查器内容摘要和原字节一致性。
用：/x-self-check <时间窗口或任务>。默认在回复交付。用户要求保存时，才写当前授权任务的 outputs/ 和 evidence/。
6.2 理解代码（investigate / research 阶段读取）
x-how
回答「这段是怎么跑起来的」。覆盖子系统架构、运行时流程、上手心智模型，以及「这块该放哪、哪个包拥有它、是不是这层」的归属与分层问题。
用：动一个不熟的模块之前；/x-how <模块> 的调用链。问「为什么这么设计」要用 x-why。
x-why
回答「当初为什么这么定」。覆盖设计缘由、回归原因、事后复盘、有数据支撑的阈值。它按可用权限发现 MCP(Model Context Protocol，模型上下文协议) 数据源。这类接口让模型读取外部工具数据。它并行查询版本库、问题记录、文档和运行数据，再给出有引用的取舍说明。并行查询不等于授权启动子代理。
用：/x-why 为什么当初选了 X；复盘「这次回归是谁引入的」。问运行时行为用 x-how。
x-blast-radius
找出一次改动在已修改文件之外可能影响的地方。用真实运行验证改动所依赖的安全条件，说明证据和限制。
用：/x-blast-radius 改 <函数> 会影响谁；或审查一组影响不明的小改动。
6.3 设计与对抗评审（design / review 阶段读取）
x-codebase-design
设计「深层模块」的共同词汇：接口怎么定、接缝放哪、怎么让代码更好测试、更好被检索和阅读，以及在哪找「加深」的机会。
用：改模块接口、决定分层切分时；也是其他技能需要这套词汇时的共同参照。
x-architect
先勾出类型、函数签名和模块结构，再让实现把内容填进去；设计定稿后仍保持在场，避免实现走形。
用：/x-architect 设计 <模块>，或任何「直接写代码会锁死错误形状」的非平凡工作。
x-arena
已获委派授权时，为同一任务并行生成多个候选。选一个作为底稿，再合入其他候选的有效部分。设计阶段不默认使用。
用：/x-arena <任务>。一次尝试就会锁死形状、而你不确定该选哪种形状时。
x-prototype
造一个用完就扔的原型来回答设计问题——状态模型或逻辑合不合手、界面大概该什么样。产物是结论，不是要留下的代码。
用：/x-prototype 验证 <设计假设>。
x-interrogate
已获委派授权时，让多个 LLM(Large Language Model，大语言模型) 审查者独立检查同一批改动或结论。目标是找遗漏的假设和风险。
用：/x-interrogate <改动或结论>。需求评估、方案定稿、重要改动合入前的第二双眼睛。
6.4 代码审查与冲突处理（review 阶段读取）
x-requesting-code-review
主动请求代码审查的规范流程，用来确认「做出来的东西是否符合要求」。委派形态的操作规则与实测数据见 docs/review-delegation.md：默认由主会话直接执行，只有当前用户或项目规则明确授权才启动独立审查；取证（跑命令、比对）交脚本，判断（归类、定级）交独立审查者。
用：完成任务、实现主要功能后，或合并前。
x-receiving-code-review
收到评审意见后该怎么处理：先核实、再实现，禁止表演式附和，也禁止不看技术依据就照做。对不清楚或技术上可疑的意见，要求技术上的严谨与验证。
用：别人（或另一个模型）给了你 review 意见，正准备动手改之前。
x-resolving-merge-conflicts
处理 Git（保存代码版本的工具）的合并或变基冲突。变基会将分支提交重新放到另一条基线上。
用：/x-resolving-merge-conflicts，仓库正处于 merge 或 rebase 冲突中时。
6.5 写作与语言规范
x-unslop
去掉任何文本里的 AI 味。设计要求是「始终适用」——只要在产出给人看的文字就该带上。
用：写报告、文档、需求说明、对外文字时。入口把它列在「按需读取」里。
x-technical-writing
先选择教程、操作、参考或解释的文档类型，再用短句和明确动作表达。使用 ASD-STE100(ASD Simplified Technical English，简化技术英语规范) 的指令表达原则。中文优先，不声称中文符合其英语词典。
用：/x-technical-writing；写或审文档、方案说明、仓库说明、合并请求描述和提交信息时。
x-html
把一个主题或一份文档做成一个 HTML(HyperText Markup Language，超文本标记语言) 讲解文件，双击可离线阅读。面向初中生，以图为主。图使用 SVG(Scalable Vector Graphics，可缩放矢量图形)，样式使用 CSS(Cascading Style Sheets，层叠样式表)，都写在文件内。文字一句一个意思，不超过 20 字，一段最多 3 句。自带检查器 scripts/check_html.py，核对离线、标签闭合、图有名称、每节有图或表格、句子长度。
用：/x-html <主题或文档路径>；要“讲给不懂的人听”、给文章配图、做网页图册时。接口参考用 x-technical-writing。外部事实先在研究阶段核对。用户指定路径时写该路径。
x-teach
把一摊工作讲清楚到人真的懂。它会调用 x-how 和 x-why，再把两边查到的东西编成一段解释。
用：/x-teach <模块或改动>；「帮我真正搞懂 X」「给我讲讲这次改动」。
x-typescript-best-practices
TypeScript 最佳实践，声明了文件匹配范围 **/*.ts、**/*.tsx。
用：用户点名，或当前代码使用 TypeScript 且项目规范不足时。主入口不因文件后缀而自动加载。
6.6 环境准备、人工步骤与验证
x-worktree
在当前项目里开一个隔离工作区：识别主分支（main 或 master）→ 在 .worktrees/<名称> 下建同名分支 → 把主分支目录的 .env.local 复制进去 → 新工作区里有 pnpm-lock.yaml 时跑 pnpm install。依赖只装在新工作区里，禁止 node_modules 符号链接。重名或目录已存在一律拒绝，不覆盖、不删除；pnpm 缺失或安装失败时报错停下。
用：优先直接调用 scripts/create_worktree.sh，本机已配置时可用 wt <名称>。名称需要推断或已有任务需留档时才用 /x-worktree <名称>。不写名称用 feat-{YYYYMMDDHHmmss}。回归：bash scripts/test-worktree.sh。
x-wizard
生成交互式 Bash 向导，带操作者完成需要人工参与的步骤，例如配置账号和密钥、设置自动检查所用的凭据、操作第三方后台或执行迁移。
用：/x-wizard <目标>。agent 自己能做的步骤不要用它。
x-create-verification-skill
生成项目本地验证技能，按用户路径操作应用。适合缺少脚本检查的界面、命令行或服务行为。需要建立项目验证技能时，它是 ops 阶段的参考技能。
用：/x-create-verification-skill，或「给这个仓库做一个控制技能」。
6.7 十三条工程原则（x-principle-*）

这些是短小的单条原则，多数由其他技能引用，也可以在你自己卡住时点名。格式统一为：一句话是什么 → 什么时候用。

x-principle-fix-root-causes
调试时把每个症状追到根因并在根因处修：先复现，一路问「为什么」直到追上，拒绝用空值判断让崩溃闭嘴。
用在：bugfix 阶段。
x-principle-attack-the-premise
当两个以上共享同一前提的修复都在同一个关口失败时，先普查「哪些角色持有这个失衡」，然后质疑前提，而不是再写一个假设前提成立的修复。
用在：连续修复失败、bugfix 阶段触发熔断前后。
x-principle-prove-it-works
宣布完成前，运行真实功能，核对实际值和文件差异。结论必须对应实际观察结果，不能只靠自述或编译通过。
用在：review 阶段，以及你自己的完成判定时刻。
x-principle-foundational-thinking
写逻辑之前先定核心类型和数据结构，安排「搭骨架」与「做功能」的先后，先问清并发各方共享什么。数据结构对了，下游代码就变得显然。
用在：design 阶段。
x-principle-type-system-discipline
让类型只表示有效状态，在系统入口解析外部数据。处理全部状态分支，从唯一的数据结构定义派生类型。
用在：exec 阶段，任何静态类型语言的类型设计或签名评审。
x-principle-boundary-discipline
把校验、错误处理和框架适配集中在命令行、配置、网络和外部接口的入口。内部逻辑使用已核对的类型，避免重复检查。
用在：exec 阶段接线校验、错误处理或框架适配时。
x-principle-laziness-protocol
重构或评估改动量时，选择能解决问题的最小修改。新增抽象、分层和参数传递必须有当前需求依据。
用在：exec 阶段。
x-principle-redesign-from-first-principles
把新需求融进既有设计时，按「这个需求从第一天就是基础假设」重新设计，而不是把它当外挂焊上去。
用在：design 阶段。
x-principle-outcome-oriented-execution
有计划的重写或迁移（阶段边界明确）中，朝目标架构收敛；不要用一次性的兼容代码去维持顺滑的中间态。
用在：design 阶段，以及多阶段迁移任务。
x-principle-build-the-lever
需要可重复执行的编辑、迁移、分析或检查时，优先复用或建立工具。工具可以是代码批量修改脚本、检查脚本或生成器。保留别人能重跑的验证方式。
用在：确实需要可重复工具的计划工作。轻量文档整理不默认加载。
x-principle-guard-the-context-window
大输出先工具内统计、筛选或索引，主会话保留有界摘要。上下文大本身不授权委派。
用在：按需读取——长任务、大范围扫描时。
x-principle-encode-lessons-in-structure
同一纠正反复出现时，把规则写成静态检查、元数据标记、运行时检查或脚本。让工具直接检查重复问题。
用在：按需读取——发现重复纠正、想固化流程时。
x-principle-separate-before-serializing-shared-state
并发各方可能写同一份文件、分支、键或状态对象时，先消除共享；只有「一个共享写入方」是真实不变量时，才从结构上串行化。
用在：按需读取——并行任务、共享文件或共享状态设计时。

8. 文件边界与目录结构

普通任务直接交付结果，目标文件写授权位置。下面目录只用于严格记录。工作根是命令实际执行的目录。

<执行目录>/.work-docs/
├── index.md                     任务索引
└── tasks/<任务编号>/
    ├── contract.md              目标、范围、验收、风险和授权
    ├── state.md                 当前阶段、状态、证据和阻塞
    ├── handoff.md               当前恢复摘要
    ├── evidence/                实际输出、来源和输入摘要
    ├── outputs/                 内部报告、设计、计划和手册
    ├── audit/                   决策、阶段记录、失败、契约快照、原运行
    └── tmp/                     临时验证材料和候选状态

任务编号格式是 {YYYYMMDD}-{NN}-{slug}。日期取首次创建日；NN 是当天序号，从 01 起；slug 是小写短名。例如 20261012-01-doc-check。

  1. 先读索引。同范围任务仍进行中时续用原编号。
  2. 否则查看当天任务目录，取最大序号加一。
  3. 已完成或已删除的编号不重用、不重编。
  4. 追加索引后复查目录和索引。并发占号时保留先创建者，后来者顺延并记录原因。

契约和状态的 task_id 都等于完整目录名。一个任务只保留一个写入者。finish 生成 tmp/state-<随机值>.md 候选。通过后候选替换正式状态；失败时保留候选，原正式状态和索引保持原值。

工作流生成的持久记录只能写该目录树。用户授权的项目代码、文档和配置是任务目标，可以原位修改。不要把目标文件复制成工作流记录。

docs/file-boundary.md 只在源仓库中，不随安装复制。运行时技能使用自身内联的规则。

状态每行写 字段名: 值。新严格任务由 start 生成初始内容；不要手工制造过去的运行时间或计数。

展开字段说明（19 项）
字段含义与要求

evidence_schema新严格任务写 2
required_verification必过验收的编号、实际结果和证据路径

一条验收与证据的格式如下。A1 是第一条验收，示例时间需换成实际时间：

not_run 可以没有证据文件。通过记录必须绑定真实非空证据。只在重要决定、验证、转向、阻塞和阶段边界更新状态，不为每个工具动作重写文件。

11. 常见疑问

为什么辅助技能没有自动唤起？

所有技能都禁用模型自动调用。入口按条件读取辅助说明，用户也可点名。用安装校验脚本核对文件，不只看模型显示的技能列表。

任务复杂就必须建档或进长模式吗？

先看失败代价和恢复需求。当前会话能完成的普通多阶段任务可以直接交付。只读分析不为流程落盘。跨会话、外部等待或依赖汇总才进长模式。

为什么普通任务没有 state.md？

普通任务用实际工具结果和回复交付。严格任务才创建状态和完成候选。已有严格任务必须按原记录继续，不能通过删除记录降级。

任务卡住了怎么看？

普通任务看当前回复中的阻塞和下一步。严格任务看状态里的阻塞原因、解除条件和第一步动作。等待授权与工具故障分开说明。恢复原运行前先查询，不重复启动。

证据时间够新，为什么仍被拒绝？

时间只是一个条件。输入摘要还必须匹配当前文件，契约版本也必须一致。新时间不能补救旧内容或缺少的实际验收。

fields must use key: value 是什么意思？

意思是字段必须从第一列写成“字段名：值”。将 - key: value 改成 key: value。保留字段的原值。

confirmation is pending 是什么意思？

意思是敏感动作仍待确认。先取得当前动作的明确授权，再记录确认人、时间和来源。草稿可用 --draft 核对结构，但草稿通过不授权执行。

required acceptance not passed 是什么意思？

意思是必过验收没有满足。按准确报错补齐实际验证、证据、当前输入、依赖或审查。不能为了让检查通过而降低验收要求。失败不会把正式状态写成完成。

contract changed without a new revision 是什么意思？

意思是契约变了，版本号却没提高。提高契约版本，记录新旧值、原因、批准来源和受影响证据。保留旧快照，再按新版本重新封存和验证。

finish 会替我运行测试吗？

不会。自动验收用 run。finish 只生成候选并检查已有材料。check-state.sh 也只读检查，不能代替候选提交。

untracked/60 是什么意思？

调用数未跟踪，60 是规模提示。没有宿主真实计数时，不填写人工总数。--used 只保存观察值。旧数值预算和明确截止时间仍受校验。

文本搜索通过能证明功能可用吗？

只能证明指定文本出现。验收要求本地行为、外部服务或用户流程时，要实际运行并核对结果。证据覆盖什么，结论就写到什么。

能顺手扩大修改范围吗？

不能。先说明范围变化的背景、推荐和后果，再取得明确同意。普通任务更新目标和范围；严格任务还提升契约版本并记录来源。

第三方技能意外写出文件怎么办？

暂停并保存现场、准确路径和原因。严格记录写 blocked_by: external_skill_write_outside_work_docs，意思是第三方技能越界写文件。未经同意不移动、删除或覆盖。

长任务到限制时怎么办？

保存阶段记录、真实结果和暂停原因。适用预算刚好耗尽且全部验收满足时可以提交候选。其他情况保留未完成状态，追加预算需记录授权，不因换一天重置。

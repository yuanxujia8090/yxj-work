1. 这是什么

yxj-work 不是一个替人写代码的「大提示词」，而是一套会话管理制度。它管三件事：

  • 边界：这次任务允许改什么、不允许改什么，工作流文件写在哪，代码改到哪为止。
  • 证据：每个结论必须有可复现的命令输出或真实运行结果支撑，「编译过了」「agent 说完成了」都不算。
  • 续接：任务可以中断、过夜、换会话。第二天的新会话只读文件就能接着干，不依赖上一次对话的记忆。

它由三个入口技能（你自己敲命令触发）和三十个辅助技能（入口按阶段主动读取，或你点名调用）组成。 入口负责流程骨架，辅助技能是每个阶段的具体方法，十三条 yxj-principle-* 则是短小的单条工程原则，被其他技能引用。

谁在什么时候读哪份文件，是写死的：入口 yxj-work 里有一张「阶段 → 参考技能」映射表（见 第 6 节）， 进入某阶段就先读该阶段的 playbook，再读表里列出的技能文件。没有第二份清单，也不靠模型临场决定。

2. 安装与调用

安装哪些技能由 scripts/runtime-skills.txt 决定：3 个入口 + 30 个辅助技能，一起复制到同一个技能目录。因为同级安装，入口里的相对读取路径 ../<技能名>/SKILL.md 在源仓库和安装目标下都成立。

cd /Users/yuanxj/Documents/github/yxj-work

# 1) 先自检仓库
bash scripts/check-repo.sh

# 2) 安装（默认拒绝覆盖已有目录）
bash scripts/install.sh --dest "$HOME/.pi/agent/skills"

# 3) 安装后校验：源仓库与安装目标逐项对照
bash scripts/check-workflow.sh --source "$PWD" --installed "$HOME/.pi/agent/skills"

若要更新已安装副本，只覆盖带本仓库写入标记 .yxj-work-installed 的目录：

bash scripts/check-repo.sh
bash scripts/install.sh --dest "$HOME/.pi/agent/skills" --update

安装完成后，日常只敲这三个命令：

命令用途对应场景
/yxj-work <任务说明>普通任务入口：调研、设计、计划、执行、修复、审查本文 4.1 – 4.5
/yxj-work-long <长任务说明>跨阶段、跨会话、过夜或长时间外部运行的任务入口本文 4.6 – 4.7
/yxj-work-handoff <补充说明>把当前任务写成交接文件，供新会话继续（只能你主动调用）本文 4.7
辅助技能全部设置了 disable-model-invocation: true，也就是模型不会因为任务内容自动唤起它们。 两种加载方式：入口按映射表主动读取，或你主动点名 /yxj-why、/yxj-arena。看不到它们被自动调用是设计如此，不是没生效。

3. 五个必须先懂的机制

3.1 路由：L0 与 L1/L2/L3

每次调用先分流。fast-answer（L0）是快问快答——术语解释、简单命令说明、单一事实确认——直接回答，不创建任何工作目录。

除此之外进正式任务，按层级记账：

层级典型规模工具调用预算无进展阈值
L1一次读取 + 一个小改动3020 次工具调用
L2多步骤、需要设计和计划10020 次工具调用
L3 / long跨阶段、跨会话、过夜400，另有 8 小时上限每个子任务 60 次工具调用或 30 分钟

同时按目标路由到阶段：investigate（现状、定位、恢复）、research（外部事实、产品、市场、技术选型）、design（方案设计，不改代码）、plan（逐任务实施规格）、exec（按计划改并验证）、bugfix（复现、根因、最小修复、回归）、review（只读审查）、ops（平台操作手册，不代点网页）、mixed（研究 → 决策门 → 设计/计划 → 执行 → 验证）。

三条常用链路：

  • 开发：design → plan → exec → review。需求明确且改动很小可跳过 design，但要在契约里写明原因。
  • 排查修复：investigate → bugfix → review。无法稳定复现就停在 investigate，不要假装进入修复。
  • 调研：research → decision gate。只有决策门判 proceed 才继续进开发和评审。

3.2 契约与状态

正式任务先写两份文件，再动真东西：contract.md（这次任务做什么、范围到哪、怎么算做完）和 state.md（现在在哪一步、有哪些证据、被什么挡住）。L1 只写一句 done_when、允许范围、验证方式和未知项；L2 还要写任务类型、禁止改动、验证层级、产物位置、阶段和下一入口；L3 每个检查点再带状态、证据、依赖、阻塞和第一步。

状态只会按下面这条路走：

pending ──► active ──► done        （只能通过完成判定）
                │
                ├──► blocked       （工具、证据、依赖、边界问题，可恢复）
                └──► stopped       （不可逆动作、等你拍板、生产变更、花钱、对外发布、改需求范围）

blocked ──► active                 （阻塞解除 / 共同前提重新验证通过 / 有新证据的新策略）

3.3 证据与证据新鲜度

每条证据记录 command、run_at、result 和相关文件的 last_edit_at。运行时间早于文件最后修改时间的证据作废——改了代码还引用旧跑出来的结果，等于没验证。

验证分五层，按契约要求从窄到宽跑：syntax/config → static → runtime/local → external → consumer。关键词搜索和 grep 属于 static，只能证明「字符串在那儿」，不能单独证明「行为生效」。

3.4 完成判定

下面五条同时成立才能写 status: done：

  1. 所有 required（必需）验证项为 passed；
  2. 所有 required 子任务已结束；
  3. 没有未处理的越界文件；
  4. 所有决策门允许交付；
  5. 每个结论都有 evidence 指针。

出现 failed、blocked、not_run、未解决的决策门、仍在跑的 required 子任务或结论缺证据，一律禁止标 done。可选（optional）项必须在契约里声明，并写明跳过原因。

3.5 预算与熔断

熔断的触发条件（每个子任务独立计数）：

  • 同一命令 + 同一错误首行出现 2 次；
  • 错误各不相同时，required 验证连续失败 3 次；
  • L1/L2 连续 20 次工具调用无进展；L3/long 每子任务 60 次工具调用或 30 分钟无进展；
  • 第三方技能越界写入 .work-docs 之外的路径；
  • 共同前提被证据否定。

熔断后必须：停止同策略重试 → 在 audit/ 记录失败动作、错误摘要、策略指纹（修改文件 + 执行命令 + 错误首行）和证据 → 状态改为 blocked 并填 blocked_by、attempted_paths、shared_assumption、unblock_condition、next_action → 写 checkpoint 或交接 → 父任务不得 done。

恢复时，新策略指纹不能与已有指纹相同。说不出新旧策略差在哪，就停下来交给人。

3.6 技能加载边界

辅助技能加载后仍受当前任务的契约、.work-docs 文件边界、预算、熔断和验证要求约束。如果技能自带规则与当前契约冲突，以契约为准，并把差异记到 audit/。

调用第三方技能前先按 playbooks/third-party-skill.md 分类：只读的可以直接跑；能指定输出根的必须传入本次任务目录；固定写入或写入不可知的，只能在隔离的临时目录里试跑，否则任务标 blocked。调用前后都要存目录清单，发现 .work-docs 之外的意外文件立即熔断，且未经授权不得移动、删除或覆盖那个文件。

4. 七类日常场景

下面每节按同一模板写：什么情况下用它、怎么敲、内部走什么、你会拿到什么产物、验收看什么、常见坑。标 原生阶段 的是工作流本来就有这个阶段；标 组合用法 的是用现有阶段拼出来的用法。

4.1 产品调研 原生阶段 research

什么时候用
要摸外部事实：某个产品/竞品/市场情况、技术选型对比、用户反馈、某个方向值不值得做。和「代码里怎么跑的」无关——那属于 investigate。
怎么敲
/yxj-work 调研 <产品/技术>：现在有哪些替代方案，各自的能力边界和真实使用成本，给出是否值得投入的判断
想强制收敛到结论，就把停止条件一起写进去： 
/yxj-work 调研 X。要求：隐含假设显式列出，结论必须能落到 proceed / do_not_build，每条附证据出处
内部走什么
读 playbooks/research.md，并主动读取 yxj-why（查设计缘由类证据）和 yxj-how（看现有实现怎么跑）。要点：先把对象、术语、版本、环境确认清楚（身份不明就阻塞，禁止直接下结论）→ 把请求改写成可证伪的问题，拆成 1–5 条断言 → 证据按优先级取：官方文档/API、官方仓库/发布说明、一手数据或用户原话、可复现测量，最后才是二手来源 → 维护证据台账（claim / source / date / fact_or_inference / confidence / reproducible / contradiction / scope）→ 事实、推断、未知分开写 → 只有当一个测量可能改变决策时，才真去跑它。
产物落在哪
最终报告写 .work-docs/tasks/<task-id>/outputs/；证据台账和运行记录写 evidence/ 或 audit/。报告结尾必须给 decision_gate: proceed | design_only | gather_more | do_not_build，并附开发交接：范围、证据指针、验收方向、仍需人拍板的不可逆决策。
验收看什么
每条结论有没有来源和日期；事实与推断有没有混在一起；失败路径有没有记（「搜不到」不等于「不存在」）；决策门有没有给，而不是留一句「供参考」。
常见坑
把「查到了几篇文章」当结论；把不可复现的一次性体验当数据；没确认版本就开始横向对比。以上三种都会被 research playbook 挡回 gather_more。

4.2 需求评估 组合用法

什么时候用
需求来了，要先判断：这事该不该做、做到哪一层、边界在哪、有没有隐含的不可逆代价。工作流没有单独的「需求评估」阶段，它由三块拼成：research 的决策门 + design 的范围与不可逆决策清单 + yxj-interrogate 的对抗评审。
怎么敲
/yxj-work 评估需求：<需求描述>。产出：（1）该需求解决的真实问题，不做会怎样；
（2）最小可用范围 vs 完整范围；（3）涉及的不可逆决策；（4）有证据支撑的结论：
proceed / design_only / do_not_build。不要改代码。
需要更强的对抗时点名它： 
/yxj-interrogate 刚才的需求评估结论，找出我漏掉的前提和盲点
内部走什么
先按 research 建立事实（现状、已有能力、外部约束）并给决策门；design playbook 要求写出当前链路、可复用能力、边界、假设与备选方案，并显式定义 done_when、验证层级、文件边界和不可逆决策；证据不足就停在 design_only 或 gather_more，不建执行任务。对抗评审阶段读 yxj-interrogate，用多个独立视角挑战同一批改动或结论。
产物落在哪
outputs/ 下的一份评估报告（含范围切分与决策门）；研究证据与台账在 evidence/；决策记录在 audit/。
验收看什么
「最小范围」是否写清了不做什么；不可逆决策是否单列（例如数据结构定型、对外发布、花钱）；决策门是不是四选一而不是「都可以」；每条判断有没有证据指针。
常见坑
把需求评估做成方案设计（越界改代码或提前定实现）；结论是「可以做」但没说清做到哪停；漏掉不可逆项，等执行到一半才发现退不回来。

4.3 方案设计 原生阶段 design

什么时候用
需求已经明确，要定结构和接缝：模块怎么切、接口长什么样、数据怎么流、放在哪一层。这个阶段明确不改项目代码。
怎么敲
/yxj-work 设计 <要做的东西> 的实现方案：模块边界、接口、数据流、验证方式和不可逆决策
想先探形状，再定稿： 
/yxj-prototype 用一次性脚本验证「状态这样设计是否够用」，结论写回设计
方案有分叉、想同时看多个答案： 
/yxj-arena 同一个接口设计给我 3 个独立候选，选出底稿，并把其余的优点嫁接进来
内部走什么
读 playbooks/design.md，并主动读取：yxj-codebase-design（深层模块的共同词汇：接口、接缝、可测试性）、yxj-architect（先画类型、签名、模块骨架）、yxj-arena（并行候选 + 嫁接）、yxj-prototype（一次性原型回答设计问题），以及三条原则 yxj-principle-redesign-from-first-principles、yxj-principle-foundational-thinking、yxj-principle-outcome-oriented-execution。
产物落在哪
设计写 .work-docs/tasks/<task-id>/outputs/。设计阶段不碰项目代码；如果研究证据不够，就停在 design_only 或 gather_more，不创建执行任务。
验收看什么
有没有写清当前链路和可复用能力；有没有备选方案与取舍；done_when、验证层级、文件边界、不可逆决策是否齐全；接口是否让下游代码变简单，而不是把复杂度搬了个位置。
常见坑
把设计写成实现清单（跳过「为什么」直接排任务）；新需求硬塞进旧结构而不重新审视整体形状（redesign-from-first-principles 就是针对这个）；类型和数据结构没定就先写逻辑（foundational-thinking 的适用点）。

4.4 开发执行 原生阶段 plan → exec → review

什么时候用
方案定了，要真正动代码（也可以是文档、配置、脚本）。
怎么敲
/yxj-work 按上面的设计实现 <功能名>。范围：<文件/模块>，其他文件不动
需求明确、改动很小，可以一句走完全程： 
/yxj-work 给 <模块> 加上 <行为>，跑通现有测试，给出改动前后的对比输出
想在同一任务里连着走完： 
/yxj-work 实现 <功能>：先计划、再执行、最后只读审查一遍
内部走什么
读 playbooks/plan.md：抄下已批准的 done_when 和边界（不得扩大范围），把工作拆成可独立验证的任务，每个任务写清目标文件、允许改动、必需验证、期望证据、被阻塞时的退路；每个验证和子任务都标 required 或 optional，optional 必须写跳过原因。计划写 outputs/，并给出第一个可执行动作。
然后读 playbooks/exec.md：先读契约、计划、状态、目标文件、调用方、测试和当前差异 → 动手前先写下「本次逻辑改动 + 它需要什么验证」→ 只改任务边界内的文件（用户项目文件是目标，工作流记录留在 .work-docs）→ 由窄到宽跑验证 → 验证失败就记录策略指纹，换一条实质不同的路 → 真实输出存 evidence/，决策和检查点进 audit/。对应的参考技能是 yxj-typescript-best-practices（读写 TS 时）、yxj-principle-type-system-discipline（让非法状态不可表示）、yxj-principle-boundary-discipline（校验集中在系统边界）、yxj-principle-laziness-protocol（偏删除、最小改动）。
最后读 playbooks/review.md（只读）：对照契约、改动集、证据和未验证项，检查正确性、安全边界、可维护性、完成条件覆盖、工作流文件边界，把发现分成 must-fix / consider / note / rejected，并说明哪些没审。参考技能：yxj-requesting-code-review、yxj-receiving-code-review、yxj-interrogate、yxj-principle-prove-it-works。
产物落在哪
计划与审查报告进 outputs/；命令真实输出进 evidence/；决策、checkpoint、失败记录进 audit/；可复用的临时夹具进 tmp/。项目代码按契约修改，但不被当成工作流产物。
验收看什么
required 验证是否全 passed 且证据比代码新；改动是否越出契约范围；计划里的 optional 项是否写了跳过原因；审查是否说清了未覆盖部分。退出码、文件存在、编译通过、agent 自报完成，都不能单独满足完成条件。
常见坑
把「可以顺手改」当授权，范围外顺手改了别的文件；验证只跑关键词 grep 就宣称行为生效（只能算 static）；改了代码还引用改动前的旧结果。

4.5 问题定位排查 原生阶段 investigate → bugfix → review

什么时候用
出现异常行为、报错、结果不对、线上症状；或者只是想知道「现在到底是什么状态」。分两步：先定位（investigate），能稳定复现才进修复（bugfix）。
怎么敲
/yxj-work 定位：<症状描述>。给出最小复现、受影响范围和证据，先不改代码
复现稳定后再修： 
/yxj-work 修复 <症状>：先复现，追根因，最小改动，跑回归，给出修复前后的对比输出
想知道「这块代码改动会波及哪里」时点名： 
/yxj-blast-radius 我要改 <函数/模块>，列出可能被影响的其他地方，并用真实运行证明安全前提
内部走什么
playbooks/investigate.md：先读任务状态、契约和近期证据，再大范围探索 → 说清可观察的问题和 done_when，找出能回答它的最小读取或运行检查 → 先缩小文件、配置、服务、版本范围再跑命令 → 结论分「事实 / 推断 / 未知」并带证据指针 → 说明命中的验证层级 → 契约没要求就不产出正式报告，命令结果进 evidence/、决策进 audit/ → 证据不足以回答就设 blocked，填清尝试路径、共同前提、解除条件和下一步。
playbooks/bugfix.md：用「期望 vs 实际」复现，优先一条失败命令或行为测试 → 复现失败就记录尝试路径并停止猜测 → 定位根因和那个错误假设（带文件/日志证据）→ 做最小的根因修复，只治症状的缓解措施必须显式标注 → 重跑原复现面和相关既有检查 → 连续三次 required 验证失败就停止修改、记录策略指纹、重新验证共同前提 → 保留「修复前失败、修复后通过」两段证据，可复现的任务缺任一段都不能算完成。
参考技能：yxj-principle-fix-root-causes、yxj-principle-attack-the-premise（多个共享同一前提的修复都失败时，先普查失衡方，再质疑前提）；investigate 阶段还会读 yxj-how（这块怎么跑的）和 yxj-blast-radius（改动波及面）。
产物落在哪
复现命令与前后输出进 evidence/；根因结论、绕过方案、失败策略指纹进 audit/；需要交付的分析写 outputs/。
验收看什么
「修复前失败 / 修复后通过」是否都有真实输出；根因是否指到具体文件和日志；缓解措施有没有被标成「只治症状」；回归是否跑了原来那条复现命令，而不是换了条更容易过的命令。
常见坑
复现不了就开始猜着改；用空值判断把崩溃盖住（fix-root-causes 明确反对「让崩溃闭嘴的空值保护」）；同一命令同一错误重复试（第二次就熔断，必须换方法）；把「搜不到相关代码」当成「问题不存在」。

4.6 长任务执行 入口 yxj-work-long

什么时候用
满足以下任一条就进长任务（否则用普通 /yxj-work）：跨两个以上阶段、跨会话或过夜、多个子任务、长时间外部运行（等训练、等构建、等第三方批处理）、研究→决策→开发的交接、证据量明显超出普通阈值。
怎么敲
/yxj-work-long <长任务说明>。预算：400 次工具调用或 8 小时；每个阶段结束写 checkpoint
建议把「分几个阶段、每阶段验证什么」写清楚，后面的 checkpoint 就按这个切。
内部走什么
在当前命令执行目录初始化唯一的 .work-docs，建 L3 契约和状态；父任务和每个子任务都用唯一 task id，格式 {YYYYMMDD}-{NN}-{slug}（当天日期 + 当日两位自增序号，从 01 起、不回收空号）。取号前先读 .work-docs/index.md：同范围且进行中的任务续用原 id，否则取当天最大序号 +1 并追加索引行。
每个阶段结束追加一个 audit/checkpoint-<序号>.md，写明状态、本阶段 done_when、真实验证输出、证据路径、下一阶段依赖、阻塞和下一步第一动作；同时更新 state.md 的 stage、status、next_action、calls_since_progress、last_progress_at、updated_at。阶段结束不等于任务完成。
准备暂停、过夜、等外部运行或结束会话前，必须更新 state.md 和 handoff.md。handoff.md 是第二天的入口，标准是「新会话只读它就能执行第一步」。
长任务熔断阈值：每子任务 60 次工具调用或 30 分钟无进展；同一命令同一错误首行 2 次；required 验证连续失败 3 次；越界写入；共同前提被否定。总预算默认 400 次工具调用或 8 小时，耗尽写最终 checkpoint，不标 done。
产物落在哪
除常规的 outputs/ evidence/ audit/ tmp/ 外，长任务多了两个关键文件：阶段记录 audit/checkpoint-<序号>.md（只追加，不覆盖旧记录）和恢复入口 handoff.md（只保留当前恢复所需内容）。
验收看什么
每个阶段是否有对应 checkpoint 且带真实验证输出；state.md 的阶段与状态是否和最新 checkpoint 一致；父任务是否在 required 子任务还 active/blocked/stopped 时被标了 done（应当禁止）。
常见坑
把「阶段做完了」写成任务完成；过夜前忘了写 handoff，第二天只能靠聊天记录回忆；checkpoint 覆盖旧文件导致历史丢失；预算耗尽后强行标 done。

4.7 长任务次日状态检查（恢复） 恢复流程 + yxj-work-handoff

什么时候用
过夜、换会话、外部运行等完了，或者你只是想确认昨天那件事现在到哪了、下一步第一动作是什么。
怎么敲
/yxj-work-long 继续 <task-id>：先给恢复摘要（当前状态、已完成、下一步第一动作、阻塞、证据位置），再执行下一步
不确定 task-id 时直接问： 
/yxj-work-long 检查 <项目目录>/.work-docs 下有哪些未完成任务，每个给一行状态摘要
内部走什么
新会话不依赖上一次对话记忆。启动已有任务时先依次读取：.work-docs/index.md → 任务 state.md → audit/ 下最近的 checkpoint-*.md → handoff.md → evidence/；然后在回复开头给出恢复摘要，至少包含：当前状态、已完成、下一步第一动作、阻塞、证据位置；之后才动任务。
恢复时重新读一次 checkpoint 和证据。如果状态与证据不一致，以证据为准，并先把状态退回 active 或 blocked，不得直接宣称完成。恢复只能来自三种理由：阻塞解除、共同前提重新验证通过、有新证据的新策略；且新策略指纹不能与已有指纹相同。
想主动补一份交接时
你点名 /yxj-work-handoff（入口不会自动触发它）。它只写当前任务的 .work-docs/tasks/<task-id>/handoff.md，不得写到工作区外。步骤：读 state.md、contract.md、最近 checkpoint 和 evidence → 检查每条证据的 run_at 是否不早于相关文件的 last_edit_at，新鲜的就直接引用，过期的重跑并记真实结果 → 更新 handoff.md，内容含背景、done_when、当前阶段与状态、验证输出、已完成、下一步第一动作、卡点与已尝试策略、约束、待拍板、关键文件和证据路径 → 熔断过的任务还要写 blocked_by、attempted_paths、shared_assumption、unblock_condition 和禁止重复的策略指纹 → 自检「新会话只读这份文件能否直接执行下一步」。
产物落在哪
handoff.md（恢复入口）、state.md（当前状态）、audit/checkpoint-*.md（阶段记录，只追加）。
验收看什么
恢复摘要里有没有「下一步第一动作」和「证据位置」两项；引用的证据是否仍然新鲜；有没有出现「状态说 done、证据却不支持」的情况（出现就该退回 active/blocked）。
常见坑
拿上一会话的记忆当事实；把 handoff 当完成证明（它只是状态入口）；状态与证据冲突时顺着状态走。

5. skills 目录逐个说明

33 个技能全部设置 disable-model-invocation: true：不会被任务内容自动唤起。加载方式只有两种——入口按第 6 节映射表主动读取，或你主动点名 /yxj-<名字>。

5.1 三个入口技能

yxj-work
普通任务入口。支持 fast-answer、investigate、research、design、plan、exec、bugfix、review、ops、mixed 十种路由。契约格式、状态字段、熔断规则、完成判定和文件边界都由它定义。
用：/yxj-work <任务说明>。绝大多数日常任务从这里进。
yxj-work-long
跨阶段、跨会话、过夜或长时间外部运行的任务入口。在普通规则之外增加 L3 契约、阶段 checkpoint、次日恢复摘要、400 次 / 8 小时总预算。
用：/yxj-work-long <长任务说明>。进入判据见 4.6。
yxj-work-handoff
把当前任务写成 handoff.md，作为下一个会话的恢复入口，并保证里面的「下一会话第一步」与 next_action 第一条一致。
用：/yxj-work-handoff <补充说明>。要收工、过夜、或把任务交给下一个会话接着干时。入口不得自动触发它，只能你点名。

5.2 理解代码（investigate / research 阶段读取）

yxj-how
回答「这段是怎么跑起来的」。覆盖子系统架构、运行时流程、上手心智模型，以及「这块该放哪、哪个包拥有它、是不是这层」的归属与分层问题。
用：动一个不熟的模块之前；/yxj-how <模块> 的调用链。问「为什么这么设计」要用 yxj-why。
yxj-why
回答「当初为什么这么定」。覆盖设计缘由、回归原因、事后复盘、有数据支撑的阈值。它会自己发现可用的 MCP 数据源，并行查询各类证据：源码版本库、issue 跟踪、长文档、实时聊天、基础设施可观测、错误跟踪、产品分析数仓，最后给出带引用的决策与取舍读解。
用：/yxj-why 为什么当初选了 X；复盘「这次回归是谁引入的」。问运行时行为用 yxj-how。
yxj-blast-radius
找出一次改动在 diff 之外可能波及的地方，并用真实运行证明「它之所以安全的那个关键事实」，而不是写一篇分析交差。
用：/yxj-blast-radius 改 <函数> 会影响谁；或审查一个你不太放心的小 diff。

5.3 设计与对抗评审（design / review 阶段读取）

yxj-codebase-design
设计「深层模块」的共同词汇：接口怎么定、接缝放哪、怎么让代码更好测试、更好被检索和阅读，以及在哪找「加深」的机会。
用：改模块接口、决定分层切分时；也是其他技能需要这套词汇时的共同参照。
yxj-architect
先勾出类型、函数签名和模块结构，再让实现把内容填进去；设计定稿后仍保持在场，避免实现走形。
用：/yxj-architect 设计 <模块>，或任何「直接写代码会锁死错误形状」的非平凡工作。
yxj-arena
同一任务并行生成 N 个候选方案，选一个当底稿，再把落选者里更强的部分嫁接到它上面。
用：/yxj-arena <任务>。一次尝试就会锁死形状、而你不确定该选哪种形状时。
yxj-prototype
造一个用完就扔的原型来回答设计问题——状态模型或逻辑合不合手、界面大概该什么样。产物是结论，不是要留下的代码。
用：/yxj-prototype 验证 <设计假设>。
yxj-interrogate
让多个 LLM 评审者从互相独立的角度挑战同一批改动，找盲点。对应「对抗评审」「多模型评审」「压力测试这段代码」「把它撕开看看」。
用：/yxj-interrogate <改动或结论>。需求评估、方案定稿、重要改动合入前的第二双眼睛。

5.4 代码审查与冲突处理（review 阶段读取）

yxj-requesting-code-review
主动请求代码审查的规范流程，用来确认「做出来的东西是否符合要求」。
用：完成任务、实现主要功能后，或合并前。
yxj-receiving-code-review
收到评审意见后该怎么处理：先核实、再实现，禁止表演式附和，也禁止不看技术依据就照做。对不清楚或技术上可疑的意见，要求技术上的严谨与验证。
用：别人（或另一个模型）给了你 review 意见，正准备动手改之前。
yxj-resolving-merge-conflicts
解决正在进行的 git 合并 / 变基冲突的标准做法。
用：/yxj-resolving-merge-conflicts，仓库正处于 merge 或 rebase 冲突中时。

5.5 写作与语言规范

yxj-unslop
去掉任何文本里的 AI 味。设计要求是「始终适用」——只要在产出给人看的文字就该带上。
用：写报告、文档、需求说明、对外文字时。入口把它列在「按需读取」里。
yxj-technical-writing
分层技术写作标准：Diátaxis 结构（教程 / 操作 / 参考 / 解释四类文档各司其职）、Google 开发者写作风格的句子、STE 指令写法、Global English 语法。
用：/yxj-technical-writing；写或审文档、RFC、README、PR 描述、提交信息时。
yxj-teach
把一摊工作讲清楚到人真的懂。它会调用 yxj-how 和 yxj-why，再把两边查到的东西编成一段解释。
用：/yxj-teach <模块或改动>；「帮我真正搞懂 X」「给我讲讲这次改动」。
yxj-typescript-best-practices
TypeScript 最佳实践，声明了文件匹配范围 **/*.ts、**/*.tsx。
用：读或改任何 .ts / .tsx 时（exec 阶段的参考技能）。

5.6 人工步骤与验证（ops 阶段读取）

yxj-wizard
生成一个交互式 bash 向导，一步步带人做那些只有人能做的事：开基础设施、配密钥或 CI secrets、走一个陌生的第三方后台、跑一次性迁移或切换。
用：/yxj-wizard <目标>。agent 自己能做的步骤不要用它。
yxj-create-verification-skill
生成一个项目本地验证技能，让它像用户那样驱动你的应用——不挑语言、框架或平台。适合「这个项目没有脚本化手段证明 UI / CLI / 服务行为」。它属于 ops 阶段的参考技能。
用：/yxj-create-verification-skill，或「给这个仓库做一个控制技能」。

5.7 十三条工程原则（yxj-principle-*）

这些是短小的单条原则，多数由其他技能引用，也可以在你自己卡住时点名。格式统一为：一句话是什么 → 什么时候用。

yxj-principle-fix-root-causes
调试时把每个症状追到根因并在根因处修：先复现，一路问「为什么」直到追上，拒绝用空值判断让崩溃闭嘴。
用在：bugfix 阶段。
yxj-principle-attack-the-premise
当两个以上共享同一前提的修复都在同一个关口失败时，先普查「哪些角色持有这个失衡」，然后质疑前提，而不是再写一个假设前提成立的修复。
用在：连续修复失败、bugfix 阶段触发熔断前后。
yxj-principle-prove-it-works
完成之后、宣布完成之前，对着真实产物验证：跑功能、读实际值、看 diff。不接受代理指标、自述或「编译通过」。
用在：review 阶段，以及你自己的完成判定时刻。
yxj-principle-foundational-thinking
写逻辑之前先定核心类型和数据结构，安排「搭骨架」与「做功能」的先后，先问清并发各方共享什么。数据结构对了，下游代码就变得显然。
用在：design 阶段。
yxj-principle-type-system-discipline
让非法状态无法被表示、给语义化的基础类型打标记、在边界解析外部数据、不向编译器撒谎、穷尽所有变体、从权威 schema 派生类型。
用在：exec 阶段，任何静态类型语言的类型设计或签名评审。
yxj-principle-boundary-discipline
把校验、错误处理、框架适配集中在系统边界（命令行、配置、网络、外部 API）；内部信任类型，业务逻辑留在纯函数里。
用在：exec 阶段接线校验、错误处理或框架适配时。
yxj-principle-laziness-protocol
重构或评估 diff 大小时，偏向删除和「能解决问题的最小改动」；对新增抽象、分层、信号透传保持警惕。
用在：exec 阶段。
yxj-principle-redesign-from-first-principles
把新需求融进既有设计时，按「这个需求从第一天就是基础假设」重新设计，而不是把它当外挂焊上去。
用在：design 阶段。
yxj-principle-outcome-oriented-execution
有计划的重写或迁移（阶段边界明确）中，朝目标架构收敛；不要用一次性的兼容代码去维持顺滑的中间态。
用在：design 阶段，以及多阶段迁移任务。
yxj-principle-build-the-lever
任何非平凡工作（不只是批量工作：编辑、迁移、分析、检查），优先造出「做它或证明它」的工具——codemod、脚本、生成器，或子代理照着走的技能。工具才是审阅者能重跑的产物。
用在：plan 阶段。
yxj-principle-guard-the-context-window
上下文快满时（大输出、长文件、反复读取、扇出规划），把批量活路由给子代理，主线程只留摘要，不留原始负载。
用在：按需读取——长任务、大范围扫描时。
yxj-principle-encode-lessons-in-structure
当你第二次写同一条指令，或发现同一个纠正反复出现时，把规则编码成 lint、元数据标记、运行时检查或脚本，而不是再写一段文字。
用在：按需读取——发现重复纠正、想固化流程时。
yxj-principle-separate-before-serializing-shared-state
并发各方可能写同一份文件、分支、键或状态对象时，先消除共享；只有「一个共享写入方」是真实不变量时，才从结构上串行化。
用在：按需读取——并行任务、共享文件或共享状态设计时。

7. 文件边界与目录结构

以命令实际执行的目录为工作根，创建或复用一个 .work-docs/：

<执行目录>/.work-docs/
├── index.md                     任务索引（task-id / scope / status / updated_at）
└── tasks/<task-id>/
    ├── contract.md              这次做什么、范围、done_when
    ├── state.md                 当前阶段、状态、证据、阻塞、预算
    ├── handoff.md               恢复入口（新会话只读它就能开工）
    ├── evidence/                命令真实输出、来源指针、可复现测量、失败证据
    ├── outputs/                 最终报告、设计、计划、操作手册
    ├── audit/                   决策、checkpoint、进行中记录、失败记录、策略指纹
    └── tmp/                     可复用夹具、一次性验证材料

<task-id> 就是任务目录名，格式 {YYYYMMDD}-{NN}-{slug}，例如 20260928-01-yxj-work-independent-workflow。日期是任务首次创建当天的本地日期；{NN} 是当日两位自增序号，从 01 起、不回收空号；{slug} 是小写短名。

取号规则（按顺序执行）：

  1. 读 .work-docs/index.md。若有覆盖同一范围且仍在进行中的任务，续用原 id，不新建。
  2. 否则列出 .work-docs/tasks/，取当天日期目录中最大的 {NN}，加 1。
  3. 已完成或已删除的任务号不得重用或重编。
  4. 把新任务追加到 .work-docs/index.md。

契约与状态里的 task_id 字段等于完整目录名，这样从任务自己的记录就能定位回目录。docs/file-boundary.md 只存在于源仓库、不随安装复制，所以运行时技能把需要的规则内联在自己文件里——不要指向那个路径。

工作流生成的持久文件只能落在上面这个目录树里。禁止写到 .audit/、docs/handoff/、00-Inbox/、项目的 docs 目录、外部 local:// 或外部 .audit/。用户指定的项目代码是任务目标，不是工作流产物：在契约和证据里记录它的路径，但不要把它复制进 .work-docs（除非你要求）。

8. state.md 字段速查

state.md 用「每行一个 key: value」的简单格式，方便脚本校验。固定字段：

字段含义
task_id等于任务目录名
levelL1 / L2 / L3（long 模式按 L3/long 计阈值）
stage当前阶段（investigate / research / design / plan / exec / bugfix / review / ops / mixed）
statuspending / active / done / blocked / stopped
done_when什么算做完（可逐条）
evidence一行一条：evidence:名称|command=...|run_at=...|result=...|last_edit_at=...
unknowns还没搞清的事
blocked_by被什么挡住（status 为 blocked 时必需）
unblock_condition满足什么才能解除阻塞（blocked 时必需）
next_action下一步第一动作（blocked 时必需）
calls_since_progress距上次有效进展的工具调用次数，有进展就归零
last_progress_at上次有效进展的时间
budgetused/limit
strategy_fingerprints已用过的策略指纹（修改文件 + 执行命令 + 错误首行）
updated_at最后更新时间

必需验证项单独一行：required_verification: 名称 status=passed evidence=路径，状态只能是 passed | failed | not_run | blocked。

有效进展只有两种：某个 done_when 条目拿到新 evidence，或某个 required 验证从 failed|not_run 变为 passed。每次有效进展都更新 calls_since_progress（归零）、last_progress_at、budget 和 strategy_fingerprints。

10. 常见疑问

为什么辅助技能没有被自动唤起？

因为全部设了 disable-model-invocation: true。这是刻意设计：避免模型因为「看到 .ts 文件」或「看到报错」就自行塞进一段技能指令，让任务范围失控。要用就两条路——入口按阶段读，或你点名。

装完看不到它们，是不是没装成功？

用 check-workflow.sh 对照源仓库和安装目标，它会逐项检查目录、安装标记和文件。这比「在列表里看到」可靠。

任务卡住了怎么办？

看 state.md 的 status。是 blocked 就看 blocked_by 和 unblock_condition，那两条就是你需要提供的输入；是 stopped 通常意味着等你拍板（不可逆动作、花钱、对外发布、改需求范围）。恢复必须换一条实质不同的策略，同一策略重试会被熔断规则挡住。

证据过期是什么意思？

证据的 run_at 早于相关文件的 last_edit_at。等于「跑完之后又改了代码」，那条证据不再代表当前状态，必须重跑。

为什么 grep 通过不算验证过？

grep 属于 static 层，只能证明文本里出现了某个字符串。如果契约要求 runtime/local 或 consumer 层，就必须真的运行并观察行为。

一个任务里能顺手改点别的吗？

不能。plan 阶段明确「不得扩大范围」。确实需要改范围，就得回到需求评估、重新定义契约，而不是在执行中悄悄扩大。

第三方技能把文件写到 .work-docs 外面了？

立即熔断（blocked_by: external_skill_write_outside_work_docs），保留现场，不要移动、删除或覆盖那个文件，等确认后再处置。

长任务预算用完了但活还没干完？

写最终 checkpoint、更新 state.md、保持 active 或 blocked，不许标 done。第二天恢复时按新预算继续，且必须换策略。

# Review Delegation

把「审查」这件事委派给子 agent 时的操作规则，以及支撑这些规则的实测数据。
本文是 `x-requesting-code-review` 流程在本环境（Pi + pi-subagents）下的适配补充；流程本身不变，变的是执行形态。

## 结论：委派判断，不委派调查

取证（跑命令、grep、比对）是确定性的，交给脚本；判断（归类、定级、拒绝）是不可复现的，交给独立的脑子。
给子 agent shell 和开放问题（「复核是否还有旧名残留」），它**不会自己停下来**——多查一次的成本不记在它头上。

| 形态 | 耗时 | 工具调用 | 产出 |
|---|---|---|---|
| 通用 agent + shell + 开放问题 + 无预算 | **1800s 超时** | **50（全为取证）** | **0 字节** |
| 无 shell 判断者 + 确定性证据包 + 有界问题 | **79–108s** | **1–4** | 可用报告 |

实测时间：2026-10-09/10，同一审查任务、同一模型（deepseek-v4.1-flash），详见
`.work-docs/tasks/20261009-05-ab-review-method/` 与 `20261009-07-evidence-pack-v2/`。

## 四堵墙（按撞到的顺序）

1. **时间墙** —— 有 shell 的通用 agent 会一直取证到超时。工具预算只是保险丝，不是解法；解法是把取证移出它的职责。
2. **验收墙** —— 委派层默认假设子 agent 是**执行者**（应留下「跑了哪些命令」的证据或结构化验收报告）。
   只读判断者必然触发 `Acceptance rejected`（`commands-run evidence missing` 或 `Structured acceptance report not found`），
   报告可能被掐断。判据是**产物是否落盘且非空**，不是 run 状态；不要依赖状态字段判断审查是否成功。
3. **输出预算墙** —— thinking 与正文**共享**同一个输出预算。问题数一多、思考档一高，预算在思考阶段烧光，
   正文输出 0 字符（实测：thinking 103,704 字符、正文段数 0、报错 `stopReason "length"`）。
   对策：给报告设字数上限、每问限行数、依据只写位置编号不复述原文；必要时降思考档。
4. **证据覆盖墙** —— 证据包不声明采集范围时，判断者会越界猜。
   在证据包末尾加一节**事实陈述**（采了什么 / 没采什么，不给结论），它才能把「证据不足，无法判定」当作正当输出。

## 配方

```text
1. 确定性脚本生成证据包（只读、可复现、分节编号）
2. 委派无 shell 的只读审查者；证据包路径 + 内联关键摘要
3. 任务写成有界判定：「判定这 N 行是必需还是漏改」，不是「查有没有残留」
4. 要求每条结论引用证据编号（如 E4 numstat 段）
5. 工具预算 soft 6 / hard 10（仅保险丝；实测 1–4 次即够）
6. 报告字数上限（≤1800 字）+ 每问 3 行
7. runner 侧绑定产物落盘
8. 明确「证据不足」是有效输出，不是失败
```

## 证据包该有什么

v2 实测 20 节 / 47KB / 523 行，覆盖一次完整合并前审查所需：

| 节 | 内容 |
|---|---|
| E0–E1 | 元信息、改动规模、提交列表 |
| E2–E3 | 目录改名对照、旧前缀命中**全文**（含行号） |
| E4–E5 | 脚本改动（numstat + 断言行数对照）、门禁与测试**实测退出码** |
| E6–E8 | 元数据一致性、跨技能引用可达性、安装 marker |
| E9–E12 | 文档命中、软链状态、合并前置、**采集范围声明** |
| E13–E19 | 采证时的 HEAD/工作区状态、反向一致性（新名是否铺满）、marker 全局、已安装清单（逐条链接→目标）、脚本**完整 diff**、仓库外引用、远端位置 |
| E20 | 更新后的采集范围声明 |

必须避免的两个坑：
- 证据行**不要 grep 过滤后再展示**：只显示含关键字的改动行会让判断者看到「删除行远多于新增行」的假象。
  要么给完整 diff，要么在节标题里写明过滤条件。
- `find` / `grep` 面对**符号链接**安装目录：`grep -R dir`（无尾随斜杠）不进入软链目录，扫到 0 文件后
  exit=1 会被当成「clean」**静默通过**。遍历软链目标时用 `dir/` 或 `find -L`。

## 实测：判断者查出了什么

同一任务下，只读判断者独立查出了实现者与首轮 parent 审查都漏掉的项：

- `docs/session-scenarios.md:3` 是**可操作指针**（「决定优化时再取材改 X」）而非历史档案 → 真漏改；
  教训：豁免要有粒度，「这类文件整体不改」是文件级判断，漏改恰恰藏在活文档的一行指针里
- 门禁负向断言未纳入刚退役的名字 → 护栏缺口
- 已安装链接数与仓库目录数的差额来源（逐条清单比对才能发现）
- 加固后的护栏仍是点状枚举（`<old>-work/SKILL`），同类其它名字仍可穿过 → 通配更稳
- 「这个修复方向正确但不足以确认」——因为它缺「修前失败 / 修后通过」的对照输出

## 局限（不要把这些当成普适结论）

- n=1/2，同一模型，非跨模型交叉验证；A 组为回顾性对照
- 证据包由发起方生成 → 发起方是单点过滤器。纠错机制只有一个：判断者自报缺口（每轮 5–12 条），
  所以「缺口清单」是这类报告里最有价值的部分，不要裁掉
- 缺口逐轮收敛但**不归零**（10 → 5）：证据包不可能完备，这正是不该要求「零缺口才敢合并」的原因
- 少数派做法（判断者自己去跑命令）在需要**探索**（判据未知）时仍是对的——那是探索，不是审查

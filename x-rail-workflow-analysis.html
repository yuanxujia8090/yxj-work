01一页速览

x-rail 不是应用代码，是一套「工作流技能」。它用 XML 规则加 Python 标准库脚本，约束一次会话怎么推进、什么时候必须落盘、什么算做完了。

一句话理解：入口判断三件事——要交付什么、失败代价高不高、有没有敏感动作。前一件决定用哪套步骤，后两件决定「普通记录」还是「严格记录」。严格记录时，脚本接管，逐条校验，直到完成门放行。

两条记录强度

普通
默认 · 不落盘

简短列目标与完成条件，先读、最小改动、实际验证，直接交付。不建任务目录。

严格
契约驱动 · 全程留档

写 contract.md，start 封存快照，实施必须携带证据，最后过完成门。

本图的重点不是「有几步」，而是「哪一步会拦你」。流程里真正不可绕过的门只有三类：契约门（写对了才能开始）、证据门（记录必须新鲜且绑定输入）、完成门（六项全过才能算 done）。其余多为提醒与自觉。

02全景分流图

一次请求进来后，先按「交付结果」选阶段，再按「风险与恢复需求」选记录强度。两条岔路之后就再没有回头合并——普通路径永不落盘，严格路径永不跳过完成门。

03路由与记录强度

阶段决定「怎么做」，记录强度决定「记多细」。两者独立判断：调查一个高风险系统，阶段是 investigate，但记录仍是严格。

阶段：先看交付结果

交付结果阶段典型形态
一个直接答案fast-answer解释、定位、口径统一，最短路径
对现状的判断investigate根因、影响面、复现路径
外部或新知识research文档、竞品、资料，需区分事实与推断
方案与取舍design选项、边界、被否决方案
可执行步骤plan切分、依赖、验证点、停止条件
变更exec / bugfix实施；bugfix 另走最小复现
结论与缺口review发现、风险、未验证项
状态变更或诊断ops高风险动作优先，验证优先于执行
多种结果并存mixed主阶段 + 若干子阶段前缀

failure_cost_high		必须严格记录；且 risk 会落到 medium / high

反直觉的一条：任务名里带「正式」「v2」不触发严格。判定只看代价与恢复 名字唬人没关系，代价高才升级。这条专门防止模型「看名字加重流程」。

04严格任务运行时序

严格路径是整个流程的重心。四条泳道分别是人、模型会话、脚本、磁盘文件。实线是调用，虚线是返回；标 ◆ 的位置是脚本会直接拒绝的卡点。

五个验证层

验收条目按 谁执行 分成五层，脚本只管其中两层——这是理解整个流程的关键边界。

层谁执行脚本管吗怎么记录
automatic脚本自己跑命令管run --acceptance --command
manual人不管record + 报告文件
review独立审查者不管record --review
consumer下游消费者不管record
external外部系统不管record

脚本不证明语义。它能确认「你记录了、证据新鲜、输入没变」，不能确认「你的结论正确」。这条边界写在 SKILL.md 里，是整个设计能长期存活的前提。

05工作项状态机

复杂实施会拆成工作项。每个工作项是一个独立小状态机，只有 verified 与 skipped 允许任务收尾。转移全部走白名单，非法跳转直接拒绝。

整体状态 vs 工作项状态

两层状态不要混。整体状态管任务生死，工作项状态管颗粒进度。

层取值含义
整体 statusdraft · active · blocked · done · stopped只有 done 能进完成门
整体 stage11 个（intake → … → closed 等）表示当前处于生命周期哪一段
工作项pending · in_progress · awaiting_verification · needs_fix · blocked · verified · skipped每个工作项独立流转

06完成门六检

任务想从 active 变成 done，必须依次穿过六道检查。任何一道失败，状态原地保留，候选文件留在 tmp 目录——流程不会为了「跑通」放宽必需验收。

最容易踩的坑是 G2。校验用的是文件修改时间：只要输入文件在取证之后被任何工具碰过（格式化、git 检出、编辑器保存），证据立刻变 stale，必须重跑。这是刻意的保守设计，代价是大文件或多工具链场景会频繁触发。

07关键卡点总表

十六个硬卡点。每一行都是脚本会拒绝或阻断的位置——也就是流程真正的「关节」。拒 表示直接失败，警 表示记录但放行。

#卡点触发条件结果
G1契约格式门字段不是 key: value；缺必需字段或必需段落拒 无法进入生命周期
G2敏感动作确认门命中四类敏感动作，但确认未 required + confirmed拒 仅草稿可读
G3风险—审查匹配门risk=medium 用 auto；或 risk=high 未 full-review拒
G4可选验收理由门required=no 却没有跳过理由拒
G5契约版本链门locked 状态下改契约，缺新 revision / 快照 / 变更记录拒
G6重建拒绝门任务目录已有 state.md 仍执行 start拒 要求续接而非重建
G7实施清单门exec / bugfix 严格任务，缺 work_items_schema拒
G8依赖环门工作项自依赖、成环，或需求未被覆盖拒

常见的非卡点

这几件事容易被误当成硬门，实际只是建议或提醒，理解这一点能避免过度紧张。

事项实际强度说明
预算上限（60 / 150 / 400）警离线提示，不阻断；只有记为 tracked 才参与校验
无进展提醒（20 / 60 次）警提醒收口，不是硬门
文档收口（6 / 20 次动作）警判断「够不够写」的启发式，可被覆盖
任务名含「正式」「v2」不触发明确写不因名字升级严格度

08熔断与预算

防止「无限打转」的机制。分为软提醒与硬熔断两档——硬熔断会把 in_progress 状态直接判为不合法。

机制阈值行为
无进展提醒L1/L2 20 次 · L3/long 60 次警 提醒收口
无进展硬门L3/long 持续 30 分钟拒 in_progress 校验失败，必须转暂停
deadlineL3/long 8 小时拒 超时未暂停即失败
验证连败连续 3 次必过验证失败拒 停止修改，记录策略指纹
重复命令错误同一命令错误 2 次拒 停止继续试同一路径
预算L1 60 · L2 150 · L3/long 400警 离线提示
 
退出码语义
  0  → pass          通过
  1  → material/acceptance fail   有实质或验收失败
  2  → usage/runtime error        用法或运行时错误

注意 3 连败 与 2 次同错 是「停止并记录」，不是「回滚」。流程要求把失败策略写成指纹留档，避免换汤不换药地重试同一路径。

09分析与建议

这个流程的完成度很高，代价是概念密度大。下面按「设计意图 → 复杂度来源 → 观察到的风险 → 建议」四段说。

设计意图：三条撑住全局的哲学

  1. 脚本只管机械，语义归人。脚本能校验格式、时间、指纹，不能判断结论对错。这条边界让规则不随业务漂移。
  2. Fail-closed。漏字段就拒绝，不自动降级；历史格式必须显式 --legacy-readonly 才读。宁可拦住，不放过去。
  3. 记录强度按需。普通任务零落盘——流程自己就把「太重」这件事收敛掉了，这是它能日常使用的前提。

复杂度来源：为什么会「相当庞大」

维度数量为什么难记
整体状态 × 阶段5 × 11两层状态名近似，容易混用
工作项状态7含退回边，不能只记主线
验证层5只有 automatic 走脚本，其余走人
审查策略3与风险等级强耦合（G3）
敏感动作类别4决定是否必须用户确认（G2）
硬卡点16分散在 5 个子命令里
规则载体5 处SKILL.md、10 个 playbook、README、architecture、usage-guide

单看每一项都不复杂，但它们是相乘关系。本次纯为「讲清一次运行」就画了四张图和两张长表——这本身就是复杂度的度量。

观察到的风险

  1. 规则多处表述，存在漂移窗口。同一条约束同时写在 XML、playbook 与文档里。近期任务已经在处理「模板文档与实现一致」，说明漂移是真实发生过的。
  2. 大量规则靠模型自觉，脚本管不到。「不重复调查」「达到 N 次就收口」这类只有文字约束。规则越多，长上下文里越容易漏——这也是 0.0.6 提出分段执行的原因。
  3. 证据新鲜度门偏严格。用文件修改时间判定，任何触碰输入的工具都会让证据失效。保守是安全的，但在多工具链或大批文件下会频繁重跑。
  4. 完成门有递归成本。done 要递归检查依赖任务状态，依赖链长时会变慢（脚本已用祖先集合防环）。
  5. 三方引用矩阵易配错。需求 ↔ 工作项 ↔ 验收三方互指，还有「未被引用的可选验收」这类边角——细节多，靠校验器兜底。
  6. 项目自身回归负担不轻。伴随多个测试脚本与 31 个真实任务记录，规则每改一次都要跑一遍行为夹具。

建议

短期（低成本，收益直接）

  • 列一份「单一事实源」清单。为每条约束指定唯一出处，其余位置只链接不复述。可先把 architecture.md 已有的边界说明延伸成表格。
  • 给普通路径补示例。明确写两三个「判定为普通」的例子，避免模型在模糊场景下过度升级为严格。
  • 把高频卡点前置到提醒。如 G11 证据新鲜，可在 capture 时就警告「输入 mtime 晚于上次取证」，把失败从完成门提前到取证时。

中期（配合 0.0.6 方向）

  • 上下文控制。执行时只加载当前工作项所需材料，配合精简摘要输出。这是对「规则太多记不住」最直接的对策。
  • 用数据裁剪规则。用 self-check 的统计看哪些字段或命令长期从未被真实使用，作为精简候选——但保留「三周未用不等于无用」的判断。
  • 保持测试为行为夹具。规则文字与实现同步改时，一律跑 test-flow 与生命周期测试，这是防漂移最有效的一招，已有基础，继续即可。

不建议做的

  • 不要给脚本增加语义猜测。它的价值恰恰在于「不懂业务」。
  • 不要为了显得轻量而砍掉 fail-closed。放宽必需验收这条路，一旦打开就收不回来。

总体判断：结构是健康的——三层分离清晰，边界（脚本 vs 语义）明确，且自带「按需加重」的收敛机制。真正的问题不是设计，而是概念总量与表述分散。方向应是「收敛表述、控制上下文」，而不是重写流程。

10附录：命令速查

严格任务的完整命令序列。左侧是命令，右侧是它会把守的卡点。

# 1. 写契约并校验（可在生命周期前反复跑）
python3 scripts/check-contract.sh <task-dir>          # 门1/2/3/4/5

# 2. 开启生命周期
python3 scripts/task.py start <task-dir>               # 门6/门7

# 3. 实施循环
python3 scripts/task.py update --item <id> --status <s>  # 门13
python3 scripts/task.py run --acceptance <id> --command "..."   # 门9/门10
python3 scripts/task.py capture --acceptance <id> --input <p>  # 锁输入
python3 scripts/task.py record  --acceptance <id> ...          # 门12
python3 scripts/task.py record  --review ...                   # 门3

# 4. 收尾
python3 scripts/task.py finish   <task-dir>            # 门15（完成门六检）
python3 scripts/task.py complete <task-dir>            # 门16（原子替换）
python3 scripts/task.py summary  <task-dir>

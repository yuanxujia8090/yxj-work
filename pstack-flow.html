pstack / poteto-mode — skill 流程解剖

♛ pstack 流程与决策全景图

pstack（作者 poteto，Cursor）把编程 agent 变成一个真正的工程团队。入口只有一个： /poteto-mode。它读取任务 → 匹配一个 playbook → 把 playbook 步骤逐字复制进 todo 列表 → 在步骤触发时路由到其它 skill → 每个 subagent 都经过 role 化模型分配 → 验证通过后才允许 PR 与落地。 本图完整呈现主链路与 9 个关键决策点。

01

主链路：一次任务从进入到落地

所有任务共用一条主干。playbook 决定分支细节，但每个 playbook 都遵循同样的骨架： 先开 todo（步骤逐字复制）→ 执行步骤（按需触发 skills）→ 委托/验证 → Opening a PR。 "回复工程"贯穿始终：每条结论自带证据标签（measured / inferred / guess）。

1

入口：用户给出目标 + 验收信号

用自然语言描述意图和"怎么算完成"（如"repro first, then fix and verify"）。不需要指定 playbook、不需要列 skills。

/poteto-mode <goal> [+ checkable outcome]　·　mode 常驻则每轮自动裁决是否介入
2

分类路由：匹配 playbook 决策点 D1

读取请求 → 从 23 个 playbook 中匹配一个（无匹配则 figure-it-out 设计定制流程；项目级则 orchestrate）。 同时做前置裁决：架构问题先 how；跨函数边界 → architect；并行扇出 → swarm。

SKILL.md → Playbooks 段（逐条匹配规则）
3

开 todo 列表：playbook 步骤逐字复制

playbook 的每个 step 原样拷贝为 todo 的第一批条目（跳过项保留并标注 skip: <reason>），之后才加任务专属 todo。todo 即执行合同。

这是硬性要求：steps copied in verbatim, before any task-specific todos
4

逐步执行：步骤触发 skill 路由

每个 step 声明它需要哪些 skill，agent 按需加载：理解 → how / why；设计 → architect / arena / prototype； 并发 → swarm；争议 → interrogate；写作 → unslop / technical-writing / no-comments；数字 → benchmark-checklist。

回复中必须点名"哪个原则影响了哪个决定"，且只引用本会话真正读过的原则
5

委托：subagent 扇出 决策点 D2 + D3

用 throughput checkpoint 四问决定扇出结构；默认 fresh subagent + consolidated scope；每个角色分配显式模型； bulk 数据交给 subagent，主线程只留摘要（guard-the-context-window）。

playbook 内子代理：subagent_type: "poteto-agent"，run_in_background: true
6

验证：真实表面 + 三方证据 决策点 D6

铁律："仅有测试不算验证。PR 的 unit / live / perf 三栏全勾才算 verified。" live lane 强制（真应用 + control skill + 截图）；大型交付用 swarm 扇出 10+ lanes 独立裁决。

"Inconclusive" 或 "wrong surface" 不算通过——必须标记出来
7

收尾：Opening a PR（每个 playbook 的终点）

worktree 隔离 → /deslop → /no-comments → Conventional Commits 标题 + briefing 式 PR body → 开 ready 不开 draft。开 PR 不自动进入 babysit。

优先 5 个窄 PR 而不是 1 个大 PR；stack 子分支 rebase 到父分支 tip
8

交付循环：Babysit → Shipping（用户显式触发）

Babysit 把 PR/stack 驱到 merge-ready（冲突、review 线程、CI）；Shipping 独立逐 PR 验证后， 只落地"从底部开始的连续已验证段"。两者都不许 babysit 越权 merge。

Green ≠ safe。Nothing gets armed before an independent per-PR verdict
贯穿全局的三条纪律：① tier 由证据决定——每行代码都能回溯到运行时证据；② 回复面即 prose 面——所有输出过 unslop 规则（短句、无长破折号、不用冒号连接）； ③ 你拥有每个 subagent 的产出——亲自审 diff、亲自写总结，不转述下属报告。
D1

决策点：如何选择 playbook

匹配规则来自 SKILL.md → Playbooks 段。核心原则：先看任务动词（诊断/构建/交付/自主），再看规模与风险，最后看有没有现成 playbook。 语言信号（"repro first"、"going to bed"、"check on PR X"）也是路由信号。

Decision Tree

任务 → playbook 匹配树

  • 任务是只读问题？（怎么工作、为什么这么建、是否确定） Investigation read-only，输出引用式答案，无 PR
  • 有报告缺陷要复现、根因、修复？ Bug fix 有廉价本地测试路径时叠加 tdd：先写失败测试
  • 测量到明确变慢？
    • 一次性修复 Perf issue 7 条性能咒语按序尝试，最早达成目标即止
    • 对单一指标持续逼近目标（循环假设 + 前后测量 + 每次只留一个 commit） Hillclimb
  • 诊断运行中症状（泄漏、空转 CPU、渲染毛刺）？ Runtime forensics 活体插桩，交付诊断不交付修复
  • 手里已有 profiling 工件（cpuprofile / trace / spindump / heap snapshot）？ Trace forensics 固定数据集，读它，不重跑
  • 新增或改变行为？ Feature 先命名数据形状；多合法形状 → arena
  • 保行为改结构（重命名/抽取/内联/去重/迁移）？ Refactoring 先钉住行为契约再动结构；大范围 → figure-it-out
  • 要用最低成本做一个设计/行为决策？（"试试这个布局"） Prototype 唯一一条"质量不重要"的 playbook；决策做完交给 Feature
  • 两个实现的像素级 UI 等价？ Visual parity image diff 归零才算过，base 不动
  • 写/改 SKILL.md？ Authoring a skill
  • 评估 skill/prompt 改动对 agent 行为的影响？ Eval 盲法：目录名、prompt、judge 全部去标识
  • PR/stack 状态请求？（"check on PR X"、"get it green"） Babysit 4 种模式，见 D8；绝不路由到 Cursor 内置 babysit
  • 要落地一个已绿的 stack？（"ship it"、"land it"） Shipping 独立验证 + 连续已验证段 bottom-up
  • 长任务、跑到谓词满足才停？（"/loop until X"、"run until done"） Autonomous run
  • 独立 PR 队列、全授权直通 merge？ Autopilot-full 每 PR 一 owner；root 每轮 swarm 裁决
  • 队列要构建成 stack 交操作员 review 后自己落地？ Autopilot-stack owner 不 merge，root 只 append
  • 项目级常驻程序？（多日、多 stack、agent 舰队、人每天看两次） Orchestrate coordinator 不写代码；见第 08 节
  • 恢复/接管前一个 agent 的进行中工作？ Session pickup 先读 trail，不重做已完成工作
  • 要干净地暂停？ Pause safely 只有显式要求才暂停；wip commit + resume note
  • 跨 phase / 多 stacked PR 的规划？ Multi-phase plan 计划即交付物，不实现；1-2 文件且方案显然 → 跳过
  • 回收磁盘（worktree / 模拟器）？ Worktree cleanup 唯一无代码审查兜底的破坏性 playbook
  • 没有匹配的 playbook？或大规模迁移 / 跨切面修改 / 人离开后要审计？ figure-it-out 定制一个严格、可审计的 playbook
  • 任何 playbook 走到最后 Opening a PR 所有 playbook 的公共终点
Escalation

升级/降级规则：什么时候偏离最直观的匹配

规模升级
跨大量调用点的迁移、宏大的多部分修改、人离开要事后信任的工作 → figure-it-out，即使 Feature 等窄 playbook 名义匹配。
项目升级
多日、多个 stacked PR、一支 subagent 舰队的常驻项目 → Orchestrate。figure-it-out 设计"一次定制 run"，orchestrate 跑"一个项目程序"。
降级判定
一个 agent 在会话预算内能完成的 → 不进 Orchestrate，无论措辞多像"项目"；进 Autonomous run 或直接做。先算：单元数 × 预算。
跳过规划
改动只碰 1-2 个文件且方案显然 → Multi-phase plan 直接说"不需要"并停止。
一次 vs 长期
性能：一次性 → Perf issue；持续科学逼近指标 → Hillclimb。诊断：活体 → Runtime forensics；事后工件 → Trace forensics。
测试叠加
Bug fix 且有廉价测试路径 → 叠加 tdd（失败测试先于修复进入 git 历史）。
回答边界
路由还决定"是否要写代码"：Investigation / forensics 是只读的，交付引用式答案；不要顺手改代码，除非用户要求或后续转 Route。
语言即路由信号。"repro first" → Bug fix；"I'm going to bed / land it by morning" → 自主授权 + Autopilot/Shipping； "check on PR 123" → Babysit(check)；"compare them" → Prototype/Arena；"trust it was done right when I'm back" → figure-it-out + show-me-your-work。 写 prompt 时把"怎么算完成"说清楚，比列 skill 清单更有用。
D2

决策点：是否使用 subagent / 如何扇出

子代理是默认，不是例外——但"用几个、什么形态、fresh 还是 resume"都有判定规则。 来源：SKILL.md → Subagents、Feature 的 throughput checkpoint、swarm/orchestrate 的形态规则。

Checkpoint

扇出前必答四问（Feature step 3 的 throughput checkpoint）

每个 playbook 在动手前必须写出这四项（不适用的也保留条目并标注 n/a: <原因>，不许跳过）：

Q1 Blocking first steps
有必须先跑的门禁（架构决策、共享脚手架、基线捕获）吗？→ 门禁全部先行，再谈扇出。
Q2 Independent workstreams
存在不相交的文件/服务/层的独立工作流吗？→ 独立流并行；共享写串行。
Q3 Shared mutable state
并发角色会写同一个文件/分支/键/对象吗？→ 默认拆分目标（separate-before-serializing-shared-state）；只有真实的单写者不变量才串行。
Q4 Smallest safe decomposition
最小安全分解是什么？→ 如果一个 worker 最好，必须写明理由。

形态选择单 owner vs 父级扇出

  • 代码耦合工作（一个 feature、一次迁移）→ 单个 owner，checkpoint 内联给 owner，owner 在内部自行扇出。
  • 父级扇出只用于产出独立工件的切片：审计、跨子系统调查、竞品实验。
  • phase 边界要重写 checkpoint；继续下一步用 fresh owner，不链式中断（interrupt-chained resume 会静默丢指令）。

默认参数每个 Task 调用的基线

  • run_in_background: true；agent 模式（readonly 会剥掉 MCP）。
  • 文件指针，不内联上下文（file pointers not inlined context）。
  • 每个角色带显式 model（见 D3）。
  • playbook 步骤内的子代理一律 subagent_type: "poteto-agent"；routed skills（how/why/interrogate/reflect/swarm）自设 subagent_type，不许覆盖。

Fresh vs Resume默认 fresh

  • 默认 fresh：原 brief + 所有后续指令 + 前 agent 报告与分支 = consolidated scope。适用于修复轮、follow-up、retry、下一个队列项。
  • 只有新工作严格依赖现有状态才 resume：本地 checkout、未提交改动、仍在跑的进程（dev server / 模拟器 / watcher）。
  • 给运行中 agent 的 stop/hold 指令不算复用。
  • 禁止 resume-chain；空间换正确：fresh + 完整 scope。

上下文守恒guard-the-context-window

  • bulk 数据（大日志、长文件、批量扫描、transcript）→ 全部交给 subagent。
  • 主线程只保留摘要 + 文件指针，绝不落原始 payload。
  • 探活不 resume：读 ledger、units.tsv、gh、已推分支、云面板状态；transcript mtime 不算活。
Fan-out Patterns

三种扇出形态对照：pair / swarm / orchestrate

形态何时用结构收敛方式
单 owner + 内部扇出 代码耦合：一个 feature / 一次迁移 / 一个 bug 修复，产出物互相依赖 Lead 持有任务，阶段间自行 delegate（bug-fix 模型），自审 diff Lead 亲自验证 + 写总结
Swarm（多 worker 并行） 覆盖矩阵（每个 slice 一个 worker）、race（同一 brief 多模型）、两者混合 N 个 cloud worker 一条消息扇出；每个 brief 自包含；写者各自独立输出 聚合为一张报告：结果表 + 一行式问题 + 缺口；race 用事先声明的 first-pass / rank-all / best-of
Orchestrate（程序级） 一个项目超出单会话预算：多日、多 stack、几十个 subagent、人每天看两次 Coordinator（本地、不写码）→ track 级 sub-coordinator（>1 drain 阈值才设）→ worker/verifier（cloud，深度 ≤3） 每次 drain 分类所有指针；ledger 按 PR+SHA 记账；frontier 计算式推进
验证独立性规则：verifier 永远用与 worker 不同模型族（同 prompt 换模型 = 高信号第二意见）。 swarm race 的每个 arm 事先命名模型；测量类 brief 必须携带精确 SHA 与方法（样本数、样本定义、顺序）。
Ownership

委派后的所有权：你仍然拥有一切

审 diff，写总结
每个 subagent 的产出由你复核；亲自写总结，不转述 agent 的自我报告。
第二意见
同一 prompt 换模型跑第二意见；一致 = 高信号。
brief 是产品
（orchestrate 层级）brief 字段：GOAL / SCOPE / CONTEXT / ACCEPTANCE / VERIFY / TIMEBOX / FORBIDDEN / REPORT / STANDING orders 逐字粘贴。 填不满的字段 = 还没 scoping 的单元，拒发。
不许沉默加倍
丢失的 child 必须记账（arrived / respawned / scope 被显式吸收）；默默重做会掩盖双重浪费和覆盖缺口。
D3

决策点：subagent 用什么模型

模型按角色分配，不按心情。默认配置由 /setup-pstack 写入 ~/.cursor/rules/pstack-models.mdc； 缺省时回退到硬编码默认。role 行可写 inherit-parent / auto（省略 Task model，跑父模型）。

Role → Model 分配表 默认面板：opus 5.5 / grok
角色默认模型判定规则
代码委托（feature / refactoring / bug-fix / perf / hillclimb） grok-4.7-xhigh-fast 按难度分层。读各自 playbook 对应的 role 行。
最难改动（hardest tasks） claude-opus-5-5-xhigh 跨切面设计、棘手的并发、微妙算法。两种都收：需要判断模糊意图的，或需要逐字执行精确步骤序列的。
散文与判断（judgment and prose） claude-opus-5-5-xhigh 写作、评审、裁决类角色。
Swarm workers grok-4.7-xhigh-fast 读 swarm workers 行；模型 race 时每个 arm 事先命名。
Verifier / judge ≠ worker 模型族 验证独立性：同 prompt 不同模型 = 高信号第二意见。
机械琐碎编辑 fast code model trivial mechanical edits → 最快的代码模型。

回退链slug 被拒时

  • Task 工具拒绝 slug → 用默认并说明。
  • 默认也被拒 → 从其报错信息里取同族最近的有效 slug。
  • role 行缺失 → 保持默认；auto / inherit-parent → 省略 model。

覆盖优先级谁盖谁

  • setup-pstack 的 per-role 行 覆盖 SKILL.md 默认与 routed skills（how/why/arena/swarm/architect/interrogate/reflect）的模型选择。
  • 默认值变更后，旧规则仍钉住旧默认——删掉对应 role 行或删文件重跑 setup。
D4

决策点：问人，还是自己决定

核心分类器：如果答案是一个"跑一下就能观察到的事实"，那它就不属于人类回答。 行为、时序、布局、输出、性能、甚至"eval 能否分离两种方案"——全部用 Prototype 让实验结果来定。

例外

Just do it直接做，不问

  • 可逆工作。
  • 外部动作：team chat、ticket 更新、跑评测。

AskQuestion 反面清单绝不阻塞在人身上

  • "should I keep going?" → 继续。
  • 可逆的收尾工作 → 不进"留给人"的清单。
  • 自主 run 中发现的中途问题（坏 skill、相关 bug、flakey 验证器、review 噪音）→ 自己修，单独开 PR。

D5

决策点：暂停红线与会话授权

自治程度由两条清单界定：一条"永远暂停"，一条"会话级覆盖"。

Always pause不可逆写入 —— 永远停下确认

  • force-push 到共享分支
  • 部署
  • 删除数据
  • 给客户的对外消息

此外（orchestrate 级）：关闭别人的 PR、影响共享分支的破坏性动作，全部进 gates.md 排队问人。

Session override会话级自治授权

  • "Don't stop" / "going to bed" / "run until done" / "be fully autonomous" → 持续执行,不再询问。
  • "I want everything merged by morning" → 覆盖 CI flake 容忍度，直通 Autopilot/Shipping。
  • 授权 + root 的干净 verdict = merge 的完整授权；单靠 babysitting 永远没有 merge 授权。
Pause safely 是反向决策：只有显式要求（或即将压缩上下文）才做 checkpoint：停在安全边界 → 不发起新动作、取消嵌套子代理 → wip commit → 写离场 resume note（意图/进度/已验证项/下一步/关键文件/坑）。"keep going" 语境下不暂停。
D6

决策点：验证有多严 & swarm 如何裁决

验证是 pstack 的承重墙。铁律一：测试单独不够——unit / live / perf 三栏全勾才算 verified。 铁律二：CI 绿不是 verdict，agent 自我报告不是证据，只有独立验证者检查真实工件才算。

Iron Rule

三栏验证模型（每个 PR 的验证块都以此开头）

Unit

指定测试文件 + 新增用例 + 运行命令。

Live（强制）

10 条 lane 在 PR head 驱动真实表面（control-ui / control-cli），每条 lane = 一个场景 + 一张截图 + 一个通过谓词。
其中一条必是 Regression lane vs trunk。

Perf

双侧对比：trunk 与 head 都必须产出指标；先测 trunk 基线；给出会失败的数值规则。场景不同不比 ratio，用绝对预算。

trunk 缺功能怎么办：记录该事实，将门禁改为"diff 新增的行为 + 用户等待的最终状态"，不许发明一个 trunk 结果。 交互类的 PR 是 review-gated：操作员在 chat 里看截图 + 30-60s 视频后才能 merge。
Swarm Gate

合并前的 swarm 裁决结构（每轮 code-ready head SHA）

每次到达 code-ready head SHA、以及之后每一次改变 patch 的 push，都 fan out 一轮独立验证并聚合为一个 verdict：

GATES在该 SHA 重跑仓库门禁（lint / typecheck / tests）PASS 必需
LIVE ×10真实表面驱动，含 Regression lane vs trunk（live lane 是地板：没有它的 verdict 不干净）截图 + 谓词
PERFtrunk 基线 vs head 的指标对比数值规则
AUDIT ×2+读 diff 与 receipts、不信任 PR body 的审查 lane（各自一个焦点：消费者一致性 / 生命周期与竞态 / 数据与配置安全）恶意假定
Clean 条件
每一条 lane 都是 PASS。lane 以 note 形式记录下的缺陷也算 finding，照样打回 owner。
finding 回传
所有实锤 finding 一次性 fix-forward 给 owner；行为类 finding 要求覆盖所有同缺陷位点的红测试，测不出来的要 repro receipt。
新 head
新 head 拿全新 swarm + 全新 verdict；patch-id 规则（shipping 里）决定旧 lane 结果是否仍有效。
Patch-ID Rule

rebase 之后，verdict 何时失效？

verdict 记录三元组：verdict head SHA + base SHA + base→head diff 的稳定 git patch-id。rebase/retarget 重写 SHA，可能静默作废一个 verdict（哪怕没碰任何检查）。落地前必须比对 patch-id：

仅噪声差异
当两个 patch 只在 tests / docs / lint 配置上不同 → build 各 lane 所跑的产物两次（verdict SHA）＋一次（当前 head）。差异若在 verdict SHA 的两次 build 中也出现，或只是内嵌 commit SHA → 判为噪声，该 lane 结果保持有效；checks 和一次变更 review 重新跑。
禁止复用
dev server 的 lane 结果（无 build 产物）一律重跑；不许用相同 commit message 或旧 SHA 的绿勾当替代。
patch 变了
重验；patch 没变 → 保留代码 verdict，在当前 head 重跑 mergeability 与 CI。

数字纪律benchmark-checklist 触发条件

只要你亲自跑了 benchmark、测了性能、要报告提速或回归 → 报告或据此行动前先过 benchmark-checklist：查限速因子、调参、错误数、重复运行、端到端相关性。

Forensics 边界诊断 ≠ 修复

Runtime / Trace forensics 的交付物是带引用的诊断，不是修复。确认病因后再 route 回 Bug fix 或 Perf。

D7

决策点：交付编排选哪一个（自主四件套）

Autonomous run / Orchestrate / Autopilot-full / Autopilot-stack —— 四个都"自主"，但分界线很清楚： 看工作是否超出单会话预算、PR 是否独立、落地授权是否给出。

Selector

自主编排选择器

  • 是"一个任务驱动到一个谓词"？（repro 修好、测试全绿、pixel-diff 归零） Autonomous run 你拥有退出条件；迭代循环最小改动 → 验证 → 前进或回退
  • 是"一个项目程序"？（多日、多 stack、几十个 subagent、人每天看两次） Orchestrate coordinator 落地已验证工作，但 worker 永不 merge；见第 08 节
  • 是"一队独立 PR 队列"？
    • PR 互相独立 + 落地授权已给（directly to merged） Autopilot-full 每 PR 一个 owner 走完 build→merge 全生命周期；root 每轮 swarm 验证 + 小时级 audit tick
    • 要 review 后才落地 / 工作有顺序或耦合 / merge 授权被扣留 Autopilot-stack owner 不 merge；root 是唯一拓扑写者，组装一条线性 stack 交操作员落地
共同骨架（Autopilot 双胞胎）：owner 15 分钟内建立 decisions.tsv trail + 推首分支快照 + 开 ready PR → 每个可验证单元后推一次 → code-ready head SHA 上报 → root 的 swarm 每轮裁决 → clean verdict 后 full 交给 owner merge / stack 由 root append。 "State-then-wait"：请求"陈述计划"不是执行指令；只有操作员明确的 go 才开跑。

Orchestrate vs 其它词面像程序、实质是任务？

"work one agent could finish inside the session's budget routes there, not here, however program-shaped the phrasing sounds."
—— 先量化：单元数 × 粗糙工作量 × 墙钟预算。一个 agent 能在预算内完成 → 降级。

Multi-phase plan 的位置计划先于执行

跨 phase / stacked PR 的工作可先产出计划文件（计划即交付物，不实现）： 原型解决开放问题 → subagent 探索 → 填 skeleton → 过 check-plan 脚本 → 交还给操作员。执行按计划点名的 execution playbook 启动。

D8

决策点：Babysit 的四种模式

任何 PR 状态请求都走 Babysit playbook（不是 Cursor 内置 babysit，尽管描述词相同）。 第一步永远是声明模式再轮询；未声明默认 drive。

请求 → 模式映射 Babysit step 1
模式触发语行为
drive"babysit this" / "get it green" / "merge-ready"跑循环直到 merge-ready（默认模式）
background计划还在执行中，不想被打断triage 但不阻塞
threads-only"address the bugbot comments"只回 review 评论，其它不碰
check"check on X" / "is it green"；小 PR 或纯文档 PR一次状态扫描 + 报告

Babysit 绝不越权

  • babysit 不授权 merge；merge/land/ship 的请求一律 route 到 Shipping。
  • watcher 重新 arm 也不授权 merge。
  • 唯一允许的创建：修复的归属 PR 已 merge 时 → 在剩余 stack 顶部开新 PR，绝不重写已 merge 历史。
  • 一次只为一条 stack 做 babysit；只处理 frontier（最低未 merge PR），不许越级。

CI 分级纪律

  • flake / 基础设施失败 → 一次 fresh build（只一次重试）。
  • 同样的第二次失败 = 从来不是 flake → 重新分级，读子日志。
  • 失败代码在 diff 之外 → 检查 stale base（git merge-base --is-ancestor），报告需要 rebase，不烧重试。
  • 只有失败在 diff 自己的代码里 → 才提交修复。
Bugbot / 安全评审 = 怀疑姿态：它们既抓真 bug，也报非问题和 nitpick。逐条按事实评估，用具体理由 dismiss 噪音，绝不为了安抚 bot 而 churn 代码。 第三次 pass 起倾向 dismiss 有文档记录的模式，但安全 / 认证 / 计费 / 数据 / 迁移永远升级给人。

大程序拓扑：Orchestrate 的三层结构

当工作超出单会话预算，Orchestrate 把程序拆成三层，深度固定 ≤ 3（更大的扇出靠宽度，不靠深度）。 三条铁律：完成是队列事件不是中断；每次 spawn/resume 逐字携带 standing orders；brief 就是产品（模糊的 brief 会安静地失败，因为 worker 无法向你提问）。

Sub-coordinator · track A

Store状态全部外化到磁盘

  • preferences.md — standing orders 登记处，逐行编号，每条一个约束；spawn/resume 逐字粘贴。
  • units.tsv — 每单元一行：id / track / state / branch / PR / head SHA / brief path。
  • ledger.tsv — 验证账本，一 verdict 一行，键 = PR 号 + head SHA。
  • frontier.json — 计算式 merge frontier（有序 PR 列表 + generation）。
  • inbox/ · gates.md · decisions.tsv · status.md（从表派生，永不手写）。

Ledger verdicts验证状态机

  • live-ui-verified / unit-test-verified / type-check-only / verifier-blocked / verifier-failed。
  • CI 绿是 verdict 的输入，不是 verdict；行为工作必须好于 type-check-only。
  • verifier-blocked 不是 pass——环境恢复后 respawn；verifier-failed → 开修复单元，不是重验。
  • 新 head SHA 作废旧行——restack 后必须重验。

Queue & Drain排空纪律

  • 完成通知 → orch inbox push 记账 → 回到手头工作。绝不 inline 深审；需要 review 的完成 = 一个 verifier 单元。
  • 四个 drain 点：关键区段结束、track rollup、frontier watcher 唤醒、对人报告之前。
  • 每个 drain 分类所有指针（landed / needs-verify / failed / zombie / noise）→ 写行 → orch status → 一条消息发下一波。
  • drain 回合以三行结束：状态计数、变更、open gates。

Liveness失败与重试分级

  • 探活永远只读；永不 resume 一个 agent 去检查它（resume 会重启一个空闲 agent）。
  • 按模式重试：cap-hit/OOM → 缩小 scope respawn；网络 → 原样重试；工具错误 → 换模型；未知 → 重试一次；两次后弃单元并重规划。
  • 迟到 zombie：先对 frontier 与 ledger 校对，通过 fresh 单元抢救独特发现，绝不盲 merge。
  • 连续工具 abort → 停止重试，写终态 handoff（已完成/在哪/恢复命令）并结束运行。

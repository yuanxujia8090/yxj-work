# yxj-work 0.0.2 优化方案：借鉴 gstack 的工作流产品化能力

> 状态：规划中；本文件只定义优化方向和实施边界，不代表已实施
> 创建：2026-10-09
> 参考项目：`/Users/yuanxj/Downloads/gstack-main`
> 当前项目：`yxj-work` v2.1 工作区
> 核心结论：**保留现有契约、证据和完成门体系，借鉴 gstack 的入口体验与真实使用面验证，不复制其角色堆叠、自动发布和第二套记忆系统。**

---

## 1. 目标

让 `yxj-work` 在不牺牲可靠性和边界控制的前提下，更容易被人使用、更容易被新会话恢复，并且更接近真实用户对功能是否可用的判断。

本次优化聚焦四个问题：

1. 用户能否快速知道当前应该进入哪个阶段；
2. 阶段开始时，当前任务的范围、风险、证据和下一步是否清楚；
3. 验证是否覆盖真实使用面，而不只是运行了若干命令；
4. 技能的职责、调用边界和安装范围是否能被稳定检查。

### 1.1 已按推荐选择的路线

**已按推荐选了渐进式增强，因为当前项目的任务契约、状态文件、证据绑定、文件边界和熔断机制已经是核心优势，主要缺口在可用性表达和验证视角，不需要重建底层工作流。**

### 1.2 不改变的核心原则

- 源仓库仍是唯一事实源；
- `contract.md`、`state.md`、`evidence/`、`audit/`、`handoff.md` 继续作为任务事实链；
- required 验收条件全部通过前不得标记 `done`；
- 证据必须绑定验收条件，并满足新鲜度要求；
- 同一错误和同一策略不得原样重试；
- 辅助技能继续默认 `disable-model-invocation: true`；
- 未经授权不扩大需求范围、不推送、不发布、不做生产变更；
- 不引入新的第三方运行时依赖。

## 2. 现状 / 问题 / 影响

### 2.1 现状

当前 `yxj-work` 已具备：

- `fast-answer`、`investigate`、`research`、`design`、`plan`、`exec`、`bugfix`、`review`、`ops`、`mixed` 等任务路由；
- `contract.md` 定义目标、范围、验收条件、风险和审查策略；
- `state.md` 记录阶段、证据、阻塞、预算和策略指纹；
- `check-contract.sh` 和 `check-state.sh` 提供结构与完成门检查；
- `.work-docs/tasks/<task-id>/` 提供任务级文件边界；
- `checkpoint`、`handoff` 和熔断规则支持跨阶段、跨会话恢复；
- 33 个技能通过运行时清单安装，辅助技能默认不自动唤起。

`gstack` 的优势主要集中在：

- 用面向用户的语言说明“什么时候使用哪个入口”；
- 通过统一启动程序展示会话状态和降级状态；
- 按浏览器、API（应用程序接口）、命令行、后台任务等真实使用面组织质量检查；
- 把技能元数据、版本、触发词和生成检查做成可维护的产品机制；
- 提供保存上下文、恢复上下文和管理经验的清晰交互入口。

### 2.2 问题

| 编号 | 现状 | 问题 | 影响 |
|---|---|---|---|
| 1 | 路由和阶段规则已经完整，但主要以工作流内部语言表达 | 用户需要先理解 `L1/L2/L3`、contract、state 等概念才能判断入口 | 使用门槛高，入口选择依赖经验 |
| 2 | 阶段规则要求读取契约和状态，但没有统一的阶段启动摘要 | 当前阶段、允许范围、未完成验收和下一步不一定同时可见 | 跨阶段和跨会话时容易丢失上下文 |
| 3 | 验证条件可绑定 automatic、manual、consumer、external 等类型 | “验证了什么命令”与“用户如何感知功能可用”还没有统一映射 | 代码层通过，但真实流程可能未验证 |
| 4 | 技能已有安装清单和调用边界 | 技能版本、职责、参考关系和输出边界没有形成统一的检查视图 | 技能持续增长后更难维护 |
| 5 | `handoff`、`checkpoint`、memory 和 scratchpad 分别承担不同职责 | 用户层面的恢复入口不够直观 | 下一次会话恢复成本仍然偏高 |

### 2.3 影响

如果直接继续增加技能或规则，会放大已有复杂度；如果只保留底层门禁，又会让工作流难以被日常使用。

因此本版本应优先改进**表达、入口和验证模型**，而不是扩展功能数量。

## 3. 优化范围

### 3.1 纳入范围

#### A. 阶段入口说明产品化

为每个主要阶段补齐统一的用户说明：

- 什么时候使用；
- 需要提供什么；
- 会产出什么；
- 明确不会做什么；
- 下一阶段通常是什么；
- 什么情况下会停在当前阶段。

优先覆盖：

- `investigate`
- `research`
- `design`
- `plan`
- `exec`
- `bugfix`
- `review`
- `ops`
- `mixed`

`fast-answer` 保持轻量，不增加正式任务文件。

#### B. 阶段启动摘要

在正式阶段开始时形成固定格式的摘要，至少包括：

```text
当前阶段：
任务：
风险：
允许改动：
禁止动作：
必过验收：
已有证据：
当前阻塞：
下一步第一动作：
```

启动摘要是人类可读的运行信息，不新建第二套状态文件，不替代 `state.md`。

#### C. 真实使用面验证模型

在现有 `Acceptance` 和 `evidence` 体系上，补充验证层的统一解释：

| 验证面 | 生活化解释 | 示例 |
|---|---|---|
| 代码层 | 看零件有没有装对 | 类型检查、静态检查、单元测试 |
| 接口层 | 看按钮或插口能不能用 | API、命令行、配置入口 |
| 流程层 | 按用户路径走一遍 | 登录、发布、恢复、完整任务链 |
| 运行层 | 在真实环境里试用 | 浏览器、服务、外部系统 |
| 交付层 | 看交给别人后能不能照做 | 文档、操作手册、部署后检查 |

这只是对现有 `layer` 的解释和使用规范，不新增与 L1/L2/L3 并行的等级体系。

#### D. 技能元数据和边界检查

评估并补充最小必要的技能元数据：

- `name`
- `description`
- `version`（只有确实需要版本管理的入口或高变动技能才增加）
- `disable-model-invocation`
- 参考技能或所属阶段
- 预期输出边界

优先通过现有检查脚本和运行时清单实现，不新建独立技能注册系统。

#### E. 恢复入口的人类可读性

保留现有 `state.md`、`checkpoint` 和 `handoff` 的事实分工，只优化恢复时的摘要表达：

- 当前状态；
- 已完成事项；
- 未完成事项；
- 证据位置；
- 阻塞原因；
- 下一步第一动作。

不引入 gstack 的第二套跨项目记忆系统。

### 3.2 明确不纳入范围

- 不新增 CEO、设计师、工程经理等角色技能；
- 不复制 gstack 的自动扩大需求范围机制；
- 不把提交、推送、创建 PR、部署设为默认自动闭环；
- 不新增独立的 `learn` 或 `gbrain` 记忆系统；
- 不新增 Quick / Standard / Exhaustive 这套与现有任务等级并行的分类；
- 不把自然语言质量评分强行塞进 shell 检查器；
- 不迁移历史任务的 `.work-docs` 文件；
- 不修改当前项目之外的已安装技能副本；
- 不在本版本直接执行代码重构或行为变更。

## 4. 推荐设计

### 4.1 总体结构

保留当前工作流主干：

```text
用户任务
  ↓
任务路由
  ↓
阶段入口说明
  ↓
contract / state / evidence
  ↓
阶段启动摘要
  ↓
真实使用面验证
  ↓
完成门
```

其中：

- **任务路由**决定进入哪个阶段；
- **入口说明**帮助人理解阶段；
- **contract**定义目标、边界和验收；
- **state**记录当前事实；
- **evidence**证明验收结果；
- **真实使用面验证**补充“用户实际如何感知”的角度；
- **完成门**决定能否标记完成。

### 4.2 启动摘要的事实来源

启动摘要只能从以下事实来源生成或整理：

| 摘要字段 | 来源 |
|---|---|
| 当前阶段 | `state.md` |
| 任务 | `contract.md` / 任务目录 |
| 风险 | `contract.md` |
| 允许改动 | `contract.md` |
| 禁止动作 | `contract.md` |
| 必过验收 | `contract.md` 和 `state.md` |
| 已有证据 | `state.md` 与 `evidence/` |
| 当前阻塞 | `state.md` |
| 下一步第一动作 | `state.md` 或最近 checkpoint |

如果来源之间冲突，以真实证据和 `state.md` 的校验结果为准；不能用摘要覆盖事实源。

### 4.3 真实使用面验证的写法

每条新增或调整的验收条件，优先回答三件事：

1. 用户或下游系统通过什么表面感知它；
2. 最小可观察结果是什么；
3. 失败时应该留下什么证据。

推荐写法：

```text
outcome: 过期登录状态下，页面不再显示为已登录
verification: 运行真实登录页的过期 cookie 场景，并确认页面显示登录入口
verification_type: consumer
layer: runtime/local
required: yes
```

不推荐只写：

```text
verification: 运行测试
```

因为它没有说明测试验证了什么行为，也没有说明谁能观察结果。

### 4.4 失败和降级规则

本版本继续沿用当前项目的失败纪律：

- 启动摘要缺字段：回到契约或状态文件修复，不凭记忆补全；
- 证据无法证明真实使用面：标记 `not_run` 或 `blocked`，不写 `done`；
- 外部环境不可用：记录阻塞原因、尝试过的路径和解除条件；
- 同一命令与同一首行错误再次出现：停止原样重试，改用新策略或交付阻塞状态；
- 第三方技能写入工作目录外：停止并记录越界，不移动或覆盖文件。

## 5. 分阶段实施方案

> 以下是后续实施顺序，不是本次执行记录。每一阶段完成后都必须先验证，再决定是否进入下一阶段。

### Phase 1：入口说明和验证词汇统一

**目标：**先改善可理解性，不改变运行行为。

**计划工作：**

1. 盘点 `yxj-work` 各阶段的现有说明和 playbook；
2. 为每个正式阶段补齐“适用场景 / 输入 / 输出 / 不做什么 / 停止条件”；
3. 统一 `layer` 各值的中文解释和示例；
4. 在 `skills/README.md` 增加面向用户的阶段选择表；
5. 检查入口说明与 `yxj-work/SKILL.md` 的路由没有第二份冲突清单。

**验收：**

- 用户只阅读阶段选择表，能够区分 `investigate`、`research`、`design`、`plan`、`exec`、`bugfix`、`review`、`ops`；
- 每个正式阶段都有明确的输入、输出和禁止范围；
- 文档没有引入与当前任务等级、风险等级重复的分类；
- 现有安装和检查脚本不受影响。

### Phase 2：启动摘要规范

**目标：**让阶段开始时能快速恢复当前任务，不新增事实源。

**计划工作：**

1. 确定启动摘要的固定字段和顺序；
2. 将摘要生成规则放入对应的工作流说明，而不是复制到多个辅助技能；
3. 规定新任务和历史任务的兼容行为；
4. 为启动摘要增加一个最小示例；
5. 用一个低风险只读任务验证摘要是否能从现有 `contract/state/evidence` 重建。

**验收：**

- 摘要能显示当前阶段、风险、允许范围、未完成验收、阻塞和下一步；
- 摘要不改变 `contract.md`、`state.md` 的事实；
- 历史任务缺少新字段时可以明确显示“未记录”，而不是臆造；
- 跨会话恢复时只读任务记录即可找到第一步动作。

### Phase 3：真实使用面验证规范

**目标：**让验收条件从“跑过什么命令”提升到“用户观察到了什么结果”。

**计划工作：**

1. 抽样检查已有任务的 `Acceptance` 和 `evidence`；
2. 为代码层、接口层、流程层、运行层、交付层分别补一个正确示例和一个反例；
3. 在 `yxj-work` 的契约和验证规则中增加使用说明；
4. 明确 consumer、external、runtime/local 等验证类型的适用边界；
5. 选一个真实任务做一次小范围试跑，只改任务文档和证据，不改产品代码。

**验收：**

- 至少一个验收条件能同时写出“观察对象、预期结果、验证动作”；
- `check-contract.sh` 和 `check-state.sh` 的结构职责不被扩大；
- 验证失败时能落到 `not_run`、`failed` 或 `blocked`，不会被误写为完成；
- 没有引入第二套任务等级或审查等级。

### Phase 4：技能元数据和边界检查

**目标：**降低技能继续增长后的维护成本。

**计划工作：**

1. 盘点现有技能头部字段和 `runtime-skills.txt` 的一致性；
2. 只为真正需要的字段补元数据，不为了形式增加版本号；
3. 检查每个入口技能是否能说明辅助技能的读取关系；
4. 增加最小静态检查：清单目录存在、技能名称一致、禁止自动唤起规则没有被意外移除；
5. 保留现有“入口主动读取、辅助技能默认不自动唤起”的边界。

**验收：**

- 运行时清单、技能目录和文档说明能互相对应；
- 缺失或错误技能元数据能被检查脚本指出；
- 检查脚本不会自动覆盖、删除或修复用户文件；
- 不新增独立技能注册中心。

### Phase 5：小范围试跑和是否继续决策

**目标：**用真实任务判断优化是否真的减少理解和恢复成本。

**建议试跑对象：**

- 一个只读 `review` 任务；
- 一个 `investigate → bugfix → review` 任务；
- 一个跨会话的 `yxj-work-long` 任务。

**记录指标：**

- 用户首次选择正确阶段所需的解释次数；
- 阶段启动后是否需要重复读取同一背景；
- 验收条件中真实使用面验证的覆盖率；
- 恢复时是否能直接执行第一步；
- 是否出现新的边界冲突或重复事实源。

**决策规则：**

- 如果入口说明和启动摘要已经降低理解成本，保留当前设计；
- 如果真实使用面验证只能增加文档负担而没有带来更强证据，暂停扩大范围；
- 如果技能元数据检查产生大量维护成本，优先删除非必要字段；
- 只有试跑暴露出稳定重复问题，才考虑修改 playbook、检查脚本或契约模板。

## 7. 验证计划

后续真正实施时，至少需要覆盖以下验证层：

### 静态层

- 技能清单目录与实际目录一致；
- 技能头部字段格式正确；
- 阶段选择表和入口技能没有互相矛盾的路由；
- 文档中没有引入第二套等级或事实源。

### 行为层

- 启动摘要能从现有任务记录正确整理；
- 历史任务缺字段时不被臆造；
- 真实使用面验证的证据能绑定到具体验收条件；
- `not_run`、`failed`、`blocked` 不会被完成门当作 `passed`。

### 回归层

- `bash scripts/check-repo.sh`；
- 现有技能清单检查；
- `bash skills/yxj-work/scripts/check-contract.sh <task-dir>`；
- `bash skills/yxj-work/scripts/check-state.sh <task-dir>`；
- 当前项目已有测试脚本；
- 至少一次跨会话恢复试跑。

具体命令应以实施时读取到的当前脚本和项目说明为准，不在本规划阶段假定尚未确认的命令路径。

## 8. 风险与控制

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 为了借鉴 gstack 增加过多技能 | 路由复杂、技能互相覆盖 | 只优化入口、验证和元数据，不增加角色技能 |
| 启动摘要成为第二套状态 | 摘要和 state 不一致 | 摘要只能由现有事实源整理，不能独立保存事实 |
| 真实使用面验证增加文档负担 | 任务变慢、证据过度 | 只要求写清观察对象和预期结果，不要求所有任务都做真实环境验证 |
| 引入新的记忆系统 | 事实源分裂 | 继续使用 `.work-docs`、项目决策、全局记忆的现有分层 |
| 自动发布边界被放宽 | 不可逆操作风险 | 发布、推送、生产变更仍作为明确决策门 |
| 兼容历史任务时产生假字段 | 恢复信息失真 | 缺失字段显示未记录，不能推断 |
| 元数据检查变成新的维护负担 | 技能开发速度下降 | 只检查能直接证明一致性的最小字段 |

---

## 9. 完成标准

本优化方案只有在后续实施满足以下条件时，才可以标记为完成：

1. 阶段入口说明已覆盖主要正式阶段，且没有与主路由形成第二份冲突清单；
2. 启动摘要能从既有任务事实源重建，并明确处理历史任务缺字段的情况；
3. 真实使用面验证已经写入契约和 evidence 的使用规范，并完成至少一次小范围试跑；
4. 技能元数据检查只覆盖必要字段，且没有引入第二套技能注册或自动唤起系统；
5. 现有 contract/state/evidence/checkpoint/handoff/熔断机制保持兼容；
6. 相关静态检查、契约检查、状态检查和试跑证据均已落盘；
7. 未发生未经授权的代码修改、生产操作、推送、发布或历史任务迁移；
8. 试跑结果已经明确记录“继续、缩小、暂停”中的一个结论，并说明依据。

---

## 10. 后续决策门

以下事项在真正实施前仍需根据 Phase 1–5 的证据决定，不在本方案中预先扩大范围：

- 是否需要把启动摘要做成脚本，而不是只由技能规则生成；
- 是否需要为技能头部增加统一 `version`；
- 是否需要新增专门的真实使用面验证辅助技能；
- 是否需要把某些重复出现的自然语言要求编码成检查脚本；
- 是否需要把试跑指标长期记录到项目文档。

默认建议：**先不做这些扩展，只有小范围试跑证明现有文档规则无法稳定工作时，才进入下一轮设计。**

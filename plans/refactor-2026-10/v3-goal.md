   ## 四、第一性原理分析要求

   不要从“保留现有文件”开始，而要从任务系统必须解决的基本问题开始：

   1. 一个任务到底需要保存哪些信息？

   4. 哪些规则必须每次加载？
   5. 哪些规则应按需加载？
   6. 哪些状态必须持久化？
   7. 上下文压缩后，模型如何恢复？
   8. 一个弱模型最容易在哪些地方犯错？
   9. 什么操作必须可重复执行？
   10. 什么操作必须有顺序证据？
   11. 什么情况应该自动继续？
   12. 什么情况才应该阻塞用户？
   13. 什么失败可以重试？
   14. 什么失败重试只会制造更多损害？
   15. x-rail 的核心价值到底是“强制流程”，还是“降低任务完成成本并提供可靠证据”？

   如果现有设计把“模型必须记住的内容”误写成“模型每次都必须阅读的规则”，优先拆分。

   ## 五、目标设计约束

   请评估并在设计中优先采用以下方向：

   ### 1. 入口技能轻量化

   将：

   skills/x-rail/SKILL.md

   压缩到约 5 KB 左右，目标是只保留：

   - x-rail 是什么；
   - 什么时候使用；
   - 路由表；
   - 必须遵守的少量安全规则；
   - 如何加载更详细的规则；
   - 最小完成清单；
   - 恢复入口。

   不要把所有规则继续塞回入口文件。

   详细规则应拆成按需加载的模块，例如：

   - 任务识别；
   - 状态管理；
   - 计划；
   - 实施；
   - 验证；
   - 错误恢复；
   - 子代理；
   - 交接；
   - 上下文压缩恢复。

   模块命名和目录结构必须以当前项目已有约定为准，不要为了形式增加过多文件。

   ### 2. 替换复杂管道记录

   评估是否可以把严格 pipe record 替换为简洁 Markdown checklist。

   推荐最小格式：

   ```md
   # Task

   ## Intent
   - Goal:
   - Scope:
   - Done when:

   ## Status
   - [ ] Understand
   - [ ] Plan
   - [ ] Implement
   - [ ] Verify
   - [ ] Handoff

   ## Evidence
   - Command:
   - Result:
   - Path:

   ## Decisions
   - Decision:
   - Reason:

   ## Risks
   - Remaining risk:
   - Next action:
 ```

 要求：

 - 模型可直接读写；
 - 弱模型不需要记忆复杂参数；
 - 机器可以检查关键字段；
 - 不依赖脆弱的管道分隔符；
 - 支持上下文压缩后恢复；
 - 支持重复执行和中断后继续。

 不要为了替换格式而删除旧记录。评估是否需要：

 - 旧格式只读解析；
 - 旧格式转换器；
 - 兼容期；
 - 迁移说明。

 ### 3. 降低 task.py 权限

 评估将 task.py 和 task_checks.py 从“任务完成硬门禁”降级为“可选检查器”：

 - 默认不阻止任务完成；
 - 用户或 CI 可以主动运行；
 - 检查失败时给出清晰报告；
 - 不让复杂记录格式成为任务完成的唯一入口；
 - 不允许检查器制造虚假完成状态；
 - 保留安全相关检查和数据损坏防护；
 - 如果移除某个门禁会造成真实数据风险，必须明确指出。

 必须验证 task.py 当前被哪些文件、脚本、文档和流程依赖，不能只删调用点。

 ### 4. 子代理策略

 默认关闭子代理自动启动,根据实际需要再启动。

 但不要删除 Pi Subagents 能力。建议目标：

 - 默认由单个 Pi Agent 完成任务；
 - 任务明确声明“启用子代理”时才使用；
 - 子代理只用于真正独立的研究、审查或并行工作；
 - 不允许多个写入者同时修改同一个工作区；
 - 不让子代理成为完成任务的隐含前置条件；
 - 子代理失败时主任务仍能给出可恢复状态；
 - 记录子代理的输入、输出、失败原因和是否被主任务消费。

 如果研究证明默认委派比默认单代理更可靠，必须用数据说明，而不是凭感觉恢复默认委派。

 ### 5. 超时和重试

 设计清晰的时间和重试策略：

 - 单个工作项硬上限：15 分钟；
 - 可以在 10–15 分钟范围内选择更合理的默认值，并写入 DECISIONS.md；
 - 第三方 API 出现瞬时错误时，最多自动重试 1 次；
 - 重试必须计入工作项时间；
 - 不对代码逻辑错误、参数错误、权限错误和验证失败盲目重试；
 - 重试后仍失败，保存恢复信息并结束当前工作项；
 - 不允许无限重试；
 - 区分 API 错误、工具错误、模型输出错误和项目测试失败。

 ### 6. 上下文压缩和恢复

 设计一个短小、稳定、适合弱模型读取的恢复机制。

 要求：

 - 规则不依赖模型长期记忆；
 - 当前状态保存在任务文件；
 - 压缩摘要只保存索引和当前事实，不重新描述所有规则；
 - 恢复时优先读取任务清单、当前状态、未完成项和最新证据；
 - 规则模块按需重新加载；
 - 不让 4B 模型负责生成完整系统规则；
 - 上下文压缩后可以从文件继续，而不是从聊天摘要猜测。

 ### 7. pstack 能力引入

 对以下能力逐项评估，不要盲目照搬：

 - TDD：是否能减少回归；
 - recall：是否能降低重复取证成本；
 - reflect：是否能发现流程错误；
 - never-block-on-the-human：哪些场景可以自动选择推荐方案；
 - make-operations-idempotent：哪些命令可安全重复执行；
 - sequence-verifiable-units：如何把大任务拆成可独立验收的小单元。

 每项给出：

 - pstack 的具体实现方式；
 - x-rail 是否已有类似能力；
 - 引入成本；
 - 对弱模型是否友好；
 - 与当前 Pi Agent 的适配程度；
 - 推荐结论。

 九、验收标准

 只有同时满足以下条件，才能认为重构完成：

 ### 结构

 - skills/x-rail/SKILL.md 压缩到约 5 KB，且只承担入口和路由职责；
 - 详细规则可以按需加载；
 - 不存在通过拆分文件而增加总复杂度的假优化；
 - 任务状态不依赖聊天上下文才能恢复。

 ### 使用体验

 - 普通任务默认不启动子代理；
 - 任务记录可以用简单 Markdown checklist 读写；
 - task.py 是可选检查器，不是默认完成门禁；
 - API 瞬时错误最多自动重试一次；
 - 单个工作项不会无限运行；
 - 中断或上下文压缩后可以从任务文件继续。

 ### 可靠性

 - 旧格式、旧脚本和旧任务的迁移策略明确；
 - 关键操作可重复执行；
 - 失败后能保存恢复信息；
 - 检查器不会制造错误的完成状态；
 - 不会因为弱模型漏记一个复杂参数而让整个任务不可恢复。

 ### 证据

 - 有 pstack 对比报告；
 - 有真实 Pi Agent 会话取证，或明确记录无法访问；
 - 有近 14 天提交分析；
 - 有改动前后的指标对比；
 - 有测试或可执行验证；
 - 有独立审查结果；
 - 有残余风险和未完成项清单。

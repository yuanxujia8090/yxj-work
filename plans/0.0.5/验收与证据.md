# x-rail 0.0.5 验收与证据

> 本文定义如何证明延迟优化有效。2026-10-16 已按用户要求完成 P0-2、P1-1 的规则层实施；本次未执行配置修改、网关探针或真实任务对照。

## 1. 验收原则

这次验收必须把四件事分开：

1. 配置是否按预期生效；
2. 模型和网关是否真的更快；
3. 任务质量是否保持；
4. 长会话是否更容易恢复。

不能用“模型回应变快”单独证明任务效率提高，也不能用“测试通过”单独证明上下文策略正确。

所有比较都使用同一任务、同一代码基线、同一模型、同一网关、同一工具权限和尽量相同的任务提示。若环境变化，报告中单独标记，不能混入同一组数据。

## 2. 固定基线

实施前保存以下只读事实：

- 模型供应商和模型标识；
- 当前生效的 `contextWindow`（上下文窗口，即模型本轮可读取的最大上下文容量）；
- 当前生效的 `reserveTokens`（保留 token，即为输出和压缩预留的容量）；
- 压缩触发计算方式；
- 默认思考级别；
- 工具调用是否支持同轮多个调用；
- 网关请求超时、重试和空响应表现；
- 统计脚本版本和会话日志路径。

固定基准任务至少包含：

- 一次多文件只读调查；
- 一次局部代码修改；
- 一次测试和类型检查；
- 一次需要明确验收和收尾的任务。

基准任务不能包含删除、强推、生产迁移、对外发布等不可逆动作。

## 3. 统一指标

### 3.1 时间指标

| 指标 | 定义 |
|---|---|
| 墙钟时间 | 从任务开始到交付说明的实际经过时间 |
| 模型记录时间 | 会话中 assistant `durationMs` 的总和；只作为模型侧记录，不等同于网关纯推理时间 |
| 工具执行时间 | 工具结果 `durationMs` 的总和 |
| TTFT | 首 token 等待时间，模型开始返回首个 token 前的等待时间 |
| p50/p95/p99 延迟 | 多轮样本的中位数、95 分位和 99 分位 |
| 长轮次数 | 超过 60 秒、300 秒和 600 秒的模型轮次数 |

### 3.2 上下文指标

- 每轮输入 token；
- 每轮缓存读取 token；
- 最大上下文规模；
- 压缩触发次数和触发时上下文规模；
- 压缩前后保留的恢复事实；
- 大于 8KB 的工具输出数量与总字符数。

### 3.3 任务质量指标

- 必要测试的明确通过数量；
- 类型检查和静态检查结果；
- 需求覆盖是否完整；
- 是否出现编辑覆盖、重复修改或遗漏修改；
- 是否生成有效 handoff；
- 是否需要人工纠正模型错误；
- 审查发现的问题数量与严重程度。

### 3.4 可靠性指标

- 工具错误数和错误率；
- 网关空响应数；
- 原样重试次数；
- 连续错误最长长度；
- handoff 后重复读取量；
- 恢复后重复劳动或丢失事实的次数。

## 4. P0 验收

### 4.1 压缩阈值实验

**目的：** 验证较早压缩是否降低长轮延迟，而不损失任务质量。

**实验组：**

- 基线组：保持当前生效配置；
- 实验组：上下文窗口约 220,000，保留 token 约 70,000，目标触发线约 150,000；
- 其他变量保持不变。

**步骤：**

1. 记录基线配置和回退命令；
2. 执行同一基准任务；
3. 记录每轮上下文、缓存读取、TTFT、完成时间和错误；
4. 确认实验组确实触发压缩；
5. 对照任务测试、代码差异和交付内容；
6. 恢复原配置，确认恢复成功。

**通过条件：**

- 配置读取结果与实验值一致；
- 至少出现一次可识别的压缩事件，且记录触发上下文；
- 实验组最大上下文低于基线；
- 长轮次数或 p95 延迟有明确改善，或证据显示没有改善；
- 测试、类型检查、需求覆盖和审查质量没有下降；
- 回退后配置恢复原值。

不能因为压缩发生就判定实验成功；必须同时看延迟和质量。

### 4.2 工具调用合并

**目的：** 减少独立只读操作的模型往返。

**正例：** 同轮读取多个互不依赖的文件，或同时获取 Git 状态和任务摘要。

**反例：** 前一个命令输出决定后一个命令参数；两个命令写同一文件或数据库；编辑操作依赖前一次编辑结果。

**通过条件：**

- 独立只读调用能够同轮合并；
- 有依赖的调用仍保持正确顺序；
- 没有因合并导致工具结果混淆、错误遗漏或共享写入冲突；
- 同等任务的模型轮次减少；
- 必要读取、测试和验收没有被省略。

不设固定“必须减少多少轮”的门槛，报告实际轮次数和质量结果。

### 4.3 思考级别分层

**目的：** 机械步骤提速，高风险步骤不降级。

准备两类任务：

- 机械类：目录查询、状态查看、单文件读取、明确命令执行；
- 判断类：并发锁序、数据状态机、需求取舍、独立审查。

**通过条件：**

- 机械类任务使用 `low` 或 `medium`；
- 并发、安全、迁移和最终审查使用 `high`；
- 机械类任务耗时下降或不变，但准确率不下降；
- 判断类任务不因默认降级而失去关键检查。

## 5. P1 验收

### 5.1 大输出落盘

**目的：** 避免原始测试和命令输出长期占据上下文。

**通过条件：**

- 超过 8KB 的输出有明确证据路径；
- 上下文只保留退出码、通过数、失败项和摘要；
- 原始输出仍可按路径读取；
- 摘要没有隐藏失败；
- 测试输出含明确通过数量，不能只引用尾部耗时。

### 5.2 handoff 门槛

**目的：** 在延迟风暴前切换到新会话。

测试以下触发条件：

- 上下文超过约 150,000 token；
- 约 60 个模型轮次；
- 同阶段出现两个超过 5 分钟的模型轮次；
- 阶段完成，需要读取完全不同的文件集合。

**通过条件：**

- handoff 写出已完成、未完成、证据路径和下一动作；
- 新会话可以只读 handoff 和必要文件恢复；
- 不重复执行已完成修改；
- 不丢失未完成项、限制或用户已有修改；
- 原任务编号和状态连续。

### 5.3 连续错误熔断

**目的：** 避免空响应和工具错误形成重试风暴。

构造安全、低成本的失败演练，不发起大规模网关请求。验证：

- 第一次错误保留准确错误；
- 第二次连续错误停止原方法；
- 随后换读取、换命令、换模型或换会话，并说明理由；
- 不原样重复失败调用；
- 五次同类错误不会继续自动循环；
- 当前工作区、状态和证据仍可恢复。

## 6. P2 网关探针

### 6.1 探针输出

每个样本至少保存：

```text
sample_id
model
provider
context_tokens
new_input_tokens
cache_read_tokens
output_tokens
request_started_at
first_token_at
request_finished_at
ttft_ms
completion_ms
http_status
empty_response
retry_count
error_kind
```

探针报告只打印聚合统计和异常样本，完整样本落盘，避免再次把数据全文塞回主上下文。

### 6.2 样本矩阵

至少测量以下上下文大小：

```text
32K、64K、128K、160K、220K、320K
```

每个规模至少重复若干次，区分：

- 首次请求；
- 短间隔重复请求；
- 较长间隔后请求；
- 只改变尾部少量内容的请求。

样本数量、间隔和费用需在实施前核对；本方案不授权付费或压力测试。

### 6.3 假设判定

| 假设 | 支持证据 | 不能单独证明的内容 |
|---|---|---|
| 大上下文导致延迟上升 | TTFT/完成时间随上下文规模稳定上升 | 不证明一定是缓存驱逐 |
| 缓存命中降低延迟 | 同尺寸重复请求明显快于首次请求 | 不证明网关内部缓存策略 |
| 缓存 miss 触发重预填 | miss 样本耗时与上下文规模相关 | 不证明具体重试实现 |
| 存在约 300 秒重试单元 | 多次延迟接近 300 秒整数倍且伴随错误/排队 | 不可只凭整数倍命名内部机制 |
| 空响应是网关问题 | 多次在相同请求层出现，客户端无工具错误 | 不排除模型或代理偶发故障 |

## 8. 失败判定与停止条件

以下情况立即停止当前实验，不原样重试：

- 配置无法证明已生效；
- 网关返回空响应或连续请求错误；
- 测试结果无法确定，只有尾部耗时没有通过计数；
- 编辑发生部分应用但未重新读取确认；
- 上下文压缩丢失任务状态；
- 实验引入安全、权限、数据完整性问题；
- 需要购买、更换网关、对外发布或改需求范围。

停止后报告准确错误、当前路径、已保存证据和恢复第一步。

## 9. 效果结论规则

### 可以得出的结论

- 某一配置在某一模型、某一网关、某一任务上的实测延迟变化；
- 某条规则是否减少模型轮次；
- handoff 是否能在当前任务类型中恢复；
- 错误熔断是否阻止重复失败；
- 任务质量是否保持。

### 不能直接得出的结论

- 一次会话证明所有长任务都会提速；
- 缓存读取 token 等于实际费用；
- 约 300 秒整数倍必然代表网关固定重试机制；
- 工具调用减少就一定交付更快；
- 更早压缩一定优于原配置；
- 更换模型或网关一定解决问题。

## 结论先行

这次慢的主要不是代码工具，也不是业务任务本身，而是**长上下文叠加模型网关延迟**：上下文持续增长后，模型每一轮都要携带大量历史；一旦网关缓存没有命中，就可能重新预填全部上下文，形成数分钟到二十分钟的单轮等待。任务质量没有因耗时明显崩溃，主要损失体现在等待时间、串行往返和失败后的恢复成本。

建议先做低风险、可测量的三件事：

1. 降低上下文触发压缩的阈值，验证压缩是否真的发生；
2. 让相互独立的工具调用在同一轮合并，减少模型往返；
3. 将机械步骤与高风险推理步骤分级，机械步骤不默认使用最高思考级别。

已按推荐选了“先缩短上下文、减少往返，再探测网关”，因为本次证据把主要耗时定位在模型等待而非工具执行；网关缓存失效和约 300 秒重试单元仍需实测，不能直接当成已证实事实。

## 二、根因分层

### 已证实事实

1. 会话持续约 226 分钟，模型记录耗时约 217 分钟。
2. 250 个模型轮次对应 258 个工具调用，大多数轮次只有一个工具调用。
3. 后半段出现多次 5–20 分钟级别的模型轮次。
4. 工具平均执行很快，但工具错误和编辑冲突会增加模型恢复轮次。
5. 会话在完成用户要求的“暂停并写 handoff”前，仍继续处理多个复杂阶段。

### 高概率解释

1. **上下文变大后，网关缓存命中不稳定。** 同等上下文规模的轮次可能出现几秒和十几分钟的巨大差异，符合缓存命中与全量预填差异。
2. **大上下文提高缓存驱逐成本。** 一次缓存未命中，重预填成本随上下文规模增加，进一步拖慢后续轮次。
3. **串行微操作放大固定延迟。** 每读一个文件、跑一条命令、改一处内容，都可能触发新一轮模型调用。
4. **高思考级别覆盖机械步骤。** 全程 `high` 会让简单检查和路径判断也承担最高推理开销。
5. **阶段边界不够早。** 前端、后端 P2 和真实数据库并发验收被放在同一长会话中，导致上下文和恢复成本继续累积。

### 尚未证实的假设

- 网关是否存在约 300 秒的重试、排队或超时单元；1189 秒约等于多个 300 秒单元，只能作为线索。
- 缓存 miss 是否由上下文长度、请求间隔、供应商驱逐策略或网关限流造成。
- `contextWindow`、`reserveTokens` 的当前生效配置是否正是另一份分析引用的数值。
- 5 次“网关空响应”是否来自同一个服务端原因。

## 四、建议优先级

| 优先级 | 建议 | 目标 |
|---|---|---|
| P0 | 将压缩触发线从当前实际约 88.8 万 token 的量级，实验性下调到约 15 万 token 量级 | 让长会话更早压缩，降低缓存 miss 的重预填代价 |
| P0 | x-rail 规定独立工具调用尽量合并到同一轮 | 减少 250 次模型往返中的固定开销 |
| P0 | 普通机械轮默认 `low`，设计/并发/审查轮手动升 `high` | 把高推理留给真正需要判断的环节 |
| P1 | 单条大工具输出超过 8KB 时落盘并只带摘要 | 降低上下文滚雪球 |
| P1 | 上下文超过约 15 万 token 或约 60 轮时强制 handoff | 用新会话切断历史累积 |
| P1 | 连续两次工具或模型错误后暂停并换方法/新会话 | 避免错误重试风暴 |
| P2 | 建立网关延迟探针，测上下文长度、TTFT、完成时间和缓存线索 | 验证网关假设，决定是否换网关或分流本地模型 |

这些阈值是实验起点，不是永久配置，也不是完成条件本身。

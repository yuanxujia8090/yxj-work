# x-rail 0.0.5 优化方案：降低 Pi Agent 长会话延迟

> 本文原为实施前方案。2026-10-16 已按用户要求完成 P0-2、P1-1 的规则层实施；其他优先项暂不调整。实际改动和验证记录见本目录 README，真实模型运行效果尚未验证。

## 1. 现状、问题与影响

### 1.1 当前现象

会话 `01a13f5b-8cd2-73b2-86b0-1c394ca2f7cd` 在约 3 小时 46 分钟内完成了多个后端、前端和真实数据库并发验收阶段。工具本身执行很快，但模型多次出现 5–20 分钟级别的单轮等待。

这像前端页面不是接口慢，而是每次交互都重新加载一份越来越大的页面状态：按钮点击本身只花几百毫秒，但页面重新渲染和数据传输拖慢了整体体验。

### 1.2 已观察到的问题

| 现状 | 问题 | 影响 |
|---|---|---|
| 上下文从约 34K 增长到约 354K token | 每轮携带的历史越来越大 | 缓存命中时还能工作，缓存失效时预填成本很高 |
| 250 个模型轮次对应 258 次工具调用 | 大多数轮次只处理一个微操作 | 固定往返成本被放大 |
| 35 个轮次超过 60 秒 | 少数长轮次吞掉大部分模型时间 | 平均耗时被极端延迟拉高 |
| 多次编辑失败、文件状态变化、路径误判 | 每次错误都需要重新读取和恢复 | 有效代码产出被返工打断 |
| 前端、后端 P2、真库并发验证共用一段会话 | 阶段边界过晚 | 上下文、任务规则和中间结果长期累积 |
| 高思考级别贯穿全部轮次 | 机械步骤也使用高推理成本 | 简单检查的单位成本过高 |
| 大工具输出直接回到上下文 | 历史事实与原始输出混在一起 | 上下文滚雪球 |

### 1.3 影响

- 交付速度降低，但工具性能不是主要原因。
- 发生网关缓存 miss 时，等待时间可能从秒级升到分钟级。
- 错误恢复和编辑冲突进一步放大模型等待。
- 长会话更容易出现“已经读过但重新确认”的循环。
- 若只优化测试命令或 Bash 速度，收益会很小。

## 2. 根因模型

### 2.1 主因：大上下文 × 网关缓存不稳定

另一份分析观察到：相近上下文规模的轮次，一次只需数秒，另一次却需约 913 秒；多个极端轮次约为 300 秒的整数倍。这个现象支持以下假设：

1. 上下文变大后，网关缓存更容易被驱逐或无法命中。
2. 缓存 miss 后，服务需要重新预填完整上下文。
3. 网关可能存在排队或重试单元，约 300 秒只是当前线索。
4. 重预填越慢，后续会话越容易进入延迟风暴。

当前只把第 1–2 点列为高概率解释；第 3 点必须通过网关探针验证，不写成事实。

### 2.2 次因：串行微操作

250 个模型轮次中，约 230 个轮次只有一个工具调用。独立的目录检查、文件读取和测试命令没有充分合并，每个动作都重新经过模型网关。

即使每轮只有 7–15 秒，250 轮也会形成很高的固定时间地板；发生缓存 miss 后，损失进一步扩大。

### 2.3 次因：阶段未及时切分

本次实际阶段耗时按模型记录估算：

| 阶段 | 模型记录耗时 |
|---|---:|
| 初步检查 | 约 14.4 分钟 |
| 前端实现 | 约 55.4 分钟 |
| 并发验收 | 约 123.6 分钟 |
| 收尾 | 约 24 分钟 |

真库并发验收阶段占比最高。并发验收同时修改了验收脚本、模拟客户端、环境变量和断言，导致“测试业务逻辑”和“调试测试脚本”混在一起。

### 2.4 放大器：失败恢复和高思考级别

已记录 19 次工具错误，其中包括：

- 未先读文件就编辑；
- 文件已变化导致旧文本无法匹配；
- 多编辑部分应用；
- 旧文本不唯一；
- 文件读取记录过期；
- 路径或文案文件位置判断错误。

这些错误不一定耗费大量工具时间，但会强制模型重新判断当前状态。

同时，会话使用高思考级别贯穿全部 250 个模型轮次。高思考应留给架构、并发、审查和安全判断，不应覆盖每个机械查询。

## 3. 优化目标

### 3.1 目标

1. 降低长会话的最大上下文规模。
2. 减少独立操作触发的模型往返次数。
3. 让机械步骤使用低成本推理，让高风险步骤保留高推理。
4. 让大输出只保留摘要，原文落盘可追溯。
5. 在延迟风暴前切换到新会话。
6. 通过实验确认网关缓存和重试假设。

### 3.2 非目标

- 不牺牲代码读取、输入校验、安全校验和验收质量。
- 不把工具调用越少当成唯一目标。
- 不把所有任务强行并行。
- 不把模型自报完成作为实际验证。
- 不直接换供应商或购买服务。
- 不凭单次会话承诺固定提速比例。

## 4. 分层方案

## 4.1 P0：配置与提示词层

### P0-1：降低上下文压缩触发线

另一份分析按当前配置估算，压缩触发线约为：

```text
contextWindow - reserveTokens ≈ 1,044,480 - 156,672 ≈ 888,000 token
```

建议先做隔离、可回退实验：

- 检查当前实际生效的模型配置，不假设文件值就是运行值。
- 将目标上下文窗口实验设为约 220,000 token。
- 将保留 token 实验设为约 70,000 token。
- 观察是否在约 150,000 token 附近触发压缩。
- 记录压缩前后的模型延迟、上下文大小、输出质量和错误率。

这是实验参数，不是永久推荐值。必须在修改前备份当前配置并确认恢复方式；修改全局配置属于实施动作，不在本方案编写阶段执行。

### P0-2：合并独立工具调用（已实施：规则层）

在 x-rail 规则中加入：

> 相互独立、无共享写入、无前置依赖的读取或检查调用，应尽量合并到同一轮；存在顺序依赖、共享资源或副作用时保持串行，并记录原因。

适合合并：

- 同时读取多个只读文件；
- 同时查询目录、Git 状态和任务摘要；
- 同时检查多个不相干测试文件。

不适合合并：

- 前一个命令决定后一个命令参数；
- 两个命令写同一状态、数据库或构建目录；
- 一个编辑依赖另一个编辑后的最新内容；
- 生产、删除、覆盖等敏感动作。

验收不只看一次消息里有几个工具调用，还要看是否保留正确依赖和文件所有权。

### P0-3：思考级别分层

建议默认规则：

| 工作类型 | 默认级别 | 说明 |
|---|---|---|
| 目录查询、状态查看、简单读取 | `low` | 重点是准确执行，不需要长推理 |
| 单文件局部修改、普通测试修复 | `low` 或 `medium` | 先读后改，遇到分歧再升高 |
| 需求拆分、锁顺序、并发、数据迁移 | `high` | 保留完整推理 |
| 独立审查、最终验收、风险决策 | `high` | 不能为省时降级 |

不要通过提示词强行压短安全、权限或数据完整性判断。

## 4.2 P1：工作流层

### P1-1：大输出落盘，摘要进入上下文（已实施：规则层）

建议规则：

- 工具输出预计超过 8KB 时落盘；
- 上下文只保留：命令、退出码、通过数量、失败摘要、证据路径；
- 原始输出保留在证据目录，不丢失可追溯性；
- 测试输出至少保留失败测试名和明确通过计数；
- 不用 `tail` 在源头截断到无法判断全局结果的片段。

`context-mode` 已提供 `ctx_execute`、`ctx_execute_file` 和索引能力，优先复用现有工具，不新增自定义日志服务。

### P1-2：按上下文和轮次切会话

建议实验门槛：

- 上下文超过约 150,000 token；或
- 连续约 60 个模型轮次；或
- 同一阶段出现两个超过 5 分钟的模型轮次；或
- 阶段目标已经完成，下一阶段需要读取完全不同的文件集合。

触发后：

1. 先更新 handoff；
2. 写明实际已完成、未完成、证据和下一动作；
3. 新会话只读取 handoff、当前状态和必要文件；
4. 不把整段旧会话原样带入新会话。

这不是把任务切碎，而是把上下文缓存边界前移。

### P1-3：连续错误熔断

建议规则：

- 连续两次工具或模型错误后停止原方法；
- 先判断错误类型：路径、读取状态、编辑冲突、测试失败、网关错误；
- 换方法而不是原样重复调用；
- 若错误来自网关或空响应，保存当前事实，换模型或新会话；
- 若错误来自文件状态，重新读取后再编辑；
- 连续五次同类错误不得继续自动重试。

## 4.3 P2：网关层

### P2-1：延迟探针

写一个最小探针，逐步增加上下文大小，记录：

- 请求时间；
- 首 token 等待时间（TTFT，模型开始返回第一个 token 前的等待时间）；
- 完成时间；
- 输入 token、缓存读取 token；
- 输出 token；
- HTTP 状态、错误和空响应；
- 是否重复请求；
- 任务时间段和模型标识。

探针只测获授权的网关和模型，不发起大规模压力测试。

建议至少覆盖：

```text
32K、64K、128K、160K、220K、320K token
```

每个规模至少做多次重复，区分：

- 首次请求；
- 短间隔重复请求；
- 较长间隔后请求；
- 改变少量尾部内容后的请求。

### P2-2：分流策略

只有探针确认网关在大上下文下持续退化后，才评估：

- 机械轮分流到本地模型；
- 大任务错峰执行；
- 更换网关；
- 将长任务拆成更短会话。

更换供应商、购买服务或对外发布前，必须单独确认授权；本方案不授权这些动作。

## 5. 实施顺序

### 阶段一：固定基线

只读收集：

- 当前生效模型配置；
- 当前压缩相关参数；
- 会话日志统计脚本；
- 模型轮次、上下文、缓存读取、工具耗时和错误分类；
- 一条固定、可重复的代表性任务。

输出基线报告，固定统计口径。

### 阶段二：只改一项配置做 P0 实验

先只调整压缩阈值，其他变量不变。完成同一代表性任务，比较：

- 墙钟时间；
- 模型时间；
- 最大上下文；
- 长轮次数量；
- 工具调用数；
- 错误数量；
- 质量和验收结果。

### 阶段三：加工具合并和思考分级

在同一任务类型上，保持配置不变，单独观察工作流变化。不能把多个优化同时上线后再声称某一项有效。

### 阶段四：加入大输出和 handoff 规则

使用一项真实但可回退的长任务，观察上下文峰值、handoff 次数、恢复正确性和是否重复劳动。

### 阶段五：运行网关探针

用探针验证缓存 miss、上下文长度和空响应假设。没有探针证据时，保留“高概率解释”，不升级为根因定论。

## 6. 风险与回退

| 风险 | 处理 |
|---|---|
| 压缩过早，丢失关键上下文 | handoff 保留关键状态；对照验收；必要时提高阈值 |
| 工具调用合并导致依赖错误 | 只合并纯读取；任何共享写入保持串行 |
| 思考级别降低导致判断质量下降 | 高风险任务固定使用 high；比较验收质量而非只看时间 |
| 大输出只保留摘要导致漏读失败 | 原始输出落盘；摘要必须包含失败名、退出码和通过数 |
| 过早 handoff 造成重复读取 | handoff 写最小恢复事实；新会话只补必要文件 |
| 错误熔断过于激进 | 保存当前状态，允许人工按证据恢复，不自动丢弃工作 |
| 改全局配置影响其他项目 | 先备份、记录范围、隔离验证，确认回退命令 |
| 网关探针增加费用或触发限流 | 小样本、低频、先确认费用与授权 |

## 7. 不做的优化

- 不把 `Bash` 改成更快的 shell 当主方案。
- 不一味减少读取和测试。
- 不用更短的回答掩盖未验证状态。
- 不把模型轮次少等同于任务完成快。
- 不通过跳过独立审查、压缩验收或减少证据来换提速。
- 不把“缓存 miss”写成没有请求日志支持的确定事实。

# x-rail 0.0.10 最小闭环改进方案

> 状态：待实施方案。本文只定义改进范围和验收，不修改实现。  
> 依据：[近三日运行分析](./近三日运行分析.md)、`plans/v3/02-pstack对比与借鉴.md`、`plans/v3/03-技术方案.md`、`plans/v3/04-模型降级与续跑.md`、`plans/0.0.7/README.md`、`plans/0.0.7/优化方案.md`、`plans/0.0.7/DECISIONS.md`。

## 本次修订关系

具体接口与验收以 [实施计划与影响评估](./实施计划与影响评估.md) 为准。本版把原阶段四中的完成门并入核心闭环，预算 70% 自动收尾独立启用。旧格式运行只读交接，不自动续跑；显式补验收后才能按新标准恢复。放弃后的下游依赖必须改接到替代项，仍等待替代项完成验证；不把 abandoned 当成 done。

## 结论

**已按推荐选了“最小可验证闭环”，因为当前主要短板是运行状态与宿主行为缺少端到端证据，不是缺少更多流程规则。**

目标不是重写 x-rail，也不是追求更多并发，而是证明：每个长任务都有唯一持久状态；错误按类型采取有界恢复；恢复不会丢约束或重复已验证工作；预算触发时能停止扩张并交付已验证部分；只有完成判据全部满足才报完成。

## 目标与非目标

### 目标

1. 将一个真实任务、运行状态、验证证据和恢复记录用同一 RUN 标识关联。
2. 建立可审计的错误分类、恢复动作、次数上限和暂停/交接条件。
3. 通过压缩/中断故障注入，证明系统从持久状态恢复并复用已完成单元。
4. 通过预算阈值场景，证明运行能停止新增派发并进入收尾。
5. 用真实 Pi 宿主生命周期验收，不以 mock、类型检查或脚本通过替代。

### 非目标

- 不重写 x-rail、PStack 式工具链或阶段卡。
- 不为了展示能力扩大子代理并行度。
- 不以扩大样本或推算总体提速作为本期门槛；先建立可复现的运行记录。
- 不自动执行生产发布、付费模型回放或仓库外配置变更。这些需要单独授权。
- 不把 0.0.7 历史审查的所有条目重新打开；先核验哪些根因仍影响目标闭环。

## 不变量

- **单一运行身份**：调度、验证、模型切换、子代理、恢复、暂停与完成事件均引用当前 RUN。
- **状态可重建**：模型上下文不是状态真相源；重启或压缩后可从运行文件确定当前单元和下一步。
- **完成有证据**：Done 判据、验证命令及结果与当前工作版本对应；判据变化使旧验证失效。
- **恢复有界**：每个错误类别有明确动作和上限；超过上限就暂停并交接，不无限循环。
- **单写入者**：每个可写文件集只允许一个执行者；多代理修改必须通过独立工作区并由主控合并。

## 实施顺序

### 阶段一：打通 RUN 与账本关联

#### 范围

- 每个符合长任务条件的执行创建唯一 RUN，并保存目标、范围、完成判据、验证方式、预算/时间盒、禁止事项和当前工作区/版本指针。
- 单元清单记录依赖、状态、负责人、验收条件；验证账本记录命令、退出结果、时间、工作版本和关联单元。
- 所有运行事件引用 RUN 标识。提示用户切换、错误交接和恢复时使用真实指针，不出现通用占位符。
- 先复核 0.0.7 已指出的状态写入和完成证据根因，只修复与本闭环直接相关的部分。

#### 验收

- 建立一个多单元任务后，RUN、单元、验证和事件能互相追溯。
- 在新会话中只读运行状态文件，能确定未完成单元、下一步和已验证单元；不依赖旧对话摘要。
- 并发写入压力测试不会丢失单元状态或破坏账本；路径边界拒绝写到仓库外。
- 正常回答、子代理通知和工具输出不能误写为任务状态。

### 阶段二：错误分类与有界恢复

#### 范围

- 将真实宿主错误映射到少量可执行类别，例如可重试网络错误、不可重试鉴权/余额错误、流中断、工具/验证错误、上下文/容量错误、未知错误。
- 每类按主计划 4.4 的逐条映射规定动作：账号池/网关保留切换，瞬时服务错误保留一次同模型重试，鉴权/余额停止；每种自动恢复均有明确次数上限。子代理重派另受原运行终态核对约束。
- 恢复动作记录原错误、分类依据、尝试次数、所用模型/代理和结果，并与 RUN 关联。
- 未确认的错误不做宽泛自动重试，进入有信息的暂停/交接状态。

#### 验收

- 对每种类别分别注入可复现错误，Pi 宿主事件触发的动作与策略一致。
- 对“不应重试”的鉴权/余额错误，断言不会重复请求或切换造成额外调用。
- 对已观测的 503、`service temporarily unavailable`、`Stream ended without finish_reason` 分别验证续跑或明确暂停；不将其混成一个成功案例。
- 达到上限后不再产生新重试，状态保留可继续操作的 RUN 指针和交接摘要。

### 阶段三：中断/压缩恢复与阶段成果复用

#### 范围

- 恢复流程先读取 RUN 与账本，再决定继续现有单元、重新派发或请求用户决策。
- 只复用与当前工作版本和当前验收条件匹配的 VERIFIED 结果；验证条件或代码版本变化后要求重新验证。
- 每个已验证单元留下短检查点，包含产物、证据、剩余风险和下一步。
- 子代理超时/失败先查询原宿主运行：仍活跃只续接原运行，已终止才接收已有成果并重规划剩余范围，状态未知保持阻塞和占用。不默认新建代理；查询状态本身不得触发执行。

#### 验收

- 在两个单元已验证、一个单元进行中时注入会话中断或压缩，重新启动后能从账本恢复。
- 已完成单元不重复执行；未完成单元不会被误标完成；变化过的验证命令使旧证据失效。
- 恢复后能指出复用与重做的单元，并有日志可计算重复工作量。
- 压缩胶囊/摘要只携带 RUN 指针与下一步，权威状态仍可从磁盘读取。

### 阶段四：预算收尾与完成门

#### 范围

- 将时间/成本预算记录在 RUN；预算约 70% 时进入 Landing：停止非必要的新派发，优先验证、合并、记录已完成成果和剩余事项。
- 用户明确取消某类预算限制时遵从该任务的授权，不把默认预算升级成不可覆盖的硬限制。
- 最终完成检查只比较可核验 Done 判据及其有效证据，不以文件指纹、代理状态或模型自述替代。

#### 验收

- 故障注入预算阈值后，系统停止新增非必要工作，并在记录中标注已验证交付与未完成项。
- 修改 Done 判据或验证命令后，旧证据不能使任务通过。
- 所有判据满足且证据对应当前版本时才可标为完成；否则只能继续、暂停或交接。
- Landing 路径能在剩余预算内生成可读交接，不要求把未完成任务伪装成完成。

## 验证矩阵

| 层级 | 验证内容 | 能证明什么 | 不能替代什么 |
| --- | --- | --- | --- |
| 单元/脚本测试 | 状态转换、路径校验、错误分类、次数上限、判据变更 | 纯逻辑符合预期 | Pi 实际加载与生命周期事件 |
| 扩展集成测试 | 真实事件顺序、模型切换、错误后续跑/暂停 | 扩展与宿主接口相容 | 长任务跨压缩恢复 |
| Pi 端到端故障注入 | 503、流中断、工具错误、压缩/中断、预算阈值 | 运行闭环在宿主中的真实行为 | 生产环境稳定性与总体效率 |
| 小规模真实任务观察 | RUN 覆盖、人工续接、恢复重做、完成证据 | 实际使用摩擦与基线 | 统计显著的总体提速结论 |

## 运行指标

先记录事实，再决定目标阈值；不从当前小样本倒推总体指标。

- **RUN 覆盖率**：符合长任务口径且创建有效 RUN 的运行数 / 符合口径运行数。
- **账本闭合率**：完成的单元中有当前版本有效验证记录的比例。
- **自动恢复率**：各错误类别中无需人工继续即可恢复到有效产物或验证活动的比例；只有发消息不算成功。明确暂停单列为安全暂停率，不混进恢复成功。
- **人工续接率**：错误/中断后需要用户发消息继续的运行比例。
- **恢复复用率**：恢复后正确复用的有效已验证单元数 / 中断前有效已验证单元数。
- **重复工作量**：恢复后重做的验证/单元数，区分因版本变化必须重做与无效重复。
- **预算收尾率**：达到预算阈值的运行中按策略进入 Landing 并形成交接的比例。
- **完成证据率**：标记完成的运行中，所有 Done 判据均有关联有效证据的比例。
- 同时记录各阶段墙钟、模型等待、工具时间和人工等待；在没有可靠遥测前不宣称净提速或节省费用。

## 风险与边界

- Pi 扩展事件顺序、子进程是否加载扩展、`pi-subagents` 配置实际值需在目标运行环境核实；mock 通过不够。
- 错误分类过宽会造成无效重试或跨模型重复成本；未知错误默认暂停。
- 账本设计若再次演变为整文件读改写，可能丢更新；优先单写入者并验证原子写入/并发边界。
- RUN 机制不能反过来强制所有短问答进入编排；按交付复杂度决定是否创建运行。
- 预算阈值、并行上限和错误策略应在运行前可见，并尊重用户针对单次任务给出的明确约束。

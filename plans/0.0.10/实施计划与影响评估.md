## 1. 建议如何选

**推荐：保留原方案的四个目标，但不要一次性开启全部自动化。先做运行绑定、完成门和故障恢复；预算收尾作为可独立启用的后一批。**

像前端表单一样：先保证数据和校验一致，再增加自动提交。否则自动化越积极，错误状态越容易被放大。

| 选择 | 包含内容 | 收益 | 代价与限制 | 推荐程度 |
| --- | --- | --- | --- | --- |
| 只补测试与记录 | 基线、运行事件、反例测试，不改恢复或完成行为 | 先知道真实缺口 | 已确认的错误完成判断继续存在；不能称“闭环改好” | 不建议作为最终交付 |
| **核心闭环** | 运行绑定、运行级验收、错误恢复、压缩恢复、真实 Pi 本地模拟验收 | 减少误报完成、人工续接和错误恢复 | 增加运行级验收记录；不保证模型更快；需要多个回归场景 | **推荐先执行** |
| 全部改进 | 核心闭环 + 显式墙钟预算、预算收尾、运行统计 | 长任务可预留收尾时间 | 增加暂停/收尾策略；不能凭本地日志精确限制真实费用 | 可执行，但预算功能独立启用 |

这里的核心闭环不是缩水版：持久状态、可计算的待办集合、版本绑定验证、失败分类、审查和恢复仍按 PStack 原则保留。暂缓的是未经证实的**自动计费控制**与**未经查询的子代理重派**，不是回避长期编排能力。

### 本次的关键修正

1. 原方案把多项已有能力当成待建设目标；当前已有锁、原子写、胶囊、分类和切换，应复用而非重写。
2. “自动恢复成功”和“安全暂停”必须分开统计；明确暂停不是恢复成功。
3. 当前运行级完成判断确实过宽，不只是缺少日志。需要新增明确的验收关联，而非只改提示词。
4. “格式完全不变”和“可计算运行级完成判据”不能同时保证。推荐新增一个小型验收表，保留旧表可读，不批量迁移历史任务。
5. 原方案要求失败后默认新建子代理，和当前查询原运行、保留占用范围的规则冲突。保留现行安全规则，不默认重派。
6. 改仓库不等于对个人环境没有影响：当前安装的技能是指向此工作区的软链接。实施必须隔离。

### 3.2 将产生的运行材料

继续使用 `.work-docs/runs/<运行标识>/`。保留现有 RUN、units、ledger、events、capsule、gates；核心新增或保存的材料如下：

- `acceptance.tsv`：验收关联表，像表单里“某项需求由哪些字段校验负责”。列为 `id`、`statement`、`source`、`units`：要求标识、要求原文、可核对的需求来源、负责证明它的单元。
- `finish.json`：运行通过验收的收据，记录验收表摘要、相关文件/命令摘要与证据路径。它是可重新计算的结果，不是另一份可手改状态。
- 每次验证独立的 `notes/verify-<单元>-<唯一值>.log`：新验证不覆盖旧日志；账本引用对应文件。

不增加数据库、后台进程、网络遥测或新依赖。新 init/import 在 RUN 写 `format_version: 2` 并建带 source 列的空验收表，空表表示等待计划，不是 legacy；首批单元和验收就绪前 automation_allowed=false。旧 run 不自动写新字段；第一次明确采用新验收命令时才创建新表并标注新格式、phase=paused，补齐后显式 resume。旧记录只读查看和交接，不能被猜成已满足机器验收；新格式标记存在而验收表缺失/损坏是 invalid，不能降级成 legacy。

### 3.3 必须公开的行为变化

- **结束更严格**：所有单元 done 不再自动等于整个任务完成；失效验证、未审查或没有完成证据时明确交接。
- **放弃不是完成**：`cap` 只是拆分原因。必须把原验收关联到后继单元，并在后继单元验证后才能完成。删除原需求属于范围变化，仍需用户同意。
- **余额/鉴权更保守**：推荐停止，不继续调用备用模型。相较当前代码，这是有意的策略变化；如果用户选择保留自动切换，就不能再承诺该错误后不新增请求。
- **模型选择不扩大**：保留现有主/备用模型，不增第三模型、不提高请求/续跑上限。切换只能发生在已授权的策略内。
- **状态归属更严格**：同目录 ACTIVE 改变不会让旧会话抢跑新任务。新任务须显式绑定。
- **验证有少量额外开销**：运行边界会读取当前文件摘要并启动本地 `xr inspect`；具体耗时需测，不承诺总体提速。

## 4. 核心技术规格：执行者不用再猜接口

本节是拟实施接口，不是当前可用命令。实施阶段按测试先行完成，不在评估稿中复制整套生产代码。

### 4.1 一个权威检查器

扩展不再手工解析 TSV（制表符分隔表，即用制表符分列的小表）并按状态猜完成；复用 Python 侧 `verified_now`、文件范围和账本逻辑。

新增命令：

```text
xr --repo <绝对工作目录> --run-id <运行标识> inspect --json
xr --repo <绝对工作目录> --run-id <运行标识> acceptance set A1 "这项需求的原文" --source <需求证据引用> --units unit-a,unit-b
xr --repo <绝对工作目录> --run-id <运行标识> finish
xr --repo <绝对工作目录> --run-id <运行标识> pause --reason "准确原因" --record "错误或宿主结果引用"
xr --repo <绝对工作目录> --run-id <运行标识> resume --confirm --record <原运行状态与授权依据>
xr --repo <绝对工作目录> --run-id <运行标识> plan replace <已放弃单元> --with <替代单元列表> --record <拆分依据> --confirm
```

所有运行级命令（包括现有 next、verify、done、fail、reopen、close、status、capsule 和拟议预算命令）统一支持显式 `--run-id`。扩展与代理任务包必须同时传入固定的 `--repo` 和 `--run-id`；省略运行标识的人工交互才可使用 ACTIVE。解析后的目录必须是该工作目录 `.work-docs/runs/` 下的直接子目录，拒绝绝对运行标识、路径穿越及逃逸的软链接；校验 RUN 标识与请求一致。显式目标无效直接报错，不回退 ACTIVE。读取旧绑定不改变 ACTIVE；写入旧绑定还须满足会话归属、占用与阶段检查；close 只条件释放指向自己的 ACTIVE，不触碰另一运行的指针。

参数解析在 `main()` 统一处理：沿用剥离 `--repo` 的方式，同时剥离 `--run-id`，支持子命令前后两种位置；重复参数、缺值和不适用命令报错，不能静默取最后一个。`init/import` 创建新运行，不接受 `--run-id` 选择旧目标；`cmd_import` 与 init 使用同一个活动指针保护入口，导入失败不得抢占 ACTIVE。

- `inspect`：严格只读，成功时退出 0，返回 `schema_version`、`mode`（legacy/managed，旧格式/新验收格式）、`run_id`、`phase`、`automation_allowed`、`acceptance_status`、`done_met`、`ready`、`doing`、`blocked`、`stale_units`、`reasons`。空单元、无验收关联、坏表、丢失日志、过期输入、未处置放弃都不能给 `done_met=true`。文件读取失败属于检查失败，与“尚未完成”区分。
- `acceptance set`：在原运行锁内保存/更新验收关联并追加事件；拒绝空要求、未知单元和循环依赖。`source` 必填，允许固定任务文件路径+内容摘要，或保存的用户消息/宿主会话条目引用+摘要；finish 要求来源可读取、摘要一致，不能仅填任意非空字符串。需求关联修订会使旧 finish 收据失效。首次建表须把 RUN 中完整要求逐项对照并记录；不能只录入容易通过的要求。已有要求的删除/收窄需引用用户授权。来源引用只提供可追溯性，不自动证明语义正确。
- `finish`：在同一检查路径上验证所有要求均有可核对来源、对应完成单元、有效文件/命令摘要及可读取证据，且没有未核对的宿主运行或开放的必需决策门；通过才写 finish 收据并标记运行完成。高风险标记保存在 RUN 的 `review_required`，须关联独立审查验收单元，其负责人会话不同于实现者，报告/状态收据和当前变更摘要有效；不能由实现者用 `true` 替代独立报告。所有运行须有最终集成验证单元。失败退出 2，保留原状态与证据。成功只在 ACTIVE 仍指向自己时释放它，不删除其他任务指针。
- `pause`：在 RUN.md 增加可选运行阶段字段与暂停原因，追加事件并更新 capsule，停止本运行的自动续跑，不删除 ACTIVE 或历史材料。旧 RUN 没有阶段字段时解释为未完成，不能猜为 finished。恢复须显式核对绑定、证据和原宿主状态，再将运行阶段改回执行；仅查看状态不得恢复运行。
- `resume`：显式确认本次运行目标、用户中止/权限门约束、原宿主状态、证据新鲜度和工作区占用；仅把 phase 从 paused（或明确要重新开启的 finished/closed）改为 executing，使原 finish 失效并记录原因，不启动模型、不重派子代理、不解除决策门、不把单元从 blocked 自动改 doing。存在未知宿主或冲突时保留暂停；有仍活跃宿主只能关联原运行，不创建第二写入者。旧格式须先明确建立验收关联，不能以 resume 绕过 legacy 交接。ACTIVE 为空可重新绑定；指向另一执行中运行时拒绝抢占。
- 当前 `close`：保留安全关闭用途，但未有有效 finish 收据时标为“暂停/关闭，未证明完成”，不能冒充完成；活动指针仅在它仍指向本运行时释放。

**旧格式兼容采用明确交接：** 没有新格式标记、没有 acceptance 表且尚未采用新验收的旧运行返回 `mode=legacy`、`automation_allowed=false`、`done_met=false`，保留原单元终结统计供人工查看；守护器先检查此模式，直接本地通知交接，不能进入续跑/无进展计数路径，也不自动写 pause。旧单元全 done、仍有 todo/doing、只含 abandoned 三种都不自动发模型请求。已有表却损坏/缺来源是 invalid，不回退 legacy。用户明确接入时，通过 acceptance 命令补齐完整要求与来源，再 resume；这是逐个显式接入，不是批量迁移。

`done` 的幂等要求也改变：已 done 时仍复查当前有效证据；证据过期应拒绝，不再无条件返回 unchanged。错误给出显式目标的 `xr verify <id>`，成功后再 `xr done <id>`；首次 verify 无状态限制可复用，不要求为重验释放原写入占用。`next` 检查依赖单元的有效证据，不仅看 done 状态。

**拆分不放宽依赖：** 保留“依赖单元 done 且证据有效”规则，不把 abandoned 视为已完成。新增 `plan replace` 在同一个运行锁内：核对原单元 abandoned、原宿主确已终止、替代单元已存在且非活跃；替代单元继承原前置依赖，不能依赖原 abandoned；将尚未启动的直接下游依赖从原单元改接到全部替代单元，同时迁移验收关联并保存变更前后记录。检测循环、自引用、未知单元及已启动下游，任何一项不满足则整体拒绝，不改一半。替代项未完成，下游不得 ready；验收只是交给替代项负责，仍需全部验证，不能据“已接管”立即放行。无可派发项又无活跃/可等待工作时交接说明依赖阻塞，不空转到 stall。

`inspect.done_met` 表示新验收格式的当前判据已经满足，不要求先存在 finish 收据，以免 finish 与 inspect 互相等待；最终报告“运行完成”还须成功执行 finish 并取得有效收据。守护器新增本地 notify 决策，达到判据后停止自动继续，按契约摘要只提示一次执行带显式目标的 finish，不触发模型回合；已暂停/legacy 运行不被该提示重新启动。

绑定信息追加到现有 `guard.json`，运行阶段保存在 RUN.md；两者分别负责会话归属和运行状态，不再新增第三份可修改调度状态。宿主运行状态不能由 Python 凭单元表推断，必须引用下述查询收据；无法取得可核查终态收据时 finish 拒绝完成。

**宿主收据的来源与核对：**

- 宿主开发接口已在锁定版本类型声明中确认有 `tool_call`（调用前）与 `tool_result`（调用结果）事件，二者都有 `toolCallId`，前者可阻止调用；不等于已确认子代理结果字段。适配器在 tool_call 先登记派发意图，在 tool_result 配对确认实际启动的 host_run_id，状态查询结果也从 tool_result 捕获。调用前事件可能被其他处理器阻止，不能单凭它当启动成功；只有可核对的阻止/启动前失败结果且没有部分启动，才解除该意图。并行/工作流部分成功须展开并核对所有子运行；调用后缺结果、结果解析失败或进程中断均为未解决意图，阻止 finish。嵌套调用使用 parentToolCallId 对齐；宿主内部未暴露的启动不得声称可追踪。
- 启动收据及查询收据分别保存为现有 `notes/` 下的唯一文件。字段包括 schema、workspace、run_id、unit_id、host_run_id、宿主工具名/调用标识、查询时间、状态、原始结果引用与内容摘要；状态只归一为 active、completed、terminated、unknown。摘要用于检测证据变化，不构成防恶意篡改的安全认证。
- 适配器把引用追加到现有事件流；`inspect` 在运行锁内核对启动清单和查询证据的一一对应、原始结果摘要、目标绑定、状态转换与工具来源。工具返回字段与版本的解析规则需用实际宿主结果固定，不能只靠手工 JSON 样例。运行开始时保存捕获能力/工具清单：未安装子代理工具且整个受控会话无派发能力，或完整捕获区间内已安装但从未调用，才允许空启动清单；中途启用、重启丢区间或导入历史不能据空表推断没有子代理，须补查记录，否则交接。
- active、unknown、缺失、错绑定或摘要不符均不能 finish；completed/terminated 只是宿主已停止，仍需接收产物、处置失败和验证验收。终态运行标识不可复用。采用 `dispatch_epoch`（派发代号，像表单每次编辑后增加的版本号）：在已有 events 中为每次启动/续接意图递增，先在短运行锁内落盘，再放行工具；不跨异步子代理生命周期持锁。finish 在同一短锁内确认所有意图已配对/解决、终态收据齐全和代号一致后写 finish 收据，记录代号与契约摘要；finished/paused 时工具前置处理器阻止新派发。若新派发意图先获得锁，finish 拒绝；finish 先获得锁，调用被拒绝。显式恢复后新代号使旧 finish 失效。已有事件流损坏/缺失代号则检查失败，不另建一个可漂移的计数文件；无法约束的宿主外派发不在自动完成保证内。
- 验收覆盖真实宿主查询结果的采集与解析，以及缺失、活跃、已终止、未知、错任务、证据改变、终态后新增派发。没有可验证适配器时只能手动交接，不能给自动 finish 放行。

**能力边界**：程序可以检查验收覆盖和证据新鲜度，不能自动判断自然语言需求是否被一个 `true` 命令真实证明。计划/审查必须审阅验证命令是否验证了要求；命令退出 0 仍不单独等于需求满足。

### 4.2 完成判据与版本关系

- 验收表 + 当前单元定义形成契约摘要；范围/命令/关联变化使 finish 收据失效。
- 文件新鲜度沿现有 scope/output_scope 摘要计算。不因为换会话或无关文件改变就一律重测；相关代码、测试、依赖配置必须列进单元输入范围。
- 多单元合并后在最终集成树执行一次明确的最终验证单元；不是把各个分支上的通过结果直接相加。
- 缺失旧日志的 ledger 只能查看，不能作为新完成证明；先实际重验。保留历史事实，不改写它当年的结论。
- 正常运行边界异步计算 inspect；自动边界检查初始时限 5 秒，超时终止并回收检查子进程，明确交接，不排队重复检查、不回退旧快照。capsule 刷新同样改异步且有 5 秒初始时限；压缩必须继续时保留真实路径与失败说明，不能宣称便签已刷新。显式人工 inspect/capsule 同样支持 `--timeout-ms` 正整数毫秒，默认 5000；Python 检查器核对截止时间，扩展另设外层进程超时。5 秒是初始策略值，须报告实际耗时分布，不能据此宣称性能通过。
- 进度指纹包含有效单元定义/状态、有效 ledger 证据、acceptance 的内容/来源/关联和 RUN 的语义 phase；不纳入普通事件时间戳、重复查询、累计计数或胶囊生成时间。单改验收或阶段算变化；重复写相同内容、仅更新 updated 不算进展。指纹变化不能自动清零故障切换总上限。

### 4.3 运行绑定与事件

绑定单位不是只有一个短 run id，而是 `workspace`（绝对工作目录）+ `run_id` + `session_id`（宿主会话标识）。

- `xr init/import` 在仓库级活动指针锁内检查旧 ACTIVE：executing 或 legacy 未明确交接时拒绝覆盖；paused/finished/closed 可创建新运行，记录 old_run/new_run/reason 的指针释放/接管事件到原有事件流，不新增 pointer.released 文件。paused 但仍有活跃或未知宿主时仍拒绝释放；不能以暂停掩盖冲突写入者。新运行材料准备成功后再条件切指针，失败保留旧值。finish 成功条件释放自身 ACTIVE；pause 本身保留指针，resume 和 init 接管规则见第 4.1 节。
- 会话首次确认本次运行后固定绑定。ACTIVE 改变时仅提示冲突，不自动重绑定；需要显式 `/x-run bind <id>`，该命令只绑定，不启动模型回合。
- 主会话绑定中保存 `owner_session_id=ctx.sessionManager.getSessionId()`；只有该会话可写主控 guard 续跑计数。旧 owner 不同的会话只读提示，接管须核实原 owner 已停止并显式绑定；未知则不抢占。不能仅靠 X_RAIL_SUBAGENT 环境变量识别角色。
- store 的会话计数使用 canonical workspace/run_id/session_id 组合键：工具调用进展只更新发出它的会话，不给父会话添加工具进展；运行级切换/续跑总次数继续按 workspace/run 聚合，并在锁内更新，防止换会话绕过上限。已知子代理不启用主控自动续跑；子代理自身错误仍受分配策略和统一运行总上限约束。主控重复通知按 toolCallId/host_run_id 去重；原有以 run_id 为键的计数作为历史下限保留，不能迁移后清零。
- Python 与扩展事件统一携带可取得的 `schema, ts, event_id, workspace, run_id, session_id, unit_id, host_run_id, model, type, action, reason`；不适用字段为 null，不编造。
- 原始完整错误保存在本地受限证据中；事件保存截断/脱敏摘要与引用，不记录令牌、密钥或完整环境变量。
- 事件不复制一份可修改单元状态；当前调度从单元、验收、账本和明确暂停状态重建。派发意图及其代号以已核对事件为事实来源，只用于判断是否仍有未核实运行及 finish 版本是否失效，不凭事件里的模型描述改任务状态。

### 4.4 两种失败不能混为一谈

**准确映射表：** E1–E5 是现有错误编号，下表保留编号并增加 `reason` 子原因和明确动作；不整体改写 E1，也不从编号推断所有错误动作相同。优先级：已确认用户中止 → 明确鉴权/余额 → 其他匹配；只有实际错误回合或真实状态码可分类。401/403 与账号池提示同时出现时停止，不能因前者被后者覆盖而发新请求。

| 现有模式或新增样本 | 拟分类/子原因 | 主模型动作 | 已在备用模型的动作 |
| --- | --- | --- | --- |
| `账号池暂无可用账号` | E1 / pool_unavailable | 按现有上限切备用 | 停止交接 |
| `gateway_concurrency_limit` | E1 / gateway_pressure | 按现有上限切备用 | 停止交接 |
| `Server requested <数字>s retry delay (max: 80s)` | E1 / excessive_retry_delay | 按现有上限切备用，不等长延迟 | 停止交接 |
| `INSUFFICIENT_BALANCE` | E1 / balance | 停止，不重试不切换 | 同左 |
| `insufficient_quota` | E1 / quota | 停止，不重试不切换；不能猜是瞬时限流 | 同左 |
| 单词 `billing`，忽略大小写 | E1 / billing_unclear | 保守停止；泛词不能证明具体余额原因 | 同左 |
| `HTTP 401`、`HTTP 403`、`status 401/403`、真实 status=401/403 | E1 / auth | 停止，不重试不切换 | 同左 |
| `The service is temporarily unavailable`、`The service is busy`、`Upstream stream ended prematurely`、`stream disconnected`、`upstream_error` | E2 / transient_service | 同模型最多一次，之后按既有上限切备用 | 同模型最多一次，再失败交接 |
| 新增准确串 `Stream ended without finish_reason` | E2 / stream_interrupted | 同上一行 | 同上一行 |
| `Request timed out`、`HTTP 524`、`terminated`、`Connection error`、`ECONNRESET`、`socket hang up` | E3 / transport | 保留现有立即切备用 | 最多同模型一次，再失败交接 |
| 新增真实 status=502、`HTTP 502`、`502 Bad Gateway` | E3 / bad_gateway | 保留网络故障立即切备用策略 | 最多同模型一次，再失败交接 |
| `unknown variant 'developer'`、422、`bad request`、其余 4xx | E4 / request_incompatible | 保留现有一次切备用与总上限 | 停止交接；未知4xx不可当成瞬时限流 |
| 仅裸 503、未匹配上面模式的错误 | unknown / unclassified | 明确暂停；先保存样本，不编造账号池归因 | 同左 |
| 看门狗已确认触发 | E5 / watchdog | 复用相同上限后切备用 | 保留现有最多同模型一次，之后交接 |
| 用户主动 aborted | E0 / user_abort | 停止自动动作 | 同左 |
| 正常回答，无错误 | none | 不进入故障动作 | 同左 |

E2 同模型重试沿用当前等待常量；E1 pool/gateway、E3、E4、E5 不统一改成“先同模型一次”。重试额度按错误链和运行总上限核对，内置重试与扩展重试需分别记录。未知错误不得伪装成正常 none。每个模式逐条测试，并覆盖混合错误、大小写、正常正文引用和主/备用两侧。

| 失败来源 | 推荐动作 | 不能做什么 |
| --- | --- | --- |
| 主会话模型服务瞬时不可用、断流 | E2 同模型一次；E1/E3 等按上表不同策略处理；准确记录错误链 | 不增加次数，不把工具业务失败当成提供商错误 |
| HTTP 502（网关异常）、超时 | 按当前已授权网络故障策略处理，保证看门狗路径也走同一上限检查 | 不仅凭正常回答里包含“502”就触发 |
| 401/403、余额/额度 | 推荐停止并写交接；是否另选模型是明确授权策略 | 不默认用新请求验证余额是否恢复 |
| 未知模型错误 | 明确暂停，保留准确错误与下一步 | 不与正常完成的 none 类别混用后静默结束 |
| 用户主动中止 | 停止自动动作 | 不用看门狗恢复把它重新启动 |
| 子代理/工作流基础设施失败 | 查询原宿主运行；活跃则按宿主允许方式续接，已终止才收集结果、重规划剩余项，状态未知则保留阻塞与写入占用 | 不自动重派，不绕过宿主换 CLI，不释放未确认终止的写入范围 |
| 实现或验证失败 | 保存证据，修复/重规划后再验证 | 不把重复运行同一失败验证当作修复，不自动换模型掩盖业务失败 |

看门狗不是新的一套重试器。`agent_settled`（宿主确认本轮结束事件）上的恢复回调必须使用与普通错误相同的开关、绑定、计数和决策应用函数。设置模型成功才写成功事件；没有备用认证、超过上限或关闭自动恢复时写明确暂停。

错误链计数不能简单地因为一次工具输出就全部清零；需测试“连续错误”“成功恢复后新错误”“压缩后同一错误链”三个边界。用户在某次任务给出的更严格次数限制优先，不能改成全局放宽。

### 4.5 压缩和跨会话恢复

- 保留 2 KB capsule（恢复便签）设计，便签只保存目标、运行/证据路径、当前单元和下一步；完整约束留在 RUN 和决策记录。
- 刷新失败时记录错误，不用旧便签声称恢复正确；压缩后读取绑定运行并重新 inspect。
- 示例验收：两个已验证单元 + 一个未完成单元，中断后准确恢复；不重复已验证且输入未变的单元；相关输入变化时标为 stale（证据过期）并要求重新验证。
- 不从 doing 状态推出子代理已死或应重派。宿主状态未核对前保持原运行和范围占用。

## 6. 预算收尾：如果要全做，具体怎么做

这是可独立选择的后续单元。目标是为收尾留时间，不是新增“到时杀进程”。

### 推荐策略

- 只限制**显式设置**的运行墙钟时长；没有设置就不启用自动预算。默认不设金额预算，不读账单，不上传用量。
- 新增 `xr budget set --wall-minutes N` 和 `xr budget disable --reason ...`；预算从显式启用时开始，暂停不计时，恢复后继续累计。保存到可选 `budget.json`，历史 run 缺文件等于关闭。
- 以实际单调时钟累计进程内时段，跨会话保存累计值；时间倒退、跨进程数据异常时暂停预算判断并报告，不凭异常时间强行关闭任务。
- 累计到 70% 进入 Landing（收尾阶段）：`xr next` 不再领取普通实现/研究单元；已运行的单元继续；验证、审查和交接仍允许。单元角色新增可选 `--landing` 标记，不靠标题猜。
- 收尾允许创建范围明确的安全修复/验证单元，但不扩大原需求。没有时间完成时交接，不能把部分交付说成全部完成。
- 到 100% 明确暂停新工作并交接，不强杀工具/子代理；宿主原有超时仍有效。
- 用户说“成本不限”只解除费用限制，不能被误读为“墙钟无限”；墙钟限制解除须明确记录。

### 文件与影响

修改 `scripts/xr`、`guard-core.ts`、`x-run-guard.ts`、`scripts/test-xr.py`、扩展测试和五张阶段卡，必要时同步 `modules/cost-policy.md`；不修改旧 task.py 的预算语义。

主要影响：长任务会更早拒绝新增普通工作，但当前工作和必要收尾不被预算强杀。暂缓本单元时，保留现有宿主超时与人工交接，**不能承诺自动 70% 收尾已落地**。

### 必过场景

关闭预算、阈值之前、恰好 70%、阈值之后、100%、暂停/恢复、时间异常、旧 run、显式豁免、正在验证、等待子代理、收尾缺陷修复。任一场景出现越权终止或错误完成，都不能启用。

### 7.3 指标口径

- RUN 覆盖率：应采用长任务运行机制的任务中，实际建立且绑定 RUN 的比例；分母人工按固定任务清单核对，不能靠日志缺失自动估计。
- 自动恢复成功率：错误后无需人工介入，恢复到产生有效产物/验证事件的比例。单纯发出续跑消息不算。
- 安全暂停率：明确达到上限/权限限制后保存状态并停止的比例；与恢复成功分开。
- 人工续接：等待用户发“继续”的事件数和时间，区分用户主动暂停。
- 恢复复用率：中断前有效完成单元，恢复后正确复用的比例；过期证据重验单独统计。
- 预算收尾：只有配置预算且触发阈值的运行才进入分母。
- 墙钟/模型等待/工具耗时仅在事件可测时计算；没有请求级遥测时保留未知，不把总时间都归因于模型。

| 执行范围膨胀 | 闭环修补变成全仓库重写 | 仅本清单接口与相关反例；旧体系不迁移，不重写整个脚本 | 停止额外项，记录后续建议；保留已验证部分 |

### 回退时的活动指针保护

启用前保存版本清单与 ACTIVE 的原始内容。回退先停新派发并核对所有活跃会话/子代理，保留暂停运行和指针；旧工具不理解新状态，只允许读取，不允许继续写新格式任务。若指针已被旧工具改掉，先读取原/现两个运行、占用记录和宿主状态，不能直接用备份覆盖。确认所有者与目标后，由匹配新格式的恢复工具在仓库级活动指针锁内比较当前值再恢复；发现并发变化则退出，保留现场。该恢复步骤必须有临时仓库测试；涉及真实指针覆盖，先说明影响并取得明确同意。回退不是授权清理新文件或重置运行数据。

### 工作量预估

以下是**工程工作量估计，不是 Agent 墙钟承诺**，尚无本项目同类任务测量支持：

- 核心闭环：约 4—7 个工程日等价量。运行验收/绑定约 1—2；恢复策略与事件约 1；真实宿主注入与压缩恢复约 1.5—3；文档、回归和审查约 0.5—1。
- 墙钟预算与收尾：另约 1—2 个工程日等价量。
- 最大不确定性是 SDK 真实生命周期注入和新旧运行兼容，不是补错误正则。若宿主不支持稳定注入，不用继续扩大测试框架，应报告受限场景。
- 不估算金额；不以本样本承诺提升百分比。真实费用验证、生产使用观察不在默认执行中。

核心单元一至四共享 `xr`、扩展与阶段卡，必须单写入者串行集成；只读测试设计/审查可并行。不要为增加并行而制造重叠写入。

## 9. 多维推演与验证结论

| 角度 | 本次依据 | 计划取舍 | 剩余未知 |
| --- | --- | --- | --- |
| 第一性原理/正确性 | 临时反例证明终结状态不等于有效完成 | 一个权威检查器 + 验收关联，而非增加提示词 | 验收命令语义仍需审查，不能全自动保证 |
| PStack 机制完整性 | 磁盘状态、前沿、版本绑定、持久恢复、预算收尾 | 在已有工具上接闭环，不照搬云部署和 Cursor 设施 | 真实远端长期稳定性需后续授权观察 |
| 用户体验/安全 | 用户中止、询问、权限门、未知子代理状态 | 宁可明确暂停，不无限唤醒；自动恢复与安全停止分开 | 停止率是否偏高需实际任务基线 |
| 兼容与可逆性 | 旧 run/legacy header、个人技能软链接 | 新增小文件、历史只读、隔离后启用 | 新标准下部分旧运行需要补验收，不能零成本迁移 |
| 性能与成本 | 基线通过但无请求级收益数据；新增摘要读取 | 不扩并发/重试，不连付费服务；监测本地检查开销 | 总体提速与真实费用未知 |
| 运维与证据 | 本地故障复现、已有测试、SDK 类型入口 | 建实际 Pi + 假服务层，和纯函数层分开 | 本轮尚未跑新增生命周期测试 |
| 反向挑战/最小化 | 大部分组件已存在；独立审查指出三处接口/回退缺口 | 不新建控制器、不合并旧 task.py；补显式目标、收据与旧版只读回退 | 修订未独立复审；宿主收据捕获能力需实施前实测 |

## 第一性原理：什么叫任务完成

任务完成不是“模型说做完了”，也不是“工具调用结束”。最小定义应同时满足：

1. 任务有明确、可检查的完成判据（Done predicate）。
2. 每项完成判据有针对当前代码状态的验证证据。
3. 判据、证据、运行版本和剩余事项保存在会话之外，可在模型切换、上下文压缩或中断后继续。
4. 未满足判据时，系统只能继续、明确暂停或交接，不能误报完成。

因此效率也不能只看墙钟时间。还要看等待人工的时间、失败重做量、恢复后重复验证量，以及最终交付是否满足判据。

### 红帽：风险与痛点

- **状态与执行脱节**：缺少活动运行账本时，无法可靠知道当前单元、已验证事项和正确恢复位置。结果可能是重复劳动、错过未完成项，或用通用提示续跑错任务。
- **错误覆盖不完整**：按错误类别恢复尚未形成可观察的闭环。部分服务错误仍依赖用户重新触发；用户等待与介入会吞掉自动化带来的时间收益。
- **恢复正确性不可验证**：压缩后若只靠对话摘要续接，已完成工作可能重做，或关键约束丢失。当前样本没有足够账本来量化恢复保真度。
- **局部并行不等于整体提速**：子代理能并行产出，但主会话仍需等待、核对和合并；如果没有可独立验证的单元及阶段记录，并发可能转化为更多收拢成本。
- **完成信号可能早于证据闭合**：没有运行级完成判据与验证账本的可追踪关联，就难以审计“完成”是否对应当前代码状态。
- **预算风险未知**：没有运行证据能说明达到预算阈值后停止扩张并收尾。这里是验证缺口，不据此断言预算机制一定未实现。

### 黑帽：谨慎判断

1. 样本小且由真实会话可访问性决定，不能推断总体错误率或平均完成效率。
2. 一次 failover 成功只覆盖该错误与当时的宿主状态；不能推断其他错误分类、子代理中途失败或切回主模型也有效。
3. 测试通过不能替代扩展在真实 Pi 生命周期中的加载、事件顺序、注入与恢复验收。
4. 看不到 RUN/ledger 可能是未创建、路径不同或日志/工作区不完整；需要在运行时显式记录状态指针，减少这种歧义。
5. 0.0.7 的结构问题是历史审查结论；不应未经当前代码核验就写成 v3 当下已复现缺陷。

- 一次 503 切换与续跑真实发生，说明至少一条宿主恢复路径可用。
- 三个子代理并发完成并通知，说明委派机制在合适任务上能产出并行结果。

### 绿帽：可行的新办法

把一次运行收敛为一个可追踪的闭环：

`RUN 指针 → 可验证单元 → 验证账本 → 错误分类与有界恢复 → 完成判据`。

每次调度、模型切换、子代理派发、验证、暂停和完成都引用同一 RUN 标识。恢复时先读账本，再决定续跑或重派；完成只由当前版本上全部判据的有效证据决定。用少量真实 Pi 故障注入场景验证闭环，而不是先扩充提示词或重写所有工具。

### 蓝帽：结论与控制

首要改进顺序：先让每个运行可关联到持久状态；再补失败类型到恢复动作的闭环和恢复后验证；最后验收预算收尾与整体任务完成。指标须来自运行事件，而不是从对话文本事后猜测。具体方案见[最小闭环改进方案](./最小闭环改进方案.md)。

## 最终判断

**现状：**v3 已出现真实故障切换和并行委派成功案例，也有单测与脚本验证。  
**问题：**这些能力尚未在本次样本中组成以持久状态为中心、按完成判据驱动、可从压缩/错误恢复并可量化收尾的运行闭环。  
**影响：**无法可靠判断任务是否高效完成；局部自动化收益可能被人工续接、重复工作和不可审计的完成状态抵消。

建议把 0.0.10 的目标设为“证明闭环并收敛根因”，而不是增加更多流程规则。

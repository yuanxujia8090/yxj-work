# x-rail 0.0.10 决策记录

> 状态：评估中。以下是实施计划作者的推荐，不是用户已批准的实现决策。用户确认后，才可把“推荐”转为实施范围。

## 推荐执行

### 实施工作区

- 选择：继续在当前 `v3` worktree 实施；此前独立 worktree 的读写在工具层间歇性落到 `v3` 或被权限边界拒绝，故不再对该路径操作。
- 依据：`v3` 当前 HEAD 包含独立 worktree 的基线提交；0.0.10 计划已在此目录，且现有用户修改可明确保留。
- 边界：不安装个人 Pi、不推送、不运行付费模型；保留本目录已有 `skills/x-rail/extensions/package.json` 与 `plans/0.0.10/` 内容。


| 决策 | 推荐 | 依据 |
| --- | --- | --- |
| 运行状态 | 复用现有 `.work-docs/runs/<run-id>/`、`RUN.md`、`units.tsv`、`ledger.tsv`、`events.jsonl`、`capsule.md`；不另建控制器 | 当前已有运行锁、原子写、账本和胶囊；重建会增加双状态源 |
| 完成门 | 增加运行级权威检查：完成判据、当前证据、未解决运行和必要决策门都通过后才可 finish | 临时反例证明失效证据和 `abandoned` 当前仍可使 `doneMet=true` |
| 验收关联 | `acceptance.tsv` 增加可核对的 source，finish 检查来源、当前证据、最终验证及高风险独立审查；保留 finish 收据 | 来源使要求可追溯，但不能单独证明语义正确，仍需审阅验证命令 |
| 错误分类 | 补 `Stream ended without finish_reason`、`502 Bad Gateway` 等实际错误表达；未知错误默认暂停 | 当前分类器对这些错误返回 `none`，可能静默结束 |
| 恢复身份 | 续跑、切换、压缩、事件记录统一引用真实 `workspace + run_id + session_id`；所有运行命令支持显式目标；ACTIVE 改变不自动换绑 | 防止旧会话接管新运行或检查错任务，解决 `<id>` 占位符和跨运行歧义 |
| 宿主证据 | 由实际宿主工具结果采集启动与状态收据；缺失、未知或活跃不允许 finish；适配能力不足明确阻塞 | 不能用模型自行填写的状态当成宿主已停止的事实 |
| 旧版回退 | 新格式运行保留目录和 ACTIVE；旧工具只读，不能继续写；恢复指针需核对所有权与并发变化 | 旧 init/close 不理解新增暂停语义，可能改坏活动指针 |
| 旧格式接入 | 选择明确交接：legacy 的 automation_allowed=false、done_met=false；不自动写状态/唤醒/计 stall；显式补要求与证据后接入 | 不沿旧完成快照认证已过期或 abandoned 结果，也避免无验收表导致空转 |
| 放弃后的依赖 | 保持 done+有效证据门槛；plan replace 原子改接验收和未启动下游依赖，替代项继承原前置条件 | “已接管验收”不等于“已完成”，不能因此提前运行下游 |
| 暂停恢复与新运行 | resume 显式核实后只改阶段；init/import 可接管已安全暂停/完成的 ACTIVE，未知或仍活跃宿主不释放 | 补齐 pause 的出口，不抢占写入者；finish 条件释放自身 ACTIVE |
| 错误精确映射 | 保留 E1 账号池/网关切换；E2 瞬时故障同模型一次；余额/鉴权停止；逐模式映射见主计划 4.4 | E1 是混合分类，整体停掉会误伤可恢复故障 |
| 派发与收据 | tool_call 登记意图，tool_result 确认启动/查询；派发代号在短锁内递增、finish 校验同代号 | 不跨异步生命周期持锁；调用前事件不能冒充实际启动成功 |
| 会话进展 | owner_session_id 决定主控；计数分工作区/运行/会话，运行总上限聚合；语义指纹纳入验收与阶段 | 子代理不假冒父会话进展，换会话不能清零上限；时间戳不算进展 |
| 检查时限 | inspect/capsule 异步、初始 5 秒时限；失败交接，明确人工检查可调 | 避免阻塞宿主事件循环；5 秒是待实测策略值，不是测得性能 |
| 子代理故障 | 先查询原运行；活跃则保留原范围，终止后再接收/重规划，未知则阻塞；不盲目重派 | 两个写入者可能同时改同一文件，数据风险高 |
| 宿主验收 | 用锁定 Pi SDK 和本地假服务验证真实扩展加载与事件顺序；与纯函数测试分开报告 | 当前类型检查和 mock HTTP 通过，不等于 Pi 生命周期通过 |
| 压缩恢复 | 复用现有 capsule；压缩/重启后先读绑定状态，再决定继续或重验 | 已有胶囊，不需要第二摘要系统 |

## 暂缓或独立启用

| 决策 | 推荐 | 原因 |
| --- | --- | --- |
| 预算 70% 自动收尾 | 独立工作包，默认不启用 | 当前缺统一墙钟/成本计量；自动停止会改变任务范围和用户体验 |
| 真实模型回放 | 不纳入默认实施 | 会产生模型调用和费用，需要明确授权 |
| 个人 Pi 安装/切换 | 不纳入默认实施 | 当前技能软链接指向工作区，实施隔离不足时可能影响其他会话；安装还会改变用户环境 |
| 第二备用模型 | 不做 | 不是当前证据证明的根因，会增加路由和成本复杂度 |
| 提高重试、续跑或并行上限 | 不做 | 当前问题是闭环证据和边界，不是单纯吞吐不足 |
| legacy `task.py` 迁移到 v3 | 不做 | 两套协议有明确边界，混迁会扩大范围和兼容风险 |
| 自动盲目重派子代理 | 不做 | 与“先核对原运行”安全规则冲突 |

## 随实施范围一并评估的行为变化

这些是供评估的推荐，不是要求用户逐项回答的问题。

1. 余额/鉴权类错误默认停止，而不是切换备用模型；选择保留切换时，就不能承诺不产生额外请求。
2. `abandoned`（因拆分或放弃而终结的单元）本身不满足原要求；替代单元完成并重新关联原验收后，原要求才可通过。删除要求仍需用户批准范围变化。
3. 旧运行只读检查并本地交接，不自动续跑；采用新标准时显式补来源/关联、核实原证据再 resume，不批量迁移。这采用审查列出的第二种兼容方式，避免延续旧快照的误判。
4. 真实 Pi + 本地假服务作为核心验收门；不调用真实模型，SDK 注入能力不足的场景如实保留为未验证。
5. 显式墙钟预算独立选择；先确定计量口径，再启用自动收尾。

# 2026-10-20 方案审查核实与修订

> 对照 [方案审查原文](./方案审查-2026-10-20.md)、当前提交 `d44133b` 的代码和锁定的 Pi 1.3.0 类型声明。本轮只改计划文档，保留审查原文；未实施新功能、未重复跑全套基线。

## 结论

审查指出的三类规格缺口属实，六项重要建议有代码或开发接口依据；但三条具体建议不能照抄：旧格式不沿旧完成规则认证，abandoned 不直接满足依赖，调用前事件不等于启动成功。已经据此完善主计划、摘要、决策记录与最小闭环方案。

## 三类规格缺口

| 原建议 | 核实证据 | 采纳方式 |
| --- | --- | --- |
| 错误编号混装，需逐模式映射 | `classify.ts` 中 E1 同时收账号池、网关压力、余额、额度、billing、401/403 和长延迟；直接调用分类/切换函数确认它们当前都会在主模型上切备用。E2 busy 为同模型重试，E3 timeout 为直接切换 | 主计划 4.4 新增逐模式、主/备用两侧动作表。保留账号池/网关/长延迟切换，余额/鉴权停止；断流映射 E2、502 映射 E3，不统一放宽重试 |
| 无验收表的旧任务会触发无意义续跑 | `guard-core.ts` 在 doneMet=false、active=true 且未到限额时返回 continue；本轮直接调用复核。当前快照无新格式区分，计划若只收紧 doneMet，确实会引入该问题 | 选择原审查列出的第二种方式：`mode=legacy`、`automation_allowed=false`、`done_met=false`，只读检查并本地交接；不累计续跑/无进展、不新增模型请求。显式补齐来源与验收后 resume |
| 放弃依赖和 pause 出口缺失 | `ready()` 只接受 done 依赖。直接调用：替代项/下游依赖 abandoned 都 false；替代项去掉该依赖、下游改接替代项后，替代项 ready，下游要等它 done。计划此前无 resume 接口，init 对 paused 的说明含糊 | 不采用“abandoned 已被接管就等于依赖完成”。新增原子 `plan replace`：改接下游/验收，替代项继承前置条件，环与活跃下游拒绝。新增显式 resume；init/import 可接管已安全暂停/完成任务，未知/活跃宿主仍保留占用 |

旧格式方案未选审查推荐的第一种：沿旧规则计算 done_met 会继续接受失效证据与 abandoned。无需靠这种完成判断防止唤醒；单独的 automation_allowed 已能阻止模型请求。旧表仍可读，旧终结统计不冒充新标准完成。

## 六项重要建议

| 项目 | 是否属实 | 修订 |
| --- | --- | --- |
| finish 与派发互斥机制缺失 | 属实；不能跨整个异步生命周期持文件锁 | 采用 dispatch_epoch（派发代号，启动/续接意图的版本号）和短锁。先登记意图递增代号，再放行工具；finish 核对配对/终态及同代号，收据记录代号；暂停/完成时前置处理器拒绝新派发 |
| 收据事件只写工具结果过窄 | 部分属实。锁定 SDK 的 `ToolCallEventBase`/`ToolResultEventBase` 都有 toolCallId，tool_call 可 block；但前置事件只是意图，可能被其他处理器拦截 | 前置登记意图，结果配对确认启动/查询；缺结果阻止 finish。空启动清单要求完整捕获区间；没装工具、装了未用、重启缺口分开测试 |
| 验收自证缺工程约束 | 属实，但 source 非空不足以解决 | 增加可读取且摘要一致的 source；核对 RUN 完整要求；高风险 review_required 强制独立审查单元、不同负责人会话与当前报告。来源仍不能自动证明验证命令的语义正确 |
| 指纹未含验收和 phase | 属实，unitsFingerprint 当前只有 units+ledger | 纳入验收内容/来源/关联和语义 phase，排除时间戳、重复查询等噪音；不能据指纹变化清零运行故障总上限 |
| 子代理可能重复计数 | 属实；x-failover 的 tool_result 用 ACTIVE 的 run_id 写进度，缺会话过滤；store 仅 run_id 键 | owner_session_id 固定主控，工作目录/运行/会话组合键隔离本地计数，运行总上限聚合保留。SDK 类型明确允许 `ctx.sessionManager.getSessionId()`；实际子代理身份与工具输出仍待集成验证 |
| 参数解析和 import 连带影响 | 属实；main 只预剥离 repo，直接传 run-id 的只读 status 本轮退出 2；import 内部调用 init | 明确 run-id 同层剥离、前后位置/重复/缺值测试；init/import 不用旧 run-id，统一保护 ACTIVE，导入失败保留原指针 |

## 小问题与事实校正

- 已列守护器 notify 改动：满足判据后本地提示一次 finish，不额外发模型请求；legacy/paused 不启动该提示流程。
- 已写 done 证据过期后的恢复命令：显式目标 verify，再 done；不必为重验重新派发。
- 已同步原阶段四：完成门在核心闭环，预算自动收尾独立启用；纠正最小方案中“子代理失败默认重建”和“安全暂停计入恢复成功”两处旧表述。
- inspect/capsule 改异步，初始 5 秒时限并回收检查进程。该数值是计划策略，不是实测性能；需在实现时记录耗时。
- 原审查称 close“无条件删”不够准确：当前 cmd_close 先检查 ACTIVE 值，再 unlink；缺的是暂停语义兼容与比对/删除的原子并发保护。init 当前确实直接写 ACTIVE。回退风险成立，不能省略已有保护来夸大问题。
- 原审查称 repo 参数“不在 argparse 里”不准确：build() 已声明 `--repo`，main() 另做预剥离以支持子命令后置。真正缺口是 `--run-id` 尚未声明/传入，以及前后位置与重复参数规则未定义，计划已补。
- 原审查“README 及四份子文档”实际列了五份；仅为计数笔误，不影响结论。原文件保持不动。

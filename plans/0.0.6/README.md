## 推荐方向

**已按推荐选了“先固化主动委派，再按证据增加工具”，因为指定会话更直接支持完整工作的接力与材料隔离，尚未证明任务摘要是主要瓶颈。**

奥克姆剃刀在本版的判断方法：去掉一项机制，哪个已观察到的问题会重新出现？没有明确依据的机制先推迟。像前端容器组件与子组件分工，主会话管理目标和共享约定，执行者承接完整实现；有先后依赖也可以接力。

首批只落实三件事：

1. **主动委派执行。** 已有委派授权、相应费用授权和宿主能力时，将目标、范围、输入和验收明确的完整执行单元交给子代理；独立项可并行，有依赖项接力。短小且主会话已掌握材料的工作直接完成，紧密耦合的实现由同一位执行者承接。
2. **精简交接。** 返回结果、实际修改位置、必要约定、验证证据、偏差和下一步；大量原文留在执行侧，主会话按实际问题展开。
3. **按缺口验证。** 核对真实产物，复用仍有效的证据；补受输入、环境或集成变化影响的检查，保留必需独立审查，达到约定验收即交付。

普通／严格记录和长模式继续按现行规则判断；“任务大小”只作解释，不再增加前置分类流程。工作项定义交付，下一动作说明当前做哪部分；发现范围、风险或验收变化时调整边界，再继续执行。

## 事实依据与限制

用户反馈：会话 `01a142a2-c668-73b2-86b0-1c3a0a9e2116` 在要求主动使用子代理后体感更快。原记录显示共派发 7 次执行、3 次审查，已结束运行按顺序接力；抽查三次主要实现均从新上下文开始，模型与主会话相同。第三次审查指出了页面选择与服务端校验不一致的缺陷，随后派发修复。

这些事实支持优先固化主动接力和有针对性的审查；没有同条件对照，暂不能量化提速或推导普遍收益。取证时间、来源和观察边界见[优化方案](优化方案.md)。

## 后续增强与验收边界

`summary --compact`（任务摘要的精简视图）调整为有证据后再实施的独立增强，首批不改摘要脚本、不以摘要测量阻塞交付。确有重复摘要负担时，首版只考虑精简视图；`--item`（指定展开某一工作项）继续推迟。这些拟议选项当前不可作为已有命令使用。

首批用一条真实接力任务观察主动派发、交接、核验与结束，再用短小改动作反向核对。跨会话恢复、并行补位和批量试跑按实际变更选择；日常任务不重复整套演练。效率先随正常执行观察，需要承诺具体幅度时再安排获授权的配对实验。既有实施契约已承诺的必需项继续履行，不能借本次方案修订取消。

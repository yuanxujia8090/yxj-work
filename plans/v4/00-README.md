## 这版解决什么

用户原始要求：

> 阅读资料，重新设计本次 v4 版本。之前方案可以参考，但不作为实施依据。责任分离，x-rail 关注做好任务；模型重试独立成 Pi 的 plugins，作为 x-rail 的辅助，但不是必须。方案放在 plans/v4，后面执行以这个目录下内容为准。

把它类比为前端应用：页面负责把业务做完，请求层负责网络重试。页面不能因为请求层没装，就不知道怎样提交、验收或保存现场。

本版对应两份独立交付：

1. **x-rail 任务系统**：理解目标，拆成可验收工作，按依赖推进，接收结果，验证当前产物，交付或留下明确的暂停位置。
2. **Pi 模型恢复插件**：在用户主动选择后，利用 Pi 内建重试和虚拟模型能力处理暂时性模型故障。虚拟模型就是“对外一个模型名，每次请求前决定交给哪个真实模型”的选择器。

**x-rail 不依赖模型恢复插件；插件也不依赖 x-rail。二者通过 Pi 已有的请求与会话生命周期自然衔接，不设计私有握手协议。**

## 目标与完成标准

- 普通任务直接交付；需要跨会话恢复、依赖推进或持久验收的任务统一用 `xr`，即现有任务记账命令。
- 模型正常返回但任务未完时，有可执行事项就继续；真实等待、用户中止、证据不确定或权限边界会明确停下。
- “完成”由同一个当前证据检查器判断；已放弃、旧证据、异步启动回执都不能替代交付。
- 冷启动能从磁盘恢复；先核实原执行者与副作用，再继续，不盲目重派。
- x-rail 单装、模型插件单装、二者同时装，分别有本地假模型验收。假模型是只监听本机的模拟服务，不调用收费模型。
- 安装产物可独立审阅，开发工作区与安装版本分开；实际宿主安装必须另获明确授权。

## 取舍

已按推荐选了“任务内核 + 可选模型插件”，因为任务是否完成与模型请求是否成功是两种独立事实。

保留 PStack 的核心任务机制：可验证拆分、按当前证据计算可做事项、滚动推进、持续接收结果、失败分类与重规划、版本绑定、独立审查、持久记录和暂停恢复。借鉴范围见仓库 [PStack 设计参考](../../docs/pstack-design-reference.md)。这里的本地化是使用 Pi、工作区和磁盘文件；不能借精简之名取消上述机制。

舍弃：把任务守卫与模型重试合成一个大状态机、手写多分钟退避与模型看门狗、按模型熔断文件调整任务并发、固定服务商压缩阈值、所有任务强制填第二套表。

## 一句话结论

**v3 的稳定性原则是对的，缺的是“宿主事实层”。** v4 不再增加流程规则，而是把 Pi 扩展做成 x-rail 的内核适配层：固定运行身份、记录工具调用的意图与结果、统一所有恢复入口、用权威检查器决定是否完成。

**本轮取舍：只做“身份 + 工具生命周期 + 统一恢复 + 完成门”四件事。** 不做第二套调度引擎、不做多模型轮转、不做预算自动收尾、不做付费回放。

## 为什么需要 v4，而不是继续改 v3

v3 与 0.0.10 已经提出了正确方向，且 0.0.10 的接口规格更细。v4 相对它们的增量只有三点：

| 增量 | 原因 |
| --- | --- |
| **把“工具调用”当成一等事实记录** | 0.0.10 已定义派发收据，但未覆盖普通工具产生的副作用。长任务最危险的失败是“工具已执行、模型没收到结果、恢复时重跑” |
| **扩展不再自己算完成** | `runSnapshot()` 只看单元状态，`done` 与 `abandoned` 都算终结；权威判断必须来自一个检查器 |
| **恢复决策收敛为单一函数** | 现状至少有四条路径各自判断（普通错误、看门狗、边界续跑、压缩），分类器漏掉的错误会被两边同时忽略 |

## 设计原则

1. **模型提议，宿主记录，检查器裁决。** 模型可以说“做完了”，但不能决定完成。
2. **事实与解释分离。** 宿主事件是事实（调用了什么、返回了什么）；单元状态是解释；两者不互相冒充。
3. **未知即暂停。** 无法判断工具是否执行、子代理是否存活、证据是否新鲜时，停在可核对的位置，不自动重放。
4. **一个动作只有一个入口。** 所有自动恢复都经过 `decideRecovery()`；看门狗只报告，不自行换模型。
5. **规则少而硬。** 能用脚本检查的不写进提示词；新增文件尽量少，优先扩展既有 `events.jsonl`、`RUN.md`、`units.tsv`、`ledger.tsv`。

## 非目标

- 不重写 `xr` 的 1000 行脚本，不换语言，不引入数据库或后台进程。
- 不改变主/备用模型配置，不增加第三模型，不提高重试与续跑上限。
- 不自动重放可能有副作用的工具调用。
- 不自动接管未知状态的旧运行。
- 不做费用统计、账单读取、预算强停。
- 不执行个人 HOME 安装、技能软链接切换、推送或发布。

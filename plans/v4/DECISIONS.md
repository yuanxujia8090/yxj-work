## 接口决定

- 任务命令使用显式 workspace、run、session；PI_SESSION_ID 仅在宿主实际提供时读取，缺失不猜身份。
- 任务调度、暂停、证据与完成写现有 run 文件体系；不使用模型插件断路器文件改变并发额度。
- 异步启动、子任务终态、父会话收到结果分成不同记录；启动回执不是结果。
- 失败证据按尝试只增不覆；验证通过依赖原始输入、命令、产物、报告摘要及当前运行范围。
- 模型错误处理回归 Pi 内建 retry；unknown 最终失败由任务守卫暂停，不跨越宿主重试上限继续模型循环。
- 子代理插件支持作为能力门验证；不支持时子代理用明确物理模型，父会话接收后按任务规则恢复。
- 为普通任务提供只读 `/x-rail-run status|attach` 和 `/model-recovery status`；命令本身不得向模型发起请求。

- 不更改 `~/.pi`、`~/.agents`、个人环境变量、默认模型、重试设置或安装软链。

## 2026-10-22 阶段 A 实测修订

- Pi 1.3.0 在本地假模型返回 HTTP 503 时，会把传输错误直接交给虚拟模型的 `retry` 路由；本次实际请求顺序为 `fixture-a -> fixture-b`，虚拟模型收到 `failed` 文本 `503: {"message":"gateway_concurrency_limit"}`。
- 该传输层错误没有产生可供扩展改写的 `message_end` assistant error，因此不把 `message_end` 当作网关错误统一入口，也不自造独立重试器。模型插件首版只覆盖 Pi 原生可重试错误；中转网关自定义文案若 Pi 不识别，按最终失败交给任务守卫暂停。
- 阶段 A 仅更新了本地宿主探针和夹具，未改变 x-rail 或宿主配置；完整绿测仍需重跑。

## 已记录但尚未验证

## 2026-10-22 阶段 B/C1 实施修订

- 任务并发、前置有效性与证据全部落在 `xr` 单机实现，不再读 `X_FAILOVER_STATE`。任务层与模型插件之间没有共享文件。
- 事件写入只走 `xr event --record <本进程私有临时文件>`：`xr` 在运行锁内校验 workspace/run/session/generation，并按 `event_id` 去重；扩展不再自己 append `events.jsonl`。写意图失败就阻断该工具，宁可停也不留无记录的副作用。
- 只有 `outcome=success` 的动作自动关闭。`isError` 只证明工具报错，不证明没写入，保持未决直到 `xr op reconcile`；`completed` 只解除“结果未知”，不替代验收；`failed` 保持阻塞。
- 宿主观测修正：别的扩展抢先 `block` 时，后注册的 `tool_call` 处理器不再执行；这类工具没有 op_intent，但 `tool_execution_end` 不带 `durationMs`，据此记 `not-started`。因此“没有意图”不等于“没有执行”，两者都要看。
- `x-run-guard.ts` 增加独立默认导出，单独加载即可绑定与记账；不引入 failover 模块。取消、settle 顺序与续跑策略仍属 D 阶段，未完成。
- 子代理事实用双阶段事件：`worker_started` 登记宿主 run、工具调用、合同摘要、状态路径与启动时输入摘要；宿主通知只有在结构化 `subagent-notify.details.runs[]` 到达后才尝试接收，不解析自由文本。接收另存只增不覆报告，绑定进程终态、退出码、子会话 transcript 和输出摘要；接收本身不把父工作项标成 done。
- `inspect` 同时给出 `pending_workers` 与 `receipt_status`；pending worker、未决副作用、坏事件尾阻断自动推进与完成。扩展对 inspect JSON 校验必需字段和类型，未知 schema 按暂停处理。
- 早期“失败消息改写不可用”的结论仍待复核：探针当时的 `message_end` 返回结构与宿主声明不一致，且只匹配原始文案。插件首版继续只依赖 Pi 原生可重试分类。

## 2026-10-22 阶段 C4 实施修订

- 人工证据不新建第二账本：扩展现有 `ledger.tsv`，追加 `evidence_kind / observer / session_path / session_hash / input_scope / input_hash / final_hash / record` 八列；旧的三种表头（含 `command`、`previous`、`legacy`）读取时按名称补默认值，历史行不重写。
- 单元表 `units.tsv` 增加 `verify_kind`（`command|observation|review`），缺列时按 `command` 读；`command` 单元仍必须写 `--verify`，observation/review 单元不允许用 `--verify "true"` 冒充可执行测试。
- 人工证据统一跑 `xr evidence record <id> --kind ... --report ... [--inputs ...] [--observer ...] --record ...`：报告先校验非空且位于仓库内（运行目录原件拒绝），副本以独占创建写到 `notes/evidence-<id>-<kind>-<n>.md`，绝不覆盖旧报告；已有当前有效证据时拒绝重复登记，过期后重取只追加。
- 审查独立性靠会话事实：`--observer` 指向的 jsonl 首条必须是 `type=session` 且 `cwd` 等于当前仓库，会话 id 不得等于绑定会话、事件里出现过的会话或已接收的实现子会话；报告文字必须出现在该会话助手消息里，防止用任意文件冒充审查。
- 审查证据不绑定单个单元摘要，而绑定 `review_input_hash`：所有非 review、非 abandoned 单元的当前验证摘要加 `acceptance.tsv` 摘要。这样审查报告本身不会让自己失效，而任何真实交付变化都会让审查变 stale。
- `review_required: true` 必须存在当前有效的 review 证据（`done` 且 `try_verified` 且报告与会话摘要均未变），否则 `inspect` 判不完成、`finish` 拒绝。`finish.json` 增加 `review_digest`，审查证据或输入变化会让收据变 stale。
- 已知取舍：审查身份只校验会话文件头与报告文字，不验证签名或密钥；本地单机场景按“有证据比无证据强”处理，不声称防伪造。跨机器或多用户审查需要额外签名时才重评。

## 2026-10-22 阶段 D1/D2 实施修订

- 宿主事实：`agent_before_settle` 各扩展的结果是链式覆盖，后运行者返回的 `entries` 会整体替换前者。因此任务续跑必须只有一个责任方，否则两个扩展同时注入会让另一方的条目丢失。
- 选型：`agent_before_settle` 由 `x-run-guard.ts` 自己注册，failover 不再调用 `guardBoundary`；两边都从 `event.entries` 开始追加，不整体重建。任务续跑与模型切换因此真正解耦，守卫单装即可续跑。
- `AgentSettledEvent` 只有 `aborted`，没有 `outcome`/`error`。settled 记录使用 `before_settle` 当时实际保存的 outcome，并显式不写 error 字段；缺字段不猜。
- 停止语义统一走 `stopWithHandoff`：写 handoff 失败也返回 `continue:false`，提示包含失败原因与“停在原状态”；不带着失效状态继续跑。
- 已知取舍：未提交、未推送、未安装。D2 的中止/切会话时序与 handoff 写失败仍只有代码分支，没有真实宿主探针，计为未验证。

## 2026-10-22 阶段 D2 实施修订

- 宿主事实（实测 RPC）：`new_session` 会重置扩展的模块状态，且不会重发 `session_start`；若只靠 `session_start` 判定身份，新会话会变成未绑定并静默停摆。
- 处理：`agent_start` 时校对 `ctx.sessionManager.getSessionId()`，与已绑定会话不同才重新 `bind`（generation 递增）；绑不上就清空绑定并提示，不用旧身份写状态。
- 中止用真实 RPC 控制通道：`prompt → abort` 后 `agent_settled.aborted=true`，续跑数为 0；切会话后旧身份不再产生任何任务事件，绑定文件不被静默改写。
- 已知取舍：切会话后的重新接管需要用户显式 `xr bind` 或重开进程，不自动抢占；宁可停摆也不猜身份。

## 2026-10-22 阶段 E/F 实施修订

- 插件宿主验收用隔离 agent dir 加本地假模型，覆盖“未配置/配置无效/链中模型不可用”三种零请求路径；真实模型只在 `RECOVERY_REAL_MODEL=1` 下跑，默认不联网。
- 实测发现：`--model model-recovery/auto` 会被 Pi 解析成 provider/model 两段；必须写成 `--provider model-recovery --model auto`。这条写进探针，避免以后误判为“虚拟模型没生效”。
- 真实模型验收范围只到“虚拟模型路由到 `bai/deepseek-v4.1-flash` 并拿到正常回答”。网关错误分类、余额/鉴权分支、工具副作用只执行一次属于未验证，不据此声称线上可靠性。
- 打包选型：只导出 `skills/x-rail` 与 `plugins/pi-model-recovery`，排除 `node_modules`、`plans/`、`.work-docs`、凭据、`.pyc` 与旧 failover 入口（`x-failover.ts`、`failover.test.ts`）。导出到已存在目录一律拒绝，不做备份覆盖。
- 未选：把两个产物合成一个包，或让包内附带用户配置样例自动写入。理由：产物独立性是用户明确要求，自动写配置会改变用户环境。
- 已知取舍：manifest 的来源提交取自当前 `git rev-parse HEAD`；工作区未提交时导出会把未提交改动打进去，但 manifest 仍标 HEAD。需要严格可复现时先提交再导出。

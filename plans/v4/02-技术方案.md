# 02 技术方案

> 本文定义接口与行为契约。伪代码用于说明，不含可直接运行的完整实现。
> 原则：**模型提议，宿主记录，检查器裁决。**

## 1. 分层与职责

```
┌──────────────────────────────────────────────────────────┐
│ L0 宿主适配层（Pi 扩展，唯一接触宿主事件的地方）            │
│   host-events.ts  事件→事实记录（tool_call/tool_result…）  │
│   run-binding.ts  workspace + run_id + session_id 绑定     │
│   recovery.ts     所有失败的唯一决策入口                   │
│   x-failover.ts   只执行“切模型”这一个动作                 │
│   x-run-guard.ts  只执行“续跑/暂停”这两个动作              │
└──────────────────────────────────────────────────────────┘
                          │ 只写事件、只读检查结果
┌──────────────────────────────────────────────────────────┐
│ L1 任务层（x-rail 技能，按需加载）                          │
│   SKILL.md → stages/*：决定下一步做什么                     │
│   不负责稳定性、不负责判断完成                              │
└──────────────────────────────────────────────────────────┘
                          │ 调用动词
┌──────────────────────────────────────────────────────────┐
│ L2 权威检查器（xr CLI，Python 标准库）                     │
│   inspect / acceptance / finish / pause / resume          │
│   唯一有权说“完成”或“未完成”的组件                         │
└──────────────────────────────────────────────────────────┘
                          │ 读写
┌──────────────────────────────────────────────────────────┐
│ L3 运行数据（磁盘，唯一真相）                              │
│   RUN.md units.tsv ledger.tsv events.jsonl                 │
│   binding.json acceptance.tsv finish.json gates.md        │
│   capsule.md handoff.md                                    │
└──────────────────────────────────────────────────────────┘
```

**硬边界：**

- 扩展不读 `units.tsv` 判断完成。需要完成判断时调用 `xr inspect --json`。
- `xr` 不启动模型、不派发子代理、不改 `events.jsonl` 里的宿主事实。
- 技能层不写状态文件，只调用 `xr` 动词。

## 2. 状态文件契约

目录不变：`<repo>/.work-docs/runs/<run-id>/`。

### 2.1 新增 `binding.json`

**唯一写入者**：`xr bind`。扩展只读。

```json
{
  "schema": 1,
  "workspace": "/Users/yuanxj/Documents/github/x-rail/.worktrees/v4",
  "run_id": "20261020-1530-v4-design",
  "session_id": "pi-session-8f3c...",
  "owner": "host",
  "created_at": "2026-10-20T15:30:12+08:00",
  "lease": "active"
}
```

规则：

- `workspace` 必须是绝对路径，实时计算 `path.resolve()` 后比较。
- `lease` 取值 `active | paused | released`；只有 `active` 允许自动续跑与新派发。
- 已存在且 `session_id` 不同、`lease=active` 时，`bind` 拒绝并提示“该运行被另一会话占用”。
- 接管需要 `xr resume --confirm --take-ownership`，并记录原会话标识。
- `ACTIVE` 降级为“发现入口”：`session_start` 时若本会话尚未绑定，用 `ACTIVE` 找候选；绑定后不再读它。

### 2.2 扩展 `events.jsonl`

保持只追加，新增事件类型。**唯一写入者按运行划分：宿主进程写宿主事件，`xr` 写命令事件，二者不写同一 `type`。**

| 字段 | 说明 |
| --- | --- |
| `schema` | 固定 `1` |
| `ts` | ISO 8601 带时区 |
| `event_id` | `<session_id>:<单调序号>`，用于去重 |
| `workspace` `run_id` `session_id` | 三者必须同时存在；缺失说明记录不完整 |
| `type` | 见下表 |
| `unit_id` `host_run_id` `model` | 不适用时为 `null`，不编造 |
| `detail` | 该类型专属字段 |

| `type` | 写入者 | detail 关键字段 | 用途 |
| --- | --- | --- | --- |
| `turn_start` | 宿主 | `turn_id`, `model` | 回合边界 |
| `turn_end` | 宿主 | `turn_id`, `outcome`, `stop_reason` | 区分完成/错误/中止 |
| `op_intent` | 宿主 | `op_id`, `tool`, `input_digest`, `side_effect` | 执行前登记 |
| `op_result` | 宿主 | `op_id`, `is_error`, `blocked` | 配对确认 |
| `recovery` | 宿主 | `failure`, `decision`, `reason` | 审计每次自动恢复 |
| `finish` | `xr` | `acceptance_digest`, `tree_digest` | 完成收据 |
| `pause` `resume` | `xr` | `reason`, `record` | 阶段变化 |

`op_intent.side_effect` 取值 `read | write | unknown`：`read` 包含 `read/grep/find/ls`，`write` 包含 `write/edit/bash/powershell`，其余自定义工具为 `unknown`。

**追加的原子性**：单行 JSON 用 `fs.appendFileSync` 追加。并发多进程写同一文件时，只保证“整行不撕裂”，不保证顺序。检查器读取时丢弃最后一行不完整记录，并记录 `truncated_tail=true`。

### 2.3 新增 `acceptance.tsv`

列为 `id`、`statement`、`source`、`units`、`status`。

- `statement`：需求原文，非空。
- `source`：`<path>#sha256:<hex>` 或 `session:<session_id>#entry:<entry_id>`；`inspect` 时必须能读取且摘要一致。
- `units`：逗号分隔的单元标识；必须存在且不能是 `abandoned`。
- `status`：`pending | covered`，由 `xr` 派生，不手工改。

### 2.4 新增 `finish.json`

```json
{
  "schema": 1,
  "run_id": "20261020-1530-v4-design",
  "finished_at": "2026-10-20T18:02:00+08:00",
  "acceptance_digest": "sha256:...",
  "units_digest": "sha256:...",
  "ledger_digest": "sha256:...",
  "tree_digest": "sha256:...",
  "dispatch_epoch": 7,
  "unresolved_ops": 0
}
```

`finish.json` 是**可重算的收据**，不是第二份状态：任一摘要变化即失效，必须重跑 `xr finish`。

### 2.5 `RUN.md` 增加可选阶段

```markdown
## Status
phase: executing        # executing | paused | finished | closed
```

无该字段的旧运行按 `legacy` 处理，不猜成 `finished`。

## 3. `xr` 接口

### 3.1 全局参数

```text
xr [--repo <绝对路径>] [--run-id <运行标识>] <动词> ...
```

- `--run-id` 可放在子命令前后；重复或空值报错。
- 显式 `--run-id` 无效时**直接报错，不回退 `ACTIVE`**。
- 省略 `--run-id` 时才使用 `ACTIVE`，仅限人工交互。
- 解析后的目录必须是 `<repo>/.work-docs/runs/` 的直接子目录；拒绝绝对路径、`..`、逃逸软链接。
- 所有新动词都支持 `--timeout-ms`（默认 5000，正整数）。

### 3.2 新动词

| 动词 | 作用 | 退出码 |
| --- | --- | --- |
| `xr bind --session <id>` | 建立或校验绑定；已绑定同一会话则幂等 | 0 成功；1 冲突；2 参数错误 |
| `xr inspect --json` | 只读权威检查 | 0 检查成功（不代表完成）；2 运行无效；3 检查超时 |
| `xr acceptance set <id> "<statement>" --source <ref> --units a,b` | 写入/更新验收关联，追加事件 | 0 成功；1 拒绝 |
| `xr acceptance list --json` | 列出验收与覆盖状态 | 0 |
| `xr finish` | 通过检查后写 `finish.json` 并释放自身 `ACTIVE` | 0 成功；2 拒绝（保留现场） |
| `xr pause --reason "<原因>" --record "<引用>"` | 置 `phase: paused`，保留 `ACTIVE` 与材料 | 0 |
| `xr resume --confirm --record "<依据>"` | 仅恢复阶段；不启动模型、不派发 | 0；1 冲突 |

### 3.3 `inspect --json` 输出契约

```json
{
  "schema_version": 1,
  "mode": "managed",
  "run_id": "20261020-1530-v4-design",
  "phase": "executing",
  "automation_allowed": true,
  "done_met": false,
  "ready": ["u3"],
  "doing": ["u2"],
  "blocked": [],
  "stale_units": ["u1"],
  "unresolved_ops": ["toolu_01abc"],
  "acceptance_status": { "total": 2, "covered": 1 },
  "reasons": ["A2 的来源摘要不匹配"],
  "truncated_tail": false
}
```

判定规则（全部满足才 `done_met=true`）：

1. 至少一个单元，且没有 `todo/doing/verifying/failed/blocked`。
2. 每个 `done` 单元都有与当前文件摘要、当前 `verify_cmd` 匹配的 `VERIFIED` 账本记录。
3. `acceptance.tsv` 非空，全部 `covered`，且来源可读、摘要一致。
4. `acceptance.units` 中的单元全部 `done` 且证据有效。
5. `unresolved_ops` 为空。
6. 没有开放且必需的 gate。
7. 存在一个最终集成单元（`kind=integration`）且 `done`。

`mode` 取值：

- `managed`：有 `binding.json` 且验收表结构合法。
- `legacy`：无新格式标记（`RUN.md` 无 `phase`、无 `acceptance.tsv`、无 `binding.json`）。返回 `automation_allowed=false`、`done_met=false`。
- `invalid`：有标记但文件损坏/缺列/缺 `source`。不得降级为 `legacy`。

**检查失败 ≠ 未完成**：文件读不了、超时、JSON 坏了返回退出码 2/3 并在 `reasons` 里说明；调用方必须按“暂停”处理。

## 4. 恢复决策

### 4.1 单一入口

```ts
// skill/x-rail/extensions/recovery.ts
export type Failure =
  | { kind: "user_abort" }
  | { kind: "provider"; klass: ErrorClass; text: string }
  | { kind: "watchdog"; text: string }
  | { kind: "unresolved_ops"; ops: string[] }
  | { kind: "unknown"; text: string };

export type RecoveryDecision =
  | { action: "ignore"; reason: string }
  | { action: "retry_same"; waitMs: number; reason: string }
  | { action: "switch_model"; to: ModelRef; thinking: "high"; message: string; reason: string }
  | { action: "compact_then_switch"; to: ModelRef; message: string; reason: string }
  | { action: "resume_run"; message: string }
  | { action: "pause"; reason: string; handoff: boolean };

export function decideRecovery(input: {
  failure: Failure;
  current: ModelRef;
  memory: RunMemory;       // 复用 switch.ts 的现有结构
  disabled: boolean;
  snapshot: InspectSnapshot | null;  // null = 检查失败
  bindingOk: boolean;
}): RecoveryDecision;
```

**这是薄组合，不是第二套引擎**：`provider` 分支调用现有 `decideSwitch()`；`resume_run` 调用现有 `shouldContinue()`；`unresolved_ops` 与检查失败优先于两者。

### 4.2 优先级（从高到低，先命中先返回）

| 顺序 | 条件 | 决策 |
| --- | --- | --- |
| 1 | `failure.kind === "user_abort"` | `ignore` |
| 2 | `bindingOk === false` | `pause`（不写、不续、不切） |
| 3 | `failure.kind === "unresolved_ops"` 且含 `write/unknown` 副作用 | `pause`，`handoff=true` |
| 4 | `failure.kind === "unresolved_ops"` 且全部为 `read` | `pause`，提示先查结果（不自动重放） |
| 5 | `snapshot === null` | `pause`，`handoff=true`（检查器失败不当作完成） |
| 6 | `snapshot.done_met === true` | `ignore`（提示执行 `xr finish`，不发模型请求） |
| 7 | `snapshot.mode === "legacy"` 或 `phase !== "executing"` | `ignore`（本地通知交接） |
| 8 | `failure.kind === "provider"` | 走 `decideSwitch()`；`none` → `pause`（未知错误） |
| 9 | `failure.kind === "watchdog"` | 走 `decideSwitch()` 的 E5 分支，**共用** `disabled`、`memory`、上限 |
| 10 | `failure.kind === "unknown"` | `pause` |
| 11 | 无失败、`outcome=completed` | 走 `shouldContinue()` |

### 4.3 错误映射（相对现状的最小改动）

| 现有模式/新增样本 | 分类 | 主模型动作 | 备用模型动作 |
| --- | --- | --- | --- |
| `账号池暂无可用账号`、`gateway_concurrency_limit`、长 retry delay | E1 | 按上限切备用 | 交接 |
| `INSUFFICIENT_BALANCE`、`insufficient_quota`、`billing`、401、403 | E1（子原因 `balance/auth`） | **停止**，不重试不切换 | 同左 |
| `The service is temporarily unavailable`、`busy`、`upstream_error`、`stream disconnected` | E2 | 同模型 1 次，再失败切备用 | 同模型 1 次，再失败交接 |
| **新增** `Stream ended without finish_reason` | E2 | 同上 | 同上 |
| `Request timed out`、`HTTP 524`、`terminated`、`Connection error`、`ECONNRESET` | E3 | 立即切备用 | 同模型 1 次，再交接 |
| **新增** `502 Bad Gateway`、`HTTP 502`、真实 `status=502` | E3 | 同上 | 同上 |
| `unknown variant 'developer'`、422、`bad request`、其余 4xx | E4 | 切备用 1 次 | 交接 |
| 仅裸 503 或完全未匹配 | `unknown` | **暂停**并保存原文 | 同左 |
| 看门狗触发 | E5 | 共用上限后切备用 | 同模型 1 次，再交接 |
| 用户 `Esc` | E0 | 不动作 | 不动作 |

**保持不变的决策**：E2 是“同模型再试 1 次”，不是直接切模型。这是既有决策（`DECISIONS.md` C4），v4 不改。

## 5. 扩展行为

### 5.1 `host-events.ts`

```ts
pi.on("tool_call", (event, ctx) => {
  const sideEffect = classifyToolSideEffect(event.toolName); // read | write | unknown
  appendEvent(runDir, {
    type: "op_intent",
    op_id: event.toolCallId,
    detail: { tool: event.toolName, side_effect: sideEffect, input_digest: digest(event.input) },
  });
});

pi.on("tool_result", (event, ctx) => {
  appendEvent(runDir, {
    type: "op_result",
    op_id: event.toolCallId,
    detail: { is_error: event.isError, blocked: false },
  });
});
```

未绑定运行时不写（避免污染）。写失败只 `notify`，不阻塞工具执行。

### 5.2 运行绑定

- `session_start`：读 `ACTIVE` 找候选；`xr bind --session <id>`。冲突则只读提示，不自动接管。
- `agent_start`：**不再重读 `ACTIVE`**。使用已绑定的运行；未绑定时不续跑。
- 绑定信息缓存在进程内，`/x-run bind <id>` 可显式更换（只绑定，不启动回合）。

### 5.3 看门狗

- `watchdogDue` 触发 → `ctx.abort()` 并标记。
- `agent_settled` 且 `aborted` 且标记为看门狗 → `decideRecovery({ kind: "watchdog" })`。
- 执行决策的代码与普通错误**同一函数**：`applyRecovery()`。
- `disabled`、`lease !== active`、超上限、无备用认证 → `pause`。

### 5.4 边界续跑

- `agent_before_settle`：先取 `failure`（无错误则 `undefined`），再取 `xr inspect --json`（5 秒超时）。
- `asksUser` 收窄：只有明确的拍板请求（“请确认/选择/决定/拍板”或存在开放 gate 且无默认值）才停；结尾问号不再单独作为条件。
- `done_met=true` 时只发一次本地提示（`xr finish`），不发模型消息。

### 5.5 压缩

- `session_before_compact`：同步 `xr capsule`（记录耗时）；失败时用上一次胶囊并在 `detail` 标 `capsule_stale=true`。
- `session_compact_failed`：追加事件；若 `fromExtension` 且 `willRetry`，交给 `decideRecovery({kind:"unknown"})` 处理。

## 6. 完成与版本绑定

1. `acceptance.tsv` + `units.tsv` + `ledger.tsv` 形成契约摘要；任一变化使 `finish.json` 失效。
2. 单元完成后文件再变：`inspect` 把该单元列入 `stale_units`，`done_met=false`，提示 `xr verify <id>` 重跑。
3. `xr done` 幂等语义调整：已是 `done` 时仍复核当前证据；过期则拒绝并给出重验命令。
4. 放弃（`abandoned`）不满足原验收。替代单元通过 `acceptance set` 关联后才可能完成。
5. 高风险运行在 `RUN.md` 标 `review_required: true`，必须有一个独立审查单元；检查器只能验证“存在且证据有效”，不能验证审查质量。

**能力边界**：程序能检查证据存在、来源可读、摘要一致、单元状态；不能判断自然语言需求是否被一条 `true` 命令真正证明。这一层仍需计划与审查。

## 7. 并发、原子性与性能

| 项 | 方案 | 已知上限 |
| --- | --- | --- |
| `events.jsonl` 追加 | `O_APPEND` 单行写 | 多进程顺序不保证；解析时容忍残缺尾行 |
| `binding.json` / `acceptance.tsv` / `finish.json` | 复用现有 `run_lock` + 原子替换 | 跨机器共享目录不在保证内 |
| `xr inspect` | 只读；不持锁跨子进程；扩展侧 5 秒超时并回收进程 | 大仓库耗时未测 |
| `runSnapshot` | **删除**，改由 `inspect` 提供 | 扩展必须处理超时/失败 |
| 计数 | `workspace + run_id + session_id` 组合键；运行总上限仍按 `run_id` 聚合 | 旧键作为历史下限保留 |

## 8. 旧格式兼容

- `mode=legacy` 的运行：只读 `inspect`、只读 `status`；`automation_allowed=false`。
- 旧运行不自动写 `binding.json`、不自动建 `acceptance.tsv`。
- 旧工具（`task.py`）继续可用，但不得对新格式运行执行 `init/close/next` 等写命令。
- 采用新标准是**逐个显式**的：`xr bind` → `xr acceptance set` 补齐 → `xr resume`。

## 9. 不做什么（防止方案膨胀）

- 不新建调度服务、数据库、后台守护进程。
- 不实现第二备用模型、不实现自动预算收尾、不实现付费回放。
- 不自动重放 `write/unknown` 工具。
- 不根据模型自述判断子代理已完成。
- 不重写 `xr` 的现有动词，只在同一脚本内扩展。

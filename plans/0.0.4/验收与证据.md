## 1. 验收原则

用测试数据检查脚本能否正确处理记录，用真实模型演练检查执行者是否真的先拆、逐项更新和恢复。两类证据分别报告，文本中写了规则不能替代行为验证。

需求数量不是固定门槛。不以“五个”“六个”作为自动分流条件，不以文件数量或复杂度分数替代语义判断。相关结构检查只证明记录的关系一致，不证明需求没有漏识别。

运行命令、产生输出、验收通过是三件事。每项结果绑定实际输入、命令或观察方法、时间和原始证据。失败保留失败输出，不覆盖旧证据。

## 3. 先准备的反例与预期

### 3.1 拆分与记录判断

| 输入 | 必过预期 |
| --- | --- |
| 四个独立需求，各有复杂业务规则、异常路径和独立验收 | 先列工作项、依赖和验收，持久记录逐项状态，再开始实施 |
| 一个需求涉及多个入口、共享模型和大范围数据写入 | 即使只有一个需求点，也先拆分并记录 |
| 单个需求包含权限、并发和多步状态变化 | 按可独立验证的交付拆分，不因“只有一项”免拆 |
| 多个按钮改用同一个现有颜色变量，改动局部且可一次验证 | 可合为一个工作项，说明同源依据，不因数量强制完整任务目录 |
| 已有合格清单 | 核对覆盖并复用，不重新规划或重复建立任务 |
| 只读分析复杂系统 | 在回复列清单与依据，保持只读不落盘 |
| 只要求方案文档 | 只写授权位置，不开始实现或创建实施记录 |

模型演练逐场景核对实际动作顺序。仅搜索到“复杂度”或“拆分”字样不算通过。

### 3.2 结构与依赖检查

在 `scripts/test-task-checks.py` 复用既有临时任务夹具，新增以下反例与正例，不引入测试框架：

- 重复需求或工作项标识、遗漏需求覆盖、工作项引用未知需求，均拒绝。
- 工作项缺少范围、验收或必需标记，均拒绝。
- 引用未知验收、未知依赖、自依赖或环形依赖，均拒绝。
- 每个契约工作项恰好对应一条状态；重复、缺失和多余状态均拒绝。
- 换行、非法分隔符和无法解析的引用明确报错，不静默丢数据。
- 一需求多工作项、多需求共享工作项、合法无环依赖均可通过。
- 未使用新格式的历史契约保持原检查行为；显式升级后完整应用新规则。
- 有新格式标记却缺记录时拒绝，不自动退回旧格式。

### 3.3 状态、命令和完成检查

在现有测试中用原生命周期构造完整任务，检查下列行为：

1. `start` 初始化全部工作项为待开始，保留现有验收初始状态；再次启动拒绝覆盖。
2. `update` 只能更新已存在工作项；缺少原因或下一动作拒绝。
3. 依赖未满足不能进入实施状态；提前准备若确实独立，应先按契约变更加入独立工作项。
4. 进入阻塞必须记录原因与解除条件，解除后必须给恢复动作。
5. 实现完成进入待验证；未验证不能直接标成已验证。
6. 关联验收失败、证据过期或缺必需审查时，已验证声明或整个任务完成被拒绝。
7. 仅有提交版本或子代理完成通知，不能替代验收。
8. 必需项不能跳过；可选项只能按契约预先记录的理由跳过。
9. 一项受阻、另一项可执行时，摘要分别展示，不宣称全部停工。
10. 多项进行中与活动工作项列表一致，未知或矛盾引用拒绝。
11. 完成候选中不得保留活动工作项；下一动作更新为交付或结束说明。只检查已知结构矛盾，不声称脚本理解了任意中文动作。
12. 正常更新不刷新真实进展；确有新结论的 `--progress` 继续要求原因。
13. 未通过候选、并发状态修改和契约变更保持现有防覆盖行为，正式状态及索引保持原内容。
14. `summary` 显示已知计数、逐项状态、证据有效性、阻塞和可执行项，并保持只读。

只读摘要应以更新前后文件内容对照证明。失败保护以正式状态、契约和索引的原字节对照证明，不以退出码单独代替。

## 4. 运行、并行与审查场景

### 4.1 已授权并行

准备两个互不依赖、不共享写入路径的实现任务和一个集成任务。先确定接口，再由子代理分别在隔离目录并行实现，集成依赖两个实际产物。另设一个共享配置修改，验证它只由一个写入者负责。

再准备一个只依赖其中一项的后续任务，核对前置完成后重新判断就绪状态，不因其他无关任务仍运行就一律等待整批结束。确需等待时记录真实资源或集成原因，不改变任务依赖来掩饰串行。

记录工作项、执行者、开始与结束时间、目录、原运行标识、正式输出引用、验证结果和主会话消费记录。通过依据是子代理承担实际实现、独立任务确实重叠执行、产物可集成、父状态基于实际结果更新，不是代理数量或仅有并行审查。适合并行却串行的任务必须有具体原因；还需验证共享文件或环境无法隔离时不会强行并行。

没有委派授权时，用同一清单串行并报告该项未验证，不自动派发。真实测试若使用数据库或构建目录，必须隔离这些可写资源。

### 4.2 等待与恢复

- 有独立工作时继续执行；无独立工作时交还控制权，完成通知到达后消费结果。
- 通知到达不直接把工作项标成已验证，必须检查实际产物及受影响验收。
- 模拟一次交接或宿主支持的上下文压缩，恢复时续用原任务编号，选取下一可执行项。
- 原子运行已结束时核对产物；可恢复时续接原运行；不可查时明确未知或阻塞，不重复启动。
- 原生通知任务不因缺少消息就反复轮询。确需显式等待时记录实际依赖，不把这段时间全部算浪费。

### 4.3 限制和超时

用合成回执或安全可控的失败演练区分模型请求超时、工具超时和子运行期限。不人为发起大规模请求来制造故障。

检查执行者是否报告准确错误、运行引用、已保存事实和恢复动作。实际容量信号不可得时应说明未知，不能根据当前配置倒推历史，也不能编造剩余百分比。

沿用已有成本授权、无进展和重复失败规则。不限成本不自动解除委派或发布限制。仅自述“预算紧张”不能作为已触发宿主硬限制的证据。

### 4.4 审查与定向复核

固定实现输入，审查集中返回问题，集中修复，再验证相关改动。保留原运行可恢复性检查；按风险和契约执行必要独立审查。

准备相关代码变化、无关文件变化、审查报告变化三类场景。相关变化必须让旧证据失效；无关变化在实际验收范围外可以复用；报告被修改也必须被识别。更新进度不应使代码证据自我失效。

## 6. 交付矩阵与效果观察

实施交付逐项列出：验收名称、实际观察结果、证据路径、输入版本、未验证原因和恢复第一步。状态明确区分实现通过、真实行为已验证、等待授权和未验证。

观察总耗时、模型响应时间、独立工作的重叠时间、重复读取、编辑失败、审查轮次、主会话容量和因限制暂停次数。记录宿主可得的实际数据；无法获得时写未知。比较任务范围、环境和模型差异，不把缓存读取量等同于实际费用，不把助手耗时简单相加后将剩余时间认定为用户空闲。

完成标准：

- 结构、流转、失败保护和兼容的必需自动检查实际通过。
- 真实模型能对复杂或大范围需求先拆分、持久记录、逐项执行并恢复。
- 必需并行或审查验证取得相应授权与实际证据。
- 用户已有修改保留，代码、文档和示例口径一致。
- 仍有必过项受阻时保持未完成，交付已有证据与解除条件。

不以固定提速比例、代理数量、工具次数或审查轮次作为版本完成条件。

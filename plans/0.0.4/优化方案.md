# x-rail 0.0.4 优化方案

> 本文保留实施前确定的目标行为与建议实施方式；正文中的“未实施”仅指原始计划快照，不维护当前交付状态。
> 当前集成状态、回归结果和未验证限制以同目录 `README.md` 及 `.work-docs/tasks/20261015-01-v004-work-items/` 为准。
> 需求与设计已在本次讨论中确定，实施不重新打开已确定的选择。

## 1. 现状、问题与影响

### 1.1 当前能力

当前仓库已经有以下机制，本版继续复用：

- `skills/x-rail/SKILL.md` 区分交付结果、记录强度、阶段、授权和成本策略。
- `playbooks/plan.md` 要求拆成可验证任务，但没有把逻辑独立性、复杂度、改动范围和依赖统一为拆分与记录的入口规则。
- `state.md` 记录整个任务的阶段、状态、下一动作及逐项验收结果。
- `task.py` 提供 `start`、`update`、`summary`、`finish`，分别用于启动、更新、摘要和完成。
- `task_checks.py` 检查契约、证据、输入摘要及父子依赖。
- `templates/long-task.md` 记录独立依赖和原子代理运行引用。

工作项指一次可独立验证的实施交付，类似前端看板中的一张开发卡。它不同于需求点，也不同于契约中的验收条件。

### 1.2 要补的缺口

| 现状 | 问题 | 影响 |
| --- | --- | --- |
| 有实施计划和整体状态 | 缺少统一的逐项进度结构 | 难以直接看出剩余工作和可并行部分 |
| `next_action` 是一行文本 | 容易串起多项工作，或完成后保留旧动作 | 恢复时重新理解，甚至重复执行 |
| 子代理主要承担审查 | 实现细节集中在主会话 | 上下文持续增大，独立工作串行 |
| 支持异步通知 | 派发后立即阻塞等待 | 有独立工作时也无法重叠执行 |
| 验证和审查绑定当前输入 | 审查后分散修改，反复重审 | 重复理解相同材料 |
| 有默认预算和不限成本策略 | 把自估容量、费用和请求超时统称“预算” | 停止理由不清，反复要求用户继续 |

### 1.3 历史证据的边界

本方案参考会话 `01a13e31-6da5-7092-8f70-4c9f4d9b65af`。原始日志位于：

```text
/Users/yuanxj/.pi/agent/sessions/--Users-yuanxj-Documents-working-website--/2026-10-15T06-13-09-159Z_01a13e31-6da5-7092-8f70-4c9f4d9b65af.jsonl
```

已观察到 12 次成功子工作流启动、13 个子运行；12 次等待累计约 59.7 分钟；八次模型错误均为 `Request timed out.`，即请求等待超时。三次收尾文字提到预算用尽。

这些数字不证明能节省同等时间。依赖审查的等待可能必要；当前模型配置不证明历史生效配置；请求超时原因仍待查。主会话日志也不能代表全部子运行成本。整段日志时间跨度不能直接当连续工作时间。

## 2. 范围与非目标

### 2.1 纳入本版

1. 按逻辑独立性、复杂度、改动范围和依赖先拆任务并记录，不设需求数量门槛。
2. 建立需求、工作项、验收之间的对应关系。
3. 逐项状态、关键事件更新和一致性检查。
4. 拆分后优先让子代理并行实现无依赖且资源不冲突的任务，明确文件所有权和结果汇总。
5. 依据实际限制恢复，减少主会话上下文重复。
6. 集中修复、定向复核和当前证据绑定。
7. 自动检查、真实行为演练及完整交付。

### 2.2 不纳入本版

- 不新建通用调度服务、数据库、看板网页或后台守护进程。
- 不默认提高模型容量、延长全局超时、改供应商或关闭思考。
- 不开发全局用量注入扩展。先验证现有宿主信号是否足够，缺口单列后续方案。
- 不增加新的任务等级，不因需求数量直接进入严格记录或长模式。
- 不自动迁移历史记录，不重写历史快照。
- 不取消权限、必过验收、独立审查、失败熔断或成本限制。
- 不把这次文档请求当成本版实施、子代理调用或外部发布授权。

## 3. 执行前先拆清楚

### 3.1 触发规则

用户已澄清：“‘超过五个需求点’不作为固定值，例如识别出 4 个独立但复杂逻辑，或者改动范围大的需求点，那也是要拆分任务并记录的。”本版以这次澄清为准，不保留六个及以上的数量门槛。

执行者先识别可单独判断是否满足的用户结果，再结合相关代码判断以下条件。出现任一情况，就必须在实施前拆清工作项，记录判断依据，并在执行时维护逐项状态：

- 存在多个独立且复杂的逻辑，各有业务规则、异常路径或验收。
- 改动范围大，跨多个模块、入口、共享逻辑或数据结构，需要分别验证影响。
- 单个需求内部包含多步状态变化、权限、并发、数据写入等复杂逻辑，不能靠一次局部改动完整交付。
- 存在前置依赖、多人协作、外部等待或交接，需要跟踪先后关系和未完成项。

需求数量只是辅助观察，不按段落、句子、文件数或编号数打分，也不设置新的复杂度分数门槛。四个独立复杂需求必须拆，一个大范围需求也必须拆；多个简单、同源且可一次验证的改动可以合为一项，但要说明依据。已有清单先核对并补齐，不重复设计。脚本只能检查所记录的关系，不能证明模型正确理解了全部自然语言需求。

触发上述条件的实施任务需要持久记录计划与逐项状态，沿用严格记录及其现有证据机制，不能仅在思考或聊天中列一次清单。普通、局部且容易一次验证的实施仍可采用会话内清单。只读分析仍只在回复中列清单，不落盘；用户仅要方案文档时只写授权位置，不代建实施任务。需要拆分和记录不自动授权委派，也不因工作项多就自动进入长模式。

### 3.2 每个工作项的最小定义

每项必须有稳定名称、可观察结果、对应需求、前置依赖、文件范围、执行者、必需或可选、验收引用。禁止把“读代码”“创建目录”“更新时间”单独包装成有业务进展的工作项。

一个需求可以对应多个工作项；一个共享实现也可覆盖多个需求。每个需求至少被一个工作项覆盖；每项至少关联一个验收条件。独立研究结论也可成为交付，但需有明确问题和检查方法。

开始前核对全部覆盖、依赖无环、共享写入已安排。只要未改变范围或敏感授权，不要求用户逐项批准普通可逆步骤。

## 4. 计划与状态只维护一套事实

### 4.1 存放职责

| 文件 | 职责 |
| --- | --- |
| `contract.md` | 目标、边界、需求目录、工作项定义、验收与授权 |
| 任务内实施计划 | 实施细节、调用关系、测试方法，引用工作项，不维护第二份状态 |
| `state.md` | 整体状态、逐项当前状态、证据引用、阻塞与下一动作 |
| `audit/runs.json` | 独立子任务的真实运行标识与产物引用，沿用现有依赖绑定 |
| `evidence/` | 实际命令输出与观察记录 |
| `handoff.md` | 引用原状态，补恢复第一步和易错点 |

同一目标阶段切换、压缩、提交、暂停或恢复均续用原任务编号。只有目标确实独立、需要单独契约的子任务才分配编号，并由父契约引用。

### 4.2 建议采用的最小结构

为避免另造状态数据库，在现有逐行记录上增加以下结构。下列字段和命令都是本版拟新增接口，不是当前可执行示例。

严格新任务写 `work_items_schema: 1`。普通任务不使用这些字段。新建严格实施任务必须采用；其他严格任务按是否存在工作清单采用。已有任务保持原格式，只在实际需要清单时显式升级契约并保留快照，不能静默补造历史。

```text
# contract.md，示例：需求 R1 表示域名换址，W1 表示换址服务端工作项，A1 是其验收条件
work_items_schema: 1
requirement:R1|outcome=管理员可修改站点域名
work_item:W1|title=换址服务端|requirements=R1|depends=none|scope=src/domain.ts,tests/domain.test.ts|required=yes|acceptances=A1|skip_reason=none

# state.md，与上述 W1 一一对应；A1 的真实结果继续使用现有 required_verification 行
work_item_state:W1|status=pending|owner=unassigned|evidence_refs=none|commit=none|blocked_by=none|unblock_condition=none|reason=尚未开始|next_action=先读相关服务和测试
active_work_items: none
```

字段值不允许换行或包含分隔符 `|`。逗号用于引用列表；标识符采用字母开头的字母、数字、下划线与连字符。路径和文本若需要无法表示的内容，应报明确错误，不能静默截断。工作范围最终仍受整个契约限制。

工作项状态不复制 `passed` 验收结论，只引用证据。检查器从原验收记录读取结果与输入有效性。提交版本仅是辅助事实，不作为必填完成证据。

工作项名称和范围变化按契约变更处理；执行者、进度和阻塞变化走状态更新。不得修改已封存契约中的清单来规避未完成项。

### 4.3 状态与流转

| 工作项状态 | 含义 |
| --- | --- |
| `pending` | 待开始 |
| `in_progress` | 进行中 |
| `awaiting_verification` | 实现已有，等待必过验证 |
| `needs_fix` | 验证或审查指出必须修复 |
| `blocked` | 暂时无法推进，记录原因和解除条件 |
| `verified` | 关联验收全部通过且证据适用于当前输入 |
| `skipped` | 仅可选工作项可跳过，必须引用契约中的跳过理由 |

正常流转为待开始、进行中、待验证、已验证。待验证可进入需修复，再回到进行中。非终结项可以阻塞，恢复时保留原因。依赖未满足不能开始实施；可提前准备的工作应在计划中表达成真实的独立交付，而非绕过依赖。

已验证项的输入变化时，摘要显示证据过期，完成检查拒绝放行；执行者通过更新将其退回待验证或需修复。脚本不在只读摘要时暗改状态。可选项的已验证与已跳过均须明确，不能靠空白记录推断。

整个任务继续使用现有 `in_progress|done|blocked|stopped|cancelled`。多项同时进行时，`active_work_items` 可记录多个工作项，主会话对状态文件保持唯一写入权。

### 4.4 更新事件与下一动作

开始、实现完成、新验证结果、审查返回、阻塞或解除、重要阶段变化、提交、压缩和交接前核对相关状态。普通读取和每行编辑不更新。

整体 `next_action` 写一个能直接执行的第一动作，其他待办留在工作项中。某项受阻但其他工作可继续时，不把整个任务标为阻塞。任务完成候选必须把下一动作改成明确的交付或结束说明，不保留“等待审查”等旧动作。

沿用 `update --progress` 的真实进展要求。状态改字、换执行者和更新时间不自动刷新最后进展时间。

## 5. 在现有命令上补逐项检查

建议扩展 `task.py update`，增加工作项标识、状态、执行者、证据引用、提交和逐项阻塞字段；现有参数继续表达整体状态。工作项更新须提供原因与下一动作，前缀使用 `--item-`，避免与整体参数混淆。

建议命令形态如下，仅作为实施接口约定：

```text
task.py update TASK_DIR --item W1 --item-status in_progress \
  --item-owner parent --item-reason 开始换址服务端 \
  --item-next-action 读取换址服务和测试 \
  --next-action 读取换址服务和测试
```

实施时完整参数为 `--item`、`--item-status`、`--item-owner`、`--item-evidence-ref`（可重复）、`--item-commit`、`--item-blocked-by`、`--item-unblock-condition`、`--item-reason`、`--item-next-action`。未传的既有值保留；清空使用明确的 `none`，不能把遗漏解释为删除。

| 入口 | 新增职责 |
| --- | --- |
| `start` | 校验静态定义并初始化全部工作项为待开始 |
| `update` | 更新已存在工作项，检查状态流转、依赖和暂停原因 |
| `summary` | 输出需求覆盖、工作项计数、实际状态、过期证据、阻塞和可执行候选 |
| `finish`、`complete` | 除原有完成检查外，要求所有必需工作项已验证、可选项明确处理 |

解析、状态更新、完成检查共用同一组工作项检查函数。不增加第三方包，不让命令行或摘要成为第二份状态源。完成时继续校验原验收、审查、输入和依赖，不能仅检查工作项标签。

新格式必须拒绝重复名称、未知引用、依赖环、自依赖、遗漏状态和必需项跳过。候选失败保留正式状态与索引；并发修改检测沿用现有机制。旧格式不因缺少新字段批量失败，但也不能冒充已采用本版逐项检查。

## 6. 已授权后按依赖并行

拆分任务后，优先把无依赖、或前置已满足且彼此没有依赖的工作项交给子代理并行实现，不只把子代理用于事后审查。主会话负责共享约定、调度、集成和最终验收，避免自己包揽全部实施。

每轮从清单选出当前可执行的工作项，核对文件、数据库、构建目录等资源是否冲突，再分配给子代理。一个任务完成后重新检查后续依赖，及时启动新就绪项，不必等待所有同批任务结束。并发数量按独立工作数量、宿主能力和集成成本调整，不固定为两条，也不追求用满额度。

适合并行却选择串行时，在现有状态或决定记录中说明具体原因，例如任务过小、接口尚未稳定、共享资源无法隔离或宿主能力受限。无依赖不代表可以同时写同一文件，能隔离实现的也仍须核对合并冲突。

执行时依当前用户或项目授权核对委派权限。这次补充确立本方案的并行优先要求，不表示立即实施或启动子代理，也不构成其他任务的永久委派授权。未获授权时按清单串行并记录原因。

- 共享接口、公共配置和集成由一个写入者负责。
- 并行写入者使用独立工作副本，类似各自的前端开发目录；分配前核对宿主隔离要求。
- 运行验证也可能写数据库、缓存和构建目录，不能一概视为只读，必须明确环境所有权。
- 子代理接收工作项、固定输入、允许路径、依赖、验收、授权、成本策略和正式输出绑定。
- 父会话消费实际产物、差异和验证，再更新父状态；子代理完成通知不自动通过父验收。
- 依赖有序的不同工作项可以在同一个被授权的工作流中协调，遵循宿主当前单工作流和单写入者规则。

派发异步运行后，有独立工作就继续；没有独立工作就交还控制权，等原生通知。需要结果才能继续的位置才汇总。只有宿主允许且同轮确需非通知任务结果时才显式等待，不把等待时长直接当浪费。

## 7. 依据实际限制续跑

### 7.1 分开处理限制

| 类型 | 依据与动作 |
| --- | --- |
| 成本与总量 | 沿用当前任务授权和现有成本策略，不能擅自取消默认规则 |
| 上下文容量 | 采用宿主实际用量与压缩信号；信号不可得就写未知，不编造百分比 |
| 模型请求超时 | 保存准确错误与当前事实，核对请求层，不套用工具超时设置 |
| 工具或子运行超时 | 保存实际运行标识、已产出内容、目录和宿主限制 |
| 无进展、重复错误、验证失败 | 保留原熔断规则，不能以不限成本为由持续重复 |

不能仅凭“感觉容量紧张”宣称硬上限已触发。无法继续时说明实际已知、未知和恢复第一步。实际压缩按宿主能力执行，压缩后核对状态、工作区和证据，不要求用户重复批准同范围普通推进。

明确不限成本授权持续到本任务结束或用户收紧。含糊文字由模型结合上下文理解，不在脚本中猜错别字含义。授权仍不解除宿主硬限制、委派边界或敏感动作确认。

### 7.2 缩小主会话输入

主会话读取与当前工作项有关的材料，子代理汇总结果、证据、风险和恢复引用，不复制全部施工过程。大量测试输出提取明确通过计数与失败项，原始证据仍保存。

修改前读当前代码，局部修改优先精确编辑。批量脚本适合机械变更，但要检查命中数量与差异，不一刀切禁止。按内容量而非工具名称判断是否节省上下文，批量工具返回全文同样可能膨胀。

恢复时先读总清单与状态，再核对必要证据。原运行先查再恢复；基础设施故障不能静默改协议、重复启动或把主会话核对冒充独立审查。

## 8. 审查集中处理，修复定向复核

完成一批实现和自检后固定当前输入，再派发必要独立审查。审查集中交回必修问题，执行者集中修复，然后重跑受影响检查。

优先恢复原审查运行复核修复；不能恢复时记录原因并按宿主规则建立同角色替代。原审查复核不能替代契约要求的独立最终审查。

审查后修改相关代码或报告时，更新受影响证据。无关文件变化不自动使全部证据失效，但相关范围由实际调用和验收决定，不能通过缩小输入声明逃避重审。状态文件本身不作为代码审查输入，防止记进度就使证据自我失效。

非阻塞建议记入现有决定或后续事项，不在收口时无限顺手改。必修问题不能改成可选来减少轮次。

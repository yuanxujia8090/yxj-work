## 1. 结论先说

### 1.1 这次会话最明确的实际故障：provider 错误触发模型切换

日志直接证明两次主模型错误：

- `2026-10-17 15:28:04`：`503: ... account_pool_forbidden`。
- `2026-10-17 15:28:20`：同类 `503` 再次出现。
- `15:28:20`：记录了 `x-failover`，模型从 `openai26/gpt-6.1-sol` 切换到 `bai/deepseek-v4.1-flash`。

这说明该会话确实经历过一次 provider（模型服务提供方）故障，但故障恢复链路在这条普通错误路径上实际工作了：切换后会话继续产生大量工具调用。

### 1.2 没有证据证明 180 秒 watchdog 是这次会话的中断原因

会话里有一次：

```text
2026-10-17 16:28:11  This operation was aborted
```

但同一时段没有出现 `watchdog` 事件、看门狗提示或明确的看门狗标记。随后立即出现 `agent-summary` 和 `compaction`，会话也没有在此结束。因此只能确认“发生过一次宿主 abort（中止）”，不能确认它由 180 秒 watchdog 触发。

这一区别重要：`abort` 是现象；`watchdog` 是可能的原因。当前日志只证明前者。

### 1.3 会话最后不是“正常完成”，而是停在一个未收束的工具调用回合

文件最后一条记录是：

```text
第 777 行：assistant，stopReason=toolUse
```

当时模型正在规划状态修复和并发工具调用，之后没有新的 assistant 完成消息、用户中止记录、handoff（交接）记录或明确的任务完成记录。

因此最终状态应写成：**会话日志在工具调用流程中结束，原因未被日志直接标明**。不能写成“watchdog 导致停止”，也不能写成“任务正常完成”。

### 1.4 长时间未收束，主要表现为流程过长，而不是已证明的 run 级停止

该会话从 `11:53:50Z` 到 `23:53:38Z`，跨越约 12 小时，但其中包含很长的宿主等待、上下文压缩和人工/系统介入间隔：

- `112 → 113`：约 2023 秒，之后发生模型切换。
- `264 → 265`：约 24170 秒，之后发生上下文压缩。
- `625 → 626`：约 305 秒，是子代理结果返回间隔，不是 watchdog 证据。
- `760 → 761`：约 45 秒，随后仍继续执行。

日志更支持以下解释：

1. 上下文变大，触发多次压缩和清理；
2. 子代理或工具调用等待时间较长；
3. 模型持续修改、测试、复查，工作边界不断扩大；
4. 测试结果与后续修改交错，导致无法形成稳定的最终冻结点。

这些因素会造成“任务拖很久、像反复中断”的体感，但不等于已经触发 `x-run-guard` 的连续无进展停止保护。

## 3. 证据分层

### A. 目标会话直接证明的事实

1. 主模型发生 `503 account_pool_forbidden`。
2. `x-failover` 记录出现，模型切换到 bai，之后会话继续。
3. 发生过一次 `This operation was aborted`，但原因没有标记为 watchdog。
4. 发生过一次 Cloudflare `520`，之后会话仍继续。
5. 多次上下文压缩之后，工具调用和代码修改继续进行。
6. 会话末尾停在 `assistant stopReason=toolUse`，不是明确完成或交接。
7. 后期出现大量修改和测试，测试与后续修改交错。

### B. 外部审查报告支持的系统性风险

`plans/v3/review/gork-20261017-x-rail-v3-代码审查报告.md` 用真实 Pi 1.3.0 和 mock provider（模拟模型服务）复现了以下风险：

1. watchdog 调用 `ctx.abort()` 后，Pi 可能跳过 `agent_before_settle`，导致预期的 E5 切换不执行。
2. 在 `agent_before_settle` 中调用 `ctx.compact()`，可能让续跑被取消。
3. 没有 active run（当前活动任务）时，多个会话共用 `session` 失败计数。
4. Pi 的错误格式如 `401: {...}`，可能不符合旧分类器的匹配规则。
5. `xr` 并发读改写、验证缓存和状态终态存在风险。

这些结论说明系统设计确有中断风险，但它们来自另一份独立复现报告，**不是目标会话 `01a149b6` 中的直接事件证据**。不能把它们写成“本次会话已经触发”。

### C. 目前只能作为推测的原因

以下解释有合理性，但目标日志不足以确认：

- `16:28:11` 的 abort 可能与 watchdog 有关；也可能是用户、宿主、上下文处理或其他中止路径。
- 最后一次未收束可能与上下文压力、模型响应中断、宿主等待或会话被外部结束有关。
- 多次压缩可能增加了重新读取、重新规划和重复修改的概率，但日志没有直接证明压缩导致任务停止。
- 后期工作范围扩大，可能使会话更容易撞上宿主或模型服务的边界，但没有单独的 run 级预算触发记录。

### 4.2 原报告需要补充或收紧的结论

#### （1）“约 9 类停止路径”不能当成本次会话的停止原因

这个数字是源码和规则清单的分类结果，不是本次会话的触发统计。新报告应明确：

- “存在 9 类可能停止路径”属于系统静态分析；
- “本次实际触发了哪条”必须有会话事件、错误文本或状态文件支持；
- 目标会话只直接证明 provider 错误和一次未归因 abort，没有证明 9 类中的 watchdog、无进展、gate 或续跑上限被触发。

#### （2）180 秒 watchdog 的风险判断成立，但证据等级应标为“外部复现支持”

原报告把 watchdog 作为重点风险是合理的；但针对 `01a149b6`，不能说“watchdog 导致了 16:28 的 abort”。更准确的写法是：

> 目标会话发生一次 abort，但没有 watchdog 事件；独立真 Pi 复现证明 watchdog 路径本身存在恢复失败风险，因此它是系统性高风险，不是本次已证实原因。

#### （3）“会话多次中断”需要拆成三种现象

原报告如果只用“中断”一词，会把不同事情混在一起：

1. **模型服务错误**：503、520，可能触发切换，但会话可继续。
2. **当前回合中止**：`This operation was aborted`，本次原因不明。
3. **会话长时间不收束**：大量工具调用、上下文压缩和等待，最后停在 toolUse。

这三种现象不能都归类为 x-rail 的限制条件触发。

#### （4）原报告对“频繁中断”的判断还不能量化

目标会话只有一个，且没有记录完整的 watchdog 计时、run 级计数器和每次恢复结果。因此目前只能说：

- 系统存在多套可能中断或降级的机制；
- 本次实际 provider 错误至少发生两次，另有一次 520；
- 不能由这一个会话估计 watchdog 或 run 级停止的频率。

## 5. 对本次会话“为什么没有快速完成”的判断

按证据强弱排序：

### 主要原因：范围持续扩大，修改与验证交错

`23:30–23:51` 期间，目标会话持续修改 `x-run-guard.ts`、`x-failover.ts`、`xr`、测试和相关文档，并多次重新运行验证。部分验证输出为通过，但通过之后仍继续修改。

这会产生一个明确问题：**某次测试通过只代表当时文件状态通过，不能代表最后文件状态通过。**

### 次要原因：上下文压力和多次压缩

会话有 3 次 compaction，且多次智能清理。压缩后仍能继续工作，说明压缩没有直接杀死会话；但压缩会增加恢复、重读和重新规划成本。

### 已确认但不是主因：provider 错误

两次 503 和一次 520 都打断了部分模型回合，并触发至少一次模型切换。它们解释了部分中断和延迟，但不能解释整个 12 小时会话。

### 未确认：watchdog 和 run 级无进展保护

没有 watchdog 文案、handoff 文件事件或无进展计数变化的直接记录，不能把它们列为本次会话的已确认原因。

## 6. 修订后的最终判断

### 关于本次会话

> `01a149b6` 的直接故障证据是 provider 侧 `503 account_pool_forbidden` 和一次 Cloudflare `520`；普通 failover 至少成功执行过一次。会话另有一次 `This operation was aborted`，但日志不足以归因 watchdog。会话最后停在未收束的工具调用回合，没有明确的完成、交接或用户中止记录。长时间未收束主要与上下文压缩、子代理等待、范围扩大以及修改后继续验证有关。

### 关于 x-rail v3 限制设计

> 原报告统计的 28 类限制和约 9 类停止路径，适合作为源码与文档风险清单；不适合作为本次会话的触发统计。原报告关于“watchdog 首先中止回合、规则层级重叠、需要真实运行数据再调参”的方向正确。应补上证据分层：目标会话事实、独立真 Pi 复现、源码推断和未证实推测必须分开。

### 关于是否应立即改阈值

仍然不建议直接调大或删除 180 秒 watchdog、验证超时、failover 上限或续跑上限。当前更急的不是数值，而是记录完整的事件链：

```text
触发时间 → 限制层 → 触发规则 → 当前模型 → 当前 run/unit → 恢复动作 → 恢复结果 → 最终状态
```

只有拿到多次真实运行数据后，才能判断到底是 watchdog 过短、provider 错误过多、压缩路径不安全，还是任务范围与验证边界没有及时冻结。

## 7. 建议的后续取证顺序

1. 在真实宿主中为 watchdog、abort、failover、handoff、compaction 增加同一条可关联的事件编号。
2. 每次模型切换记录原始错误、分类结果、run id、session id 和恢复结果。
3. 每次续跑记录状态指纹是否变化，明确区分“模型回合结束”和“run 停止”。
4. 在代码冻结后再跑最终验证；验证后不再修改被验证文件，除非开启新的修复轮次。
5. 用多次真实会话统计 watchdog、provider error、compaction、handoff 的触发率和恢复率，再决定是否调参。

**复核结论：原报告方向基本正确，但对目标会话的因果判断需要收紧。已确认的是 provider 故障和未归因 abort；watchdog、run 级无进展停止属于系统性风险，不能作为本次会话的已证实原因。**

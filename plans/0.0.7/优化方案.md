# x-rail 0.0.7 优化方案

> 状态：v3 本地实现与自动验证完成；真实模型服从、效率对照及主干合入未验证/未执行。
> 日期：2026-10-19。
> 目标：让审查尽早交出可验收结果，故障后续接剩余范围，减少主会话重复全量审查。
> 组织：复用现有阶段卡、`xr`（v3 的任务记账命令）、单元清单、运行事件和报告；保持一个状态来源。
> 工具：Python 标准库、现有 shell 检查与 Pi 子代理工具，不新增依赖或调度服务。

实施者按第 6 节逐项推进。使用子代理时沿用当前授权、宿主协议和单写入者规则；本计划不要求固定代理数量或每项额外独立审查。

## 设计依据：先保住交付，再减少机制

像表单自动保存一样，恢复的前提是知道哪些内容已经可靠保存，哪些仍需补齐。第一性原理在这里指：从必要结果推导机制，而不是从现有阶段、代理数量或时限倒推工作。最小目标只有三项：**及时交付具体结论；故障前的有效结果可以复用；同项工作不重复启动。**

不可删约束：实际输入版本、检查项覆盖、必需独立审查、状态与证据持久保存、单写入者及授权。奥克姆剃刀在这里指：达到同样结果时，选择假设更少、维护更少的实现。因此复用原单元状态、事件日志和一份报告，不新建调度系统、状态枚举或必经阶段；不将“多代理”“无时限”或“更多记录”本身当成优化。

三角色审查的结论及取舍见 [DECISIONS.md](./DECISIONS.md)。下文明确区分已确认源码缺口、设计选择和待测收益。

## 3. 目标行为

### 3.1 开始时只做能派发的最小准备

1. 固定比较起点与终点提交、纳入的未提交差异、用户要求和项目修复边界；沿用同一份差异清单。
2. 只读足够划定功能边界的材料，不由主会话先审完再派给子代理重审。
3. 判断哪些检查由确定性命令完成，例如语言键集合比对、旧品牌字符串统计；命令结果交给相关审查者解释，不为机械统计另配代理。
4. 核对宿主支持的代理名、工作流入口、输出绑定和异步通知方式。首次失败后读准确报错，修正具体参数；不原样调用，也不切其他协议绕过失败。
5. 正式审查固定输入后再派发；读取中发现必要调用方可以扩大只读输入，但要说明对应检查缺口，不能悄悄扩大修改范围。

只读审查像多个组件共同读取同一个配置：允许输入重叠，禁止报告写入冲突。当前 `xr next`（领取下一项）对所有执行中单元无条件检查文件范围重叠，已经确认会把共读误判为冲突。必须修改这个实际入口：两位只读审查者可共读输入，各自独占输出；读写业务文件冲突、相同报告写入冲突仍拒绝。实现单元与共享测试资源保持独占写入，不能缩小输入声明逃避检查。

### 3.3 阶段报告从第一次结论开始保存

“阶段报告”像自动保存的表单草稿：记录已经确认的内容，后续追加，最终再核对全量覆盖。它不依赖模型在最后一分钟还能收到请求。

每个审查者首次完成一个可判断的文件组或行为链后即保存；后续在新结论、范围变化、错误、交接与结束时更新。机械逐行保存和只有“正在读取”的进度不算产出。

报告头只写一次输入版本、工作区与宿主运行引用；阶段更新仅追加已完成检查项、结论证据和剩余范围。实际执行命令才补命令结果，结束或故障时才补终态与恢复第一步，不要求每次重写全部字段。

```text
报告头：比较起止提交与差异范围；工作区；原运行引用
阶段结果：本次完成的检查项；结论及位置/依据；仍待审的范围
按需补充：实际命令与结果；准确错误；终态；恢复第一步
```

首份报告接受标准：完成至少一个明确检查项，能追到固定输入，有具体结论与依据，并列剩余范围。“已读邮件文件”拒收；指出具体邮件入口如何拼接落款、动态字段如何转义并列待查入口，可以作为阶段结果接收。它仍不代表整批完成。

写入方案二选一，由宿主能力决定，无需用户拍板：

- 审查业务代码保持只读，允许各自写独立的 `notes/<单元>-report.md`；父会话独占单元状态与汇总，不修改活动子代理的报告。
- 宿主只支持最终输出时，将每个可验收小批作为一次交付，并由父会话消费最终结果；明确记录阶段保存不可用。输出绑定只负责保存实际返回，不能保证进程硬停仍有报告。

当前用户明确只读且不允许落盘时，只能使用宿主保留的消息或更小批最终回复，不绕过只读限制创建文件。提前检查点能力只有核实支持后使用；本版不新增一个必需倒计时参数。

### 3.4 明确四种时间，移除冲突的自动动作

| 时间/信号 | 拟采用规则 |
| --- | --- |
| 用户约定的整体期限 | 保留真实来源，接近期限先交已确认内容和剩余范围，不临时降低验收 |
| 模型请求超时 | 记录准确错误、原运行、是否仍活跃和已存结果；不能通过增加子运行时限解决 |
| 子运行总时限 | 沿用宿主与代理配置；默认省略 `timeoutMs/maxRuntimeMs`（子运行总时长覆盖参数）。用户或更高规则要求时才设置并记录来源 |
| 无有效进展 | 看新结论、证据和覆盖变化；重复读取、更新时间不算。沿用既有提醒，不能用固定轮数直接证明卡死 |

需统一 v3 `stages/execute.md`、`stages/review.md`、`references/brief-template.md` 与 `references/failure-modes.md` 中固定 15/25/45 分钟、超时不续接、自动再派和旧模块的冲突。规则优先级沿实际宿主及用户指令，不能由某个文件自称“唯一权威”改变。

联合加载时：当前用户或更高规则明确规定的运行期限优先；只有一般任务时间建议时，不转写为子运行参数；同层规则仍有直接冲突且无法从适用范围消解时，保留准确条款，暂停受影响的派发，交付已有内容与未解决原因，不静默选一套规则，也不越过只读边界。website 的现有 8～10 分钟规则与新规则的联合结果必须单独验证；本版完成仅代表 v3 内部一致，不代表跨仓库冲突已修复。

错误可见时先报告并暂停受影响依赖的新派发，保存原运行和部分报告；已有无关且健康的运行继续。若宿主已经在内部恢复，不另起同项运行。核对后：原运行可续则按宿主协议续接；已经终止且不可续，先消费现有结论，再将剩余范围作为有来源的新计划。来源无法查询则保持未知/阻塞，不自动换模型或重新启动。已有终态不能写成新结果覆盖旧错误。

### 3.5 主会话只补缺口，按实际结果收口

- 异步派发后处理独立工作；没有独立工作时交还控制权等原生通知，不用同步等待或轮询占住主会话。
- 接到一个完成结果就核对输入、具体报告、覆盖、验证和限制；整批 `runs.all`（等待全部子运行的汇总操作）完成或返回成功不代表每个子项成功。
- 部分报告只能使对应已查范围可复用；必需审查未覆盖时保留阻塞或明确交付部分审查，不能写“完整审查”。
- 修复沿用用户与项目边界。审查、修复、验证分别记录；独立审查要求继续有效，父会话自查不替代它。
- 只对修复、输入变化或组合影响补验证；有效命令结果复用。修复后的代码变化使相关审查证据失效，须定向复核，不由旧报告放行。

## 4. 最小结构改动：一个恢复检查，覆盖所有出口

v3 已有 `units.tsv`（单元表）、`ledger`（验证账本）与事件日志。清单记录当前状态，事件保留错误与恢复依据，一份报告记录覆盖；不新增进度表或状态枚举。旧 `coordination.py`（原任务协调模块）依赖旧契约和状态文件，不能假定可直接接入 v3 清单。

### 4.1 已确认的源码缺口

- `cmd_fail`（登记失败）首次网络、工具或未知故障会回到 `todo`（待派发），并覆盖证据字段；需要改为阻塞并保留证据。
- `cmd_reopen`（重新打开单元）只接受终态；不能处理原运行恢复后的阻塞出口。
- `cmd_gate_resolve`（解除决策门）会将指定的任意阻塞单元改回待派发；只给重开入口加条件仍有旁路。
- `cmd_next`（领取单元）无条件拒绝与执行中项共读文件；实际入口在 `xr`，不是旧 `frontier.compute`（从旧状态计算候选项的函数）。

### 4.2 只保留一份可追溯材料

故障事件引用宿主原运行与报告，记录准确错误；恢复事件引用同一故障，记录宿主状态来源、处置和剩余范围。报告头引用输入与原运行，阶段只补结论，不重复维护命令参数中的同一事实。

删除上一稿的 `--error/--run/--report/--run-status` 多套必填参数设计。实现优先复用既有事件写入，在确需由命令携带证据时只增加一个 `--record`（记录引用）参数，指向既有报告/宿主记录或其中的明确段落；不另建交接文件。该参数为拟新增能力，当前命令尚不支持。必需材料为原运行、准确故障、宿主状态依据、处置和已审/待审；报告可以明确缺失。命令可检查材料完整性，不能仅凭一句“已经终止”证明外部事实。

### 4.3 状态必须有两条闭合恢复路径

| 事件 | 状态与动作 | 禁止事项 |
| --- | --- | --- |
| 单元已失败或明确需要暂停 | 进入已有 `blocked`（阻塞）；事件记录来源，保留原证据；依赖不派发 | 不自动回待派发，不把宿主内部一次请求重试算新任务尝试 |
| 原运行仍活跃或可续接 | 核对运行引用后使用同一运行；原故障原因已解除则恢复为 `doing`（执行中），继续保留资源占用 | 不先转待派发，不启动第二份同项工作 |
| 原运行续接并返回结果 | 接收报告，解除对应故障原因；无其他阻塞则进入执行中，再按现有 `verify → done`（验证后完成）收口 | 不跳过验证，也不让成功结果永远卡在阻塞 |
| 原运行已终止且不可续、有有效报告 | 接收已审范围，登记剩余范围和重规划；重新派发前核对原运行终态 | 不覆盖旧失败，不重做有效范围冒充必要工作 |
| 原运行已终止且不可续、没有可用报告 | 明记“无可复用结果”，未确认覆盖全部进入待审，允许有来源的重新规划 | 缺报告不单独禁止恢复；不得声称沿用旧覆盖 |
| 原运行状态未知 | 保持阻塞，写明查询限制与恢复第一步 | 不凭文件时间或参数文本认定已停止 |
| 决策门已解除 | 仅消除该门造成的原因；未解决故障或其他门仍使单元阻塞 | 不允许通过无关决策门的 `--unit`（指定单元）释放故障 |

所有从阻塞到可执行/可派发的入口共用一处恢复检查；原因和解除事实复用已有事件与决策门记录。只有全部原因已解决才能离开阻塞。相同运行继续执行与确认终止后重新派发使用不同处置结果，由原重开入口承接，不新增恢复子系统；原终态重开若关联未解决运行也受检查，不能为兼容保留旁路。

阻塞不能释放尚未终止运行的资源：`xr next` 除执行中项，还须保守考虑保留了活跃或未知原运行的阻塞项。若只读且输出独立，健康项仍可并行；若涉及相同写入或满额，等待原运行确认处理。新事件只引用运行事实，不宣称脚本已具备查询宿主的能力。

网络错误不自动等于全局故障；已有健康独立项继续。全局故障处理与扩展改造仅在实际受影响路径证实需要时纳入，首版不建设新的全局熔断机制。

## 7. 验收与效果判断

### 7.1 必须具备的确定性反例

| 场景 | 通过条件 |
| --- | --- |
| 首次网络、工具、未知故障 | 单元阻塞且调度不原样重派；错误、原运行、阶段报告可定位 |
| 局部故障 | 故障后继不启动，健康且独立的单元仍可被领取 |
| 阶段后中断 | 故障前已保存的覆盖与发现仍可读取；恢复仅处理剩余范围 |
| 有文件却没有报告正文 | 不接受为审查完成；保留准确输出状态与待审范围 |
| 外层工作流成功、子项失败 | 只按子项实际终态与报告验收，不把整批返回值当通过 |
| 修复后输入变化 | 原输入的相关报告不放行新代码；无关报告继续可复用 |
| 只读输入重叠 | 不因共读配置误阻塞；同时写同一报告或业务文件仍被拒绝 |
| 原运行续接成功 | 从执行中故障阻塞，经同一运行恢复、接收结果、验证到完成，全链可达；宿主启动次数为 1 |
| 终止且无报告 | 终态依据明确时可重规划；已审范围明确为空，不因报告缺失卡死 |
| 决策门解除旁路 | 同一单元有故障及决策门时，只解除门仍阻塞；无关门显式指定故障项也不放行；普通门照常解除 |
| 未解决运行的资源 | 阻塞且原运行仍活跃/未知时不释放冲突写入资源，不能靠解除其他门或终态重开绕过 |
| 原检查项遗漏 | 49 文件均有归属但遗漏“品牌事实边界”问题时，只能判部分审查 |
| 首份结果接收 | “已读文件”拒收；固定版本、一个明确问题的结论/依据及待审范围齐全才接收 |
| 联合规则冲突 | 给出两套真实条款和只读限制；能说明唯一适用时限/保存方式，或显式未解决并暂停受影响派发，不能静默选择 |

以上优先复用现有测试框架、临时仓库与替身；测试故障本身不应启动真实网络重试或删除用户文件。

### 7.2 一次真实行为观察

在已授权且宿主支持的任务中观察：固定输入后派发一个完整小批，取得阶段报告或小批最终报告；父会话核对产物；模拟或遭遇中断后，能指出已审与待审，按原运行恢复规则继续。若仅完成替身验证，报告写“命令行为已验证，真实模型服从待验证”。

每次观察复用宿主已有日志与单元报告：保留输入、模型/宿主版本及引用即可；新增记录只补首次可用结果的接受依据、实际复用与重做范围。已有启动、错误、终态与接收时间不重复登记。没有请求开始记录时不估算网络和模型纯耗时；原始日志留本地。

### 7.3 效率指标

首版只新增两项观察：

- 首次可用结果等待时间：从派发到第一份按第 3.3 节标准接受的具体结论；只有活动文字不计。
- 故障后复用与重做范围：列具体检查项或行为链，区分输入变化导致的必要复核与缺报告导致的重读；分母未知就不计算比例。

覆盖与必需审查始终是完成门，不降为速度指标。整体耗时按需从已有日志计算，审查、修复、验证分开且重叠区间不重复累计。只有这些观察解释不了结果时才扩展采集；测试数量、报告长度、工具次数均不能单独代表质量或进展。

本次 69 分钟样本只是故障基线。候选方案必须先满足部分结果保留与正确恢复；后续同模型、相近范围和环境的样本才用于比较效率。没有同条件对照时，只报告真实观察值与限制，不预设 20 分钟交付或固定提速百分比。

### 7.4 体积作为每次迭代考察项

本次已测基线和复测命令见[体积基线与验收](./体积基线与验收.md)。本版实施同时验收：入口不超过 4,618 字节；本次五份相关运行说明合计不超过 4,996 字节；全部阶段卡与参考说明不超过 8,608 字节。新增引用的规则不能靠移目录规避计算；全部说明文档 137,120 字节及代码规模分别记录实施前后变化。用替换旧规则、去重引用与脚本检查承接能力，案例和讨论留在计划中。

体积达标不能代替行为通过；行为通过也不能隐去体积超标。以后每轮报告入口、相关加载说明、全体说明与代码/测试的前后差值，保留本基线以观察累计增长。阈值未达到先精简，无法精简就明确记录原因和未达目标，不静默放宽。

### 7.5 能解决什么，以及怎样才算证明

**目前只有方案与源码核对，不能称原问题已经解决。** 本版是“减少可控的失败损失与错误调度”，不是“保证模型不超时或整体一定更快”。下表按不同机制分别验收，不能用一份全量测试通过替代全部结论。

| 原问题 | 本版机制 | 证明方式 | 仍不能保证 |
| --- | --- | --- | --- |
| 子代理忙了很久却无可用报告 | 按问题拆小批，完成一个明确检查即保存；父会话按质量标准接收 | 真实小批先交一份合格结果，再用受控中断验证已交结果保留；只有“正在读”必须拒收 | 模型若在首次保存前停止，仍可能零结果；硬停前临时总结不可保证 |
| B 批跨度大，文件覆盖不代表问题覆盖 | 功能单元接收原九项检查映射，小批聚焦 | 漏掉品牌事实检查的桌面反例必须判部分审查；正常例逐项有结论与证据 | 单次自然语言审查不可能证明所有潜在缺陷都被发现 |
| 首次故障后可能重复派发，恢复出口或决策门旁路错误 | 统一状态恢复检查，保留原运行与资源；所有解除入口受约束 | 执行 `doing→blocked→原运行恢复→verify→done` 反例；启动次数为 1；门解除不能释放未解决故障 | 脚本不能凭自报状态证明宿主运行确已结束；需要可追溯宿主证据 |
| 主会话接管可能重复核查 | 接收已有有效报告，只补待审与变化范围 | 受控案例固定输入与检查项，恢复后旧有效结论被引用、只补预先标明的剩余项；真实任务列实际复用与重做范围 | 输入变化或报告不足时仍需必要复核；不能预先量化可省时间 |
| 整体慢、模型响应头超时 | 减少批次失败损失，区分请求故障与运行时限 | 真实任务测首份有效结果时间与复用范围；同条件样本才比较总耗时 | 本版不修网络、客户端或服务端请求故障，不承诺从69分钟降到某值 |
| 反复优化导致技能膨胀 | 替换旧规则、三层体积目标、记录整体与代码差值 | 同口径实施前后测量，并检查新增引用；与行为回归同时验收 | 文件字节不是实际模型读取量，更不能直接推导速度收益 |

保证的含义限于有反例保护的、已执行验证的行为。实施交付先分别给出“规则一致”“脚本行为已验证”“真实模型交付已观察”“效率已有比较”的状态；任一证据缺失就保留对应待验证项。v3内部通过与website联合执行分开，后者尚未同步时不能宣称端到端闭环。

## 8. 风险与本版边界

- 拆得过细会重复准备。相同简单变化合并，紧耦合行为交同一审查者，按真实首批交付校正，不固定并发数。
- 检查点可能来不及运行。持续保存已确认结果，小批最终输出作为能力受限时的退路，不承诺硬停前一定能总结。
- 默认省略子运行时限不代表无限等待。宿主限制、用户整体期限、故障与无进展规则继续生效。
- 只修改提示词不能消除自动重派。必须验证 `cmd_fail` 与调度实际状态；扩展若会重新激活则一并修正受影响路径。
- x-rail 无法独自修复服务响应头超时。缺请求级证据时保留根因未知，不在本版调整网关、全局模型、代理账户或超时配置。
- 本轮只写 `plans/0.0.7/`。方案交付不表示 v3 已实施、全局安装已更新、真实审查已提速或额外花费已获授权。

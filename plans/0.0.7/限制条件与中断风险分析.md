> 日期：2026-10-18（Asia/Shanghai）

> 当前提交基线：`d6fc6a1`  
> 目的：回答“`watchdog`（看门狗，监测模型是否长时间没有输出）触发 180 秒后，x-rail v3 里还有多少类似限制，会不会导致任务频繁中断或停止”。

## 1. 结论先说

### 1.1 数量

按“一个独立的阈值、计数器、状态守卫或时间盒算一类；同一条规则里的上下限不拆开；文档重复不重复计算”的口径，当前 v3 有 **28 类限制条件**。

其中：

- **9 类会直接中止当前回合、停止续跑、转交接或放弃工作项**。
- **11 类只会重试、切模型、压缩、延后派发或阻塞某个单元，不会直接结束整个任务**。
- **8 类属于证据模式、旧流程或文档里的边界；不一定会被当前 v3 `xr` 流程使用，但仍可能在混用入口时生效**。

如果把一条规则里的每个数字都拆开数，数字会超过 40 个。这个数字容易制造错觉，因为 `15 分钟`、`60 分钟`、`200K` 等很多值只是同一类策略的不同参数，不是 40 多个独立的“杀任务开关”。

### 1.2 对“会不会总是被中断”的判断

**当前设计确实有“限制条件过多、层级互相重叠”的风险，但不能据此断言任务一定会频繁停止。** 更准确的判断是：

1. `180 秒 watchdog` 主要中止**当前模型回合**，设计意图是触发兜底模型和继续执行，不等于整个 run（一次长任务执行）结束。
2. 真正会让 run 停下来的主要是两组“无进展”保护：
   - 连续 failover（模型切换）后没有工具进展，达到 2 次；
   - 自动续跑后状态指纹连续 3 次不变，或续跑总数达到 200 次。
3. 任务最明显的风险不是“有 28 类限制”，而是**同一个工作可能同时受到多套时间规则约束**：子代理 45 分钟、`xr verify` 默认 180 秒、看门狗 180 秒、旧证据模式 30 分钟无进展、阶段规则 70% 预算等。
4. 当前代码和文档存在规则冲突，冲突本身比单个 180 秒阈值更危险：模型可能不知道哪一套是权威，或者执行者以为有 45 分钟，实际验证命令 3 分钟就失败。

**暂不建议盲目把所有限制调大或删掉。** 目前证据证明了“规则重复和边界冲突”，还没有证明某一个数值的触发频率足以支持改数。推荐先统一层级和记录“哪个限制触发”，再按真实触发数据调值。

## 4. 哪些限制真的会停止任务

### 4.1 直接中止当前模型回合：1 类

- 看门狗 180 秒：当前回合被 `ctx.abort()` 中止。
- 这不是 run 终止。`x-run-guard.ts:56-60` 在识别为看门狗后调用回调；`x-failover.ts:27-42` 尝试切到 `bai/deepseek-v4.1-flash`，再发起触发回合。
- 当前实际风险：如果兜底模型不可用、切换失败或宿主没有按预期执行回调，用户看到的就是一次“被中断”；这条恢复链必须单独做真实宿主验证，不能只靠静态代码判断。

### 4.2 直接停止自动续跑或转交接：5 类

1. failover 总数达到 8 次；
2. failover 连续 2 次没有工具进展；
3. 自动续跑连续 3 次没有状态变化；
4. 自动续跑总数达到 200 次；
5. 剩余单元全部被 gate 阻塞。

这 5 类里，前 4 类是防止无限循环和费用失控的安全阀；第 5 类是等待人决策，不是故障。

### 4.3 单元或兜底路径停止：3 类

1. 单元遇到 cap、logic、verify 等不可自动重试的失败，进入 `abandoned`；
2. 兜底模型重试后仍失败，当前实现没有第二兜底，转交接；
3. 严格证据模式的预算、截止时间或无进展检查不满足，要求任务进入暂停类状态。

因此，按“停止当前任务链路”的宽口径，约有 **9 类停止路径**；按“180 秒后立刻停止整个 run”的窄口径，当前没有这样的直接证据，180 秒首先中止的是当前模型回合。

## 5. 当前最值得担心的不是数量，而是重叠和冲突

### 5.1 一次工作可能被多个时钟同时管理

一个实现单元可能同时面对：

- 看门狗：180 秒无模型输出；
- `xr verify`：默认 180 秒外部验证命令超时；
- worker 硬时间盒：45 分钟；
- 无进展检查：连续若干次或 30 分钟；
- run 预算到 70%：停止新增单元；
- provider 重试和 failover 次数上限。

这些时钟测量的对象不同，但当前文档没有始终把它们分成“当前回合、验证命令、单元、run”四层。用户体感会变成“任务无缘无故被限时”。

### 5.2 已确认的规则冲突

1. `stages/execute.md:9` 明确写 worker/reviewer/researcher 的硬时限；`modules/work-items.md:105` 却说默认不另设子代理总时限。两者同时存在，执行者无法知道谁优先。
2. 阶段卡给 worker 45 分钟，但 `xr verify` 默认 180 秒。实现可以做 45 分钟，验证却可能在 3 分钟失败；这是“实现时间盒”和“验证命令超时”未对齐。
3. `SKILL.md` 的 L1/L2/L3 预算与 `task_checks.py` 的调用次数阈值、`xr` 的 run 续跑次数不是同一套预算。名称相近，但停止行为不同。
4. `MAX_FAILOVERS_WITHOUT_PROGRESS = 2` 是严格的两次阈值；部分旧说明使用“连续 3 次”描述无进展。代码和文案需要统一，否则报告会误判触发时机。
5. 看门狗只在 `activeTools === 0` 时检查。工具正在运行时，代码会不断刷新 `lastTokenAt` 并重新计时，因此它不是严格的“整轮 180 秒上限”，而是“没有工具活动时 180 秒无输出”。
6. `MAX_CONTINUES_PER_RUN = 200` 是很大的兜底上限，真正更容易触发的是连续 3 次无状态变化；但当前报告和用户体验容易把 200 误解为正常允许的工作量。

## 6. 风险分级

| 风险 | 判断 | 依据 |
|---|---|---|
| 180 秒一到就永久停止 run | 中 | 代码设计路径是 abort 当前回合后切换并续跑；但真实宿主回调仍需运行验证 |
| 多个限制叠加导致误杀 | 高 | 180 秒验证超时、45 分钟单元时限、30 分钟无进展、70% 收尾同时存在 |
| 无限循环或费用失控 | 中低 | 有 2 次无进展 failover、3 次无进展续跑、8 次 failover、200 次续跑等安全阀 |
| 用户问题被误判为“自动停止” | 高 | gate 阻塞、模型切换失败、单元 abandoned、证据检查暂停在用户体感上都像任务中断 |
| 文档规则被随机采用 | 高 | `modules/work-items.md` 与 `stages/execute.md` 对子代理时限表述相反 |
| 单纯降低所有阈值后更稳定 | 未证实 | 没有触发频率、恢复成功率、任务完成率数据支持 |

## 7. 推荐收敛方向

### 推荐 1：先按四层命名，不先改数字

所有限制只归入四层：

1. **回合层**：模型本次请求是否要恢复，例如 watchdog 180 秒。
2. **验证层**：某条验证命令最多运行多久，例如 `xr verify` 的超时。
3. **单元层**：一个工作项最多运行多久、失败几次。
4. **run 层**：整个长任务何时停止自动续跑、何时转交接。

每条规则必须标明所属层和触发后的动作：`重试`、`切模型`、`压缩`、`排队`、`暂停`、`交接` 或 `放弃`。这样用户看到“watchdog 180 秒”时，可以马上知道它是回合层恢复，不是任务层终止。

### 推荐 2：只保留一个 run 级“无进展”权威

当前有：

- failover 无工具进展 2 次；
- 续跑状态指纹无变化 3 次；
- 旧证据模式 30 分钟无进展；
- `calls_since_progress` 20/60；
- 续跑总数 200 次。

它们不一定都要删除，但 v3 主路径应明确唯一权威；旧证据模式只对旧任务生效，不应和 v3 `xr` 的状态混用。建议先保留现有安全阀，停止增加新的无进展计数器。

### 推荐 3：把 `xr verify` 默认 180 秒与单元时间盒分开说明

当前 180 秒是“验证命令超时”，45 分钟是“worker 单元时间盒”，不是同一个值。报告、错误信息和阶段卡必须直接写清：

- 180 秒到：验证命令失败，单元仍可重规划；
- 45 分钟到：worker 单元达到硬时间盒，按 cap 处理；
- 两者都不直接表示整个 run 失败。

如果真实验证命令经常超过 180 秒，再单独基于数据调整验证超时；不能因为 watchdog 触发就整体放大所有时间。

### 推荐 4：把 180 秒 watchdog 定义为“可恢复中断”

推荐保留 180 秒作为首轮观察值，但改用明确语义：

> 180 秒无模型输出 → 中止当前回合 → 记录 watchdog 事件 → 尝试切换或重新发起回合；只有恢复失败或 run 级无进展保护触发，才交接。

不要把它和“任务超时”“单元超时”使用同一个“超时”词。

### 推荐 5：增加触发原因记录后再调参

每次停止或交接至少记录：

- 限制层：回合 / 验证 / 单元 / run；
- 触发规则：例如 watchdog、verify timeout、no-progress、failover cap；
- 当前单元、模型、已经重试次数；
- 触发前是否有工具进展；
- 恢复动作是否成功。

没有这组数据，无法回答“哪个限制最常导致中断”；只能回答“代码里存在多少限制”。

## 8. 最终判断

- **数量**：28 类限制条件；其中约 9 类会进入停止、交接或放弃路径。
- **180 秒 watchdog**：首先中止当前模型回合，不应直接等同于整个任务停止；它是否能自动恢复，需要真实宿主运行证据确认。

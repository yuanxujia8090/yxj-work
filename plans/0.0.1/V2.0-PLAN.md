# yxj-work v2.0 规划

> 状态：**实现完成，Phase 4 真实任务试跑待后续**
> 创建：2026-10-02
> 核心目标：**让 AI 先把"什么算做对了"定义清楚，再动手。**

---

## 1. 背景与现状

### 1.1 v1.x 已有什么

yxj-work 当前是一套任务工作流 skill（3 个入口 + 30 个辅助），围绕"任务先立契约、过程留证据、完成要校验"运转：

- `contract.md`：任务契约，含 `done_when`（完成条件）、允许/禁止改动范围
- `state.md`：按行状态，含 `required_verification`（必过验证项）与 `evidence`（证据行，带命令、时间、结果、文件修改时间）
- 完成判定：全部必过验证 passed + 无越界 + 决策门放行 + 每个结论有证据指针，才能写 `status: done`
- `check-state.sh`：done 前强制跑的结构校验（字段、枚举、时间戳、证据新鲜度）
- 熔断与预算：同一策略重复失败即停，L1/L2/L3 预算 60/150/400 次工具调用

### 1.2 现状与核心目标的差距

**现状**：`done_when` 由 AI 开工时自己写进 contract，自己执行，自己验收；结构是否完整有脚本把关，但**语义上"这个条件写得够不够清楚、能不能判定"没有任何标准**。

**问题**（按现状 / 问题 / 影响展开）：

| # | 现状 | 问题 | 影响 |
|---|---|---|---|
| 1 | `done_when` 质量无标准：实例中既有"报告落盘 outputs/xx.md 含 Critical/Important 处置"（可判定），也有"完成独立工作流仓库"（无法判定） | "做对了"的定义粒度靠 AI 自觉，写模糊了没人拦 | 模糊契约下"done"不可信；跨会话恢复时下一任 AI 对"做到哪了"理解不一致 |
| 2 | AI 自写自验，contract 写完没有用户确认环节（流程未定义这个门） | 运动员兼裁判，且标准可能是错的 | 用户看到交付时才发现方向偏了，返工成本高 |
| 3 | `check-state.sh` 只校验结构（字段存在、枚举合法、时间戳新鲜），不校验 done_when 语义 | 脚本"passed"≠ 定义清楚 | 完成判定给人虚假确定感 |
| 4 | `done_when` 可在任务中途追加、改写（实例中有追加"——达成"后缀），无变更规则 | 可能事后放宽/漂移标准 | "先干再定义"绕过核心目标 |
| 5 | review 阶段不分级，没有"按影响面决定审查深度"的规则 | 要么全审要么没审 | 小改动浪费审力，大改动可能漏审 |

### 2.1 Anthropic 六步法要点提炼（与本项目直接相关的部分）

文章讲企业级代码现代化（AI 大批量改代码）的准备工作，分六步：**定义目标 → 定义 certificate（合格证书）→ 定义 promotion policy（晋级策略）→ 备齐前置条件 → 构建并打磨 agentic 工作流 → 小范围试跑后放量**。

与 v2.0 核心目标直接相关的四条：

1. **第 2 步 certificate = "什么算做对了"的正式定义**：一组每个变更都必须满足的条件/测试集合。硬性要求是**每条条件必须"无人值守可检查"**——agent 才能自己迭代到通过，或标记出来交人；做不到自动检查的条件形同虚设。
2. **证书质量的检验法**：写完后问一句——负责合并的人**敢不敢只凭证书里的证据就合并**。敢，说明标准立住了；不敢，证书还要改。
3. **第 3 步 promotion policy（晋级策略，即分级审查）**：agent 产出变更的速度远超人逐条审的速度，所以要事先写好分层规则——按影响半径（blast radius，改动会波及的范围）+ agent 置信度决定人审深度，关键路径保持全量人审。**反复出现的同类告警要修工作流/证书的源头**，而不是逐条人工审。
4. **第 5 步的修理原则**：试跑中问题暴露时，**改工作流本身，不改单个变更**——和本仓库已有的 fix-root-cause / encode-lessons-in-structure 原则同源，但对方把它机制化成了"工作流迭代"环节。

其他可参考的观察：验证（而非写变更）通常占成本大头；产出物除了代码，还有四件可复用资产——written certificate、promotion policy、每个变更的 evidence trail（证据链）、playbook（操作手册）。

### 2.2 对 v2.0 的启发（已收敛）

- **可借用 certificate（合格条件）的思想，但不照搬“全部无人值守检查”**：每条验收条件必须有验证方式，但允许 automatic、manual、consumer、external 四类验证。
- **promotion policy（分级审查）裁剪为单人/多会话版本**：按影响风险决定确认和审查深度，不引入多人审批链，也不使用模型自报置信度作为放行依据。
- **“修工作流源头”成为试跑后的固定回路**：同类问题重复出现时，优先修改契约模板、检查规则或 playbook，不逐个修结果。
- **项目边界决定了最小实现**：保留现有 Markdown、contract/state/evidence 和 shell 门禁体系；先增加结构化约定与独立检查脚本，后续只有在试跑证明必要时才引入更复杂的解析或格式。

## 3. 核心目标拆解

"让 AI 先把什么算「做对了」定义清楚"拆成四个可回答的问题：

1. **定义什么**：一份合格的"做对了"定义（done_when / 验收标准）必须包含哪些要素？
2. **谁来定**：AI 起草、用户确认，还是按任务类型走不同确认门？
3. **何时定**：开工前一次性定完，还是允许阶段性演进？演进规则是什么？
4. **怎么验**：谁/什么工具检查"定义本身是否合格"，不合格不许开工？

## 4. 候选方向（调研中，附初步推荐）

### 4.1 收敛后的三个方向

**方向一：契约质量门——v2.0 必做**

目标不是让脚本理解自然语言，而是保证契约具备可追踪的最小结构：

- `done_when` 从一句自由文本拆成带编号的验收条件（如 A1、A2）
- 每条验收条件写明可观察结果、验证方式、验证层级和 required/optional
- 新增独立的 `check-contract.sh`，只检查格式、字段、关联关系和明显缺失
- `check-state.sh` 继续负责状态、证据新鲜度和完成门，不承担自然语言语义裁判
- 模糊词只作为警告；只有“没有可观察结果或验证方式”才阻断

**方向二：风险分级与确认门——v2.0 必做**

不再用 L1/L2/L3 直接决定是否确认。L1/L2/L3 表示任务规模和预算，风险另行判断：

- `low`：文档、局部样式、孤立测试等低影响任务，可自动进入执行，交付时展示验收条件
- `medium`：普通功能、共享组件、公共流程，开工前需要用户确认验收条件和边界
- `high`：权限、数据、生产、外部系统、对外发布、不可逆操作，开工前确认目标/边界/验证方式，完成后完整审查
- 任务进入无人值守流程时，必须记录确认豁免原因；不可逆、花钱、对外发布和生产变更仍保留人工决策门

**方向三：最小分级审查——v2.0 纳入，但不做企业级审批平台**

先落地三档审查矩阵：

- 低风险：自动验证 + 交付摘要
- 中风险：自动验证 + 独立只读审查
- 高风险：自动验证 + 用户确认 + 完整审查

暂不实现模型置信度评分、复杂 promotion policy（晋级策略）和多人审批流。重复出现的审查问题，优先改模板、规则或工作流。

### 4.2 初步推荐

**推荐方案：契约质量门 + 风险分级确认 + 契约变更留痕，分三阶段落地。**

执行链路调整为：

```text
识别任务类型 → 起草目标/边界/验收条件 → 判断风险
→ 运行契约质量检查 → 按风险确认/豁免 → 执行
→ 生成证据 → 按风险审查 → 完成判定
```

推荐原因：

1. 直接修复“AI 自写、自验、标准漂移”三个根因；
2. 复用现有 contract/state/evidence 体系，不另起一套任务状态系统；
3. 用规则检查结构，用人或 AI 评审语义，避免把自然语言判断硬塞进 shell；
4. 先做最小门禁和三类试跑，控制误拦截与流程成本。

**明确不做：**自然语言评分、模型自报置信度、历史任务强制迁移、完整企业级审批链。

## 5. 目标模型与边界

### 5.1 Contract 的最小新增字段

```text
task_type: bugfix
objective: 一句话描述要改变的结果
scope: 允许修改范围
forbidden: 禁止修改范围
risk: low|medium|high
risk_reason: 风险判断依据
review_policy: auto|user-confirm|full-review
contract_revision: 1
acceptance: A1...An，每条含 outcome/verification/layer/required
unknowns: 已知但未解决的未知；没有则写 none
```

`done_when` 暂不删除，保留为兼容摘要；新任务以 `acceptance` 为正式完成标准。旧任务只读兼容，不要求回填。

### 5.2 三个检查脚本的职责

- `check-contract.sh`：检查契约字段、验收条件编号、验证方式、验证层级、required/optional、风险与审查策略的一致性。
- `check-state.sh`：继续检查状态枚举、预算、熔断字段、required 验证状态、证据新鲜度；额外检查 state 引用的验收条件和契约版本。
- `check-repo.sh`：继续检查仓库级文件、文档、安装清单和跨文件规则的一致性。

三者不合并，避免形成一个无法维护的总门禁脚本。

### 5.3 验证方式不强制全部自动化

每条验收条件必须有验证方式，但允许四类：

- `automatic`：脚本、测试、构建、静态检查
- `manual`：用户或专家确认
- `consumer`：真实使用者或调用方验证
- `external`：外部服务、生产或第三方系统验证

## 6. 分阶段实施策略

### Phase 0：基线与样本校正

先核对 `.work-docs/index.md` 与实际 `contract.md` 的数量，补齐缺失记录或明确排除，再统计不同任务类型的验收条件质量。没有完整样本，不把“模糊比例”写成结论。

### Phase 1：契约质量门

新增 `check-contract.sh`、测试夹具、契约模板和文档规则；先拦截结构性缺陷，不做自然语言质量评分。

### Phase 2：风险与确认门

新增风险字段、确认/豁免记录和最小审查矩阵；按风险而不是预算等级决定是否暂停等待确认。

### Phase 3：契约变更留痕

增加版本、旧值、新值、修改原因、批准人和受影响证据的记录规则；删除、放宽、降级 required 条件必须重新确认。

### Phase 4：三类任务试跑

至少覆盖低风险文档任务、中风险代码任务、高风险或外部验证任务，记录误拦截、额外耗时、返工和审查发现，之后再决定是否扩大强制范围。

## 8. 已确定的实施决策

1. **契约格式：先用 Markdown 固定章节和字段约定。**
   原因：贴近现有文档、迁移成本低；只有试跑证明解析能力不足时，才局部引入更结构化格式。

2. **中风险任务：默认要求目标和边界确认，并进行独立只读审查。**
   原因：中风险任务不能因为工具调用少就自动放行；明确低影响、可回滚且不涉及共享机制的任务才可降为低风险，并记录理由。

3. **兼容策略：保留 `done_when`，新任务以编号验收条件为正式标准。**
   原因：避免破坏历史任务，不为迁移而扩大本次范围。

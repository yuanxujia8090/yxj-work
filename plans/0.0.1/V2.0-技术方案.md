# yxj-work v2.0 技术方案

> 状态：已完成（实现与验证通过）
> 目标：在不破坏 v1.x 任务记录的前提下，让新任务在执行前具备可追踪的目标、边界、验收条件、风险和审查策略。

## 1. 实施边界

本次只改 yxj-work 源仓库，不改已安装到用户目录的副本，不迁移历史任务，不引入新的运行时依赖。

保留：

- Markdown 任务契约；
- `contract.md`、`state.md`、`evidence/` 既有目录结构；
- `done_when` 作为旧任务兼容摘要；
- 现有 `check-state.sh`、`check-repo.sh` 和测试脚本体系。

新增：

- 新任务契约的结构化章节；
- `skills/yxj-work/scripts/check-contract.sh`，负责契约结构和字段关系；
- 契约测试夹具与测试入口；
- 风险、确认、审查策略的流程规则；
- 契约版本、内容指纹与状态文件的关联校验（仅对采用新格式的任务启用）。

明确不做：

- 自然语言质量评分；
- 模型自报置信度；
- YAML/JSON 迁移；
- 多人审批系统；
- 历史任务强制回填；
- 自动修改契约或自动降低验收标准。

## 2. 新契约格式

新任务的 `contract.md` 使用固定字段和固定章节。字段仍然是 Markdown 纯文本，便于人工阅读，也便于零依赖 shell 脚本读取。

```text
task_id: 20261005-01-example
level: L2
task_type: bugfix
objective: 修复登录态过期后页面仍显示已登录的问题
scope: 允许修改登录态判断和相关测试
forbidden: 不修改用户数据结构和部署配置
risk: medium
risk_reason: 影响公共登录态流程，但可通过回滚恢复
review_policy: user-confirm
contract_revision: 1

done_when: A1、A2 均通过，证据写入 state.md

## Acceptance

### A1
outcome: 登录态过期后页面不再显示已登录
verification: 运行 tests/auth-expired.spec.ts
verification_type: automatic
layer: runtime/local
required: yes

### A2
outcome: 正常登录流程不受影响
verification: 用户确认登录和退出流程
verification_type: consumer
layer: consumer
required: yes

## Unknowns

- none

## Decision Gates

confirmation: required
confirmation_status: pending
confirmation_by: none
confirmation_at: none
review: user-confirm

## Contract Changes

- none
```

### 字段规则

- `task_id`、`level`、`task_type`、`objective`、`scope`、`forbidden`、`risk`、`risk_reason`、`review_policy`、`contract_revision` 必须存在。
- `done_when` 保留为摘要，但新任务正式完成标准是 `Acceptance` 下的编号条件。
- 每个验收条件必须有 `outcome`、`verification`、`verification_type`、`layer`、`required`。
- `verification_type` 只允许 `automatic|manual|consumer|external`。
- `layer` 只允许 `syntax/config|static|runtime/local|external|consumer`。
- `required` 只允许 `yes|no`。
- `risk` 只允许 `low|medium|high`。
- `review_policy` 只允许 `auto|user-confirm|full-review`。
- `risk=low` 默认使用 `review_policy=auto`；如果选择更严格策略允许，但必须保留更严格策略。
- `risk=medium` 不得使用 `review_policy=auto`。
- `risk=high` 必须使用 `review_policy=full-review`。
- `risk=medium|high` 必须有 `Decision Gates`，并且 `confirmation: required`。
- 无人值守任务可以写 `confirmation: exempted`，但必须填写 `confirmation_reason`，且 high 风险、生产、不可逆、花钱和对外发布不能用豁免绕过确认。
- `contract_revision` 从 1 开始，只能是正整数。

## 3. 检查脚本职责

### `skills/yxj-work/scripts/check-contract.sh`

输入一个任务目录，可选模式为 `--draft|--ready|--seal|--locked`，读取 `contract.md`，执行：

1. 必填字段和枚举校验；
2. `Acceptance` 章节存在性校验；
3. 验收条件编号唯一性校验；
4. 每条验收条件字段完整性校验；
5. 风险、确认、审查策略关系校验；
6. `Contract Changes` 存在性校验；
7. 旧契约兼容：没有 `Acceptance` 章节的历史契约只输出兼容提示，不阻断；新契约的 `--ready` 默认不允许确认门 pending。
8. `--seal` 创建不可覆盖的 `audit/contract-rN.md` 快照；`--locked` 要求历史快照和变更记录完整，用于执行/交付前复核。

脚本不判断文字是否“聪明”或“足够好”，只判断是否存在可追踪结构。

### `skills/yxj-work/scripts/check-state.sh`

保留现有状态检查，增加可选关联检查：

- 如果任务契约存在新格式，则读取 `contract_revision` 和 `contract_fingerprint`；
- `state.md` 若声明这两个字段，必须与契约一致；
- 新格式任务的 `required_verification` 必须引用 `A1` 等验收条件编号；
- `status: done` 时必须覆盖并通过所有 `required: yes` 验收条件；
- 历史 state 没有这些字段时继续按 v1.x 规则检查。

### `scripts/check-repo.sh`

增加新脚本、新夹具、新文档的存在性和关键规则标记检查，继续负责仓库级一致性，不重复实现契约解析。

## 4. 流程接入

入口技能与 playbook 明确以下时点：

1. `design` 或 `plan` 阶段起草新格式契约；
2. 执行前运行 `check-contract.sh`；
3. 根据 `risk` 和 `review_policy` 决定是否等待用户确认；
4. 变更验收条件时提升 `contract_revision`，记录旧值、新值、原因、批准人和受影响证据；
5. `exec` 完成后按审查策略运行自动验证、只读审查或完整审查；
6. 最终仍由 `check-state.sh` 和现有完成门判定是否可标记 done。

`low` 只是减少交互，不改变 required 验证和证据要求。

## 5. 兼容与失败策略

- 历史契约不强制迁移；新脚本对旧格式只提示兼容状态。
- 新契约缺字段、枚举错误、验收条件不完整、风险关系矛盾或确认仍 pending 时返回非零，禁止进入执行。
- `status: done` 未覆盖 required 条件，或契约指纹与 state 不一致时返回非零。
- 修改契约后如果版本未增加，或 state 中的 `contract_fingerprint` 未更新，检查脚本返回非零。
- 检查失败时不自动修契约、不自动放宽条件，交回任务流程重新定义。
- 不新增第三方依赖；脚本使用 Bash、`sed`、`awk`、`grep`、`sort` 等现有环境工具。

## 6. 验收指标

- 新格式合法夹具通过；字段缺失、枚举错误、重复编号、风险关系错误夹具均被阻断；
- 现有仓库检查、安装检查、state 夹具回归通过；
- 旧契约仍能被现有工作流读取，不需要历史迁移；
- 文档明确区分任务规模（L1/L2/L3）与影响风险（low/medium/high）；
- 至少一个低风险、中风险、高风险契约样例可以按规则完成检查。

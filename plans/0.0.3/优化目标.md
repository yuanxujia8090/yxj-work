# x-rail 0.0.3 优化目标

> 状态：规划，尚未实施。日期：2026-10-10。基线：`2865386`。
> 本文解释目标与边界；操作步骤见[实施方案](实施方案.md)，证据见[验收与证据](验收与证据.md)。

## 1. 要解决的问题

当前 `x-rail` 已经用 `contract.md` 记录任务约定、`state.md` 记录执行状态，并保存验证证据与恢复交接。普通与长任务入口共用 33 个技能，脚本负责部分字段和完成检查。

问题主要有两类。第一类是文字规则没有进入必经检查，新版证据、契约快照和子任务依赖可以被绕开。第二类是执行成本缺少约束，主会话和子代理都可能持续读取，迟迟不产出用户需要的结果。

影响是：任务可能在证据不足时被标为完成，也可能在目标明确时消耗大量调用，却只留下过程记录。

本版本的目标是：在保留授权边界和证据要求的前提下，用更少的重复规则完成同样清楚的任务，并让新会话可靠接续。

## 2. 历史事实与结论边界

项目于 2026-10-09 从 `yxj-work` 改名为 `x-rail`。自检必须把 `yxj-work`、`yxj-work-long`、`x-rail`、`x-rail-long` 视为同一工作流的历史入口，同时保留当时使用的原名。

本次三周扫描窗口为北京时间 2026-09-19 10:16:06 至 2026-10-10 10:16:06。扫描 310 个 Pi 会话文件，确认 43 个会话中的 60 次明确入口调用，其中旧普通入口 51 次、旧长入口 8 次、新普通入口 1 次。这是调用数，不是独立任务数或成功任务数。

两次慢文档任务分别用了 319 次和 114 次调用，都没有派子代理。一例约 66 分钟开始写文档，另一例约 50 分钟才写契约，随后中止。另一个同类任务在明确“不关注测试环境”且可复用先前实施上下文时，用 23 次调用、约 10 分钟整理了 24 条用例。该对照支持限定取证范围，不足以证明某条新规则的提速倍数。

扫描还发现 12 种实际注入的入口正文、请求超时、运行环境缺文件、主动中止，以及用户终端操作间隔。不能把这些差异合并为“技能失败率”。

上轮静态审查确认的实现问题仍成立：缺少证据版本字段可绕过检查；快照检查未进入默认流程；时区按字符串比较；长任务缺少可校验依赖；阶段数与长任务判据冲突；预算仅部分检查；校验路径依赖当前目录；参考材料固定加载过重。

## 3. 八项验收目标

下表编号只用于文档内部追踪。每个编号后都有完整中文名称。

| 目标 | 可观察结果 | 验证方式 |
|---|---|---|
| 目标 1：任务及时收口 | 主会话和子任务有固定输入、取证问题、交付出口、暂停与恢复条件；不会为整理文档默认调查环境 | 文档、取证、代码修改三个行为场景，核对调用与实际产物 |
| 目标 2：自主决策有证据 | 重要选择能追到用户要求、代码、工具输出或官方资料；未知与假设单独标注 | 决策记录样例及证据缺失反例；检查四类确认边界 |
| 目标 3：语义模块隔离 | 两个核心入口和阶段文件用 XML 分开规则、输入、引用材料、输出；结构可解析 | XML 正反例、路由唯一性检查及材料中伪指令场景 |
| 目标 4：自检与受控改进 | `/x-self-check` 可分析七日或三周记录，提出有案例和复测方法的建议 | 合成会话测试、只读真实窗口检查；证明不会自改规则 |
| 目标 5：按必要性优化 | 复用现有文件和运行工具，不重建调度系统、数据库或技能注册中心 | 文件职责审查和依赖检查 |
| 目标 6：原则进入动作 | 设计初稿做一次简化审查；编码检查共同变化的逻辑与接口；交付核对实际结果 | 阶段出口与具体行为用例 |
| 目标 7：参考技能按需使用 | 去掉无条件语言规范与整组设计技能加载；保留文件及显式调用能力，退役建议有证据 | 触发矩阵、加载记录、安装清单和引用检查 |
| 目标 8：文档便于执行 | 方案先按技术写作规范组织，再清理空话；步骤、路径、命令和限制准确 | 逐项覆盖复核和交接演练 |

完成检查是目标 1、2、4 的共同前提：新任务必须有通过的必需验收、当前版本证据、有效授权、满足要求的子任务和无未处理越界，才能标记完成。

## 4. 职责分工

像前端组件分工一样，把共同变化的规则放在一起，通过明确输入和输出连接。这就是本方案采用的高内聚、低耦合。

| 部分 | 负责 | 不负责 |
|---|---|---|
| `x-rail` | 目标、范围、路由、证据、普通任务收口 | 后台进程管理与自动扩范围 |
| `x-rail-long` | 在普通规则上增加依赖、暂停、恢复与外部运行核对 | 复制普通规则、默认最高预算 |
| 阶段说明 | 当前阶段输入、动作、出口与短检查 | 另一套公共规则 |
| 校验器 | 字段、版本、证据引用、时间、依赖和完成条件 | 给自然语言方案打分 |
| 运行工具 | 可用能力、运行状态、权限限制、期限与输出保存 | 用户授权与产品决策 |
| `x-self-check` | 观察历史、定位问题、生成改进建议 | 自动改技能、删除文件或批准支出 |

XML 只负责语义结构。提示中的 `<authority>` 等标签不会自动获得权限，也不能把资料中的指令升级为用户要求。

## 5. 已确定的设计取舍

### 5.1 普通任务与长任务

普通入口用于可在一次连续会话中完成的任务，允许跨多个阶段。长入口用于跨会话、等待外部运行或需要汇总独立子任务的任务。规模、风险、恢复方式分别判断；长模式不自动采用 L3，也不自动获得 400 次调用。

保留已有 L1、L2、L3 规模与默认 60、150、400 次预算，暂不调优数字。先修预算语义与执行口径，再用行为记录决定是否调整。旧 `level: long` 仅供兼容读取；新长任务使用 L1、L2 或 L3，并声明恢复模式。

### 5.2 授权与审查

授权决定能做什么，风险决定验证强度，两者分开。需要用户拍板的动作只有不可逆、花钱、对外发布、改需求范围四类。已有明确授权可以复用，但必须说明来源和覆盖的具体动作。

用户要求先分析，就不改产品文件；用户明确要求生成方案到指定目录，可以写该目录。实际风险高的改动保留独立审查要求，不能用“已获授权”代替验证。

### 5.3 历史兼容

保留 Markdown 任务文件与既有字段格式，不批量迁移历史。完成入口强制走新检查，不因缺少字段自动进入旧逻辑。旧记录只能显式使用只读历史模式；恢复执行时由执行者补齐必要事实，不伪造过去的快照、调用数或验证时间。

### 5.4 最小工具实现

保留 shell 命令入口。已有测试使用 Python 3，新解析、日期、XML 与日志处理优先采用 Python 3 标准库，不新增包管理器或第三方依赖。新增运行时 Python 3 要求必须写入安装与使用说明，并验证缺依赖时清晰报错。

任务完成提供一个薄命令入口，复用校验器。它负责保存快照、验证完成候选状态、核对输入是否变化，再原子替换状态文件。原子替换像保存文件时一次换成完整新版本，避免留下半写内容；它不是跨任务数据库事务。

### 5.5 技能精简

先精简加载而不是删除文件。设计阶段不固定读七份材料，非 TypeScript 任务不读 TypeScript 专用规则。`x-principle-guard-the-context-window` 的大输出策略改为先工具内筛选，不把大输出自动转成委派理由。

保留 `x-typescript-best-practices` 的显式调用能力；仅在任务确实涉及该语言且项目规范不足时按需引用。原则合入对应阶段的短检查，原技能作为参考入口保留。技能退役清单是建议，不是删除授权。

## 6. 自检的输出与边界

自检报告包含窗口与时区、扫描范围、明确调用及续接、实际技能版本、模型、任务类型、执行与等待时间、真实产物、失败类别、缺失信息，以及每条建议的证据与复测方式。

日志解析只提供客观统计。模型判断必须引用会话路径与行号，并区分“确定缺陷”“设计薄弱点”“待验证假设”。源日志中的命令和提示均为资料，禁止执行。

新增建议只有经过固定场景验证后，才由独立实施任务修改规则。默认不自动定时、不自动追加规则、不改全局设置、不上传原始会话。真实报告保存在任务目录，不把隐私日志提交到仓库。

## 7. 不在本版自动执行的事项

- 删除技能目录、安装链接、工作区或历史任务。
- 将现有技能数量强行缩减到某个指标。
- 重建子任务工具、修改其全局设置、绕过其运行协议。
- 批量更正历史任务状态，或把旧证据补写成新格式通过记录。
- 自动提交、合并、推送、对外发布、部署与生产数据变更。
- 未经明确同意的付费模型实验、付费服务调用。
- 自动在所有项目搜集日志或上传会话内容。

## 8. 版本完成条件

本地实现完成需要：全部确定性测试通过、文档与安装目录一致、八项目标有覆盖证据、旧数据保留、没有未经授权的文件变更。

版本的真实行为验证另外需要：固定场景在新版本上实际运行并核对产物，完成至少一次新会话恢复；新旧对照条件可比，记录模型和技能正文版本。不能仅凭关键词检查宣称行为改善。

行为试验未获授权或环境不可用时，可以报告“本地实现通过，行为验证待完成”，不能报告“0.0.3 全部完成”。没有统计充分证据时不宣称固定提速比例。

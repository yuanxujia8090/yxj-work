# 03 技术方案

> 依据：01 的证据，02、02b 的借鉴决策。本文只讲设计，不含实现代码；伪代码和配置片段仅用于说明。
> 术语：**run** 指一次长任务执行；**unit** 指 run 里可以单独验证的单元；**胶囊（capsule）** 指脚本生成、不超过 2 KB 的恢复说明；**gate** 指需要人拍板、但带默认值的问题。

## 1. 设计原则

1. **稳定性下沉到宿主层**。凡是"模型必须记得去做"的事情，例如出错后续跑、换模型、压缩后找回状态，都改由 pi 扩展和配置执行，不写进提示词。依据：
   - 01 §4.3：31 次需要人工输入"继续"；
   - 01 问题 4：压缩后 36% 的摘要丢了状态文件指针；
   - skills-main `.out-of-scope/subagent-recursion.md` 的同类主张。
2. **状态只在磁盘上，并且是唯一真相**。会话只是一个"执行器"，随时可以被替换：换模型、压缩、崩溃都不影响状态。
3. **规则少、硬、可检查**。入口加当前阶段卡不超过 12 KB。能用脚本检查的，不写成文字（借鉴 retro 和 writing-for-agents）。
4. **自主执行，问题集中前置**。只在 Frame 阶段问人；执行期间遇到问题写 gate、带默认值、继续推进。
5. **一切有界**。provider 重试、单元重试、单元时间、run 预算都有上限，到上限后的去向也是确定的。

## 2. 总体架构

```
┌─────────────────────────────────────────────────────────────┐
│ L0 宿主层（pi，常驻，不依赖模型记忆）                          │
│  ├─ x-failover 扩展：错误分类 → 熔断 → 切到 bai/deepseek → 续跑 │
│  ├─ x-run-guard 扩展：未完成 run 自动续跑 / 压缩注入胶囊 /     │
│  │                    停顿检测 / 单元边界上下文决策            │
│  ├─ pi settings：retry 收紧、httpIdleTimeout、bai compat 修正  │
│  └─ pi-subagents：agentOverrides（fallbackModels、timeoutMs）  │
├─────────────────────────────────────────────────────────────┤
│ L1 技能层（x-rail，按需加载）                                 │
│  SKILL.md（≤5 KB 路由）→ 阶段卡（每张 ≤6 KB）→ 参考（按需查阅） │
│  调用已安装技能：tdd / code-review / diagnosing-bugs / research │
├─────────────────────────────────────────────────────────────┤
│ L2 状态层（磁盘，唯一真相）                                   │
│  .work-docs/runs/<run-id>/ RUN.md units.tsv ledger.tsv        │
│  decisions.tsv gates.md events.jsonl capsule.md               │
├─────────────────────────────────────────────────────────────┤
│ L3 记账工具（xr CLI，幂等，一条命令进、一行结果出）            │
│  复用现有 task.py / frontier / coordination 的内部逻辑         │
└─────────────────────────────────────────────────────────────┘
```

**L0 与 L1 的边界**：
- 扩展不理解业务，只做三件事：读写 `events.jsonl`、读 `capsule.md`、切模型和续跑。
- 技能不处理稳定性，只决定"下一步做什么"。
- 这样，模型能力较弱时（例如降级到 deepseek flash），稳定性也不会跟着下降。

## 3. 状态文件（L2）

目录：`<repo>/.work-docs/runs/<run-id>/`，run-id 格式为 `YYYYMMDD-HHMM-<slug>`。

| 文件 | 写入者 | 格式 | 内容 |
|---|---|---|---|
| `RUN.md` | Frame 阶段由模型写一次；Status 段由 `xr` 生成 | Markdown | Intent（目标）、**Done 判据**（可数、可检查）、Standing orders（编号的常驻指令，含用户纠正）、Autonomy（哪些事不需要问）、Budgets（墙钟、成本、单元时间盒）、Status（自动生成）、Risks |
| `units.tsv` | 只由 `xr` 写 | TSV | `id title state deps scope timebox_min attempts owner model verify_cmd evidence updated` |
| `ledger.tsv` | 只由 `xr verify` 写 | TSV | `unit tree_hash verdict(VERIFIED/FAILED/INCONCLUSIVE) cmd exit_code evidence_path model ts` |
| `decisions.tsv` | `xr decide` | TSV，只追加 | `ts unit decision reason alternatives reversible(Y/N) by_model` |
| `gates.md` | `xr gate` | Markdown | 待人拍板的问题、默认值、截止条件（"无答复即按默认执行"）、影响的单元 |
| `events.jsonl` | 扩展和 `xr` | JSONL，只追加 | provider_error、failover、failback、timeout、retry、compaction、resume、budget |
| `capsule.md` | 只由 `xr capsule` 生成（**不用 LLM**） | Markdown，不超过 2 KB | 目标一句话、Done 判据、当前单元及其已完成步骤、下一步的一条命令、要读的文件指针、当前模型、最近 3 条决策 |
| `notes/` | 子代理或研究 | Markdown | 研究笔记和子代理报告。报告保存为文件，防止"正式输出被覆盖"（01 §5） |

**units 状态机**（只由脚本推导，模型不直接写状态；C5 已确认：用 TSV 加动词，RUN.md 保持 Markdown）：

```
todo → doing → verifying → done
         │         └→ failed(kind) → todo(attempt+1) | abandoned → 触发 replan
         └→ blocked(gate) → todo（gate 有答复或默认值生效）
```

模型只调用动词，状态迁移由脚本根据动词和 ledger 推导。这样可以消除 01 问题 5 里那类"pending→awaiting 非法迁移"错误。

## 4. 记账工具 `xr`（L3）

对外只有 8 个动词。每个都幂等，输出一行结果。出错时，输出里给出可以直接复制执行的正确命令。

| 动词 | 作用 |
|---|---|
| `xr init <slug>` | 建立 run 目录和 RUN.md 骨架，执行 preflight（§8） |
| `xr plan add <id> "<title>" --deps a,b --files <glob,...> --verify "<cmd>" [--kind impl\|review\|research] [--timebox 45]` | 新增或更新单元；`--files` 是该单元独占的文件集（用于写入冲突检查） |
| `xr next` | 返回下一个可做的单元（frontier 中优先级最高的），并把它标为 doing |
| `xr verify <id>` | 执行 verify_cmd，以 scope 内的 tree hash 为键写入 ledger |
| `xr done <id>` / `xr fail <id> --kind <cap\|net\|tool\|logic\|verify\|unknown>` | 收口单元。done 要求 ledger 中有对应当前 tree hash 的 VERIFIED 记录，否则拒绝 |
| `xr decide "<决策>" --why "<理由>"`、`xr gate "<问题>" --default "<默认>"` | 记录决策，或挂起 gate |
| `xr status` | 输出派生状态，并刷新 RUN.md 的 Status 段 |
| `xr capsule` | 生成 capsule.md。扩展在压缩、续跑、failover 时也会调用 |

**与现有代码的关系**（C3 已确认）：
- `task.py` 及其 15 个子命令保留，旧任务继续可用。
- `xr` 在内部复用 frontier、work_items、coordination 的逻辑。
- v3 文档只教 `xr`。
- task.py 从"完成门禁"降级为可选检查器（v3-goal §五.3）。完成与否只看 Done 判据加 ledger。

## 5. 长任务引擎（阶段与循环）

借鉴 pstack 的 autonomous-run、figure-it-out、orchestrate，加上 skills-main 的 to-tickets 和 PHASE-BOUNDARIES。

| 阶段 | 阶段卡 | 完成判据（可检查） |
|---|---|---|
| **Frame** | `stages/frame.md` | RUN.md 中有可数的 Done 判据；单向门决策已经问过（grilling 方式：每题附推荐答案，回答 "yes" 即接受）；preflight 通过；Budgets 已填写 |
| **Plan** | `stages/plan.md` | units.tsv 至少有 1 个单元。每个单元：竖切、能单独验证、有 verify_cmd；单元规模按 §11"单元规模"控制（预计 ≤ 40 次模型轮次、≤ 150K 上下文、一个独占文件集），不再只按分钟数；deps 无环；**≥ 5 个单元的 run 走子代理驱动执行**（§10）。宽范围重构走 expand–contract |
| **Pilot**（可选） | 同 plan | 第一个单元端到端跑通，用来校准时间盒估计 |
| **Execute loop** | `stages/execute.md` | 见下方循环；直到 frontier 为空或预算到 70% |
| **Review** | `stages/review.md` | 调用 Skill 工具 `code-review` 做两轴审查，由另一模型家族的子代理执行；发现的问题回写成新单元 |
| **Land** | `stages/land.md` | 在真实工件上确认 Done 判据成立（全量测试或 typecheck）；生成交付 brief；终止 handoff |
| **Reflect** | `stages/land.md` 末尾 | 按 retro 分类给出环境改进建议（优先自动检查）；把用户纠正追加到 Standing orders 或 preferences；把本次的失败样本加入回放语料 |

**Execute 循环**（每一轮都做检查点）：

```
loop:
  u = xr next                         # 没有可做单元 → Review
  if 预算 ≥ 70%: 停止开新单元 → Land
  执行 u（按 §10：< 5 个单元的 run 由主会话执行；≥ 5 个单元的 run 由 worker 子代理执行，
          主会话负责编排、合并、验证；可并行的单元一次派发一波）
     - 行为改动：调用 Skill 工具 tdd（seam 写入 decisions）
     - bug：调用 Skill 工具 diagnosing-bugs（先有 red 回路）
  xr verify u → VERIFIED ? xr done u + 检查点(§6) : xr fail u --kind K
  失败处理按 §11 的类型表
  单元边界：run-guard 执行上下文决策(§7)
```

**谁来驱动循环**：
- 模型在一轮回复里能推进多少，就推进多少。
- 模型停下时（stop、错误、长输出截断），x-run-guard 在 `agent_before_settle` 检查：存在 `active` 的 run，Done 判据未满足，且没有"等用户"的 gate 阻塞全部单元。三者都成立时，就注入一条续跑消息（指向 capsule）并返回 `continue: true`。
- 这一步取代了人工输入"继续"。
- 防死循环规则：
  - 连续 3 次续跑后 ledger 和 units 都没有变化，判定为无进展，写入 events，停止续跑，并输出 handoff；
  - 单个 run 的续跑总次数有上限（默认 200，**假设**，需要回放校准）。

## 6. 检查点与续跑

| 层级 | 触发时机 | 内容 | 恢复方式 |
|---|---|---|---|
| 单元检查点 | 每次 `xr done` | units 和 ledger 落盘；git 检查点见下 | 从 `xr next` 继续 |
| git 检查点 | 每个已验证单元 | 在 run 专用分支或 worktree 上做 `wip(<run>/<unit>)` 提交 | 回到上一个已验证的 tree |
| 胶囊 | 压缩前、failover 时、续跑时、会话结束时 | capsule.md | 新会话或压缩后，先读胶囊 |
| 终止 handoff | 预算耗尽、无进展、所有剩余单元都被 gate 阻塞 | `handoff.md`：已完成、未完成、阻塞原因、下一条命令；只引用路径，不重复内容 | 用户执行 `/x-rail resume <run>` |

**git 检查点的授权（C6 已确认）**：Frame 阶段的 Autonomy 段默认写"允许在 run 分支或 worktree 上做本地 wip 提交，不推送"。用户在某次 run 中明确拒绝时，退回到用 `checkpoints/<unit>.patch` 保存差异。

**四种中断各自如何恢复**：

1. **崩溃或退出**：用户重新打开 pi 并输入 `/x-rail resume`，或者 run-guard 在 `session_start` 检测到 active run 时提示。之后读胶囊，执行 `xr status`，从 doing 状态的单元继续。该单元如果没有 ledger 记录，就从头重做这个单元。单元是幂等的，因为它在 scope 内，而且可以用 git 回到上一检查点。
2. **压缩**：`session_before_compact` 返回的压缩内容由两段组成：一段是 capsule.md（脚本生成，权威）；另一段是 bai/deepseek-v4.1-flash（thinking **low**）生成的"对话要点"摘要，不超过 3,000 字符。规则和状态不由 LLM 生成（v3-goal §五.6），本地 4B 模型不再参与。详见 §7。
3. **超时**：
   - 单元超时：按 cap-hit 处理，把单元拆小后重新派发。
   - 子代理超时：拿 partial 结果加 git diff，重新派发一个新代理，范围缩小（不 resume，见 §10）。
4. **模型故障**：见 04。

## 7. 上下文与压缩

- **加载预算**：
  - 入口 ≤ 5 KB；
  - 当前阶段卡 ≤ 6 KB；
  - 参考资料只在需要时读，例如 verification 参考（原 24 KB 的 playbook 转成按需查阅）。
  - 自检脚本检查体量，超过预算就失败。
- **单元边界上下文决策**（吸收 PHASE-BOUNDARIES）：run-guard 在 `xr done` 之后读取 `ctx.getContextUsage()`，按以下顺序判断：
  1. 下一单元依赖当前推理，而且剩余空间足够（openai26 以 160K tokens 为界，bai 以 350K 为界，**假设**）→ 继续。
  2. 当前上下文与下一单元无关 → 带胶囊开新会话。**待确认**：扩展是否能以编程方式新建会话；不能的话就退回到第 4 条。
  3. 下一单元可以无人值守独立完成 → 派子代理（§10）。
  4. 其他情况 → 在边界上主动调用 `ctx.compact()`，压缩内容使用胶囊。
- **目的**：避免在单元中途、tokensBefore ≈ 224K 时被动压缩（01 问题 4），并确保回切 openai26 时上下文小于 200K（04）。
- **压缩用的 LLM（用户已确认）**：凡是需要 LLM 的压缩、摘要、胶囊补充段落，一律使用 provider `bai` 的 `deepseek-v4.1-flash`，thinking **low**（bai 的 thinkingLevelMap 支持 low），替换 smart-compact 现在用的 `lmstudio/Qwen3.5-4B-MLX-4bit`（minimal）。
  - **分工**：胶囊（目标、Done 判据、当前单元、下一步、文件指针）始终由 `xr capsule` 确定性生成；LLM 只写"对话要点"补充段：最近决策的理由、试过但放弃的做法、未落盘的观察。补充段上限 3,000 字符，超出部分截断。
  - **为什么选它**：上下文 512K，openai26 会话（约 224K 时触发压缩）整段送过去也装得下；bai 实测错误率 1.3%；low 推理可以压低延迟和成本。
  - **降级规则**：bai 摘要请求超过 120 s 或报错时，只用胶囊完成压缩，绝不让压缩卡住。bai 的成功轮次 p99 是 269 s，有长尾，所以要设这个超时。
  - **配置**：`smartCompact.summaryModel = "bai/deepseek-v4.1-flash"`，`summaryThinkingLevel = "low"`（04 §7，06 P1.5）。x-run-guard 的 `session_before_compact` 在 smart-compact 产出的摘要前面拼上胶囊。
  - **待确认**：pi-smart-compact 与 x-run-guard 同时挂在 `session_before_compact` 上时的执行先后（P0 验证）。如有冲突，就由 x-run-guard 统一生成压缩结果，并直接调用 deepseek low。

## 8. 不阻塞与权限

1. **Preflight**（`xr init` 时执行）：检查以下各项，结果写入 RUN.md 的 Autonomy 段：
   - 测试和类型检查命令能否运行；
   - 写入路径是否在项目根目录内；
   - context-mode 是否会拦截要用的命令，例如 curl（01：拦截 18 次）；
   - `apply_patch` 等工具是否存在（01：缺失 4 次）；
   - git 身份和分支状态；
   - 所需技能是否已安装。
2. **Autonomy 契约**：明确列出不需要问的事项，例如 run 分支内的本地提交、在 scope 内增删文件、安装 dev 依赖。v3-goal §十一 规定的 6 类事项必须问：删除数据、强推、生产数据库迁移、花钱、对外发布、范围变更。
3. **gate 机制**：需要人决定的事 → `xr gate --default` → 该单元标为 blocked → 继续做其他单元。只有当剩余单元全部被 gate 阻塞时，才输出 handoff 停下。默认值的生效规则（例如"Land 前仍无答复即按默认执行"）写在 gate 里。
4. **子代理的 supervisor request**：主会话先用 Standing orders 自动作答；答不了，再按第 3 条转成 gate，不让子代理停下来空等（01 §5：14 次）。工具权限类请求（例如 reviewer 的 watchdog_diff 只支持启动时的 HEAD）在 Brief 里事先给出可用命令，从源头上消除。

## 9. 验证门

| 级别 | 何时用 | 要求 |
|---|---|---|
| 单元验证 | 每个单元 | `xr verify` 执行 verify_cmd，ledger 记录 tree hash、退出码和证据路径 |
| 集成验证 | Land 阶段 | 全量测试和 typecheck 在最终 tree 上通过 |
| 独立评审 | 高风险单元（公共接口、数据、安全）和 Land 前 | 调用 Skill 工具 `code-review`，两轴；reviewer 用**另一模型家族**；fixed point 等于 run 起点的 SHA |

- **硬规则**：没有 VERIFIED 的 ledger 记录，`xr done` 就拒绝。没有在最终 tree 上通过的集成验证，就不能宣称完成（v3-goal §八"不要在没有证据时声称完成"）。
- 验证失败不自动重试同一个做法：同一单元验证连续失败 2 次，就放弃该单元并重新规划（§11）。

## 10. 子代理（C1/C2 已确认：大任务走子代理驱动执行）

用户决定：学习 pstack，大型长任务要**真正使用**子代理，不再是"默认少用"。

### 10.1 何时由谁写代码

| run 规模 | 写代码的人 | 主会话的职责 |
|---|---|---|
| **< 5 个单元**（小任务） | 主会话直接写（pstack："一个代理在预算内能做完，就不要上编排"） | 执行、验证、收尾；可选派只读子代理做研究或评审 |
| **≥ 5 个单元**（大任务或长任务） | **worker 子代理**：每个实现单元一个 worker | **编排者**：Frame、Plan、派发、合并、集成验证、处理 gate、Review、Land；只写 run 状态（通过 `xr`）、合并提交和冲突解决；另外允许做一次"小修"（≤ 3 步、在已合并的集成分支上、与在跑的 worker 文件集不相交） |

- "单元"指 units.tsv 里一个可以单独验证的竖切单元，这就是用户说的"步骤"。Plan 结束时 `xr` 统计单元数，判断走哪种模式，并记入 decisions.tsv。用户在 RUN.md 里写 `mode: main|subagents` 可以覆盖这个判断。
- **依据**：子代理成功运行里，worker 的中位时长是 6.8 min，reviewer 是 6.2 min，说明子代理本身能干活。失败主要来自两点：超时设得太短（下面 10.3）；中途无法 fallback（下面 10.5）。这两点都有对策，所以按 v3-goal §五.4 的要求"用数据说明"，大任务恢复默认委派。

### 10.2 避免写入冲突：一个文件集只有一个写入者

1. 每个实现单元在 Plan 时声明 `--files`，即独占的文件集。`xr next` 只会派发与**正在运行的**单元文件集不相交的单元；有交集的单元必须等待，或者在 deps 里串行。
2. 每个 worker 使用独立的 git worktree 和分支：`xr/<run>/<unit>`，从**当前集成分支的最新提交**拉出。
3. 合并只由主会话做，并且串行，形成一个合并队列：worker 报告完成 → 主会话把它合并进集成分支 → 立即在集成分支上运行该单元的 verify 和受影响的测试 → 通过才 `xr done`。冲突由主会话解决；冲突大时，把冲突部分退回成一个新单元。
4. 共享文件（锁文件、路由表、全局配置等）在 Plan 时归入一个"集成单元"，由主会话或单个 worker 串行处理，不并行。
5. 写并发：同时运行的 worker 最多 **2 个**（建议值）。依据是 openai26 出现过 `gateway_concurrency_limit` 和"账号池暂无可用账号"，并发高了会放大 provider 错误；合并队列也是串行的。回放之后可以调整。

### 10.3 时间盒（替代原 15 min，以证据为准）

**证据**：
- 成功 worker 运行（28 次）：中位 6.8 min，p75 15.8 min，p90 24.9 min，最长 45.2 min。其中 8 次（29%）超过 15 min。
- 被杀掉的 worker：在 20 min 和 30 min 两档超时，CR 任务正是这样失败的。
- subrun 每轮耗时：中位 0.53 min，p90 1.13 min。模型时间占墙钟的中位比例是 96%，说明慢在模型，不在工具。
- 每个 subrun 的轮次：中位 18，p90 48，最多 93。
- 成功 reviewer 运行（177 次）：p90 11.6 min，最长 22.9 min。但有 7 次 reviewer 在约 10 min 时被 timed_out。

**结论**：在本机第三方 API 上，15 min 会误杀将近三成的正常 worker。改为**按轮次和上下文控制单元规模，再用分钟做硬上限**：

| 子代理类型 | 单元规模（Plan 时估计） | 软时间盒（到点汇报进度） | 硬超时 `timeoutMs` | 依据 |
|---|---|---|---|---|
| worker（实现） | ≤ 40 次模型轮次；上下文 ≤ 150K；一个独占文件集 | 30 min | **45 min**（2,700,000） | 40 轮 × p90 1.13 min ≈ 45 min；能覆盖成功 worker 的最大值 45.2 min |
| reviewer（评审） | 一个 diff 范围 | 15 min | **25 min**（1,500,000） | 成功 reviewer 最长 22.9 min；10 min 档误杀过 7 次 |
| researcher / scout（只读） | 一个问题 | 10 min | **15 min**（900,000） | researcher 最长 12.1 min，scout 最长 7.8 min |
| 主会话执行单元 | 同 worker | 30 min | 45 min，由 run-guard 计时，到点按 cap-hit 处理 | 与 worker 一致 |

- **轮次上限**：Brief 写明"≤ 40 轮"，并配合 pi-subagents 的 `toolBudget`（建议约 60 次工具调用，**待确认** 0.76.1 是否支持单代理的 toolBudget）。上下文接近 150K 时，worker 应先报告并结束。依据：耗时最长的几个 subrun，上下文多在 178K–268K；CR 任务超时的 fallback subrun 达到 295,801。
- **到软时间盒时**：worker 把进度写进 `notes/<unit>-report.md` 并提交 wip。主会话判断：快完成就让它继续跑到硬超时；否则拆小后派发新单元。
- **v3-goal §五.5 的 15 min**：用户已用新的决定覆盖。DECISIONS 中记录：选择 45/25/15 min 加轮次规模；放弃 15 min 统一上限，理由见上面的数据；重新评估的条件是回放中 worker 的 p90 明显下降，或换到更快的 provider。

### 10.4 并发上限

| 类型 | 上限 | 说明 |
|---|---|---|
| 只读子代理（research、scout、reviewer） | **5**（用户已确认） | 一波最多派 5 个 |
| 写入子代理（worker） | 2 | 见 10.2 第 5 条 |
| 合计在跑 | ≤ 5 | 写入子代理占用这 5 个名额 |
| 熔断器打开时 | 合计减半（向下取整，至少 1） | 遇到 `gateway_concurrency_limit` 或账号池错误时自动降并发 |

### 10.5 子代理的 failover

1. **派发前**：熔断器打开时，Brief 和 pi-subagents 参数直接指定 `bai/deepseek-v4.1-flash`（thinking high）。
2. **工具活动前失败**：`agentOverrides.<agent>.fallbackModels = ["bai/deepseek-v4.1-flash"]` 自动切换。
3. **工具活动后、中途失败**：
   - 如果子 pi 进程加载了全局扩展（P0 验证），x-failover 会在子代理内部直接切模型并续跑，和主会话的处理一样。
   - 否则由主会话**重新派发一个新子代理**，模型设为 bai，Brief 中带上 worktree 的 diff、wip 提交和 `notes/` 报告，写明"只做剩余部分"。这算一次尝试（§11），不用 resume，原因是 CR 任务 02:25 那次 resume 只跑 1.1 min 就失败了。
4. **评审的模型家族**：实现跑在 openai26 时，reviewer 用 bai；实现跑在 bai 时（包括 failover 期间），reviewer 优先用 openai26。如果 openai26 正处于熔断，就用 bai 审查，在 ledger 里标记"同家族审查"；高风险单元在切回 openai26 后补一次评审。
5. **主会话自身 failover**：编排者切到 bai 后，正在跑的子代理不受影响；新派发的子代理按第 1 条处理。

### 10.6 Brief 模板（pstack 加 implement-spec 的 context pointer）

```
GOAL       一句话
SCOPE      独占文件集 --files；worktree 路径与分支 xr/<run>/<unit>；基于集成分支 <sha>
CONTEXT    只给指针：RUN.md#Intent、units.tsv 行、相关 notes/、起点 SHA
ACCEPTANCE 可检查的条件
VERIFY     一条命令（worker 自己跑并贴输出）
BUDGET     ≤ 40 轮；软 30 min 时写进度；硬超时 45 min（= timeoutMs）
MODEL      主模型 / 熔断时 bai/deepseek-v4.1-flash:high
FORBIDDEN  文件集之外不改；不推送；不 rebase 集成分支（同时写成正向目标）
REPORT     notes/<unit>-report.md + wip 提交 + 一行摘要
STANDING   RUN.md#Standing 的指针；supervisor 问题先查这里，再写 gate
```

- 子代理调用一律由模板生成，不让模型手写 workflow 语法。会话里 workflow 用法错误出现过 17 次。
- 递归深度由 pi-subagents 配置限制，不在提示词里写防递归规则。

## 11. 预算与重试（三层）

| 层 | 上限 | 到上限后 |
|---|---|---|
| Provider 请求 | 同一模型自动重试 ≤ 1 次，计入单元时间（v3-goal §五.5）。pi 的 `maxRetries` 从 5 改为 1，baseDelay 从 10s 改为 5s。E1 快速失败类错误不重试。之后的处理是"换模型继续"，不是"重试"（pstack：tool-error → 换模型），**回放校准** | x-failover 切换到 bai（04）；兜底模型同样只重试 1 次 |
| 单元 | **单元规模**：≤ 40 次模型轮次、上下文 ≤ 150K、一个独占文件集；时间盒：worker 和主会话单元软 30 min、硬 45 min，reviewer 硬 25 min，只读硬 15 min（§10.3，C2 已确认，替代 15 min）；尝试次数 ≤ 2 | 按失败类型处理：cap 或超时 → 拆小；net → 原样重试；tool → **换模型重试**；logic 或 verify → 不重试同一做法，先 replan；unknown → 重试 1 次。达到 2 次后放弃该单元并 replan |
| Run | 墙钟预算和成本预算写在 RUN.md。用户说"成本不限"时，只保留墙钟预算 | 到 70%：停止开新单元，进入 Land；到 100%：输出终止 handoff |

**错误类型的区分**（v3-goal §五.5 要求区分 API、工具、模型输出、测试四类）：
- API 错误：stopReason=error，由 x-failover 处理；
- 工具错误：toolResult 的 isError；
- 模型输出错误：工具参数校验失败、length 截断；
- 测试失败：verify 的退出码。

分类结果写入 events.jsonl，`xr fail --kind` 记录在单元上。

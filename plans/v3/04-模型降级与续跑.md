# 04 模型降级与续跑（openai26 → bai/deepseek-v4.1-flash）

> 目标（用户目标 2）：openai26 出问题时，自动切换到 bai/deepseek-v4.1-flash（thinking high）继续执行，不丢进度、不等人；等 openai26 恢复后，在安全的时机切回。
> 实现位置：pi 扩展 `x-failover`（L0 宿主层），加上 pi-subagents 的配置。x-rail 技能本身不负责切模型。
> API 依据：pi 上游 main 分支的 `extensions/types.ts`，包括 `agent_before_settle`（可以追加条目，并以 `continue: true` 再发起一次请求）、`session_before_compact`、`pi.setModel()`、`pi.setThinkingLevel()`、`pi.appendEntry()`、`ctx.getContextUsage()`、`ctx.compact()`、`ctx.modelRegistry`。**待确认**：用户本机 pi 版本（settings 中 `lastChangelogVersion` 为 1.1.0）是否提供这些事件。不提供时先升级 pi，这一步需要用户批准。

## 1. 为什么必须做，以及为什么放在宿主层

- openai26 的错误率是 4.1%（163/3975），最差的一天达到 13.6%；bai 是 1.3%。
- 25 次 openai26 错误后，会话停住等人，空等合计 6.92 h，最长一次 106.8 min（01 §4.3）。
- 有 17 次是用户在出错后 30 min 内手动换模型。用户实际上一直在手工做 failover。
- pi 自带的重试有两个缺口：
  - 一类瞬时错误根本不重试：busy、temporarily unavailable、concurrency_limit、stream ended prematurely，合计 28 次全部没有重试；
  - 503 账号池错误却被重试了 19/22 次，属于白白浪费。
- pi 本身没有"换模型"这个动作。
- 现有 x-rail 文档写的是"不自动换模型"。提示词层也做不到这件事，因为出错时模型根本不会运行。

## 2. 检测：错误分类

扩展在 `agent_before_settle` 中读取本次 run 最后一条助手消息，按下面的顺序分类。这个时机在 pi 自动重试结束之后，**待确认**回放测试 T1。

| 类 | 判定（实测错误串和次数） | 动作 |
|---|---|---|
| **E0 用户中止** | `stopReason=aborted`，且不是看门狗触发的 | 不做任何处理 |
| **E1 快速失败** | `503 账号池暂无可用账号`（22）、`gateway_concurrency_limit`（3）、`INSUFFICIENT_BALANCE` / insufficient_quota / billing（1）、401/403、`Server requested Ns retry delay (max: 80s)`（2） | **立即 failover**，熔断器直接打开 |
| **E2 pi 不重试的瞬时错误** | `upstream_error · The service is temporarily unavailable`（10）、`The service is temporarily unavailable`（8）、`The service is busy`（5）、`Upstream stream ended prematurely; safe to retry`（2）、`stream disconnected`（2） | 等 20 s 后在同一模型上续跑 1 次（`continue: true`）；再失败就 failover |
| **E3 pi 已重试耗尽** | `Request timed out.`（56）、`HTTP 524`（16）、`terminated`（15）、Connection error 等。pi 已经按 maxRetries=1 重试过 1 次才走到这里 | **立即 failover** |
| **E4 请求本身有问题** | 4xx bad request，例如 bai 的 422 `unknown variant 'developer'`（3） | 发生在 bai 上：属于配置缺陷，先修 compat（§7）；发生在 openai26 上：failover 1 次并记录。上下文溢出交给 pi 的压缩，不在本扩展处理 |
| **E5 看门狗** | 流式输出期间超过 180 s 没有任何 `message_update`（**假设**阈值，回放校准）。扩展调用 abort 并打上标记 | 按 E3 处理 |

**熔断器**：
- 以 provider/model 为键记录状态，持久化在 `~/.pi/agent/state/x-failover.json`，所有会话和子代理共享。
- 打开条件，满足任一即可：
  - 出现一次 E1 或 E3；
  - 10 min 内出现 3 次 E2。
- 依据：openai26 共有 16 个错误簇连续出错 3 次及以上；错误簇恢复时间的中位数是 1.5 min，但簇时长合计 11.89 h。"等它自己恢复"的代价远大于"先换模型"。

## 3. 切换

```
on agent_before_settle(event, ctx):
  err = 分类(最后一条助手消息)
  if err ∈ {E1, E3, E5} 或 (E2 且本单元已同模型续跑过 1 次):
     if 当前已是兜底模型: → §8 第二级 / 写 handoff 并停止
     m = ctx.modelRegistry.find("bai", "deepseek-v4.1-flash")
     ok = await pi.setModel(m); pi.setThinkingLevel("high")
     if !ok: 记录 "no auth" 并停止（不循环）
     breaker.open("openai26/gpt-6.1-sol", cooldown)
     pi.appendEntry("x-failover", {from, to, class, errorMessage, ts})
     run 目录存在时: 追加 events.jsonl；调用 xr capsule
     return { continue: true, entries: [续跑消息(custom_message)] }
```

**续跑消息**（固定模板，不依赖模型生成）：

```
[x-failover] 主模型 openai26/gpt-6.1-sol 不可用（类别 E3：Request timed out，已重试 1 次）。
已切换到 bai/deepseek-v4.1-flash（thinking high）。请继续当前工作：
1) 先读 .work-docs/runs/<id>/capsule.md；2) 以 ledger 为准，不重做已 VERIFIED 的单元；
3) 单次输出保持小块（大文件分段写），避免触达 16384 输出上限。
```

第 3 点的依据：bai 实测有 5 次 `stopReason=length`。

**防死循环**：
- 每个 run 最多 failover 8 次（**假设**）。
- 同一单元内如果连续 2 次 failover 之后仍然没有任何工具进展，就停止并输出 handoff。

## 4. 状态交接（为什么不丢进度）

1. **同一会话续写**。消息历史完整保留。bai 的上下文窗口是 512,000 tokens，openai26 是 262,144，所以切过去一定装得下。
2. **进度在磁盘上**。units、ledger、capsule 是唯一真相（03 §3）。出错发生在模型调用阶段，此前的工具调用已经完成并记录，所以续跑不会重复执行副作用。只有当前 doing 单元可能做了一半，单元内的步骤要求幂等，必要时按 git 检查点回到上一个已验证状态。
3. **跨 provider 的消息兼容**：
   - openai26 产生的 reasoning 内容和工具调用 id，在 bai 上能否被正确回放，需要验证（**待确认**，回放测试 T3）。
   - 如果不兼容，退路是：切换时先执行一次压缩（`ctx.compact()`，内容使用胶囊），再在 bai 上续跑。
4. **审计**：每次切换都记录在 session 的 custom entry 和 run 的 events.jsonl 里。交付 brief 中要列出"哪些单元由哪个模型完成"。ledger 有 model 列。

## 5. 切回（failback）

**同时满足以下条件**才切回：

| 条件 | 值 | 依据 |
|---|---|---|
| 冷却期结束 | 首次 15 min，再次熔断则翻倍，上限 60 min（**假设**） | 错误簇恢复中位数 1.5 min，但有长尾，最长连续 6 次错误 |
| 探活成功 | 用一个极小请求探测 openai26，在冷却期结束后连续成功 2 次 | 防止刚恢复就再次失败 |
| 安全边界 | 只在**单元边界**（`xr done` 之后）或新的用户轮次开始时 | 不在单元中途换模型，避免推理风格断裂 |
| 上下文 | 当前上下文 ≤ 200K tokens；超过就先在边界上执行压缩（内容使用胶囊）再切回（**假设**阈值） | openai26 是 256K 模型，实测在约 224K 时触发压缩 |
| 策略 | RUN.md 的 `failback: auto \| manual \| never`，默认 auto | 用户可以固定只用 bai |

**滞回**：切回后 15 min 内如果再次熔断，本 run 的剩余部分就留在 bai 上，并在 events 里记录。

**探活实现**：**假设**扩展可以通过 pi-ai 的 `complete()` 加上 `ctx.modelRegistry` 里的 openai26 模型发出一个只要求很少输出的探测请求；如果做不到，就退化为"冷却期结束后，在单元边界直接切回，失败后再按熔断规则处理"。

## 6. 子代理的降级

1. **启动前**：如果熔断器处于打开状态，x-rail 派发子代理时，在 Brief 里显式指定 `model: bai/deepseek-v4.1-flash`，thinking 为 high。
2. **工具活动之前的失败**：由 pi-subagents 原生的 `fallbackModels` 处理。配置示例如下，键名需要对照 0.76.1 的 schema 确认（**待确认**）：

   ```jsonc
   "subagents": {
     "agentOverrides": {
       "worker":     { "fallbackModels": ["bai/deepseek-v4.1-flash"], "timeoutMs": 2700000 },  // 45 min
       "reviewer":   { "fallbackModels": ["bai/deepseek-v4.1-flash"], "timeoutMs": 1500000 },  // 25 min
       "researcher": { "fallbackModels": ["bai/deepseek-v4.1-flash"], "timeoutMs": 900000 },   // 15 min
       "scout":      { "fallbackModels": ["bai/deepseek-v4.1-flash"], "timeoutMs": 900000 }
     }
   }
   ```

3. **中途失败**：子代理已经调用过工具，pi-subagents 判定为终态。处理方法是重新派发一个新子代理，模型设为 bai，Brief 中带上已完成部分（diff 和 notes 报告），见 03 §10。
4. **并发与熔断联动**：熔断器打开时（尤其是 E1 中的 `gateway_concurrency_limit` 和账号池错误），在跑子代理的上限从 5 减半；写入子代理的上限从 2 降到 1（03 §10.4）。
5. **评审换家族**：实现跑在 bai 上时，reviewer 优先用 openai26。openai26 也在熔断时，用 bai 审查，在 ledger 里标记"同家族审查"，切回后补审高风险单元（03 §10.5）。
6. **关键待确认**：pi-subagents 启动的子 pi 进程会不会加载全局扩展？如果会，x-failover 就能在子代理内部直接切模型，中途失败问题从根上解决；如果不会，就只能靠第 3 点。这一点在 P1 阶段最先验证。

## 7. 配套配置修改（需要用户批准后才能修改 `~/.pi/agent`）

```jsonc
// providers.bai
"compat": { "supportsDeveloperRole": false }        // 修复 3 次 422
// settings
"retry": { "enabled": true, "maxRetries": 1, "baseDelayMs": 5000, "maxAgentDelayMs": 30000,
           "provider": { "timeoutMs": 300000, "maxRetries": 0, "maxRetryDelayMs": 80000 } },
"httpIdleTimeoutMs": 120000,   // A/B：现值 60000 与 beef-claude 11 次约 61 s 超时吻合
"smartCompact": {               // 用户已确认：压缩/摘要改用 bai deepseek，推理 low
  "summaryModel": "bai/deepseek-v4.1-flash",       // 原 lmstudio/Qwen3.5-4B-MLX-4bit
  "summaryThinkingLevel": "low",                   // 原 minimal；bai 只支持 low/high/max
  "requireApproval": false
},
"x-failover": {
  "primary": "openai26/gpt-6.1-sol",
  "fallback": [{ "model": "bai/deepseek-v4.1-flash", "thinking": "high" }],
  "cooldownMin": 15, "maxCooldownMin": 60, "failback": "auto",
  "failbackMaxContextTokens": 200000, "maxFailoversPerRun": 8, "streamWatchdogSec": 180
}
```

- `httpIdleTimeoutMs` 的**假设**：openai26 的 56 次 "Request timed out." 中，有相当一部分是 high 推理等首包超过 60 s 导致的。验证方法：对照 A/B 两组的错误率，以及成功轮次延迟的 p99（基线 171 s）。
- **与 v3-goal 的对齐**：v3-goal §五.5 规定"API 瞬时错误最多自动重试 1 次"。因此同一模型只重试 1 次（pi maxRetries=1，或 E2 类由扩展续跑 1 次），之后改为"换模型继续"，不算重试同一路径。
- **待确认**：原先 Request timed out 有 75/82 次被自动重试，其中不少重试后成功了。把重试次数降到 1 次以后，会更早切到 bai。要用回放比较"完成时间"，而不只是比较错误率。

**压缩与 failover 的关系**：
- 压缩摘要固定用 bai/deepseek-v4.1-flash（low），与当前对话用哪个模型无关。所以 openai26 熔断不影响压缩。
- bai 本身出故障时，压缩只用脚本胶囊完成（03 §7），不会卡住压缩，也不会触发 failover。

## 8. 第二级兜底（bai 也失败时）

bai 的错误率是 1.3%，主要是 connection（36 次）和 timeout（29 次）。规则：
- bai 上出现 E3，先在 bai 上续跑 1 次（不切模型）；
- 仍然失败，就切到第二兜底。候选是 beef-ds 上的 deepseek，512K 上下文，样本 128 条消息、0 错误，但样本量小（**待确认**是否启用以及成本）；
- 都失败，就写 handoff 并停止，不再循环。

## 9. 适用范围与开关

- 只在当前模型等于 `primary` 时生效。用户的默认 provider 本来就是 bai，日常使用 bai 时不会触发。
- `/x-failover off|status` 命令：手动开关，查看熔断状态。
- 用户手动执行 `/model` 时，扩展尊重用户选择，熔断状态仍然保留。

## 10. 验收（与 06 的回放评测对应）

| 编号 | 场景（真实错误串） | 期望 |
|---|---|---|
| T1 | openai26 返回 `Request timed out.`，pi 重试 1 次后仍失败 | 30 s 内切到 bai 并继续执行；events 中有 failover 记录 |
| T2 | 返回 `The service is busy`（复现 `01a123b6` 那次空等 106.8 min 的场景） | 20 s 后同模型续跑 1 次；仍失败则切换；全程不需要用户输入 |
| T3 | 带 reasoning 和工具调用历史切到 bai | bai 正常接续，不出现 4xx；若出现，"先压缩再续跑"的退路生效 |
| T4 | `503 账号池暂无可用账号` | 不再浪费 19 次重试，立即切换 |
| T5 | 冷却期结束，探活成功，到达单元边界，上下文小于 200K | 切回 openai26；15 min 内再次失败，则留在 bai |
| T6 | 子代理在工具活动前遇到 provider 失败，以及工具活动后中途失败 | 前者自动 fallback；后者由子代理内部的 x-failover 切换，或者由新派发的子代理在 bai 上完成剩余部分 |
| T9 | 2 个 worker 加 3 个 reviewer 并行时出现 `gateway_concurrency_limit` | 并发自动减半，新派发的子代理改用 bai |
| T10 | 压缩时 bai 摘要请求超时（> 120 s） | 只用胶囊完成压缩；会话继续，不中断 |
| T7 | 用户按 Esc 中止 | 不续跑、不切换 |
| T8 | bai 返回 422 developer role（修复 compat 之前） | 被识别为 E4，不形成循环 |

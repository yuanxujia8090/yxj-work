# 01 问题诊断：证据、根因与现有 v3 代码的缺口

> 时间都按 Asia/Shanghai（UTC+8）。数字来自对 `sessions.tgz`、`run-history-tail.jsonl`、`pi-config-redacted.json`、`v3.tgz` 的脚本统计（口径见文末"取证口径"）。脚本放在 `evidence/` 目录。
> 标记说明：**假设** 表示有依据但没有直接验证；**待确认** 表示需要用户或本机进一步核实。

## 0. 结论先说

两个真实大任务都没交付，原因不在"规则写得不够"。它们卡在四个地方，而这四个地方现有 v3 都没有机制处理：

1. 主模型 openai26 出错后，pi 有一批错误不会自动重试，会话直接停住，要等用户回来输入"继续"；会话里也没有任何东西负责切到备用模型。
2. 长任务的单元太大（子代理 30 分钟才超时），超时以后只能人工接管，进度靠转录文本恢复。
3. 压缩摘要交给本地 4B 模型生成，摘要越压越长，规则和下一步都靠它来保存。
4. 记账协议摩擦太大：task.py 有 37% 的调用被拒绝。规则体量也没有降下来，执行路径约 71 KB，基线是 65 KB。

## 2. 七个已知问题逐条核验（对应 v3-goal §三）

### 问题 1：入口 SKILL.md 约 25 KB
- **现状**：当前入口 `SKILL.md` 是 4,568 B，已经降下来了。`SKILL.md.bak` 还留在仓库里。
- **证据**：baseline.md 记录旧入口 25,012 B；本次实测为 4,568 B。
- **根因**：问题从入口转移到了执行路径（见问题 3）。
- **是否值得修**：入口不用再动。`.bak` 文件应在后续提交中移出技能目录，否则 pi 有可能把它当作资源扫描进来（**假设**）。

### 问题 2：缺少 pstack 级能力
- **现状**：v3 已经有 frontier / dispatch / notify / inbox / consume，以及 work-items、self-check。但下面这些能力都还没有：
  - 模型故障切换；
  - 自动续跑：错误或停住之后，不需要人输入"继续"；
  - 按失败类型重试，例如 pstack 的 "tool-error → 换模型重试"；
  - 预算到 70% 时停止扩张并收尾；
  - 确定性的压缩恢复胶囊。
- **证据**：`modules/execution.md` 和 `orchestration.md` 原文写的是"Python 只记账，不启动、唤醒、恢复或等待模型；不自动重试、换模型"，失败表里"换模型"一项注明"仅宿主允许时"。全仓库搜不到任何 failover 实现。
- **根因**：设计时把"稳定性"当成提示词层的事。实际上它是宿主层的事，需要 pi 扩展加 pi-subagents 配置来承担。
- **结论**：值得修，而且是 v3 的主线。详见 03、04。

### 问题 3：规则加载约 65 KB
- **现状**：x-rail 全部 Markdown 共 126,290 B。按 exec 路由完整加载要读这些文件，合计 **71,216 B**，没有比基线下降：

  | 文件 | 体量 |
  |---|---|
  | SKILL | 4.6 KB |
  | exec.md | 10.6 KB |
  | execution | 5 KB |
  | verification 模块 | 6.9 KB |
  | playbooks/verification.md | 24.2 KB |
  | work-items | 5.6 KB |
  | recovery | 5 KB |
  | orchestration | 9 KB |

- **证据二：技能被重复读取**。主会话里一共读了 553 次 `*/SKILL.md`，结果文本累计约 3.90 M 字符：
  - x-rail 被读 81 次，分布在 41 个会话，约 655 K 字符。压缩后会重读。
  - 同时还有其他全局技能在被读：using-superpowers 53 次（35 个会话）、verification-before-completion 48 次、context-mode 33 次、brainstorming 30 次、test-driven-development 24 次、deep-think 20 次、systematic-debugging 19 次、pi-subagents 16 次。
- **根因**：
  - 拆分只是把一个大文件换成了多个模块，并没有按阶段限制加载量。
  - 全局 superpowers 体系（"必须先调用技能"一类规则）和 x-rail 同时生效，规则互相竞争。
- **影响**：上下文压力大，压缩更频繁；不同体系的规则冲突，模型行为不稳定。
- **最小改法**：
  - 每个阶段只加载一张不超过 6 KB 的"阶段卡"，硬预算是入口 + 阶段卡 ≤ 12 KB。
  - 把 24 KB 的 playbooks/verification.md 改成按需查阅的参考资料。
  - 写 `local-components-proposal.md`，建议在 x-rail 运行期间不触发 using-superpowers 和 brainstorming（见 03 §9）。
- **不改的后果**：模型继续在多套规则之间摇摆，压缩之后又会全量重读。

### 问题 4：压缩后规则丢失，小模型摘要不可靠
- **现状**：`smartCompact.summaryModel = lmstudio/Qwen3.5-4B-MLX-4bit`（thinking 为 minimal）。256K 模型的压缩一般在 tokensBefore ≈ 224K 时触发。
- **证据**：
  - 91 次压缩中，只有 58 次（64%）的摘要包含持久状态文件的指针，只有 47 次（52%）包含明确的下一步。
  - 摘要长度中位数 4,809 字符，最大 31,708 字符。
  - 在 `01a14555` 里，摘要逐次膨胀：9,572 → 20,496 → 26,049 → 31,708 字符。
  - 压缩最多的单个会话是 `01a13aca`，压缩了 9 次。
- **根因**：恢复所需的信息（目标、完成判据、当前单元、下一步）是由 4B 模型"概括"出来的，没有从磁盘状态确定性地生成。
- **最小改法**：
  - 用 pi 的 `session_before_compact` 钩子返回一份由脚本生成的"恢复胶囊"，不超过 2 KB，其中只有指针和下一步，不由 LLM 生成。
  - 在单元边界主动触发压缩，不要等到单元中途被动触发。
- **不改的后果**：每次压缩都有 1/3 的概率丢失指针，长任务越跑越偏。

### 问题 5：管道式 record 和 task.py 参数容易出错
- **证据**：
  - task.py 共调用 544 次，其中 203 次被拒绝（37%），分布在 23 个会话里。
  - argparse 用法错误 62 次。
  - 协议错误：
    - "observation must follow capture" 8 次；
    - 依赖未满足 8 次；
    - 非法状态迁移 pending→awaiting 7 次；
    - "input summary cannot include task state" 5 次；
    - 缺少评审证据 5 次；
    - 缺少章节 Contract Changes 5 次。
  - 真正属于验证失败的只有约 15 次。
- **根因**：模型被迫记住一套复杂的状态机和参数格式。被拒绝时，大多数情况拦下的是格式问题，而不是质量问题。
- **最小改法**：对外只暴露 6–8 个动词，每次一条命令进、一行结果出（借鉴 pstack 的 `orch.ts`）。状态迁移在脚本内部推导，不让模型去指定。拒绝信息里直接给出可以复制执行的正确命令。

### 问题 6：约 434 次工具错误
- **证据**：实测主会话 597 次加 subrun 41 次，共 **638 次**，比用户估计的多。按工具分：

  | 工具 | 错误次数 | 主要原因 |
  |---|---|---|
  | bash | 253 | |
  | edit | 148 | 未读先改、精确文本未找到、校验失败 |
  | read | 81 | |
  | ctx_execute | 50 | 其中 9 次是磁盘 I/O |
  | subagent | 34 | 17 次是 "workflow: true needs one fenced block" 这类用法错误；另有 workflow 与结构化单子代理混用、"Unknown agent: fixer" |

  其他：
  - context-mode 钩子拦截 curl 18 次；
  - "File access blocked outside project root" 约 13 次；
  - `apply_patch: command not found` 4 次；
  - 输出截断导致工具调用不完整 3 次。
- **根因**：一部分是工具协议复杂（subagent、task.py），一部分是权限边界事先没有探明。
- **最小改法**：
  - 长任务启动时做一次权限和工具预检（preflight）。
  - 子代理调用一律通过模板生成，不让模型手写 workflow。
  - 编辑前必须先读文件，这条交给 pi 的 edit 自身报错，不再写成文字规则。

### 问题 7：没有超时、错误分类和有界重试
- **现状**：pi 自带重试，配置为 `maxRetries 5, baseDelayMs 10000, maxAgentDelayMs 60000, provider.timeoutMs 300000, httpIdleTimeoutMs 60000`。x-rail 自身没有错误分类，也没有换模型。子代理默认超时 30 分钟。
- **证据**：见 §4、§5，涵盖 pi 不重试的错误、停住时长、子代理超时。
- **最小改法**：分三层预算。
  - provider 层：pi 重试不超过 3 次，然后 failover。
  - 单元层：时间盒 15 分钟，按失败类型最多重试 2 次。
  - run 层：墙钟和成本预算，到 70% 时收尾。

## 取证口径
- **错误**：助手消息 `stopReason == "error"`。
- **自动重试**：错误之后的下一条消息是同一 provider 的助手消息。
- **停住**：错误之后的下一条消息是用户消息，或者会话结束。
- **错误簇**：同一会话中连续错误，中间没有夹成功消息。
- **延迟**：取 `durationMs`。缺这个字段时，用相邻时间戳近似。
- 子代理运行历史以 `run-history-tail.jsonl` 为准。

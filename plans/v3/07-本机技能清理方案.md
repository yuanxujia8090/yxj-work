## 1. 加载器结论（来自 `pi-skills.js`，以及会话里的系统提示）

| # | 结论 | 依据 |
|---|---|---|
| L1 | 默认扫描两个目录：`~/.pi/agent/skills`（user），以及**当前工作目录**下的 `.pi/skills`（project）。之后再加上调用方传入的 `skillPaths` | `loadSkills()`：`includeDefaults` 分支的两次 `addSkills(...)`，然后遍历 `skillPaths`。settings.json 里没有 `skills` 键 |
| L2 | **`~/.agents/skills` 实际会被加载**。`pi-skills.js` 的默认目录里没有它，但会话的 `<available_skills>` 中出现了 16 个 `~/.agents/skills/...` 路径（code-review、grilling、research、domain-modeling、prompt-optimizer、qmd、tdd 等，每个出现约 186 次）。**推断**：是调用方（pi 主程序或某个 package）通过 `skillPaths` 加进来的。具体机制**待确认**，但"会被加载"这一点是确定的 | 会话 JSONL 中 `<location>` 的统计 |
| L3 | `~/.pi/skills` **通常不会被加载**。只有在 `$HOME` 目录下启动 pi 时，它才会被当作 project 目录加载。会话里出现的 openspec-* 来自 `~/Documents/working/website/.pi/skills`，不是 `~/.pi/skills` | L1；`<location>` 统计 |
| L4 | 项目里的 `.claude/skills` 也会进入 pi，例如 website 项目的 `cr`、`enterprise-kb-crawler`。**推断**：来自 `pi-cc-extensions` package（**待确认**） | `<location>` 统计 |
| L5 | package 自带的技能也会加载：context-mode 8 个、ponytail 6 个、pi-lens 4 个、pi-subagents 2 个。它们不在这三个目录里，本方案不处理 | `<location>` 统计 |
| L6 | 发现规则：目录里有 `SKILL.md` 就视为技能根，不再往下找；扫描根目录下的 `*.md` 文件，只要带 description，也会被当成技能；会读取 `.gitignore`/`.ignore`/`.fdignore`；跳过点目录和 `node_modules`；跟随软链；**断链静默跳过** | `loadSkillsFromDirInternal()` |
| L7 | 同名冲突时先加载的胜出（user → project → skillPaths）。同一个真实文件经由软链出现两次时，静默去重。所以 `~/.pi/agent/skills/X → ~/.agents/skills/X` 这类软链只是重复入口，不会加载两遍 | `addSkills()` 里的 `realPathSet` 和 `skillMap` |
| L8 | **会识别 `disable-model-invocation`**：必须是 YAML 布尔值 `true`。设置后，技能不会进入系统提示，但仍能用 `/skill:名称` 手动调用（settings 中 `enableSkillCommands: true`） | `loadSkillFromFile()`、`formatSkillsForPrompt()` |
| L9 | 没有 description 的技能不会加载。名称不合规只会给警告 | `loadSkillFromFile()` |
| L10 | `~/.pi/agent/skills-disabled/` 是 skills 目录的兄弟目录，不在扫描范围内。用户现有的归档做法是有效的 | L1 |

**对清理方式的影响**：
- 一个技能如果在 `~/.agents/skills` 里有实体目录，要让 pi 不加载它，必须**同时**移走 `~/.pi/agent/skills` 里的软链和 `~/.agents/skills` 里的目录。只移软链没有用，因为 L2 会从 `~/.agents/skills` 再加载一次。
- `~/.agents/skills` 可能还被其他代理工具共用（例如 Codex，或用 skills.sh 安装的工具）。移走后，那些工具也看不到这些技能（**待确认**你是否在别的工具里用这些技能）。
- 只让 pi 不加载、其他工具不受影响的替代做法：在 `~/.agents/skills/.fdignore` 中写入技能名（L6），pi 会忽略这些目录。脚本没有采用这个做法：一是 L2 的加载机制没确认，二是这个做法比较隐蔽，不便以后排查。

**额外发现**：
- `skills-disabled/README.md` 记录，2026-10-17 已经把 x-rail 的 **36 个软链**全部归档了，所以现在 pi 里没有 x-rail。v3 上线时安装 x-rail 加 3 个配套技能（x-handoff、x-worktree、x-self-check），共 4 个软链（03 §12）。
- inventory 里没有 `yxj-work`、`yxj-work-long`、`yxj-work-handoff`，但 README 写的是它们在 `~/.pi/agent/skills`，会话里也用过（yxj-work 读取 30 次）。**待确认**：它们是否已被移走或改了名。

## 2. 规则与结果汇总

**规则（2026-10-17 用户新增）**：x-rail v3 是唯一来源。只要 x-rail 有相似的技能或能力，全局那份（`~/.pi/agent/skills`、`~/.agents/skills`）就归档。只归档、不删除，并备份、给出恢复命令。

**例外**：x-rail **调用**的全局技能不归档，因为 x-rail 依赖它们。只有 x-rail 自己真正覆盖了某项能力，才归档对应的全局技能。

| 决策 | 数量 | 说明 |
|---|---|---|
| 保留 | 50 | 其中 7 个是 x-rail 调用或间接依赖的（§2.2）；很多已经是仅手动 |
| 改为仅手动（`disable-model-invocation: true`） | 4 | full-output-enforcement、prompt-optimizer、skill-creator、pr |
| 归档，批次 A：全局之间重复、断链、相似 | 12 | 现在就可以做，不依赖 x-rail |
| 归档，批次 B：**被 x-rail v3 取代** | 11 | 必须在 x-rail v3 安装并验证之后执行；脚本有守卫 |
| 不处理，单独标记 | 11 | `~/.pi/skills/openspec-*`（§5） |

按技能名去重，共 77 个。

**效果估算**（基于 inventory 中的 description，近似值）：这两个目录里会进入系统提示的技能，从 40 个降到 29 个（批次 A 加仅手动），再降到 22 个（批次 B）。description 总长度约从 8.1K 字符降到 5.8K，再降到 4.8K。

**归档清单**：
- 批次 A（12）：brainstorming、using-superpowers、test-driven-development、systematic-debugging、writing-skills、design-taste-frontend-v1、image-to-code、redesign-existing-projects、claude-handoff、hallmark（断链）、receiving-code-review（断链）、requesting-code-review（断链）

## 4. 执行方式（脚本 `evidence/skills-cleanup.sh`）

```bash
bash plans/v3/evidence/skills-cleanup.sh --dry-run      # 先看计划，不改任何东西
bash plans/v3/evidence/skills-cleanup.sh                # 批次 A + 仅手动
bash plans/v3/evidence/skills-cleanup.sh --batch B --dry-run   # 预览批次 B（守卫未通过时也只做预览）
bash plans/v3/evidence/skills-cleanup.sh --batch B      # x-rail v3 安装并验证后再执行（守卫会检查）
```

脚本行为：
- **(a) 备份**：把 `~/.pi/agent/skills`、`~/.agents/skills`、`~/.pi/skills` 和 `skills-disabled/README.md` 打包成 `~/ori-review/skills-backup-<日期>.tgz`。打包时不加 `-h`，软链按软链本身保存。同一天已有备份时跳过，所以保留的总是首次运行前的状态。
- **(b) 归档**：移到 `~/.pi/agent/skills-disabled/cleanup-<日期>/{agents-skills,pi-agent-skills}/<名称>`。
  - 用 `mv -- 源 目标`，源路径不带结尾斜杠，所以**移动的是软链本身**，目标目录不动。
  - 相对路径软链（例如 `../../../.agents/skills/x`）在归档区里会显示为断链，移回原位置后自动恢复。
  - 先移 `~/.agents/skills` 里的实体目录，再移软链。
- **仅手动**：在 SKILL.md 第一行 `---` 之后插入 `disable-model-invocation: true`。
  - 修改前把原文件备份到 `~/ori-review/skills-frontmatter-<日期>/`。
  - 文件位于 git 仓库内时（例如 `pr` 软链到 mattpocock-skills 仓库），默认跳过，需要加 `--allow-repo-edit` 才会修改。
  - 原因：改动会让该仓库多出未提交修改，这一点需要你决定。
- **(c) README**：只有本次确实有改动时，才在 `skills-disabled/README.md` 末尾追加一节：带时间的表格（技能、原位置、归档位置、类型、原因），以及逐条恢复命令。格式与你现有的归档记录一致。
- **批次 B 守卫**：执行前必须同时满足以下条件，否则拒绝（退出码 3）：
  - `~/.pi/agent/skills/x-rail*` 下能找到 `SKILL.md`（也可以用 `--xrail-path` 指定），并且该路径位于 pi 会加载的目录；
  - frontmatter 中 `name: x-rail`；
  - 存在 v3 标志文件 `stages/execute.md`（可用 `--xrail-marker` 修改）；
  - 如果 x-rail 设置了 `disable-model-invocation: true`，会给出警告，因为手动技能无法取代自动触发的全局技能；
  - retro、handoff、using-git-worktrees 这三项还要求对应的配套技能 x-self-check、x-handoff、x-worktree 已经安装，否则单独跳过。
- **(d) 汇总**：打印新移动、已归档、原本不存在、冲突、仅手动的数量。
- **可重复执行**：已经归档的项会报"已归档"；已经是仅手动的会报"已是"；目标位置有同名项时跳过，不覆盖。
- 执行完需要重启 pi 会话。
- 兼容 macOS 自带的 bash 3.2。

**恢复**：执行 README 里列出的 `mv` 命令即可，或者整体解压 `~/ori-review/skills-backup-<日期>.tgz`。
